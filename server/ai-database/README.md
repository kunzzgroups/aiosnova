# Independent AI development database

## Company defaults and recommendations

Run `003_create_ai_model_preferences.sql` once as the schema-administration
account, after scripts 001 and 002. It creates only an AI-owned preference table
and grants `ai_app` access. The application does not run DDL automatically.

Until migration 003 is applied, enabled models remain browsable, but saving
company defaults/recommendations is disabled with an explicit setup message.
Preferences use company-scoped model configuration UUIDs, allow at most six
recommendations, and use a version check to reject concurrent edits. Unavailable
references are retained for diagnostics; the Assistant does not select a substitute.

This directory belongs to the AI module. It is separate from the Core migration
directory at `src/main/resources/db/migration/mysql`.

## First step

1. Connect to a **local MySQL 8 development instance** with a schema-administration
   account. A MySQL client such as Workbench is not itself a running database server.
2. Open `001_create_ai_providers.sql`, confirm the target connection, and run it once.
3. Confirm `current_database` is `aiosnova_ai_local` and `ai_providers` exists.
4. Do not rerun the table creation if it already exists. Inspect the existing schema
   and prepare a separate migration for changes.

The script creates schema only. It inserts no Provider and contains no credentials.
It has not been applied automatically. MySQL DDL is not a rollback-based dry run.

## Data contract

- `company_id` accepts the current development company identifier and future Core
  company UUIDs. No foreign key to Core tables or permission logic is introduced.
- `id` is a Provider UUID. `company_id` plus `id` can be referenced by future AI tables.
- `api_key_ciphertext` will contain authenticated encrypted bytes. `api_key_key_id`
  identifies the encryption key version. The secret master key must remain outside
  the database, Git, and frontend code.
- `version` supports concurrent-update checks in the future repository.
- The database stores UTC timestamps; the Java datasource must be configured for UTC.

## Model table

After the Provider table and `ai_app` account exist, run
`002_create_ai_models.sql` once using the local schema-administration account:

```sql
SOURCE C:/Users/mings/aiosnova/server/ai-database/002_create_ai_models.sql;
```

Confirm `current_database` is `aiosnova_ai_local` and `model_count` is zero on a
new table. Then connect as `ai_app` and run `SELECT COUNT(*) FROM ai_models;` to
verify application access. The script grants CRUD access only to this AI table.
If a statement fails, inspect which statements succeeded before retrying;
table creation and grants do not form a rollback-based transaction.

- Model IDs generated by Java are distinct from the external `model_id`.
- A company/Provider/external-model tuple is unique. Different Providers may
  configure the same external model independently.
- New models default to disabled. Nullable capability flags distinguish unknown
  metadata from explicitly unsupported features.
- The composite foreign key prevents assigning a model to a Provider in another
  company. Deleting a Provider cascades to its model configurations.
- Agent usage counts will be derived from actual associations rather than stored
  as an independent counter in this table.

Creating the table does not migrate frontend models or change chat behavior.
The next step is an AI model repository and service, followed by frontend model
persistence and server-side model enablement checks.

Do not change or reuse Core's `AUTH_STORAGE_KEY`, database, or migrations. The shared
backend authorization integration is a later task owned by Core.
