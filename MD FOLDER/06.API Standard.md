# AIOS API Standard

> 文件编号：06
> 文件名称：API Standard
> 适用范围：AIOS 全部 REST API、Frontend API、Backend API、AI API、Internal API、Developer API、Webhook、Third-Party Integration
> 适用对象：Cursor、AI Agent、Frontend Developer、Backend Developer、AI Developer、Integration Developer
> 前置规则：必须遵守《01 产品原则》《02 系统架构标准》《03 开发与编码标准》《05 数据库设计标准》
> Backend：Spring Boot
> Frontend：React + Vite + TypeScript
> AI Layer：Python
> Database：PostgreSQL
> 核心目标：统一、安全、稳定、清晰、可预测、可扩展、可版本化、可审计

---

# 1. 文件目的

本文件定义 AIOS 所有 API 的统一标准。

AIOS 包含大量业务模块：

* Core
* AI
* CRM
* Sales
* POS
* Inventory
* Procurement
* Finance
* HRM
* Project
* Marketing
* Manufacturing
* Automation
* Developer Platform
* Integration Hub
* Admin
* Super Admin

如果没有统一 API Standard，系统将容易出现：

```text
不同 URL Naming
不同 Response Format
不同 Error Format
不同 Pagination
不同 Status Code
不同 Permission 处理
不同 Tenant 处理
不同 Date Format
不同 Money Format
```

最终造成系统无法维护。

因此：

> 所有 AIOS API 必须遵守统一 Contract。

---

# 2. API First 原则

AIOS 采用：

> API First

Frontend、Backend、AI、Integration 之间必须通过明确 Contract 协作。

标准关系：

```text
React Frontend
      ↓
REST API
      ↓
Spring Boot
      ↓
Business Logic
      ↓
PostgreSQL
```

AI：

```text
Python AI Service
      ↓
Controlled API
      ↓
Spring Boot
      ↓
Permission
      ↓
Business Logic
```

Third Party：

```text
Third Party
      ↓
Public API / Webhook
      ↓
API Boundary
      ↓
Spring Boot
```

---

# 3. Spring Boot 是核心 Business API Owner

AIOS 核心业务 API 必须由：

```text
Spring Boot
```

控制。

包括：

```text
Authentication
Authorization
Tenant Validation
Company Validation
Business Rule
Transaction
Audit
Database Access
```

React 与 Python 不得绕过 Spring Boot：

直接修改核心业务 PostgreSQL 数据。

---

# 4. REST 是默认 API 风格

AIOS 当前默认使用：

```text
REST API
```

作为核心 Application API。

例如：

```text
GET    /api/v1/customers
POST   /api/v1/customers
GET    /api/v1/customers/{customerId}
PATCH  /api/v1/customers/{customerId}
```

GraphQL 虽然属于未来 Developer Platform 能力：

但 Cursor 不得因为架构中存在 GraphQL 就同时开发：

```text
REST + GraphQL
```

除非用户明确要求。

---

# 5. API Base Path

正式业务 API 默认：

```text
/api/v1
```

例如：

```text
/api/v1/customers
/api/v1/sales-orders
/api/v1/invoices
/api/v1/employees
```

不得不同 Module 自行使用：

```text
/api/customer
/api/v2/sales
/backend/inventory
/service/hr
```

无统一规则。

---

# 6. API Versioning

公开或稳定 API 必须具备 Version Awareness。

默认：

```text
/api/v1
```

未来 Breaking Change：

可以进入：

```text
/api/v2
```

但不得因为小修改频繁增加 Version。

---

# 7. 什么属于 Breaking Change

以下通常属于 Breaking Change：

```text
删除 Response Field
Rename Field
改变 Field Type
改变 Field Meaning
删除 Endpoint
改变 Authentication
改变 Required Parameter
改变 Status Meaning
改变 Error Contract
```

必须评估调用方。

---

# 8. 非 Breaking Change

以下通常可以在同 Version 内扩展：

```text
新增 Optional Response Field
新增 Optional Query Parameter
新增 Endpoint
新增 Error Code
```

但必须确保 Existing Client 可以继续工作。

---

# 9. Resource Naming

REST URL 必须使用：

```text
Noun
```

而不是：

```text
Verb
```

正确：

```text
/customers
/sales-orders
/purchase-orders
/employees
```

不推荐：

```text
/getCustomers
/createCustomer
/updateSalesOrder
/deleteEmployee
```

---

# 10. Resource 使用复数

Collection Endpoint 默认使用复数：

```text
/customers
/users
/invoices
/employees
```

禁止：

```text
/customer
/users
/invoice
```

无规则混用。

---

# 11. URL 使用 kebab-case

URL 多单词 Resource 使用：

```text
kebab-case
```

例如：

```text
/sales-orders
/purchase-orders
/stock-transfers
/customer-segments
```

禁止混用：

```text
/salesOrders
/sales_orders
/SalesOrders
```

---

# 12. URL 不得暴露技术实现

禁止：

```text
/customer-controller
/customer-table
/customer-repository
/customer-entity
```

API 表达 Business Resource。

不是 Java Class。

---

# 13. Resource ID

Resource URL：

```text
/api/v1/customers/{customerId}
```

参数名称必须明确。

推荐：

```text
customerId
salesOrderId
employeeId
```

不要全部：

```text
{id}
```

如果同一路径存在多个 ID。

---

# 14. Nested Resource

存在明确 Parent / Child Relationship 时：

可以使用：

```text
/sales-orders/{salesOrderId}/items
```

但不得无限嵌套：

```text
/tenants/{id}/companies/{id}/departments/{id}/employees/{id}/...
```

一般避免超过：

> 2-3 层业务 Resource。

---

# 15. Tenant 不应到处放 URL

普通 Tenant API：

不应该默认要求：

```text
/tenants/{tenantId}/customers
```

因为 Tenant Context 应来自：

```text
Authenticated Context
```

而不是让用户自由指定。

普通业务请求推荐：

```text
/api/v1/customers
```

Backend 自动应用当前 Tenant Scope。

---

# 16. Super Admin 跨 Tenant API 必须分离

真正 Platform Level API：

应使用明确边界。

例如：

```text
/api/v1/platform/tenants
/api/v1/platform/subscriptions
```

或项目统一 Admin Namespace。

不得为了支持 Super Admin：

让所有普通 Business API 接受任意 tenantId。

---

# 17. Company Scope

如果当前操作属于某 Company：

Company Context 必须经过 Backend 验证。

即使 API 接收：

```text
companyId
```

也不能直接相信。

必须验证：

```text
Current User
↓
Current Tenant
↓
Company Membership / Permission
```

---

# 18. HTTP Method 标准

默认：

```text
GET
→ Read

POST
→ Create / Command

PUT
→ Complete Replacement

PATCH
→ Partial Update

DELETE
→ Delete
```

Cursor 不得随意使用 Method。

---

# 19. GET 必须是 Read-Only

GET 请求禁止产生核心业务 Side Effect。

禁止：

```text
GET /approve-invoice
GET /delete-customer
GET /pay
```

GET 必须可以安全重复调用。

---

# 20. POST 用于 Create

例如：

```text
POST /api/v1/customers
```

用于创建 Customer。

成功：

```text
201 Created
```

---

# 21. PATCH 是默认 Partial Update

普通编辑页面只修改部分字段时：

优先：

```text
PATCH
```

例如：

```text
PATCH /api/v1/customers/{customerId}
```

---

# 22. PUT 使用原则

PUT 表示：

> Client 提供完整 Resource Representation 并替换。

不得只是为了 Update 就无脑使用 PUT。

如果项目没有真正 Replacement 语义：

优先 PATCH。

---

# 23. DELETE 使用原则

DELETE 只用于业务允许真正 Delete 的 Resource。

Finance、Payment、Payroll 等历史交易：

通常不得通过普通 DELETE 删除。

应使用：

```text
Cancel
Void
Reverse
Archive
```

等业务 Command。

---

# 24. Business Action

不是普通 CRUD 的业务行为：

允许使用明确 Action Endpoint。

例如：

```text
POST /sales-orders/{salesOrderId}/submit

POST /purchase-orders/{purchaseOrderId}/approve

POST /invoices/{invoiceId}/void

POST /payments/{paymentId}/refund
```

这种 Action 必须代表真正 Domain Command。

---

# 25. 禁止滥用 Action Endpoint

不要：

```text
POST /customers/{id}/update-name
POST /customers/{id}/update-email
POST /customers/{id}/change-phone
```

普通字段修改应通过 PATCH。

Action Endpoint 应只用于：

> 有独立业务含义的状态变化或 Command。

---

# 26. Bulk API

批量操作可以使用：

```text
POST /customers/bulk-actions
```

或明确 Domain Command Pattern。

必须定义：

```text
Action
Resource IDs
Validation
Result
Partial Failure
Audit
```

不得建立万能：

```text
POST /bulk
```

处理所有业务。

---

# 27. Request Body 使用 JSON

普通 API Request / Response：

统一使用：

```text
application/json
```

除：

* File Upload
* File Download
* Streaming
* Webhook 特殊协议

之外。

---

# 28. JSON Field 使用 camelCase

API JSON 统一：

```text
camelCase
```

例如：

```json
{
  "customerId": "...",
  "customerName": "ABC",
  "createdAt": "..."
}
```

数据库使用：

```text
snake_case
```

两者不得混淆。

---

# 29. 数据库字段不能直接决定 API 命名

Database：

```text
customer_name
created_at
```

API：

```text
customerName
createdAt
```

API Contract 是独立边界。

---

# 30. Request DTO 与 Response DTO 必须分离

禁止直接：

```text
JPA Entity
```

作为：

```text
@RequestBody
```

或 Response。

必须使用：

```text
CreateCustomerRequest
UpdateCustomerRequest
CustomerResponse
```

等明确 DTO。

---

# 31. Create 与 Update DTO 不得盲目共用

例如：

Create Customer：

可能要求：

```text
name
```

Update Customer：

可能允许 Optional。

因此不应为了减少 Class：

强制共用一个巨大 DTO。

---

# 32. API 不允许 Mass Assignment

Client 不允许通过 Request 自行控制：

```text
tenantId
createdBy
approvedBy
permission
systemRole
internalStatus
auditData
```

除非对应 API 明确允许。

---

# 33. Request Validation

所有 Request 必须进行格式验证。

至少包括：

```text
Required
Length
Format
Range
Enum
Pattern
```

Spring Boot 应使用统一 Validation Pattern。

---

# 34. Domain Validation 必须再次执行

Request DTO Validation：

不能代替 Domain Rule。

例如：

```text
quantity > 0
```

属于格式 / 基础 Validation。

```text
库存是否足够
```

属于 Domain Validation。

---

# 35. Path Parameter 必须 Validate

不要只 Validate Body。

以下都属于外部输入：

```text
Path Variable
Query Parameter
Header
Body
Webhook
```

必须视为不可信。

---

# 36. Unknown Request Field

对于关键 API：

应避免 Client 随意发送未知字段却完全无察觉。

具体严格程度由统一 JSON Configuration 决定。

但安全敏感字段绝不能因为 Binding 行为被意外接受。

---

# 37. Null 与 Missing 必须区分

PATCH 请求中：

```text
field missing
```

与：

```text
field = null
```

可能代表不同意思。

必须设计清楚。

禁止 Cursor 随意将两者视为相同。

---

# 38. Empty String 与 Null

API 必须统一：

```text
null
""
```

的语义。

不得：

有些 Module 使用空字符串表示无值，

有些使用 null。

---

# 39. Success Response 标准

普通成功 Response 推荐统一：

```json
{
  "data": {
  }
}
```

需要额外 Metadata 时：

```json
{
  "data": {
  },
  "meta": {
  }
}
```

---

# 40. List Response

List API：

```json
{
  "data": [
  ],
  "meta": {
    "pagination": {
      "page": 1,
      "size": 20,
      "totalItems": 125,
      "totalPages": 7
    }
  }
}
```

---

# 41. 不要多层无意义 Wrapper

禁止：

```json
{
  "success": true,
  "status": "success",
  "result": {
    "response": {
      "data": {
      }
    }
  }
}
```

Response 必须保持简单。

---

# 42. 不需要同时返回 success=true

如果 HTTP Status：

```text
200
201
204
```

已经表达成功，

通常无需每个 Response 再添加：

```text
success: true
```

除非项目已有统一 Contract 明确要求。

---

# 43. Error Response 必须统一

所有 API Error 必须使用统一结构。

推荐：

```json
{
  "error": {
    "code": "CUSTOMER_NOT_FOUND",
    "message": "Customer was not found.",
    "details": null,
    "fieldErrors": []
  },
  "requestId": "..."
}
```

---

# 44. Error Code 必须机器可读

Error Code 使用稳定：

```text
UPPER_SNAKE_CASE
```

例如：

```text
VALIDATION_ERROR
ACCESS_DENIED
RESOURCE_NOT_FOUND
CUSTOMER_NOT_FOUND
DUPLICATE_EMAIL
INSUFFICIENT_STOCK
INVALID_ORDER_STATUS
```

---

# 45. Error Message 给人阅读

```text
code
```

给系统判断。

```text
message
```

给人理解。

Frontend 不应该依赖：

```text
message == "Customer not found"
```

判断逻辑。

必须依赖：

```text
error.code
```

---

# 46. Field Validation Error

表单 Validation：

推荐：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed.",
    "fieldErrors": [
      {
        "field": "email",
        "code": "INVALID_EMAIL",
        "message": "Enter a valid email address."
      }
    ]
  },
  "requestId": "..."
}
```

---

# 47. Error 不得暴露内部细节

禁止 Response 包含：

```text
Java Stack Trace
SQL
Table Name
Database Host
Server File Path
Secret
Token
Internal Class Name
```

---

# 48. requestId

每个 Request 应拥有：

```text
requestId
```

用于：

```text
Frontend
Backend
AI
Logging
Support
```

之间追踪问题。

---

# 49. Correlation ID

跨 Service 调用时：

应尽量传播：

```text
Correlation ID / Trace ID
```

例如：

```text
React
↓
Spring Boot
↓
Python AI
↓
Third Party
```

---

# 50. HTTP Status Code 标准

主要 Status：

```text
200 OK
201 Created
202 Accepted
204 No Content

400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
422 Unprocessable Content

429 Too Many Requests

500 Internal Server Error
502 Bad Gateway
503 Service Unavailable
504 Gateway Timeout
```

必须根据真实语义使用。

---

# 51. 200 OK

用于：

```text
GET Success
PATCH Success
Business Action Success
```

不得任何情况都返回 200。

---

# 52. 201 Created

成功创建 Resource：

使用：

```text
201 Created
```

例如：

```text
POST /customers
```

---

# 53. 202 Accepted

任务已经接受，但将在异步处理：

```text
202 Accepted
```

例如：

```text
Large Export
AI Document Processing
Bulk Import
Report Generation
```

Response 应提供：

```text
jobId
status
```

或相应 Tracking 信息。

---

# 54. 204 No Content

操作成功但无需 Response Body：

可以使用：

```text
204 No Content
```

如果使用 204：

不得再返回 JSON Body。

---

# 55. 400 Bad Request

用于：

* Request 格式错误
* 无法解析
* 基础请求错误

---

# 56. 401 Unauthorized

表示：

> 未认证或 Authentication 无效。

不是：

> 没权限。

---

# 57. 403 Forbidden

表示：

> 用户已经认证，但没有权限执行此操作。

不要把所有 Permission Error 返回 401。

---

# 58. 404 Not Found

用于：

* Resource 不存在

同时在 Security Sensitive 场景：

可以根据 Security Policy 隐藏 Resource 是否存在。

---

# 59. 409 Conflict

适用于：

```text
Duplicate
Version Conflict
Invalid State Conflict
Concurrency Conflict
```

例如：

```text
Email already exists
Order already completed
```

具体 Error Code 必须进一步说明。

---

# 60. 422 Unprocessable Content

适用于：

> Request 格式正确，但内容无法通过业务 Validation。

是否使用 400 或 422：

必须全系统统一。

默认建议：

```text
400
→ Request 格式 / 基础 Validation

422
→ Domain / Business Validation
```

---

# 61. 429 Too Many Requests

Rate Limit 被触发：

返回：

```text
429
```

并根据 API 类型提供合理 Retry 信息。

---

# 62. 500 Internal Server Error

只有真正未预期 Server Error：

使用：

```text
500
```

不得：

```text
Customer not found
```

也返回 500。

---

# 63. 503 Service Unavailable

Dependency 或系统暂时不可用：

可以使用：

```text
503
```

例如某个必要 AI / Integration Service 不可用。

---

# 64. Pagination Standard

普通后台分页默认 Query：

```text
?page=1&size=20
```

默认：

```text
page = 1
size = 20
```

最大：

```text
size = 100
```

除非特定 Endpoint 有明确不同要求。

---

# 65. Page Number 从 1 开始

Public API Contract：

统一：

```text
page=1
```

表示第一页。

不得有些 Endpoint：

```text
page=0
```

另一些：

```text
page=1
```

---

# 66. Pagination Metadata

必须返回：

```text
page
size
totalItems
totalPages
```

如果总数量计算代价极高的特殊 API：

可以采用 Cursor Pagination。

但 Contract 必须明确。

---

# 67. Cursor Pagination

大型 Feed / Audit / Event API：

可以考虑：

```text
cursor
limit
```

例如：

```text
?cursor=xxx&limit=50
```

但 Cursor 不得为了架构高级让所有普通 CRUD API 使用 Cursor Pagination。

---

# 68. Pagination 必须稳定排序

任何分页必须存在稳定 Sort。

例如：

```text
createdAt DESC
+
id DESC
```

避免重复或漏掉数据。

---

# 69. Sorting

统一使用：

```text
sort
```

例如：

```text
?sort=createdAt,desc
```

多字段 Sort 是否支持：

由 Endpoint 明确定义。

---

# 70. Sort Field 必须白名单

禁止把用户提供的：

```text
sort
```

直接拼接 SQL。

必须通过允许字段列表映射。

---

# 71. Filtering

简单 Filter 使用 Query Parameter。

例如：

```text
?status=ACTIVE
?companyId=...
?customerId=...
```

禁止 Filter Parameter 命名随意变化：

```text
status
statusCode
currentStatus
order_status
```

表达同一概念。

---

# 72. Date Range Filter

统一推荐：

```text
from
to
```

或：

```text
createdFrom
createdTo
```

根据字段语义使用明确名称。

不能用：

```text
date1
date2
```

---

# 73. Search

通用文本 Search：

可以使用：

```text
?q=
```

或系统统一：

```text
?search=
```

必须全系统选择一种。

AIOS 默认：

```text
?search=
```

---

# 74. Filter 不允许任意数据库字段

API 不得支持：

```text
?field=x&operator=y&value=z
```

直接操作任意数据库字段，

除非专门设计 Query Engine。

普通 API 必须显式定义可 Filter 字段。

---

# 75. Search 必须有明确范围

Backend 必须知道：

```text
search
```

究竟查询：

```text
Name
Email
Code
Business Number
```

哪些字段。

不得对所有 Column 模糊搜索。

---

# 76. Date / Time Wire Format

API DateTime 统一使用：

```text
ISO 8601
```

例如：

```text
2026-08-16T15:30:00+08:00
```

或：

```text
2026-08-16T07:30:00Z
```

不得返回：

```text
16/8/2026 3:30PM
```

作为 API Canonical Value。

---

# 77. Date Wire Format

纯日期：

```text
YYYY-MM-DD
```

例如：

```text
2026-08-16
```

---

# 78. Timezone 必须明确

DateTime 必须：

* 包含 Offset
* 或明确为 UTC

禁止：

```text
2026-08-16 15:30:00
```

这种没有 Timezone 的跨系统 DateTime。

---

# 79. Display Format 不属于 API

API 返回标准 Date / Time。

Frontend 再根据：

```text
Locale
Timezone
Company Setting
```

格式化显示。

Backend 不应返回 UI 专用：

```text
"16 Aug 2026, 3:30 PM"
```

作为唯一值。

---

# 80. Money API 标准

核心金额 API 必须同时表达：

```text
amount
currency
```

例如：

```json
{
  "amount": "1250.00",
  "currency": "MYR"
}
```

---

# 81. Money 使用 Decimal String

为了避免：

```text
JavaScript Floating Point Precision
```

核心金额 Wire Format 默认使用：

```text
String Decimal
```

例如：

```json
{
  "totalAmount": "1520.35"
}
```

禁止：

```json
{
  "totalAmount": 1520.3500000000001
}
```

---

# 82. Rate 使用 Decimal String

例如：

```json
{
  "exchangeRate": "3.165000"
}
```

关键：

```text
Exchange Rate
Commission Rate
Tax Rate
Discount Rate
```

不得因为 JSON 支持 Number 就放弃 Precision。

---

# 83. Percentage 必须定义语义

API 必须明确 Percentage 的值代表：

```text
8
```

还是：

```text
0.08
```

AIOS 必须统一。

默认：

```text
Percentage API 使用实际百分比值
8.5 = 8.5%
```

除非某个 Domain Standard 明确定义其他表示方法。

---

# 84. Currency Code

Currency 必须使用标准 Code。

例如：

```text
MYR
SGD
USD
AUD
```

不得用：

```text
RM
$
S$
```

作为 Canonical Currency Value。

Symbol 由 Frontend Display Layer 负责。

---

# 85. Boolean

API Boolean 必须使用：

```json
true
false
```

禁止：

```text
1
0
Y
N
yes
no
```

作为 Boolean Contract。

---

# 86. Enum

业务 Enum 使用清楚稳定的 String：

```text
DRAFT
PENDING
APPROVED
REJECTED
```

禁止：

```text
1
2
3
4
```

作为 API Status。

---

# 87. Enum 不能使用 UI 文案

Canonical API Value：

```text
PENDING_APPROVAL
```

Frontend 可以显示：

```text
Pending Approval
等待审批
```

API Enum 不应随翻译改变。

---

# 88. Unknown Enum Forward Compatibility

Frontend 应能够处理未来 Backend 新增 Enum。

未知 Status：

不得导致整个页面 Crash。

---

# 89. ID Wire Format

UUID 在 JSON 中统一作为：

```text
string
```

例如：

```json
{
  "customerId": "0198..."
}
```

Frontend 不应假设 ID 是 Number。

---

# 90. Resource Reference

如果 Response 只需要 Resource Reference：

不要返回完整巨大 Entity。

例如：

```json
{
  "customer": {
    "id": "...",
    "name": "ABC"
  }
}
```

根据 Use Case 返回必要字段。

---

# 91. 禁止无脑返回完整 Nested Object

例如 Sales Order List：

不得每个 Row 同时返回：

```text
完整 Customer
完整 Company
完整 Product
完整 User
完整 Permission
```

导致巨大 Payload。

---

# 92. List DTO 与 Detail DTO 可以不同

例如：

```text
CustomerListItemResponse
CustomerDetailResponse
```

可以拥有不同字段。

禁止为了减少 DTO：

所有 API 返回同一个巨大对象。

---

# 93. Sensitive Fields 永远不得普通返回

包括：

```text
password
passwordHash
accessToken
refreshToken
secret
privateKey
internalSecurityFlag
```

不得进入普通 API Response。

---

# 94. Authentication

所有非 Public API：

必须进行 Authentication。

不得因为 Frontend 已经隐藏页面：

就允许 Backend Endpoint 无认证访问。

---

# 95. Authorization

Authentication 成功后：

仍然必须进行：

```text
Permission
Resource Scope
Tenant Scope
Company Scope
```

验证。

---

# 96. RBAC / ABAC

API 不得自行出现不同权限逻辑：

```text
if role == ADMIN
```

到处 Hardcode。

必须经过统一：

```text
Permission System
RBAC
ABAC
```

---

# 97. Resource Ownership

例如：

```text
GET /customers/{customerId}
```

不能：

```text
findById(customerId)
→ return
```

必须验证：

```text
Tenant
Company
Permission
Resource Scope
```

---

# 98. Tenant Context

Tenant Context 必须来源于：

```text
Authenticated Session / Token
+
Authorized Tenant Context
```

不得直接信任：

```text
X-Tenant-ID
```

或 Request Body 中的 tenantId。

---

# 99. Tenant Header

如果系统使用：

```text
X-Tenant-ID
```

切换当前 Tenant：

Backend 必须确认：

> 当前 User 是否属于该 Tenant。

Header 只是请求 Context。

不是安全证据。

---

# 100. Company Header

如果使用：

```text
X-Company-ID
```

同样必须验证：

```text
Company 属于当前 Tenant
+
User 有权访问 Company
```

---

# 101. Authentication Token

Token 必须通过标准：

```text
Authorization: Bearer <token>
```

等正式 Authentication Mechanism。

不得把 Access Token 放入：

```text
URL Query Parameter
```

---

# 102. Token 不得进入 Log

禁止记录完整：

```text
Authorization Header
Access Token
Refresh Token
```

---

# 103. Refresh Token Endpoint

如果采用 Refresh Token：

应使用专门 Endpoint。

不得所有 Business API 自行 Refresh。

---

# 104. Logout

Logout 是否需要服务器端 Revocation：

必须根据 Authentication Architecture 统一设计。

Cursor 不得自行发明不同 Login / Logout Pattern。

---

# 105. MFA API

MFA 属于 Security Domain。

必须通过专门 Authentication Flow。

普通业务 Module 不得自己实现第二套 MFA。

---

# 106. CORS

Production 不得为了方便：

```text
Access-Control-Allow-Origin: *
```

同时允许 Credential。

CORS 必须根据 Environment 明确配置。

---

# 107. CSRF

如果 Authentication 使用：

```text
Cookie-based Session
```

必须考虑 CSRF Protection。

如果完全使用其他 Authentication Pattern：

根据实际 Architecture 处理。

Cursor 不得直接全局关闭 Security Protection。

---

# 108. Rate Limiting

以下 API 应特别考虑 Rate Limit：

```text
Login
Password Reset
OTP
Public API
AI API
Search
Webhook
Expensive Report
```

具体限额由后续 Security / Infrastructure Standard 定义。

---

# 109. API Key

Developer API 使用 API Key 时：

必须：

* 有 Owner
* 有 Scope
* 有 Expiry / Rotation Strategy
* 可 Revoke
* 可 Audit

不得使用一个永久 Global API Key 给所有 Third Party。

---

# 110. OAuth

第三方 Integration 若使用 OAuth：

必须统一由 Developer / Integration Security Architecture 管理。

不得每个 Module 自己保存未经保护的 OAuth Credential。

---

# 111. Public API 与 Internal API 必须区分

至少需要概念区分：

```text
Frontend / Application API
Internal Service API
Public Developer API
Webhook API
Platform Admin API
```

它们不能默认拥有完全一样的权限边界。

---

# 112. Internal API 不代表无需 Security

即使：

```text
Internal
```

也不能默认：

> 网络内部 = 可信。

必须根据架构使用：

* Service Authentication
* Authorization
* Network Policy

等方式保护。

---

# 113. Zero Trust API 原则

任何 Service Request 都不应因为：

> 来自内部服务器

就自动拥有所有权限。

---

# 114. Python AI API

Python AI Service API 必须拥有明确用途。

例如：

```text
Generate
Analyze
Retrieve
Agent Run
Embedding
Document Processing
```

不得暴露：

```text
executeAnything
runAnyCommand
queryAnyDatabase
```

这种万能 API。

---

# 115. AI Tool Calling

AI Agent 执行业务 Action：

必须调用正式 Backend API / Tool Contract。

例如：

```text
AI
↓
create_sales_order tool
↓
Spring Boot API
↓
Permission
↓
Business Validation
```

---

# 116. AI 不得拥有绕过权限的内部 API

禁止设计：

```text
/internal/admin/do-anything
```

然后所有 AI Agent 使用。

AI Tool Permission：

必须与 User / Agent Identity 绑定。

---

# 117. AI Delegation

AI 代表 User 执行动作时：

Backend 必须能够知道：

```text
User
Agent
Tenant
Action
```

而不是所有 AI Request 都显示：

```text
system
```

---

# 118. AI Action Audit

重要 AI Action 必须记录：

```text
Who requested
Which Agent
What action
Target
Result
Timestamp
```

---

# 119. AI Response 不得伪装 Business Fact

LLM Generated Content：

与正式 Business Record 必须有明确边界。

AI 输出不能因为返回 JSON：

就直接视为已经验证的业务数据。

---

# 120. AI Structured Output

AI Structured Output 必须经过：

```text
Schema Validation
Domain Validation
Permission Validation
```

然后才允许进入 Business Action。

---

# 121. File Upload API

File Upload 应使用：

```text
multipart/form-data
```

或正式 Object Storage Upload Flow。

必须验证：

```text
File Size
File Type
Ownership
Tenant
Permission
```

---

# 122. File Name 不可信

Client 提供的 File Name：

不得直接作为：

```text
Server File Path
Object Storage Key
```

必须安全处理。

---

# 123. File Download

下载文件必须再次验证：

```text
Authentication
Tenant
Permission
Resource Ownership
```

知道 fileId：

不代表有权限下载。

---

# 124. Signed URL

如未来使用 Object Storage Signed URL：

必须：

* 短时间有效
* Scope 正确
* Permission 验证后生成

不得生成永久公开 URL 给敏感文件。

---

# 125. Import API

大型 Import 推荐：

```text
POST import
↓
202 Accepted
↓
jobId
↓
Background Processing
```

不得 HTTP Request 阻塞非常长时间。

---

# 126. Export API

大型 Export 同样应考虑：

```text
Async Job
```

并提供：

```text
Status
Result File
Expiry
```

---

# 127. Job API

异步 Job 可以采用：

```text
POST /reports/export
→ 202

GET /jobs/{jobId}
```

Job 必须 Tenant Scoped。

---

# 128. Job Status

统一考虑：

```text
PENDING
RUNNING
COMPLETED
FAILED
CANCELLED
```

不要每个 Module 发明：

```text
PROCESSING
WORKING
GENERATING
DOING
```

表达同样技术状态。

---

# 129. Webhook Endpoint

Webhook 必须属于明确 Provider。

例如：

```text
/api/v1/webhooks/{provider}
```

具体路径根据 Integration Architecture 定义。

---

# 130. Webhook Signature Verification

所有支持签名的 Provider：

必须验证：

```text
Signature
Timestamp
Secret
```

禁止收到 Request 就信任。

---

# 131. Webhook Idempotency

Provider 可能重复发送 Event。

必须根据：

```text
providerEventId
```

等唯一标识防止重复执行。

---

# 132. Webhook 快速响应

Webhook Handler 不应执行长时间业务任务后才响应。

推荐：

```text
Validate
↓
Persist / Queue
↓
Respond
↓
Async Process
```

具体根据 Provider 要求。

---

# 133. Webhook Payload

原始 Payload 是否保存：

根据：

```text
Audit
Debug
Security
Privacy
Storage
```

要求决定。

不得无条件永久保存所有敏感第三方 Payload。

---

# 134. External API Client

Spring Boot 调用第三方 API：

必须通过专门 Client / Integration Layer。

禁止业务 Service 中到处：

```text
直接拼 URL
直接发 HTTP
```

---

# 135. External API Timeout

所有 Third-Party API：

必须设置：

```text
Connection Timeout
Read Timeout
```

禁止无限等待。

---

# 136. External Retry

Retry 必须基于：

```text
HTTP Method
Idempotency
Provider Behavior
Error Type
```

决定。

禁止 Payment Create 失败后无脑 Retry 多次。

---

# 137. External API Error Mapping

Third Party 错误：

必须转换成 AIOS 内部统一 Error。

不要直接把 Provider 原始：

```text
500 xyz_gateway_err_81
```

暴露给 Frontend。

---

# 138. External API Response 不可信

第三方 Response：

必须 Validate：

```text
Schema
Required Field
Status
Amount
Currency
Reference
```

不得默认 Provider 永远返回正确格式。

---

# 139. Idempotency

以下 API 必须特别考虑 Idempotency：

```text
Payment
Refund
Sales Order Creation
Invoice Posting
Webhook Processing
AI Action
Bulk Action
```

---

# 140. Idempotency-Key

高风险 API 可使用：

```text
Idempotency-Key
```

Header。

例如：

```text
Idempotency-Key: <unique-key>
```

Backend 必须定义：

```text
Scope
Expiry
Result Reuse
Conflict Behavior
```

---

# 141. Idempotency 不能只在 Frontend

按钮 Disabled：

不是 Idempotency。

真正 Idempotency 必须由 Backend 保证。

---

# 142. Duplicate Create

对于具有自然 Unique Rule 的 Resource：

Database Unique Constraint：

仍然必须存在。

Idempotency 与 Unique Constraint：

解决不同问题。

---

# 143. Optimistic Concurrency

可编辑资源存在多人同时编辑风险时：

应考虑：

```text
version
```

或：

```text
ETag / If-Match
```

机制。

Cursor 不得默认后保存的人静默覆盖前一个人的修改。

---

# 144. Conflict Response

Concurrency Conflict：

推荐：

```text
409 Conflict
```

并提供稳定：

```text
VERSION_CONFLICT
```

Error Code。

---

# 145. Cache-Control

敏感业务 API：

不得默认被公共 Cache。

例如：

```text
User
Finance
Payroll
Permission
```

必须根据 Security Requirement 设置适当 Cache Policy。

---

# 146. ETag

ETag 可以用于：

* Conditional GET
* Concurrency

但不是所有 Endpoint 强制要求。

必须有实际需求再使用。

---

# 147. API Performance

API 不得因为方便：

返回巨大 Payload。

必须控制：

```text
Payload Size
Query Count
Nested Data
Pagination
Serialization
```

---

# 148. List API 不得返回全部 Detail

List View：

只返回列表所需字段。

Detail：

通过：

```text
GET /resource/{id}
```

获取详细数据。

---

# 149. API 不允许 N+1

Backend List API：

不得因为 Entity Relationship：

产生 N+1 Query。

API 性能问题应从 Query / DTO Projection 解决。

---

# 150. Expensive Endpoint

大型 Analytics / Report：

必须避免普通用户高频无限调用。

可以考虑：

```text
Cache
Async Job
Rate Limit
Pre-Aggregation
```

但根据真实需求实施。

---

# 151. API Timeout

Backend Endpoint 自身必须避免无限执行。

长时间任务：

应转为 Async Job。

---

# 152. Partial Failure

Bulk Operation 必须明确：

```text
All-or-Nothing
```

还是：

```text
Partial Success
```

不得模糊。

---

# 153. Partial Success Response

如果允许部分成功：

Response 必须清楚：

```json
{
  "data": {
    "successful": [],
    "failed": []
  }
}
```

每个 Failed Item 必须有：

```text
resourceId
errorCode
message
```

---

# 154. Transaction 与 API

一个 API Command：

如果代表一个原子业务动作，

其 Database Transaction Boundary 必须清楚。

不得 Response 成功：

但实际只有一半数据写入。

---

# 155. HTTP Success 不等于 Business Success

如果业务失败：

不得：

```text
200 OK
{
  "success": false
}
```

作为统一做法。

应使用适当 HTTP Status + Error Contract。

---

# 156. Audit

以下 API 必须特别考虑 Audit：

```text
Create
Update
Delete
Approve
Reject
Void
Refund
Permission Change
Login Security Change
Payroll
Finance Posting
```

---

# 157. Read Audit

高度敏感数据：

例如：

```text
Salary
Bank
Secret
Security
```

是否需要记录 Read Audit：

由 Security / Compliance Policy 决定。

---

# 158. API Logging

API Log 应能够追踪：

```text
requestId
userId
tenantId
companyId
endpoint
method
status
duration
```

根据安全政策执行。

---

# 159. 不记录完整敏感 Request

禁止无脑 Logging：

```text
Request Body
Response Body
```

尤其：

```text
Password
Token
Bank Information
Personal Data
Payment Data
```

---

# 160. Slow API Logging

超过统一 Threshold 的请求：

应能够进入：

```text
Performance Monitoring
```

Threshold 由 Infrastructure Standard 定义。

---

# 161. OpenAPI

Spring Boot REST API 应逐步维护：

```text
OpenAPI
```

Contract。

尤其：

* Public API
* AI Service Contract
* Frontend Integration
* Developer Platform

必须保持 Documentation 与代码一致。

---

# 162. OpenAPI 不能成为过期文档

如果 API Contract 修改：

OpenAPI 也必须同步更新。

不得存在：

```text
Code 是 A
Documentation 是 B
```

---

# 163. API Documentation 必须说明

重要 API 至少明确：

```text
Purpose
Authentication
Permission
Request
Response
Error
Pagination
Business Rule
```

不是只列 URL。

---

# 164. Public API Documentation

Developer Platform Public API：

必须比 Internal API 提供更严格稳定的 Contract。

因为 Third Party 无法与内部代码同步修改。

---

# 165. API Deprecation

需要废弃 Public API 时：

必须经过：

```text
Deprecate
↓
Notify
↓
Migration Period
↓
Remove in New Version
```

不得突然删除。

---

# 166. Internal API 也不得随意 Breaking

即使只有 React 使用：

仍然需要检查：

```text
Frontend
Python
Integration
Test
Automation
```

调用方。

---

# 167. Field Deprecation

准备删除 Field 时：

可以先：

```text
Mark Deprecated
Stop New Usage
Migrate Client
Later Remove
```

不要直接 Rename / Delete。

---

# 168. Response Field 不得因为 Null 就随机消失

必须统一决定：

Optional Field 返回：

```text
null
```

还是：

```text
omit
```

AIOS 默认建议：

> 已定义 Response Contract 的 Field，允许为空时返回 `null`。

这样 Frontend Contract 更可预测。

---

# 169. Empty Collection

Collection 没数据：

返回：

```json
[]
```

不要返回：

```text
null
```

---

# 170. Empty Object

没有 Resource：

不能返回：

```json
{}
```

假装存在。

应返回：

```text
404
```

或业务定义状态。

---

# 171. Numeric Zero

```text
0
```

不能被处理成：

```text
null
```

或缺失。

Money / Quantity / Percentage：

必须保留真实 Zero。

---

# 172. Boolean False

```text
false
```

不能因为 Falsy 判断：

从 Response 中消失。

---

# 173. Default Value

API 不得为了让 Frontend 方便：

返回假的业务 Default。

例如未知 Currency：

不得返回：

```text
MYR
```

除非业务确实定义默认 MYR。

---

# 174. Localization

API Canonical Value：

不得直接受 UI Language 影响。

例如 Status：

```text
APPROVED
```

而不是：

```text
已批准
Approved
Diluluskan
```

Frontend 负责 Localization。

---

# 175. User-Facing Message

Backend 可以提供默认：

```text
message
```

但 Frontend 应根据产品 i18n 策略决定显示方式。

业务逻辑不得依赖已翻译 Message。

---

# 176. Country / Locale

标准 Code 使用：

```text
ISO / IANA
```

等适当标准。

例如：

```text
MY
MYR
Asia/Kuala_Lumpur
```

不得传随意显示文字作为核心值。

---

# 177. Phone

Phone API Contract 应逐步采用明确 International Format。

不得不同 Module：

自行拼接 Country Code。

具体标准由 Customer / Identity Domain 定义。

---

# 178. Email

Email Input：

必须：

```text
trim
validate
normalize according to identity rule
```

但 API 不得自行改变具有业务意义的数据而不明确。

---

# 179. Sorting Enum

如果 API 支持：

```text
sortDirection
```

Canonical Value：

统一：

```text
asc
desc
```

不得：

```text
up
down
ascending
DESCENDING
```

混用。

---

# 180. Query Parameter Naming

Query Parameter：

统一：

```text
camelCase
```

例如：

```text
companyId
createdFrom
createdTo
pageSize
```

如果 Pagination 使用：

```text
page
size
```

则保持标准。

---

# 181. Header Naming

自定义 HTTP Header：

统一使用清晰前缀。

例如：

```text
X-Request-ID
X-Tenant-ID
X-Company-ID
```

但只有确有架构需要时创建。

不得每个 Module 自己增加 Header。

---

# 182. 禁止 Business Data 放 Header

例如：

```text
Invoice Amount
Customer Name
Order Status
```

属于 Request Body / Query。

不应塞入 Header。

---

# 183. API Security Header

Security Header 主要由 Gateway / Backend Security 配置负责。

Cursor 不得单 Endpoint 自己乱设置相互冲突的安全 Header。

---

# 184. API Gateway

未来如果引入 API Gateway：

应负责：

```text
Routing
Rate Limit
Authentication Assistance
Observability
Public API Policy
```

但 Gateway 不能取代 Spring Boot：

```text
Business Permission
Tenant Authorization
Domain Validation
```

---

# 185. Gateway 不得成为 Business Logic Layer

禁止将：

```text
Finance Rules
Approval Rules
Inventory Rules
```

# 186. Service-to-Service Contract

Spring Boot ↔ Python：

必须使用明确 DTO / Schema。

不得依赖：

```text

复制 Java Entity
任意 Dict
```

作为隐式 Contract。

# 187. Python API Schema

应使用强类型 Schema。


禁止所有 Endpoint 接受：

```text

```

# 188. AI Model Provider 不得暴露给业务 Contract

业务 API 应表达：

```text

```

而不是强制业务 Client 理解：

```text
OpenAI-specific request
Provider-specific model payload
```

除非 Developer Platform 本身就是模型管理功能。

# 189. AI Model Name

业务 Frontend 不应 Hardcode Model Name：

```text

model-y
```

Model Selection 应由 AI Layer / Configuration 管理。

# 242. API 最终原则

AIOS API 必须坚持：

> 一个系统，一套 API Contract。

> REST 是当前默认核心 API 风格。

> Resource 使用 Noun，而不是 CRUD Verb。

> API Version 必须明确。

> Request 与 Response 必须使用 DTO。

> JPA Entity 不能成为公开 Contract。

> HTTP Status 必须表达真实结果。

> Error Code 给机器判断，Error Message 给人阅读。

> Frontend 不得依赖 Error Message 判断业务逻辑。

> Tenant Context 必须由 Backend 验证。

> Permission 必须由 Backend 验证。

> Resource ID 存在不代表用户有权访问。

> Money 与 Rate 必须保持 Decimal Precision。

> DateTime 必须使用标准 ISO 8601 并具有明确 Timezone。

> List API 必须考虑 Pagination。

> 高风险写入必须考虑 Idempotency。

> AI Agent 必须通过受控 API 执行业务动作。

> Third Party 永远被视为不可靠输入。

> Webhook 永远可能重复发送。

> Public API Contract 必须稳定。

> Cursor 修改 API 前必须搜索全部调用方。

> Cursor 不得为了快速完成功能破坏 API 长期一致性。

> API 是 AIOS 模块之间的契约，不是 Controller 的随意输出。
