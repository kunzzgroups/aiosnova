# AIOS Deployment Standard

> 文件编号：12
> 文件名称：Deployment Standard
> 适用范围：AIOS Frontend、Backend、AI Service、Database Migration、Worker、Scheduler、Integration
> 适用对象：Cursor、AI Agent、Developer、DevOps、Platform Engineer
> 前置规则：必须遵守《01 产品原则》至《11 Documentation Standard》
> 核心目标：可重复、安全、可验证、可回滚、环境隔离、最小停机、禁止直接修改 Production

---

# 1. 文件目的

本文件定义 AIOS 的 Deployment Standard。

Deployment 不只是：

```text
Build
↓
Upload
↓
Restart
```

正式部署必须同时考虑：

```text
Environment
Configuration
Secret
Database Migration
Compatibility
Health Check
Rollback
Monitoring
Security
```

Cursor / AI Agent 不得为了快速上线：

直接修改 Production。

---

# 2. Deployment 核心原则

AIOS 部署必须遵守：

```text
Repeatable
Automated
Versioned
Observable
Recoverable
Environment-Safe
Backward-Compatible
Secure
```

原则：

> 同一个版本在相同环境条件下，应能够重复产生相同部署结果。

---

# 3. Environment 必须分离

至少区分：

```text
local
development
staging
production
```

不同环境必须拥有独立：

```text
Database
Secrets
API Credentials
Storage
Configuration
External Provider Environment
```

---

# 4. Production 与非 Production 必须隔离

禁止：

```text
Development
↓
Production Database
```

禁止：

```text
Staging
↓
Production Payment Credential
```

禁止：

```text
Local
↓
Production Object Storage
```

除非存在经过批准的特殊只读流程。

---

# 5. Production Data 不得用于普通测试

禁止开发人员：

```text
为了测试功能
↓
直接修改 Production Data
```

测试必须使用：

```text
Development
Staging
Sandbox
```

环境。

---

# 6. Configuration 与代码分离

以下不得 Hardcode：

```text
Database URL
Backend URL
AI Service URL
Storage Endpoint
OAuth Credential
API Key
Environment Name
```

必须通过正式 Configuration 提供。

---

# 7. Secret 与普通 Configuration 分离

普通配置例如：

```text
PAGE_SIZE
FEATURE_NAME
TIMEZONE
```

可以存在 Config。

Secret：

```text
DB_PASSWORD
JWT_SECRET
API_KEY
PRIVATE_KEY
```

必须使用：

```text
Environment Secret
Secret Manager
Vault
```

等安全机制。

---

# 8. Frontend Environment Variable 默认公开

React + Vite：

任何打包进入 Browser 的变量：

必须视为公开数据。

禁止把：

```text
Database Password
Private API Key
JWT Signing Secret
Payment Secret
AI Provider Secret
```

放入 Frontend Environment。

---

# 9. Build Artifact 必须版本化

每次正式 Deployment：

必须能够知道：

```text
Version
Commit
Build
Deployment Time
Environment
```

不能 Production 上运行一个：

> 不知道来自哪个 Commit 的版本。

---

# 10. Source Code 与 Artifact 必须对应

部署 Artifact 必须由明确 Source Revision 构建。

例如：

```text
Git Commit
↓
Build
↓
Artifact
↓
Deployment
```

不得：

```text
Build
↓
之后继续手动修改 Artifact
```

导致 Source 与 Production 不一致。

---

# 11. Production 禁止手动修改源码

禁止 SSH 进入服务器后：

```text
vim file
nano file
直接改 JavaScript
直接改 Python
直接改 Java Config
```

作为正式修复方式。

正确流程：

```text
Change Source
↓
Review
↓
Test
↓
Build
↓
Deploy
```

---

# 12. Hotfix 也必须进入版本控制

紧急修复：

也必须：

```text
Commit
Build
Deploy
```

不能只修 Production：

却不回写 Git。

---

# 13. Deployment 应通过 CI/CD

正式环境优先通过：

```text
CI/CD Pipeline
```

执行：

```text
Build
Test
Package
Migration
Deploy
Verify
```

减少人工操作错误。

---

# 14. Cursor 不得擅自建立复杂 CI/CD

如果项目已有 Deployment Pipeline：

必须遵守现有流程。

不得为了一个 Feature：

擅自：

```text
更换 CI Provider
更换 Docker Strategy
引入 Kubernetes
重写整个 Deployment Pipeline
```

---

# 15. Deployment Pipeline 必须失败即停止

例如：

```text
Build Failed
Test Failed
Migration Failed
Security Check Failed
```

默认：

```text
STOP DEPLOYMENT
```

不得：

```text
ignore
continue production deployment
```

---

# 16. Build 必须在部署前完成

Frontend：

```text
Type Check
Lint if configured
Test
Build
```

Backend：

```text
Compile
Test
Package
```

Python：

```text
Syntax / Type / Test
Package / Image
```

具体命令跟随项目配置。

---

# 17. 不允许在 Production Server 临时编译修复

Production 应优先部署已经验证的：

```text
Artifact / Container Image
```

而不是把整个开发目录上传后现场处理。

---

# 18. Dependency 必须固定

正式 Build 必须使用：

```text
Lock File
Pinned / Controlled Version
```

保证依赖可重复。

不得每次 Production Build：

自动获取不同 Dependency Version。

---

# 19. Dependency Upgrade 与 Deployment 分离

普通 Feature Deployment：

不得顺便升级：

```text
React Major
Spring Boot Major
Java Major
Python Major
PostgreSQL Major
```

重大升级应独立 Deployment。

---

# 20. Database Migration 必须属于 Deployment Plan

如果新版本需要 Schema Change：

Deployment 前必须知道：

```text
Migration
Compatibility
Existing Data
Backfill
Rollback / Forward Recovery
```

---

# 21. Migration 必须先验证

正式部署前：

Migration 至少应在：

```text
Development
Staging
```

验证。

禁止第一次运行 Migration：

就是 Production。

---

# 22. Production 不使用 ORM 自动改 Schema

Production 禁止依赖：

```text
hibernate ddl-auto=update
```

或类似机制：

自动修改 Schema。

Database Change：

必须通过正式 Migration。

---

# 23. Application 与 Migration 必须兼容

推荐 Deployment Design：

```text
Old Application
+
New Schema
```

短时间能够兼容，

然后再：

```text
New Application
```

上线。

---

# 24. Expand and Contract

Breaking Database Change 应尽量采用：

```text
Expand
↓
Migrate
↓
Switch
↓
Contract
```

例如：

```text
Add new column
↓
Support old + new
↓
Backfill
↓
Application switches to new
↓
Later remove old
```

---

# 25. 不得立即 Drop Column

如果新版本不再使用某 Column：

不能默认本次 Deployment 立即：

```text
DROP COLUMN
```

必须确认：

```text
Old Instance
Worker
Report
Integration
AI Service
```

都不再依赖。

---

# 26. Migration 失败必须停止

如果 Migration：

```text
FAILED
```

Application Deployment 默认不得继续。

不得让：

```text
New Application
+
Old / Partial Schema
```

强行运行。

---

# 27. Migration 不得自动清空数据

严禁 Deployment Script：

```text
DROP DATABASE
TRUNCATE
DELETE ALL
reset schema
```

解决 Migration 问题。

---

# 28. 大型 Migration 必须评估锁表

必须考虑：

```text
Table Size
Lock Duration
Write Traffic
Index Creation
Backfill
```

大型 Production Table 不得无分析直接修改。

---

# 29. Data Backfill 与 Schema Migration 可分离

如果 Backfill 很大：

可以采用：

```text
Schema Migration
↓
Deploy Compatible Application
↓
Background Backfill
↓
Verify
↓
Final Constraint
```

不得一个 Deployment Transaction 无限执行。

---

# 30. Backup 不能代替安全 Migration

Backup 是最后恢复能力。

不能：

```text
有 Backup
所以可以随便改 Production
```

---

# 31. Major Database Change 前必须考虑恢复方案

重大变更必须明确：

```text
How to detect failure?
How to stop?
How to recover?
```

---

# 32. Rollback 必须区分 Application 与 Database

Application Rollback：

可能容易。

Database Rollback：

不一定安全。

因此 Deployment Plan 应优先考虑：

```text
Forward-Compatible Database Changes
```

---

# 33. 禁止伪造 Rollback

如果 Migration 已经：

```text
Delete Data
Drop Column
Transform Irreversibly
```

不能声称：

> rollback supported

如果实际上无法恢复。

---

# 34. Release 必须有明确版本

推荐统一 Version Strategy。

例如：

```text
2.1.0
```

具体 SemVer 是否使用由项目正式标准决定。

禁止：

```text
final
final2
latest-fixed
new-new
```

作为正式版本标识。

---

# 35. Container 使用原则

如果项目采用 Container：

每个版本应生成不可变：

```text
Container Image
```

例如概念：

```text
aios-backend:<version>
aios-ai:<version>
```

不得只长期依赖：

```text
latest
```

无法知道实际运行版本。

---

# 36. `latest` 不得作为唯一 Production 标识

可以存在 `latest` Alias。

但必须同时存在不可变 Version / Digest。

---

# 37. Container 不得包含 Secret

Docker Image：

不得 Build 进：

```text
.env.production
API Key
Database Password
Private Key
```

Secret 必须在 Runtime 注入。

---

# 38. Container 运行权限

Container：

应尽量使用最小 Runtime Permission。

不得无必要：

```text
root
privileged
host filesystem
```

运行。

---

# 39. Health Check

每个核心 Service：

必须提供合理：

```text
Liveness
Readiness
```

检查能力。

---

# 40. Liveness

回答：

> Service Process 是否仍然正常运行？

不得因为第三方临时失败：

导致 Service 无限 Restart。

---

# 41. Readiness

回答：

> Service 当前是否准备好接受真实流量？

例如：

```text
Application initialized
Required dependency available
Critical configuration loaded
```

---

# 42. Health Endpoint 不得泄露 Secret

Health Check 不得返回：

```text
DB Password
Internal Credential
Private Key
Full Infrastructure Topology
```

---

# 43. Deployment 后必须验证 Health

部署成功不应只以：

```text
Process started
```

判断。

必须检查：

```text
Health
Readiness
Critical API
```

---

# 44. Smoke Test

Production Deployment 后至少应执行关键 Smoke Check。

例如：

```text
Frontend loads
Backend health passes
Login works
Core API works
Database connected
Critical navigation works
```

---

# 45. Smoke Test 不得修改真实业务数据

尽量使用：

```text
Read-only Check
Synthetic Test Account
Controlled Test Resource
```

不得上线后用真实 Customer 做测试。

---

# 46. Deployment Verification

正式 Deployment 必须确认：

```text
Correct Version
Correct Environment
Correct Configuration
Correct Migration
Healthy Instances
No Critical Error Spike
```

---

# 47. Deployment 不能只看 HTTP 200

还必须观察：

```text
Error Rate
Logs
Health
Database
Critical Dependency
```

---

# 48. Rollback Trigger

应明确什么情况需要 Rollback。

例如：

```text
Application cannot start
Critical API failing
Tenant isolation issue
Data corruption risk
Major permission regression
Payment failure spike
```

---

# 49. Security 问题优先停止 Deployment

如果发现：

```text
Cross-Tenant Leak
Authentication Bypass
Permission Bypass
Secret Exposure
```

必须优先：

```text
STOP / ROLLBACK / DISABLE
```

而不是继续观察。

---

# 50. Rollback 不能掩盖数据问题

如果新版本已经写入：

```text
New Data Format
Financial Transaction
Migration Data
```

只 Rollback Application：

可能不够。

必须评估数据兼容。

---

# 51. Blue-Green / Rolling Deployment

未来如基础设施支持：

可以使用：

```text
Rolling Deployment
Blue-Green Deployment
Canary Deployment
```

降低停机与风险。

但 Cursor 不得为了“高级”无需求直接引入。

---

# 52. 当前默认优先简单可靠

在系统规模未需要复杂 Deployment 时：

优先：

```text
Reliable Single / Multi Instance Deployment
+
Health Check
+
Safe Migration
+
Rollback
```

而不是直接 Kubernetes 化。

---

# 53. Zero Downtime 不是绝对要求

如果业务允许短 Maintenance Window：

可以采用安全维护。

原则：

> 数据安全与一致性优先于强行零停机。

---

# 54. Maintenance Mode

如果 Deployment 会导致暂时不可用：

应使用正式：

```text
Maintenance Mode
```

而不是让用户看到随机：

```text
500
502
Connection Refused
```

---

# 55. Maintenance Mode 不得开放写入

如果 Backend 尚未准备好：

Frontend 不得继续允许用户提交：

```text
Payment
Order
Payroll
```

然后失败。

---

# 56. Backward-Compatible API

Rolling Deployment 时：

必须特别注意：

```text
Old Frontend
New Backend
Old Backend
New Frontend
Python AI
```

可能短时间同时存在。

API Contract 应尽量兼容。

---

# 57. Frontend Deployment

React Frontend 属于 Static Build。

部署后必须注意：

```text
Asset Version
Browser Cache
CDN Cache
API Compatibility
```

---

# 58. Frontend Cache Busting

Build Asset 应使用：

```text
hashed filename
```

或现有 Vite Build Strategy，

防止新 HTML 引用错误旧 Bundle。

---

# 59. `index.html` 缓存必须谨慎

不能让 Browser 长期保留旧：

```text
index.html
```

导致引用已经被删除的 Asset。

具体 Cache Header 由 Infrastructure Standard 控制。

---

# 60. Frontend Deployment 不得包含 Secret

再次强调：

Browser 可以查看所有 Frontend Bundle。

因此 Frontend Build 中不存在真正 Secret。

---

# 61. Backend Deployment

Spring Boot Deployment 必须明确：

```text
Environment
JVM Config
Application Config
Database
Health
Logging
```

---

# 62. Backend Shutdown

正式 Deployment 应尽量支持：

```text
Graceful Shutdown
```

避免正在处理：

```text
Payment
Order
File Upload
```

的请求突然中断。

---

# 63. In-flight Request

Rolling Deployment 时：

旧 Instance 应停止接收新流量，

完成合理范围内现有 Request 后退出。

---

# 64. Background Job Deployment

部署 Worker / Scheduler 时：

必须考虑：

```text
Job currently running?
Will another instance duplicate it?
Can job resume?
```

---

# 65. Scheduler 多实例

Production 多实例部署：

不得每个 Spring Boot Instance：

都执行同一个 Scheduled Job，

造成重复操作。

必须使用：

```text
Distributed Lock
Single Scheduler
Queue
```

或正式架构解决。

---

# 66. AI Service Deployment

Python AI Service：

必须与 Spring Boot API Contract 兼容。

部署其中一方前：

必须检查：

```text
Tool Schema
API Version
Response Contract
Authentication
```

---

# 67. AI Model Provider 配置

Model / Provider Change：

应通过 Configuration / Agent Configuration。

不得每次换 Model：

修改大量业务代码。

---

# 68. Agent Deployment

正式 Agent 更新必须检查：

```text
Prompt Version
Agent Version
Toolset
Permission
Model
Autonomy Level
```

---

# 69. Agent Tool Change 属于高风险 Deployment

新增：

```text
Payment Tool
Refund Tool
Delete Tool
Permission Tool
```

必须进行额外：

```text
Security Test
Permission Test
Agent Test
```

---

# 70. Agent Prompt Change 也可能影响 Production

关键 Production Agent Prompt：

不得被视为普通文案修改。

Prompt Change 应：

```text
Version
Test
Publish
```

---

# 71. Agent Autonomy 不得在 Deployment 中偷偷提高

例如：

```text
L1 Suggest
→ L3 Execute
```

属于重大产品与安全变更。

不得作为普通 Release 修改。

---

# 72. Feature Flag

高风险新 Feature：

可以通过：

```text
Feature Flag
```

逐步开启。

但 Feature Flag 不能替代：

```text
Permission
Security
Testing
```

---

# 73. Feature 默认关闭策略

未完成 / 未验证 Feature：

Production 默认：

```text
OFF
```

不能因为 UI 没有链接：

就认为功能安全。

---

# 74. Tenant Feature Rollout

如支持 Tenant-level Feature Control：

可以：

```text
Internal Tenant
↓
Selected Tenant
↓
General Availability
```

逐步发布。

---

# 75. Canary Release

重大风险功能未来可以采用：

```text
Small Percentage
↓
Observe
↓
Increase
```

但必须有真实 Infrastructure 支持。

---

# 76. Configuration Change 也是 Deployment Change

即使没有改代码：

以下修改也可能导致 Production 风险：

```text
Permission Config
Feature Flag
Timeout
Connection Pool
AI Model
Rate Limit
```

必须受控。

---

# 77. Production Config 不得随意修改

不得：

```text
直接 SSH 改 config
↓
忘记记录
```

关键 Config 应版本化或通过正式 Configuration Management。

---

# 78. Environment Config 必须验证

Production 启动前：

关键配置缺失必须：

```text
Fail Fast
```

例如：

```text
Database URL missing
Security Secret missing
Required API Credential missing
```

不得自动使用不安全 Default。

---

# 79. Production Debug Mode 禁止

正式环境不得开启：

```text
Debug Stack Trace
Verbose SQL
Dev Tool
Mock Authentication
```

---

# 80. Logging

部署后必须确认日志：

```text
正常产生
有 Request ID
无 Secret
无大量异常
```

---

# 81. Monitoring

Production 应逐步监控：

```text
CPU
Memory
Disk
Application Health
Error Rate
Latency
Database
Queue
AI Provider
```

---

# 82. Deployment Event 必须可追踪

应能够知道：

```text
Who deployed
What version
When
Which environment
Result
```

---

# 83. Deployment Audit

Production Release：

建议进入：

```text
Deployment History
```

不得只有某个人记得：

> 昨天好像更新过。

---

# 84. Release Notes

重要 Release 应记录重点：

```text
Features
Bug Fixes
Database Changes
Breaking Changes
Known Issues
```

不需要写成长篇文章。

---

# 85. Breaking Change 必须明确标记

如果 Release 包含：

```text
API Breaking Change
Migration Risk
Permission Change
Authentication Change
```

必须明确记录。

---

# 86. Deployment Documentation

特殊 Deployment Step：

必须写入项目 Deployment Documentation。

不得只存在：

> 某位开发人员脑中。

---

# 87. Manual Step 必须最少

任何长期重复的部署人工步骤：

应逐步自动化。

例如：

```text
upload
restart
migrate
health check
```

---

# 88. Manual Step 如果存在必须可重复

必须写清楚：

```text
What
Order
Expected Result
Failure Handling
```

---

# 89. Secret Rotation Deployment

如果更换 Secret：

必须考虑：

```text
Old Credential
New Credential
Application Restart
Provider Compatibility
```

避免直接切换导致全部服务同时失败。

---

# 90. Key Rotation

Signing / Encryption Key Rotation：

必须根据 Security Architecture：

允许安全过渡。

不得直接删除仍在使用的旧 Key。

---

# 91. Third-Party Integration Deployment

Payment、OAuth、Webhook 等：

必须确认：

```text
Production Endpoint
Production Credential
Callback URL
Webhook Secret
Environment
```

不能把 Sandbox URL 带入 Production。

---

# 92. Sandbox 与 Production Provider 必须明显区分

例如：

```text
Payment Sandbox
Payment Production
```

Configuration 必须明确。

不得自动根据猜测选择。

---

# 93. Webhook Deployment

Webhook Endpoint 修改：

必须检查：

```text
Provider Configuration
Signature Validation
Backward Compatibility
Event Retry
```

---

# 94. Public API Deployment

修改 Public Developer API：

必须更加谨慎。

不能强迫外部客户：

与 AIOS 同一时间同步升级。

---

# 95. API Deprecation

旧 Public API 应：

```text
Deprecate
↓
Maintain Transition Period
↓
Remove in future version
```

不得突然删除。

---

# 96. Queue Consumer Deployment

如果未来引入 MQ：

新旧 Consumer 必须考虑：

```text
Event Schema Compatibility
Duplicate Message
Ordering
Retry
```

---

# 97. Event Schema 不能直接 Breaking

Producer 与 Consumer：

可能不同时间部署。

因此 Event Schema 必须保持兼容。

---

# 98. Cache Deployment

修改 Cache Key / Cache Structure：

必须考虑：

```text
Old Cache
New Code
Invalidation
Tenant Scope
```

---

# 99. Cache 不能阻止 Rollback

如果新版本写入完全不兼容 Cache：

Rollback 旧版本可能失败。

必须设计版本化 / 可失效 Cache。

---

# 100. Deployment 顺序

多 Service Change：

必须明确正确顺序。

例如：

```text
Database Expand Migration
↓
Spring Boot
↓
Python AI
↓
Frontend
↓

```

具体根据 Contract 决定。

# 101. 不得随意决定 Deployment 顺序

必须基于：

```text

Compatibility
Migration
API Contract
```

判断。

# 102. Frontend 不应先依赖尚未上线 Backend API

如果新 Frontend 需要新 Endpoint：

必须确保：


已经可用，

或 Feature 被正确 Gate。

---

# 103. Backend 不得立即移除 Frontend 仍使用字段

必须确认新版 Frontend 已经部署并稳定。

---

# 104. Python AI 同样属于正式 Client

Backend API Change：

必须检查 Python Agent / AI Service 是否仍兼容。

# 105. Deployment Failure

必须：

```text

Identify Failed Stage
Restore Service
Investigate Root Cause
```

不得在 Production 上连续随机改动尝试。

优先：

```text

```

作为 Production 修复。

# 108. 不能通过删数据修 Deployment

不得直接删除问题数据：

# 150. Deployment 最终原则

AIOS Deployment 必须坚持：

> Production 不是开发环境。

> 所有正式 Deployment 必须可追踪到明确版本。

> Source Code、Build Artifact、Production Version 必须对应。

> Production 不允许直接手工修改源码。

> Hotfix 也必须进入 Version Control。

> Environment 必须隔离。

> Production Secret 不能进入 Frontend。

> Production Secret 不能 Hardcode。

> Production Database Schema 必须通过 Migration 管理。

> Migration 必须先验证，再进入 Production。

> Application 与 Database Change 必须考虑 Backward Compatibility。

> Rollback 不等于数据库一定可以恢复。

> 高风险变化必须先考虑 Data Recovery。

> Deployment 成功不能只看 Process 是否启动。

> Health Check、Smoke Test、Logs、Monitoring 都属于 Deployment 的一部分。

> 多实例环境必须防止 Scheduler / Worker 重复执行。

> Agent、Prompt、Tool 与 Permission 变化也属于正式 Deployment Change。

> Cursor 不得因为部署失败而关闭 Security。

> Cursor 不得因为赶上线而牺牲 Tenant Isolation 或 Data Integrity。

> 当前阶段优先简单、稳定、可恢复的 Deployment，不提前过度工程化。

> AIOS 的 Deployment 标准不是追求“最快上线”，而是追求“每一次上线都可预测、可验证、可恢复”。
