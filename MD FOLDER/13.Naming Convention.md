# AIOS Naming Convention

> 文件编号：13
> 文件名称：Naming Convention
> 适用范围：AIOS 全项目
> 适用对象：Cursor、AI Agent、Frontend Developer、Backend Developer、AI Developer、Database Developer
> 前置规则：必须遵守《01 产品原则》至《12 Deployment Standard》
> 核心目标：统一、清晰、可预测、可搜索、避免歧义

---

# 1. 核心原则

所有 Naming 必须做到：

```text
Clear
Consistent
Predictable
Searchable
Domain-Oriented
```

名称必须回答：

> 这是什么？

或：

> 这做什么？

禁止模糊名称：

```text
data
info
temp
obj
thing
stuff
abc
xxx
test1
newData
finalData
```

---

# 2. Naming 优先使用业务语言

优先：

```text
Customer
SalesOrder
PurchaseOrder
Invoice
StockTransfer
Employee
```

禁止为了技术方便使用：

```text
DataObject
BusinessItem
RecordManager
GenericEntity
```

---

# 3. 同一个业务概念必须使用同一个名称

例如系统决定使用：

```text
Customer
```

则不得其他模块自行称为：

```text
Client
Buyer
CustomerUser
```

如果实际指同一 Business Entity。

---

# 4. 不得随意使用缩写

禁止不明确：

```text
cust
usr
empInfo
ord
txn
cfg
mgr
```

除非属于项目正式认可的通用缩写。

可接受常见技术缩写：

```text
API
DTO
URL
HTTP
UUID
JWT
SQL
AI
CRM
POS
HRM
```

Agent 名称必须表达：

```text
Domain + Purpose
```

例如：

```text
SalesCopilot
FinanceAnalysisAgent
InventoryMonitoringAgent
HRRecruitmentAssistant
```

禁止：

```text
SuperAgent
SmartAgent
AI1
Bot2

```

# 35. Agent ID / Code

如果需要稳定 Agent Code：

推荐：

```text
sales_copilot

inventory_monitoring_agent
```

Display Name 可以：

```text
Sales Copilot
Finance Analysis Agent
```

---

# 36. Tool Naming

AI Tool 使用：

```text
snake_case
```

并以明确 Action 开头。

例如：

```text
search_customer
create_customer
create_sales_order
refund_payment
approve_purchase_order
```

禁止：

```text
tool1
execute
do_task
business_action
```

---

# 37. Tool 必须与 Backend Action 对齐

例如：

```text
refund_payment
```

应对应正式 Payment Refund Use Case。

不得：

```text
update_payment
```

偷偷实现 Refund。

# 38. Prompt Naming

Prompt 使用明确：

```text
{agent}_{purpose}
```

例如：

```text

invoice_analysis

```

如支持 Version：

```text
sales_copilot_system:v2
```

版本由 Prompt System 管理。

# 40. Database Column

统一：

```text
snake_case
```

例如：


# 41. Primary Key

统一：


禁止：


除非特殊数据库模型明确要求。


例如：

```text

```

# 43. Actor Field


根据真实语义。

# 44. Timestamp Field

统一：

```text
created_at
updated_at
approved_at
deleted_at
submitted_at
completed_at
```

使用：

```text
{action}_at
```

---

# 45. Date Field

纯日期使用：

```text
invoice_date
birth_date
start_date
end_date
```

不要：

```text
invoice_datetime
```

如果实际只保存 Date。

---

# 46. Boolean Database Field

使用：

```text
is_
has_
```

例如：

```text
is_active
is_default
has_access
```

---

# 47. Status Field

默认：

```text
status
```

如一张表存在多个不同 Status：

必须明确：

```text
payment_status
fulfillment_status
approval_status
```

---

# 48. Money Field

金额必须使用：

```text
{meaning}_amount
```

例如：

```text
subtotal_amount
tax_amount
discount_amount
total_amount
paid_amount
```

避免只有：

```text
total
value
money
```

---

# 49. Rate Field

使用：

```text
{meaning}_rate
```

例如：

```text
exchange_rate
tax_rate
commission_rate
discount_rate
```

---

# 50. Percentage Field

名称必须清楚表达：

```text
discount_percentage
commission_percentage
```

如果系统选择统一使用 `rate`：

必须整个项目一致。

不得混用而含义不同。

---

# 51. Business Number

使用：

```text
{resource}_number
```

例如：

```text
invoice_number
sales_order_number
purchase_order_number
```

不得使用：

```text
invoice_id
```

表示业务号码。

---

# 52. Code Field

业务 Code：

```text
customer_code
employee_code
currency_code
country_code
```

`code` 与 `id` 必须区分。

---

# 53. Name / Title

Entity 正式名称：

使用：

```text
name
```

如果存在不同类型：

```text
legal_name
display_name
short_name
```

必须明确。

---

# 54. Description / Note

正式描述：

```text
description
```

备注：

```text
notes
```

原因：

```text
reason
```

不得全部使用：

```text
remarks
info
text
```

混乱表达。

---

# 55. Database Index

建议：

```text
idx_{table}_{columns}
```

例如：

```text
idx_sales_orders_tenant_id

```

遵循项目 Migration Tool 最终实现。

---

# 56. Unique Constraint

建议：

```text
uk_{table}_{columns}
```

例如：

```text
uk_customers_tenant_code
```

---

# 57. Foreign Key Constraint

建议：

```text
fk_{table}_{referenced_table}
```

必要时加入 Column。

# 58. Check Constraint

建议：

```text
ck_{table}_{rule}
```

例如：

```text
ck_order_items_quantity_positive
```

# 64. Event Naming

Domain Event 使用：

```text
Past Tense
```

表示：

> 已经发生。

例如：

```text
CustomerCreated
SalesOrderSubmitted
PaymentCompleted
InvoiceVoided
```

---

# 65. Event 不使用模糊名称

禁止：

```text
CustomerEvent
OrderEvent
DataChanged
SomethingUpdated
```

必须知道具体发生什么。

---

# 66. Event Topic / Routing Key

如果未来使用消息系统：

推荐机器标识：

```text
sales.order.submitted
payment.completed
customer.created
```

具体格式一旦确定必须统一。

# 67. Command Naming

Command 表达：

> 请求执行某动作。

例如：

```text
CreateCustomer

ApprovePurchaseOrder

```

---

# 68. Query Naming

Query 表达：

> 获取信息。

例如：

```text
GetCustomer
```

不要：

```text

```

---

# 69. Permission Code

统一：

```text
{module}.{resource}.{action}
```

全部小写。

例如：

```text
crm.customer.read
crm.customer.create
sales.order.approve
finance.payment.refund
```

---

# 70. Permission 不使用 Role Name

禁止：

```text
admin.customer
manager.sales
```

Permission 表达能力，

Role 是 Permission Collection。

---

# 71. Feature Flag

Feature Code 使用：

```text
snake_case
```

例如：

```text

advanced_reporting
multi_company
```

如果项目未来采用其他格式：

必须统一全系统。

```text
UPPER_SNAKE_CASE
```

# 82. Git Branch

# 83. Commit Message

Commit 应表达：

> 做了什么。

例如：

```text
feat: add customer import validation
fix: prevent duplicate payment processing
```

不得：

```text
update
fix stuff
changes
final
```

---

# 84. 不使用 New / Old / Final 作为正式名称

禁止长期存在：

```text
NewCustomerService
OldCustomerService
FinalCustomerService
CustomerServiceV2New
```

版本应通过：

```text
Git
API Version
Migration
```

管理。

---

# 85. V2 使用规则

只有真正：

```text
Versioned Contract
```

才允许：

```text
v2
```

例如：

```text
/api/v2
```

普通重构不得：

```text
CustomerServiceV2
```

逃避修改旧代码。

---

# 86. Manager 使用规则

`Manager` 仅当对象确实：

> 管理多个对象、生命周期或协调资源

才使用。

例如：

```text
AgentManager
ConnectionManager
```

不要：

```text
CustomerManager
OrderManager
```

代替明确 Service。

---

# 87. Handler 使用规则

`Handler` 应用于：

```text
Event Handler
Exception Handler
Protocol Handler
```

不要所有 Class 都叫 Handler。

---

# 88. Processor 使用规则

`Processor` 只有当职责确实是：

> 对一类输入执行处理流程

才使用。

名称仍必须说明：

```text
DocumentProcessor
PaymentWebhookProcessor
```

禁止：

```text
DataProcessor
GenericProcessor
```

---

# 89. Helper / Utils 使用规则

禁止创建巨大：

```text
Helper
CommonHelper
Utils
CommonUtils
```

优先具体：

```text
CurrencyFormatter
DateTimeUtils
PaginationMapper
```

---

# 90. Common 使用规则

`common`、`shared`：

只能用于真正跨 Domain 的能力。

禁止因为不知道放哪里：

就放：

```text
common
```

---

# 91. Base 使用规则

禁止无意义：

```text
BaseService
BaseManager
BaseProcessor
```

只有存在真实、稳定的共同抽象：

才使用 `Base`。

---

# 92. Generic 使用规则

禁止：

```text
GenericService
GenericRepository
GenericHandler
```

掩盖真实业务边界。

---

# 93. Temp 使用规则

正式 Production Code：

不得长期存在：

```text
tempCustomer
temporaryService
tempTable
```

如果确为临时流程：

必须明确生命周期与清理计划。

---

# 94. Flag 使用规则

避免：

```text
statusFlag
activeFlag
deleteFlag
```

如果本质是 Boolean：

使用：

```text
isActive
```

如果本质是 Status：

使用：

```text
status
```

---

# 95. Data 使用规则

不要无意义：

```text
customerData
orderData
userData
```

如果变量本身已经是 Customer：

直接：

```text
customer
order
user
```

---

# 96. Info 使用规则

避免：

```text
customerInfo
paymentInfo
```

如果实际是：

```text
Customer
Payment
```

直接使用 Domain Name。

`Info` 只有确实代表摘要型信息时使用。

---

# 97. Detail 使用规则

`Detail` 必须有明确意义。

例如：

```text
CustomerDetailResponse
```

代表详细 View Model。

不要数据库表随意：

```text
customer_details
```

如果实际只是 Customer Entity。

---

# 98. Item 使用规则

`Item` 用于真实 Line Item / List Item。

例如：

```text
SalesOrderItem
InvoiceItem
```

不要所有 Entity 都叫 Item。

---

# 99. Record 使用规则

除 Audit / Generic Technical Record 等真实概念外：

避免使用：

```text
CustomerRecord
OrderRecord
```

替代 Domain Entity。

---

# 100. Entity 名称不得带 Table

禁止：

```text
CustomerTable
InvoiceTableEntity
```

业务对象名称：

```text
Customer
Invoice
```

数据库 Table 才是：

```text
customers
invoices
```

---

# 101. DTO 不得成为业务名称

Domain Service 不应充斥：

```text
CustomerDTO
```

作为核心业务模型。

DTO 只用于边界传输。

---

# 102. Service 方法不能叫 saveEverything

禁止：

```text
saveData
processData
handleEverything
doWork
execute
```

必须表达具体动作。

---

# 103. State Naming

业务状态必须使用同一 Canonical Term。

如果定义：

```text
CANCELLED
```

则不得其他 Module 对同一概念使用：

```text
CANCELED
CANCEL
VOID
```

除非业务意义真的不同。

---

# 104. Cancel 与 Void 不得混用

通常：

```text
Cancel
```

表示流程未完成前取消。

```text
Void
```

表示正式记录作废。

具体业务定义后：

全系统必须一致。

---

# 105. Delete 与 Archive 不得混用

```text
Delete
Archive
Deactivate
Disable
Void
Cancel
```

具有不同业务意义。

Cursor 不得因为结果看起来类似：

随意替换名称。

---

# 106. User 与 Employee 不得混用

```text
User
```

代表系统 Identity。

```text
Employee
```

代表 HRM Employee。

不得：

```text
employeeUser
staffUser
```

无必要混淆。

---

# 107. Tenant 与 Company 不得混用

```text
Tenant
```

代表 SaaS / Platform Customer Boundary。

```text
Company
```

代表 Tenant 内业务公司。

禁止：

```text
tenantCompany
companyTenant
```

表达同一概念。

---

# 108. Customer 与 User 不得混用

CRM Customer：

不等于系统 User。

名称必须保持边界。

---

# 109. Product / SKU

如果 Product 与 SKU 是不同概念：

必须明确：

```text
Product
SKU
```

不得所有库存对象都叫：

```text
Product
```

---

# 110. Order 类型必须明确

AIOS 存在：

```text
SalesOrder
PurchaseOrder
OnlineOrder
POSOrder
```

不得所有地方简称：

```text
Order
```

导致 Domain 混淆。

局部上下文非常明确时除外。

---

# 111. Invoice 类型必须明确

如果未来存在：

```text
Sales Invoice
Supplier Invoice
Platform Billing Invoice
```

必须通过 Domain / Context 清楚区分。

不得因为都叫 Invoice：

错误共享 Domain Model。

---

# 112. Account 名称必须避免歧义

`Account` 可能表示：

```text
User Account
Bank Account
Ledger Account
Customer Account
```

必须根据 Domain 使用：

```text
UserAccount
BankAccount
LedgerAccount
```

避免单独 `Account` 造成歧义。

---

# 113. Transaction 名称必须避免滥用

`Transaction` 非常宽泛。

优先：

```text
PaymentTransaction
StockMovement
JournalEntry
BankTransaction
```

而不是全部叫：

```text
Transaction
```

---

# 114. ID 命名

代码中禁止：

```text
id1
id2
otherId
targetId
```

如果可以明确：

```text
customerId
companyId
invoiceId
targetUserId
```

# 115. Source / Target

涉及 Transfer：

推荐：

```text
sourceWarehouseId

```

优于：

```text
fromId
toId
```

如果 `from/to` 容易产生歧义。

---

# 116. Before / After

Audit / Comparison：

使用：

```text

previousValue

```

根据 Context 保持统一。

# 117. Current / Previous

如果涉及 Version / Status：

```text
currentStatus

```

不要：

```text

```

# 118. Request Context

统一使用清楚：

```text

```

不要：

```text

```

# 120. Cursor 不得自行 Rename 业务概念


# 123. Naming 不得改变业务意义

例如：


* 擅自创建 `NewService`

* 擅自创建 `CommonUtils`

* 擅自使用 `id1` / `id2`
* 擅自混用 camelCase / snake_case

* 擅自让 Permission 使用不同格式
* 擅自让 Agent Tool 使用不同格式

* 擅自随意缩写业务词
* 擅自把 User / Employee 混为一谈

* 擅自把 Cancel / Void 混为一谈
* 擅自把 Delete / Archive 混为一谈

# 127. Naming 最终原则

AIOS Naming 必须坚持：

> 一个 Business Concept，只使用一个 Canonical Name。

> 名称必须表达业务，而不是表达技术便利。

> Frontend、Backend、Python、Database、API 各自遵循统一 Case Convention。

> Database 使用 snake_case。

> API JSON 使用 camelCase。

> REST Resource 使用 kebab-case + plural。

> Permission 使用 `{module}.{resource}.{action}`。

> Agent Tool 使用清晰的 snake_case Action Name。

> Domain Event 使用已经发生的 Past Tense。

> Role Name 不能代替 Permission。

> User、Employee、Customer、Tenant、Company 等核心概念绝不能混淆。

> Delete、Archive、Cancel、Void 等具有不同业务语义，不能互换。

> 不创建 New、Old、Final、V2 来逃避正确重构。

> 不创建 Common、Generic、Helper 来隐藏不清楚的职责。

> Cursor 创建新名称前必须先搜索现有项目。

> Cursor 不得为了个人偏好随意 Rename Existing Business Concept。

> 最好的 Naming，是开发人员和 AI Agent 看到名称后，不需要猜它代表什么。
