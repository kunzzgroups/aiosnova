# AIOS Security Standard

> 文件编号：07
> 文件名称：Security Standard
> 适用范围：AIOS 全系统
> 适用对象：Cursor、AI Agent、Frontend Developer、Backend Developer、AI Developer、Database Developer、DevOps、Integration Developer
> 前置规则：必须遵守《01 产品原则》《02 系统架构标准》《03 开发与编码标准》《05 数据库设计标准》《06 API Standard》
> Frontend：React + Vite + TypeScript
> Backend：Spring Boot
> AI Layer：Python
> Database：PostgreSQL
> 核心目标：Zero Trust、Least Privilege、Tenant Isolation、Defense in Depth、Secure by Default、Auditability

---

# 1. 文件目的

本文件定义 AIOS 全系统 Security Standard。

AIOS Security 不是独立模块。

Security 必须存在于：

```text
Frontend
Backend
API
Database
AI
File
Workflow
Integration
Cloud
Admin
Super Admin
```

每一个层级。

Cursor 在开发任何功能时：

不得先完成业务功能，

然后以后再补 Security。

正确原则：

> Security by Design。

---

# 2. Security 最高原则

AIOS 必须遵守：

```text
Zero Trust
Least Privilege
Defense in Depth
Secure by Default
Fail Secure
Explicit Authorization
Tenant Isolation
Data Minimization
Auditability
Secret Protection
```

---

# 3. Security 决策优先级

发生冲突时：

```text
1. Prevent Unauthorized Access
2. Tenant Isolation
3. Protect Sensitive Data
4. Data Integrity
5. Authentication
6. Authorization
7. Auditability
8. Availability
9. User Experience
10. Development Convenience
```

开发方便永远不能高于 Security。

---

# 4. Cursor Security 基本原则

Cursor 开发任何功能前必须判断：

* 谁可以访问？
* 谁不能访问？
* 属于哪个 Tenant？
* 属于哪个 Company？
* 需要什么 Permission？
* 数据是否敏感？
* 是否可以被 AI 使用？
* 是否需要 Audit？
* 是否存在高风险操作？
* 是否存在越权风险？
* 是否涉及 Secret？
* 是否来自不可信输入？

---

# 5. 默认拒绝原则

当 Permission 不明确时：

默认：

```text
DENY
```

而不是：

```text
ALLOW
```

原则：

> Explicit Allow > Implicit Allow。

---

# 6. Zero Trust

AIOS 不得默认信任：

```text
Frontend
Internal Network
Backend Service
AI Agent
Third Party
Webhook
Admin User
Device
File
User Input
```

任何请求必须根据身份、权限、Scope 和 Context 判断。

---

# 7. Internal 不等于 Trusted

禁止：

> 因为请求来自内部服务器，所以无需认证。

Internal API 同样需要：

```text
Authentication
Authorization
Service Identity
Scope
Audit
```

---

# 8. Security Boundary

AIOS 至少存在以下 Security Boundary：

```text
Public
Authenticated User
Tenant
Company
Department
Resource
Admin
Super Admin
AI Agent
Integration
Developer API
```

任何跨 Boundary 行为都必须重新验证。

---

# 9. Authentication 与 Authorization 必须分离

Authentication：

> 你是谁？

Authorization：

> 你可以做什么？

不能因为用户已经 Login：

就允许访问所有业务数据。

---

# 10. Authentication 统一管理

AIOS 所有业务模块：

必须使用统一 Authentication System。

禁止：

```text
CRM Login
Finance Login
HRM Login
POS Login
```

分别建立认证系统。

---

# 11. 禁止自定义简易 Authentication

Cursor 不得自行实现：

```text
username + password
→ 查数据库
→ 返回 userId
```

作为完整认证系统。

Authentication 必须通过正式 Security Architecture。

---

# 12. Password 永远不能明文保存

禁止数据库存在：

```text
password
plain_password
password_text
```

明文内容。

只允许保存安全 Password Hash。

---

# 13. Password Hash

密码必须使用行业认可的 Password Hash 算法。

不得使用：

```text
MD5
SHA-1
SHA-256(password)
Base64
Encryption only
```

作为密码存储方案。

---

# 14. Salt

密码 Hash 必须使用：

> 安全的独立 Salt。

不得所有 User 共享固定 Salt。

---

# 15. Password Logging 禁止

禁止：

```text
console.log(password)
logger.info(password)
audit(password)
```

任何形式记录 Password。

---

# 16. Password API Response 禁止

任何 API Response：

不得返回：

```text
password
passwordHash
salt
```

---

# 17. Password Reset

Password Reset 必须使用：

```text
Short-Lived
Single-Use
Unpredictable Token
```

不得：

```text
通过 User ID 就能 Reset
```

---

# 18. Password Reset Token

Reset Token 必须：

* 有 Expiry
* 单次使用
* 成功 Reset 后失效
* 不允许长期有效
* 不记录完整 Token

---

# 19. Password Change

已登入用户修改 Password：

应要求验证：

```text
Current Password
```

或通过足够强的再认证机制。

高风险账户应考虑 MFA / Re-authentication。

---

# 20. Credential Stuffing 防护

Login Endpoint 应考虑：

```text
Rate Limiting
Failed Attempt Monitoring
Risk Detection
MFA
```

不得允许无限高速尝试 Password。

---

# 21. Login Error

Login Error 不应泄露：

```text
Email exists
Password wrong
User exists but disabled
```

等过多信息。

应避免帮助攻击者枚举账户。

---

# 22. Account Enumeration

Password Reset / Login 等 Public Endpoint：

不得轻易暴露：

> 某 Email 是否存在。

具体 UX 与 Security 必须平衡。

---

# 23. MFA

高风险账户必须支持 MFA。

尤其：

```text
Super Admin
Tenant Admin
Finance Admin
Security Admin
```

---

# 24. MFA 不能只由 Frontend 控制

即使 UI 显示 MFA：

真正 Enforcement 必须由 Backend Authentication Flow 控制。

---

# 25. MFA Recovery

Recovery Code / Recovery Method：

必须：

```text
Secure
Single-Use Where Applicable
Audited
```

不得明文长期展示。

---

# 26. Session Security

Session 必须：

* 可过期
* 可失效
* 可撤销
* 与用户状态关联

Disabled User：

不得继续无限使用旧 Session。

---

# 27. Session Expiration

应区分：

```text
Idle Timeout
Absolute Lifetime
```

具体时间由 Security Policy 决定。

Cursor 不得擅自设置永久 Session。

---

# 28. Access Token

Access Token 应：

```text
Short-Lived
Scoped
Protected
```

不得设计为永久有效 Token。

---

# 29. Refresh Token

Refresh Token 必须：

```text
Longer-Lived
Revocable
Protected
```

如支持 Rotation：

必须防止 Token Replay。

---

# 30. Token 不得放 URL

禁止：

```text
?token=xxxxx
```

作为正常 Authentication。

因为 URL 容易进入：

```text
Browser History
Logs
Analytics
Referrer
```

---

# 31. Token 不得进入 Log

禁止记录完整：

```text
Authorization
Access Token
Refresh Token
Reset Token
OTP
```

---

# 32. Token Storage

Frontend Token Storage 必须根据 Authentication Architecture 统一设计。

Cursor 不得为了方便自行：

```text
localStorage
sessionStorage
cookie
```

随意切换。

---

# 33. Cookie Security

如果使用 Cookie：

必须根据 Architecture 配置：

```text
HttpOnly
Secure
SameSite
```

不得 Production 使用不安全 Cookie。

---

# 34. CSRF

如果系统 Authentication 依赖 Cookie：

必须考虑 CSRF 防护。

Cursor 禁止：

> 因为 CSRF 配置麻烦，所以关闭。

---

# 35. Authentication 状态变化

以下事件发生后：

应根据 Security Policy 撤销相关 Session：

```text
Password Changed
Password Reset
Account Disabled
Security Breach
Role Critical Change
```

---

# 36. SSO

SSO 必须通过统一 Authentication Architecture。

禁止每个 Tenant 自行写一个：

```text
SSO Hack
```

直接绕过用户认证。

---

# 37. OAuth / OIDC

OAuth / OIDC：

必须正确验证：

```text
issuer
audience
state
nonce
redirect URI
token signature
expiry
```

不得只收到 Token 就信任。

---

# 38. SSO Account Linking

外部 Identity 与 AIOS User 关联：

必须防止：

```text
Email Collision
Account Takeover
Incorrect Linking
```

不能只因为 Email 一样：

自动无限制合并账户。

---

# 39. RBAC

AIOS 必须拥有统一：

```text
RBAC
Role-Based Access Control
```

Role：

代表权限集合。

---

# 40. ABAC

对于复杂企业 Scope：

可结合：

```text
ABAC
Attribute-Based Access Control
```

例如：

```text
Department
Company
Resource Owner
Location
Business Unit
```

---

# 41. Permission 不得 Hardcode

禁止：

```java
if (user.getRole().equals("ADMIN"))
```

散落业务代码。

必须通过统一 Permission Service / Security Policy。

---

# 42. Role Name 不等于 Permission

`ADMIN`：

不是万能安全规则。

不同 Tenant 的 Admin：

权限可能不同。

必须最终基于：

```text
Permission
Scope
```

判断。

---

# 43. Permission 命名

Permission 应采用清晰稳定规则。

例如：

```text
crm.customer.read
crm.customer.create
crm.customer.update
crm.customer.delete

sales.order.read
sales.order.create
sales.order.approve
```

具体命名方式全系统统一。

---

# 44. Permission 应表达 Action

不要只定义：

```text
CRM_ACCESS
FINANCE_ACCESS
```

然后所有操作都允许。

至少区分：

```text
Read
Create
Update
Delete
Approve
Export
Manage
```

等实际 Action。

---

# 45. Permission Scope

Permission 必须考虑：

```text
Tenant
Company
Department
Own
Assigned
All
```

不能只判断：

> 有这个 Permission。

---

# 46. Resource Ownership

API：

```text
GET /employees/{id}
```

必须验证：

```text
User Permission
+
Tenant
+
Company
+
Resource Scope
```

而不是只查 ID。

---

# 47. IDOR 防护

任何基于 Resource ID 的 API：

必须防止：

> 用户修改 URL 中 ID 后访问其他人的资料。

这是 AIOS 必须重点防止的越权风险。

---

# 48. Tenant Isolation

Tenant Isolation 属于 AIOS 最重要的 Security Requirement。

Tenant A：

绝对不能：

```text
Read
Update
Delete
Export
Search
Analyze
AI Retrieve
```

Tenant B 数据。

---

# 49. Tenant Scope 必须存在于数据查询

禁止：

```java
repository.findById(id)
```

然后直接返回 Tenant Data。

必须通过安全 Query / Validation：

确认 Resource 属于 Current Tenant。

---

# 50. Tenant Context 来源

Tenant Context 必须由：

```text
Authenticated Identity
+
Authorized Membership
```

确定。

Header / Query / Body 中的 Tenant ID：

只代表请求 Context。

不是 Security Proof。

---

# 51. Tenant ID 不可信

以下：

```text
X-Tenant-ID
tenantId
currentTenantId
```

来自 Client 的值：

Backend 必须再次验证。

---

# 52. Company Isolation

同一个 Tenant 可能存在多个 Company。

如果 User 只允许访问 Company A：

不能因为属于同一个 Tenant：

就读取 Company B 数据。

---

# 53. Company ID 同样不可信

Frontend 提交：

```text
companyId
```

Backend 必须验证：

```text
Company belongs to Tenant
User has access to Company
```

---

# 54. Super Admin Boundary

Super Admin：

属于平台级高权限身份。

不得直接复用普通 Tenant Admin 逻辑。

---

# 55. Tenant Admin 不能成为 Super Admin

禁止通过：

```text
role = SUPER_ADMIN
```

字段修改：

让 Tenant Admin 提升自己成为 Platform Super Admin。

---

# 56. Privilege Escalation 防护

Role / Permission API：

必须防止：

```text
User grants themselves higher privilege
User grants permission they do not own
Tenant Admin grants platform permission
```

---

# 57. Permission Delegation

用户只能授予：

> 自己被允许管理的 Permission Scope。

不能因为拥有：

```text
role.update
```

就能够给予任意系统权限。

---

# 58. Super Admin 高风险操作

以下操作必须强化：

```text
Audit
Re-authentication
MFA
Reason
Confirmation
```

例如：

```text
Disable Tenant
Access Tenant Data
Change Subscription
Security Override
Role Escalation
```

---

# 59. Impersonation

如果未来 Super Admin 支持：

```text
Login as User
Impersonate Tenant
```

必须：

* 明确 UI 标识
* 有时限
* 完整 Audit
* 不得隐藏真实 Actor
* 可退出
* 高风险操作可额外限制

---

# 60. Audit 不能只显示被模拟用户

Impersonation 操作 Audit 必须记录：

```text
Real Actor
Impersonated User
Tenant
Action
```

---

# 61. Least Privilege

所有：

```text
User
Service
Database Account
AI Agent
Integration
API Key
```

必须遵守最小权限原则。

---

# 62. Service Account

Service Account：

必须：

* 有明确 Owner
* 有明确 Purpose
* 有有限 Permission
* 可撤销
* 可轮换 Credential

不得所有 Service 共用一个超级账户。

---

# 63. Database Least Privilege

Spring Boot Runtime Database User：

不应拥有：

```text
DROP DATABASE
CREATE SUPERUSER
```

等权限。

---

# 64. Migration 与 Runtime DB User

推荐分离：

```text
Migration User
Runtime User
```

Runtime User 只拥有正常运行所需权限。

---

# 65. Secret 管理

以下属于 Secret：

```text
Database Password
API Key
JWT Secret
OAuth Secret
Private Key
Encryption Key
Payment Credential
Webhook Secret
AI Provider Key
```

不得写入源码。

---

# 66. Secret 禁止 Hardcode

严禁：

```java
String apiKey = "sk-...";
```

或：

```python
API_KEY = "..."
```

---

# 67. Secret 不得进入 Frontend

任何 Secret：

不得通过：

```text
VITE_*
```

进入前端 Bundle。

所有 Frontend Environment Variable：

原则上视为公开数据。

---

# 68. Secret Manager

Production Secret：

应由：

```text
Environment Secret
Cloud Secret Manager
Secure Vault
```

等机制提供。

不得放入普通 Config File 并提交 Git。

---

# 69. Secret Rotation

关键 Secret 应支持：

```text
Rotation
Revocation
Replacement
```

不得设计成：

> 一旦创建永久不能换。

---

# 70. Secret 日志

禁止将 Secret：

记录到：

```text
Logs
Audit
Error Message
Monitoring
```

---

# 71. `.env` 文件

包含真实 Secret 的：

```text
.env
.env.production
```

不得提交 Git。

应正确加入 `.gitignore`。

---

# 72. Example Environment File

允许：

```text
.env.example
```

但必须只包含：

```text
Placeholder
Variable Name
Example Non-Secret Value
```

不得包含真实 Credential。

---

# 73. Encryption in Transit

Production 所有：

```text
Browser ↔ Server
Service ↔ Service
Integration
```

敏感通信必须通过 TLS。

不得通过普通 HTTP 传输 Credential 或敏感数据。

---

# 74. TLS Validation

调用 Third-Party API：

不得关闭：

```text
Certificate Validation
Hostname Verification
```

只为了方便开发。

---

# 75. Encryption at Rest

高度敏感数据：

应根据 Security Classification 决定：

```text
Database Encryption
Disk Encryption
Application-Level Encryption
```

---

# 76. Password 不使用 Encryption

Password：

使用 Hash。

不是可逆 Encryption。

---

# 77. Encryption Key 与数据分离

Encryption Key：

不得与加密数据存放在同一个普通 Table / Config 中。

否则加密意义显著降低。

---

# 78. Key Rotation

Encryption Key 应支持：

```text
Version
Rotation
Migration
```

但 Cursor 不得无需求擅自创建复杂 Key System。

---

# 79. Sensitive Data 分类

AIOS 应将数据概念上区分：

```text
Public
Internal
Confidential
Sensitive
Highly Sensitive
Secret
```

---

# 80. Highly Sensitive Data

包括但不限于：

```text
Password Credential
Bank Information
Salary
Identity Document
Private Key
Payment Credential
Security Configuration
```

必须施加更严格访问控制。

---

# 81. Data Minimization

数据库与 API：

只处理业务真正需要的数据。

禁止因为：

> 以后可能用到

就大量收集敏感数据。

---

# 82. Sensitive API Response

API 应只返回完成当前 Use Case 必要字段。

禁止普通 Employee List：

返回：

```text
Bank Account
Salary
Identity Document
```

---

# 83. Sensitive UI

Frontend 显示敏感数据：

应根据业务考虑：

```text
Mask
Reveal
Copy Restriction
Audit
Permission
```

---

# 84. Sensitive Export

Export：

必须拥有独立 Permission。

能在 UI 查看少量数据：

不代表可以：

```text
Export all
```

---

# 85. Bulk Export 属于高风险操作

导出：

```text
Customer Data
Employee Data
Finance
Payroll
Audit
```

必须考虑：

```text
Permission
Tenant Scope
Audit
Rate Limit
```

---

# 86. Input 永远不可信

以下都属于不可信 Input：

```text
Frontend
API
URL
Header
Cookie
File
Webhook
AI Output
Third Party
CSV
Excel
Document
```

---

# 87. Backend Validation

所有外部 Input：

必须 Backend Validate。

Frontend Validation：

只能提升 UX。

---

# 88. SQL Injection

严禁：

```text
String SQL + userInput
```

必须使用：

```text
Prepared Statement
Parameter Binding
Safe ORM Query
```

---

# 89. Dynamic Sort Injection

用户提供：

```text
sort
```

不得直接拼 SQL。

必须通过：

```text
Whitelist
Mapping
```

---

# 90. Dynamic Filter Injection

禁止构造：

```text
field
operator
value
```

后直接生成任意 SQL，

除非使用经过安全设计的 Query Engine。

---

# 91. Command Injection

Python / Java：

不得把用户输入直接拼接到：

```text
Shell Command
OS Command
```

---

# 92. Shell Execution

Business Application：

默认不应执行用户可控制的 Shell Command。

如果确有系统任务：

必须严格：

```text
Whitelist
Arguments Separation
Permission
Environment Restriction
```

---

# 93. Path Traversal

File Download / Upload：

必须防止：

```text
../../etc/passwd
```

等路径逃逸。

用户 File Name：

不能直接决定 Server Path。

---

# 94. File Name

上传文件原名：

只能作为 Metadata。

实际 Storage Key：

必须安全生成。

---

# 95. XSS

React 默认 Escape：

不得轻易绕过。

特别谨慎：

```text
dangerouslySetInnerHTML
```

---

# 96. HTML Content

如果业务允许用户提交 HTML：

必须经过明确：

```text
Sanitization
Allowed Tag Policy
```

不能直接渲染。

---

# 97. Rich Text Editor

Rich Text Content：

必须视为不可信 HTML。

后端存储与前端展示都必须考虑 Sanitization Strategy。

---

# 98. SSRF

任何让用户提供 URL 后由服务器访问的功能：

必须防止：

```text
localhost
127.0.0.1
private network
metadata endpoint
internal service
```

被恶意访问。

---

# 99. URL Fetch

例如：

```text
Import from URL
AI Fetch URL
Webhook Test
Image Download
```

都属于 SSRF 高风险入口。

---

# 100. Open Redirect

Redirect URL：

必须验证允许目标。

禁止：

```text
?redirect=https://evil.example
```

任意跳转。

---

# 101. CORS

Production CORS：

必须使用明确：

```text
Allowed Origins
Allowed Methods
Allowed Headers
Credential Policy
```

---

# 102. CORS 禁止通配 Credential

不得：

```text
Allow-Origin: *
```

同时允许敏感 Credential。

---

# 103. Security Header

Web Application 应根据 Infrastructure 配置适当：

```text
Content-Security-Policy
X-Content-Type-Options
Referrer-Policy
Frame Protection
```

等安全 Header。

---

# 104. Clickjacking

敏感后台页面：

不得允许任意第三方网站 iframe 嵌入。

除非存在明确业务需求。

---

# 105. MIME Sniffing

应防止 Browser 错误解释上传或返回内容类型。

Server 必须返回正确 Content-Type。

---

# 106. File Upload

File Upload 必须验证：

```text
Size
Type
Extension
MIME
Permission
Tenant
Ownership
```

---

# 107. MIME 不可信

Client 提供：

```text
Content-Type
```

不能作为唯一验证依据。

---

# 108. File Extension 不可信

`.jpg`：

不代表内容一定是图片。

---

# 109. Dangerous File

以下类型根据业务需求应严格限制：

```text
Executable
Script
Macro
HTML
SVG
```

# 287. Security 最终原则

AIOS 必须坚持：

> Never Trust the Client.

> Never Trust Tenant ID from the Client.

> Never Trust Resource ID Alone.

> Authentication 不等于 Authorization。

> Authorization 必须在 Backend 执行。

> Tenant Isolation 是系统底线。

> Company Scope 不能因为同 Tenant 而忽略。

> Default Deny，而不是 Default Allow。

> Least Privilege 应用于 User、Service、AI Agent、Database 和 API Key。

> Security Failure 必须 Fail Secure。

> Secret 永远不能进入 Frontend。

> Secret 永远不能 Hardcode。

> Password 永远不能明文保存。

> Frontend 隐藏按钮不能代替 Backend Permission。

> AI Agent 不拥有特殊豁免权。

> AI Output 永远必须被视为不可信输入。

> Prompt Injection 不能改变系统权限。

> RAG 必须先执行 Permission Filter，再 Retrieval。

> AI 不得直接执行任意 Production SQL。

> High-Risk AI Action 必须受 Confirmation / Approval / Audit 控制。

> Third Party 永远必须 Validate。

> Webhook 永远可能被伪造、重放、重复发送。

> File Upload 永远属于 Security Boundary。

> Super Admin 必须比 Tenant Admin 拥有更严格安全控制。

> Audit 不能成为可随意修改的普通业务数据。

> Cursor 不能通过关闭 Security 来解决开发问题。

> Cursor 不能因为“只是内部系统”而降低安全标准。

> Security 不是 AIOS 的一个 Feature。

> Security 是 AIOS 每一个 Feature 的基本属性。
