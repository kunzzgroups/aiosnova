# AIOS Permission Standard

> 文件编号：08
> 文件名称：Permission Standard
> 适用范围：AIOS 全系统 Role、Permission、RBAC、ABAC、Data Scope、Tenant、Company、Admin、Super Admin、AI Agent、API、UI
> 适用对象：Cursor、AI Agent、Frontend Developer、Backend Developer、AI Developer、Security Developer
> 前置规则：必须遵守《01 产品原则》《02 系统架构标准》《03 开发与编码标准》《06 API Standard》《07 Security Standard》
> 核心目标：统一权限模型、最小权限、默认拒绝、Tenant 隔离、Scope 明确、可审计、可扩展

---

# 1. 文件目的

本文件定义 AIOS 全系统统一 Permission Standard。

AIOS 包含：

```text
Core
CRM
Sales
POS
Inventory
Finance
HRM
Project
Marketing
AI
Automation
Developer Platform
Admin
Super Admin
```

所有 Module 必须使用统一 Permission Architecture。

禁止每个 Module 自己建立：

```text
自己的 Role
自己的 Permission
自己的 Admin 判断
自己的 Data Scope
```

最终原则：

> AIOS 只能存在一套统一权限体系。

---

# 2. Permission 核心模型

AIOS Permission 必须围绕以下关系设计：

```text
User
↓
Tenant Membership
↓
Role
↓
Permission
↓
Scope
↓
Resource
↓
Action
```

完整判断不能只有：

```text
User has Permission?
```

必须判断：

```text
Who
+
Tenant
+
Company
+
Permission
+
Scope
+
Resource
+
Action
```

---

# 3. Authentication 不等于 Permission

用户成功 Login：

只代表：

> 身份已经被确认。

不代表：

> 可以访问所有系统功能。

标准链路：

```text
Authentication
↓
Tenant Context
↓
Company Context
↓
Role
↓
Permission
↓
Scope
↓
Resource Authorization
```

---

# 4. 默认拒绝原则

AIOS Permission 必须：

```text
Default = DENY
```

只有明确满足权限条件：

才允许：

```text
ALLOW
```

禁止：

```text
没有配置 Permission
↓
默认可以访问
```

---

# 5. Least Privilege

所有：

```text
User
Role
Service Account
API Key
AI Agent
Automation
Integration
```

默认只拥有：

> 完成工作所需要的最低权限。

禁止为了开发方便赋予：

```text
ADMIN
SUPER_ADMIN
ALL
*
```

---

# 6. Permission 由 Backend 执行

真正 Permission Enforcement：

必须位于：

```text
Spring Boot Backend
```

Frontend：

只能负责：

```text
Hide
Disable
UI Access Control
```

Frontend 不能成为 Security Boundary。

---

# 7. Frontend Permission 只是 UX

即使 Frontend：

```text
隐藏 Edit Button
```

攻击者仍可以直接调用 API。

因此 Backend 必须再次执行：

```text
Permission Check
```

---

# 8. 禁止 Role Hardcode

禁止：

```java
if (user.getRole().equals("ADMIN"))
```

作为普遍业务权限逻辑。

禁止：

```typescript
if (user.role === "manager")
```

决定真正安全权限。

应该使用：

```text
Permission
+
Scope
```

判断。

---

# 9. Role 是 Permission Collection

Role 的定义：

> Permission 的集合。

例如：

```text
Sales Manager
```

可能拥有：

```text
sales.order.read
sales.order.create
sales.order.update
sales.order.approve
sales.report.read
```

Role 本身不是最终业务规则。

---

# 10. Role 不应该写死业务逻辑

错误：

```text
Manager can approve invoice.
```

写死在代码。

正确：

```text
finance.invoice.approve
```

由 Role 获得对应 Permission。

---

# 11. Permission Naming Standard

Permission 必须使用稳定统一格式。

AIOS 推荐：

```text
{module}.{resource}.{action}
```

例如：

```text
crm.customer.read
crm.customer.create
crm.customer.update
crm.customer.delete

sales.order.read
sales.order.create
sales.order.update
sales.order.submit
sales.order.approve

finance.invoice.read
finance.invoice.create
finance.invoice.post
finance.invoice.void
```

---

# 12. Permission 使用小写

Permission Code 使用：

```text
lowercase
```

并以：

```text
.
```

分层。

例如：

```text
inventory.stock.adjust
```

禁止混用：

```text
INVENTORY_STOCK_ADJUST
inventory-stock-adjust
Inventory.Stock.Adjust
```

---

# 13. Permission 必须表达 Domain

禁止过度通用：

```text
read
write
manage
admin
```

应带明确 Module / Resource。

例如：

```text
hrm.employee.read
```

而不是：

```text
employee.read
```

---

# 14. 标准 Action

常见 CRUD Action：

```text
read
create
update
delete
```

业务 Action：

```text
submit
approve
reject
cancel
void
refund
export
import
assign
publish
archive
restore
manage
```

---

# 15. 不得所有操作都叫 manage

`manage` 应用于：

> 确实需要一个高层综合 Permission 的场景。

不得所有 Resource 都只有：

```text
customer.manage
invoice.manage
employee.manage
```

否则权限无法细分。

---

# 16. Read 与 Export 必须分离

能够：

```text
read
```

不代表能够：

```text
export
```

尤其：

```text
Customer
Employee
Finance
Payroll
Audit
```

Bulk Export 属于更高风险能力。

---

# 17. Create 与 Approve 必须分离

例如：

```text
purchase.order.create
```

不代表：

```text
purchase.order.approve
```

重要业务必须支持职责分离。

---

# 18. Update 与 Status Transition 分离

能够：

```text
sales.order.update
```

不代表可以：

```text
sales.order.approve
sales.order.cancel
```

状态转换必须拥有独立 Permission。

---

# 19. Delete 与 Void 分离

例如：

```text
finance.invoice.delete
```

与：

```text
finance.invoice.void
```

业务意义不同。

交易数据通常不提供普通 Delete。

---

# 20. Module Access Permission

如产品需要控制整个 Module 是否可见：

可以定义：

```text
crm.access
finance.access
hrm.access
```

但 Module Access：

不能代替 Resource Permission。

---

# 21. Permission 层级

AIOS Permission 可以概念上分为：

```text
Module
↓
Resource
↓
Action
↓
Scope
```

例如：

```text
finance
↓
invoice
↓
approve
↓
company
```

---

# 22. Scope 不写进 Permission Code

默认不推荐建立：

```text
crm.customer.read_own
crm.customer.read_company
crm.customer.read_all
```

大量 Permission。

更合理：

```text
crm.customer.read
+
scope = OWN
```

或：

```text
COMPANY
TENANT
```

---

# 23. Permission 与 Scope 分离

Permission：

回答：

> 能不能做这个动作？

Scope：

回答：

> 可以对哪些数据做？

例如：

```text
Permission:
crm.customer.read

Scope:
OWN
```

表示：

> 可以读取 Customer，但只能读取自己负责的数据。

---

# 24. 标准 Data Scope

AIOS 推荐支持概念上的：

```text
OWN
ASSIGNED
TEAM
DEPARTMENT
COMPANY
TENANT
ALL
```

具体某个 Resource 是否支持全部 Scope：

根据 Domain 决定。

---

# 25. OWN Scope

`OWN`：

代表：

> 由当前 User 创建、拥有或业务定义为 Owner 的数据。

必须明确：

`owner` 是哪个字段 / 业务关系。

不得模糊。

---

# 26. ASSIGNED Scope

`ASSIGNED`：

表示：

> Resource 当前被分配给 User。

例如：

```text
Lead assignedTo
Ticket assignedTo
Task assignee
```

---

# 27. TEAM Scope

只有系统真正存在 Team 概念时：

才支持：

```text
TEAM
```

不得为了未来假设提前创建复杂 Team Permission。

---

# 28. DEPARTMENT Scope

HRM / Organization 等模块：

可能需要：

```text
DEPARTMENT
```

必须基于真实 Organization Hierarchy。

---

# 29. COMPANY Scope

表示：

> 当前授权 Company 内的数据。

必须同时满足：

```text
tenant_id
+
company_id
```

---

# 30. TENANT Scope

表示：

> 当前 Tenant 内允许的数据。

不能跨 Tenant。

即使：

```text
scope = TENANT
```

也绝不代表 Platform Global。

---

# 31. ALL Scope

`ALL`：

属于极高权限 Scope。

通常只用于：

```text
Platform Super Admin
```

或明确 Platform-level Resource。

普通 Tenant 用户不应获得跨 Tenant `ALL`。

---

# 32. Tenant 是绝对边界

对于 Tenant Business Data：

Permission 判断顺序必须首先保证：

```text
Resource.tenantId == CurrentTenant
```

然后才继续判断：

```text
Permission
Scope
```

---

# 33. Permission 不能跨 Tenant

即使用户拥有：

```text
crm.customer.read
scope = TENANT
```

也只能读取：

> 当前 Tenant。

不能读取其他 Tenant。

---

# 34. User 可以属于多个 Tenant

AIOS 必须允许：

```text
User
├── Tenant A
├── Tenant B
└── Tenant C
```

不同 Tenant：

可以拥有不同：

```text
Role
Permission
Company Access
Scope
```

---

# 35. User Role 必须属于 Tenant Context

不能简单：

```text
users.role_id
```

假设 User 全系统只有一个 Role。

应该支持：

```text
User
↓
Tenant Membership
↓
Role Assignment
```

---

# 36. Tenant Membership

User 与 Tenant 的关系必须明确。

至少概念上包含：

```text
user
tenant
status
role assignment
joined at
```

只有 Active Membership：

才能进入 Tenant。

---

# 37. Membership Disabled

如果 User 在 Tenant A 被 Disable：

不能影响他在 Tenant B 的 Membership，

除非 User Account 本身被 Platform Disable。

---

# 38. Global User 与 Tenant Membership 分离

```text
User
```

代表 Identity。

```text
Tenant Membership
```

代表：

> User 在这个 Tenant 内的身份与权限。

两者不能混为一谈。

---

# 39. Company Access

同一个 Tenant：

可能存在：

```text
Company A
Company B
Company C
```

User 可以只访问部分 Company。

---

# 40. Company Access 必须独立验证

User 属于 Tenant：

不代表自动访问 Tenant 下所有 Company。

必须根据：

```text
Company Membership
Role Scope
Permission Scope
```

决定。

---

# 41. Default Company

如果 UI 存在：

```text
Current Company
```

它只是 Context。

不是 Security Authority。

Backend 必须验证该 Company 是否授权。

---

# 42. Company Switch

用户切换 Company：

必须：

```text
Validate Tenant
Validate Company Access
Set Context
```

禁止仅依赖 Frontend 切换。

---

# 43. Organization Scope

对于：

```text
Department
Division
Team
Branch
Outlet
```

等 Organization Node：

可以进一步限制 Resource Scope。

---

# 44. Organization Hierarchy Permission

如果用户管理 Department A：

是否自动管理其 Child Department：

必须有明确 Policy。

不得 Cursor 自行推断。

---

# 45. Permission Inheritance

Role Permission 是否继承：

必须明确设计。

不得隐式：

```text
Manager > Staff
```

所以自动获得 Staff 所有 Permission，

除非 Role Hierarchy 正式定义。

---

# 46. 默认不使用复杂 Role Hierarchy

初期优先：

```text
Role
→ Permission
```

直接 Assignment。

不要一开始建立：

```text
Role inherits Role inherits Role
```

复杂继承体系。

---

# 47. Role 模板

AIOS 可以提供：

```text
System Role Template
```

例如：

```text
Tenant Admin
Sales Manager
Sales Staff
Finance Manager
```

但 Tenant 应可根据产品策略：

复制 / 自定义 Role。

---

# 48. System Role

System Role：

必须明确：

```text
isSystemRole
```

或等效概念。

不能随意删除系统关键 Role。

---

# 49. Custom Role

Tenant 可创建：

```text
Custom Role
```

由其拥有的 Permission 范围决定可配置内容。

---

# 50. Tenant 不能创建 Platform Permission

Tenant 创建 Role：

不能选择：

```text
platform.tenant.manage
platform.billing.manage
platform.security.manage
```

等 Platform Permission。

---

# 51. Platform Permission 与 Tenant Permission 分离

至少概念上区分：

```text
Platform Permission
```

与：

```text
Tenant Permission
```

防止权限提升。

---

# 52. Super Admin

Super Admin：

属于 AIOS Platform Control Plane。

不是：

> Tenant 内最大的 Admin。

---

# 53. Super Admin Permission

Super Admin Permission 应使用明确 Platform Domain。

例如：

```text
platform.tenant.read
platform.tenant.update
platform.subscription.manage
platform.security.manage
platform.monitoring.read
```

---

# 54. 禁止 `SUPER_ADMIN = allow everything`

即使 Super Admin 权限很高：

仍应通过明确 Permission 系统。

避免代码到处：

```text
if superAdmin:
    bypassEverything()
```

---

# 55. Super Admin Bypass 必须极少

如果确实存在 Platform Emergency Bypass：

必须：

```text
Explicit
Audited
Restricted
```

不得成为正常业务路径。

---

# 56. Tenant Admin

Tenant Admin：

只管理：

> 自己的 Tenant。

不能：

```text
Read Tenant B
Manage Platform
Change Global Plan Definition
```

---

# 57. Tenant Admin Permission

例如：

```text
core.user.manage
core.role.manage
core.organization.manage
core.company.manage
```

仍必须 Scope 在当前 Tenant。

---

# 58. Tenant Admin 不能授予自己不存在的权限

如果 Tenant Plan / Policy：

没有：

```text
finance.payroll.manage
```

Tenant Admin 不能通过 Role Editor：

自行生成此 Permission。

---

# 59. Permission Assignment 权限

管理 Role / Permission 本身也是 Permission。

例如：

```text
core.role.read
core.role.create
core.role.update
core.role.assign
```

---

# 60. Role 管理与 Role Assignment 分离

能修改 Role Definition：

不一定代表能把该 Role Assign 给任何 User。

必须考虑：

```text
role.update
role.assign
```

是否分开。

---

# 61. Privileged Role Assignment

高权限 Role：

例如：

```text
Tenant Admin
Finance Admin
Security Admin
```

Assignment 应考虑：

```text
Extra Permission
Audit
Confirmation
```

---

# 62. 不能授予比自己更高的权限

默认规则：

> User 不能授予自己无权管理的 Permission。

例如：

Sales Manager：

不能创建 Role 并加入：

```text
finance.invoice.approve
```

---

# 63. Permission Grant Boundary

Role Editor 可看到的 Permission：

应根据：

```text
Current User Manageable Permissions
Tenant Features
Plan
Module Availability
```

过滤。

---

# 64. Permission Revocation

Permission 被撤销后：

必须尽快生效。

不得需要：

> 用户退出再登入几天后才生效。

---

# 65. Permission Cache

如使用 Cache：

必须设计：

```text
Invalidation
Version
Expiry
```

特别当：

```text
Role changed
Permission revoked
Membership disabled
```

时。

---

# 66. Permission Cache Key

Permission Cache 必须至少包含：

```text
user
tenant
```

如果与 Company 有关：

还必须考虑：

```text
company
```

禁止：

```text
permission:user123
```

混淆多个 Tenant。

---

# 67. Permission Snapshot

Request 开始时：

可以建立 Current Permission Context。

但长时间 Workflow / Job：

不得永远依赖旧 Permission Snapshot。

---

# 68. Background Job Permission

异步 Job 执行时：

必须明确：

```text
Run as user
Run as service
Run as system
```

不能模糊。

---

# 69. Run as User

如果 Job 是用户发起：

并代表用户执行敏感动作，

应保存：

```text
requestedBy
tenant
permission context
```

并根据业务决定执行时是否再次验证权限。

---

# 70. System Job

真正系统级 Job：

必须使用明确：

```text
Service Identity
```

不能假装为普通 User。

---

# 71. Automation Permission

Workflow / Automation：

不能自动绕过 Permission。

必须明确：

> Automation 以谁的权限运行？

---

# 72. Automation Execution Mode

可根据系统正式设计支持：

```text
Run as Triggering User
Run as Workflow Owner
Run as Service Account
```

但必须明确。

---

# 73. Automation 不允许无限系统权限

禁止：

```text
All automations run as SUPER_ADMIN
```

---

# 74. Approval Permission

拥有：

```text
approval.read
```

不代表拥有：

```text
approval.approve
```

---

# 75. Approver Eligibility

即使 User 有：

```text
purchase.order.approve
```

仍必须检查：

```text
Workflow Step
Approver Assignment
Scope
Amount Limit if applicable
```

---

# 76. Permission 与业务限制分离

Permission：

```text
purchase.order.approve
```

只代表有资格执行 Approve。

业务规则仍可能限制：

```text
Amount
Department
Workflow Step
Status
```

---

# 77. Approval Limit

例如：

Manager：

可批准：

```text
≤ RM 10,000
```

Director：

可批准更高金额。

这属于：

```text
ABAC / Business Policy
```

不能仅靠 Role Name Hardcode。

---

# 78. ABAC

AIOS 在复杂权限场景中可以使用 ABAC。

可使用 Attribute：

```text
User
Tenant
Company
Department
Resource
Owner
Amount
Status
Location
```

---

# 79. ABAC 不得成为随意脚本

禁止建立：

```text
eval(expression)
```

执行任意字符串作为 Permission Rule。

必须使用受控 Policy Model。

---

# 80. ABAC Policy 必须可审计

Policy 必须能够解释：

```text
Why Allowed?
Why Denied?
```

不能成为不可维护黑箱。

---

# 81. Permission 与 Feature Control

拥有 Permission：

不代表 Feature 一定可用。

完整判断：

```text
Feature Enabled
+
Plan Allows Feature
+
Permission
+
Scope
```

---

# 82. Feature Disabled

如果 Tenant Plan 没有 Finance：

即使旧 Role 还拥有：

```text
finance.invoice.read
```

也不能访问 Finance。

---

# 83. Feature Control 不能代替 Permission

反之：

Feature Enabled：

不代表所有 User 都拥有权限。

---

# 84. License / Plan 与 Role 分离

禁止：

```text
PRO Plan User = Admin
```

Plan 控制：

> Tenant 可以使用什么 Feature。

Permission 控制：

> User 可以在 Feature 中做什么。

---

# 85. API Permission Standard

每个受保护 Endpoint：

必须明确：

```text
Required Permission
Required Scope
Resource Check
```

---

# 86. Controller 不应该散落复杂权限逻辑

Controller 可以声明：

```text
Permission Requirement
```

但复杂 Scope / Resource Authorization：

应交给统一 Authorization Service / Policy。

---

# 87. Application Service 再次保护关键 Action

对于高风险业务：

即使 Controller 已经 Permission Check，

Application / Domain Boundary：

仍应确保不能被其他调用路径绕过。

---

# 88. Internal Service 不得绕过 Permission

例如：

```text
REST Controller
→ Permission
→ Service
```

但另一个 Internal API 直接调用 Service：

不能自动获得权限。

必须设计清楚：

```text
Authorized Use Case
```

与纯 Domain Logic 的边界。

---

# 89. Repository 不是 Permission Layer

Repository 不负责：

```text
Current User Permission
```

但 Query 必须支持安全 Scope。

Authorization 应在 Repository 之前确定。

---

# 90. Secure Query

安全查询优先：

```text
findByIdAndTenantId(...)
```

而不是：

```text
findById(...)
↓
later check
```

对于敏感 Tenant Data。

---

# 91. 禁止查询后再过滤全量数据

不能：

```text
findAll()
↓
filter by permission in Java
```

必须在 Query 层限制 Data Scope。

---

# 92. 404 与 403

对于 Resource 不属于当前 Tenant：

根据 Security Policy：

可返回：

```text
404
```

避免泄露 Resource 存在。

对于明确知道 Resource 且无操作 Permission：

可以：

```text
403
```

全系统保持一致策略。

---

# 93. List API Permission

List Endpoint：

必须将 Permission Scope 转换成 Query Scope。

例如：

```text
OWN
→ owner_id = currentUser

COMPANY
→ company_id = currentCompany

TENANT
→ tenant_id = currentTenant
```

---

# 94. Search Permission

Global Search：

必须在搜索阶段限制 Permission。

禁止：

```text
Search everything
↓
Frontend hides unauthorized results
```

---

# 95. Dashboard Permission

Dashboard KPI：

必须基于当前用户数据权限。

不能：

User 只能看 Company A，

Dashboard 却统计 Tenant 全部 Company。

---

# 96. Report Permission

Report Permission 建议独立：

```text
sales.report.read
finance.report.read
```

不能因为可以读 Transaction：

就自动允许看所有 Aggregate Report。

---

# 97. Export Permission

Export 必须拥有：

```text
resource.export
```

或正式对应 Permission。

---

# 98. Import Permission

Import 同样需要独立：

```text
resource.import
```

因为 Import 可以批量修改系统数据。

---

# 99. Bulk Permission

Bulk Action：

必须对每个 Resource 验证 Scope。

不能：

> 只验证第一个 ID。

---

# 100. Bulk Partial Authorization

如果 Bulk List 中包含无权限 Resource：

必须明确策略：

```text
Fail all
```

或：

```text
Partial failure
```

不能静默跳过而不告知。

---

# 101. Field-Level Permission

某些敏感 Resource：

需要 Field-Level Permission。

例如 Employee：

```text
hrm.employee.read
```

不一定包含：

```text
Salary
Bank Account
Tax Information
```

---

# 102. Sensitive Field Permission

可定义类似：

```text
hrm.employee.salary.read
hrm.employee.bank.read
finance.bank-account.read
```

只在真正敏感领域使用。

不得所有字段都建立 Permission，造成无法维护。

---

# 103. Field-Level Write

敏感字段修改：

应使用独立 Permission / Domain Action。

例如：

```text
hrm.employee.salary.update
```

---

# 104. Response Filtering

Backend 必须根据权限：

避免返回无权限 Sensitive Field。

不能：

```text
API 返回 salary
↓
Frontend 隐藏 salary
```

---

# 105. Column Permission

Table Column 是否显示：

可以由 Frontend Permission 控制。

但数据本身必须从 Backend 不返回或受保护。

---

# 106. Row-Level Permission

Data Scope：

本质上属于 Row-Level Authorization。

例如：

```text
Customer A
Customer B
```

用户可能只可访问其中部分。

---

# 107. Action-Level Permission

同一 Resource：

用户可以：

```text
read
```

但不能：

```text
update
delete
approve
```

必须分别判断。

---

# 108. Object-Level Permission

对于 Project / Document / Ticket 等：

可以存在 Resource-specific ACL。

例如：

```text
Project Member
Document Collaborator
```

---

# 109. ACL 使用原则

只有真正需要 Resource-level Sharing：

才建立 ACL。

不要所有 Entity 一开始都做复杂 ACL。

---

# 110. ACL 与 RBAC 关系

最终允许访问可能为：

```text
RBAC Permission
+
Data Scope
+
Resource ACL
```

具体 Domain 决定。

---

# 111. Document Permission

Document Management 可能需要：

```text
Owner
Viewer
Editor
Approver
```

但仍必须受 Tenant Boundary 限制。

---

# 112. Shared Document 不能跨 Tenant 默认共享

任何 Cross-Tenant Sharing：

必须属于明确产品功能。

默认禁止。

---

# 113. Permission UI

Role / Permission UI：

必须反映统一 Permission Model。

建议结构：

```text
Module
├── Resource
│   ├── Read
│   ├── Create
│   ├── Update
│   ├── Delete
│   ├── Approve
│   └── Export
```

---

# 114. 禁止数百 Checkbox 无分组

Permission UI 必须：

```text
Module Group
Resource Group
Action
```

清楚组织。

---

# 115. Permission UI 不得显示未启用 Feature

Tenant Plan 没有某 Module：

Role Editor 不应让 Tenant 配置该 Module Permission。

---

# 116. Permission UI 必须区分危险权限

例如：

```text
Delete
Refund
Payroll
Permission Manage
Export Sensitive Data
```

应具有更明显风险提示。

---

# 117. Permission Search

大型权限矩阵：

可以提供：

```text
Search
Filter
Expand / Collapse
```

提升管理效率。

---

# 118. Select All

Permission UI 的：

```text
Select All
```

必须限定明确 Scope。

例如：

```text
Select all actions for Customer
```

不能一个按钮默认选中全系统所有 Permission。

---

# 119. Permission Dependency

如果：

```text
update
```

逻辑上必须拥有：

```text
read
```

系统可自动保证依赖。

但必须统一定义。

Cursor 不得每个 Module 自行决定。

---

# 120. Dangerous Permission Confirmation

赋予高风险 Permission 时：

可以要求明确确认。

例如：

```text
finance.payment.refund
core.permission.manage
platform.tenant.manage
```

---

# 121. Role Copy

复制 Role：

必须复制：

```text
Permission
Scope
```

但创建新的 Role Identity。

---

# 122. Role Rename

Rename Role：

不能改变已有 Permission。

Role Name 是 Display。

Permission 是真正能力。

---

# 123. Role Delete

删除 Role 前必须检查：

```text
Assigned Users
System Role
Active Workflow
```

不得直接删除导致用户权限异常。

---

# 124. Role Disable

如果 Role 暂时不允许新 Assignment：

可考虑 Disable。

但现有 Assignment 如何处理：

必须有明确规则。

---

# 125. Permission 删除

已经发布过的 Permission：

不得因为代码重构直接从数据库删除。

必须考虑：

```text
Existing Role Assignment
Migration
Replacement Permission
```

---

# 126. Permission Rename

Permission Code：

属于稳定 Contract。

修改：

```text
sales.order.edit
→ sales.order.update
```

需要 Migration。

不得仅 Rename Constant。

---

# 127. Permission Version Compatibility

部署过程中：

Old Backend / New Backend：

可能短暂同时运行。

Permission Migration 必须避免：

部署中所有用户突然失去权限。

---

# 128. Permission Seed

系统 Permission Definition：

应由版本化 Seed / Migration 管理。

禁止在 Production：

每次启动随机重建权限。

---

# 129. Permission Definition 属于代码控制

核心 Permission Code：

应该由系统定义。

Tenant：

可以配置 Role Assignment。

但不能创建任意核心 Permission Code。

---

# 130. Custom Permission

除非未来产品明确支持：

> Customer-defined Permission Policy

否则 Tenant 不应自行创建新 Permission Code。

---

# 131. Permission Database Model

概念上至少需要：

```text
permissions
roles
role_permissions
user / membership role assignments
```

实际 Schema 按 Database Standard 设计。

---

# 132. Permission Table

Permission Definition 至少应能表达：

```text
code
module
resource
action
risk level
status
```

具体字段根据实现需要。

---

# 133. Role Table

Role 应至少明确：

```text
tenant scope
name
system/custom
status
```

Platform Role 与 Tenant Role：

必须有清晰边界。

---

# 134. Role Permission Association

Role 与 Permission：

采用正式 Many-to-Many Relationship。

禁止：

```text
permissions = "a,b,c,d"
```

字符串存储。

---

# 135. User 不应直接拥有大量 Permission

默认优先：

```text
User
→ Role
→ Permission
```

而不是每个 User 单独配置几百 Permission。

---

# 136. Direct User Permission

如未来确实需要例外：

可以支持：

```text
User Permission Override
```

但必须谨慎。

否则权限很难理解。

---

# 137. 默认避免 Deny Override

复杂：

```text
Role allow
User deny
Role B allow
```

容易产生难以解释的规则。

初期优先保持简单 Permission Model。

---

# 138. 多 Role

如果 User 可以拥有多个 Role：

权限通常采用：

```text
Union of Allowed Permissions
```

但必须受：

```text
Tenant
Company
Scope
Feature
```

约束。

---

# 139. 多 Role Scope 合并

例如：

Role A：

```text
customer.read = OWN
```

Role B：

```text
customer.read = COMPANY
```

最终 Effective Scope：

可以为：

```text
COMPANY
```

但合并规则必须统一。

---

# 140. Scope 不得简单字符串比较

不能：

```text
if scopeA > scopeB
```

除非 Scope Hierarchy 正式定义。

---

# 141. Permission Resolution

统一 Permission Engine 应输出：

```text
Allowed / Denied
Effective Scope
Reason
```

至少内部逻辑应可以解释。

---

# 142. Permission Debug

开发环境可以提供安全的 Permission Debug 信息。

例如：

```text
Permission denied because scope=OWN
```

但 Production 不应暴露过多 Security Detail 给普通用户。

---

# 143. Permission Denied 用户体验

Frontend 可以显示：

```text
You do not have permission to perform this action.
```

但不应显示：

```text
You are missing internal policy xyz_9382.
```

---

# 144. Audit Permission Denied

不需要记录每一次普通 403 为高等级 Audit。

但异常：

```text
Repeated Privilege Escalation
Cross-Tenant Attempt
Super Admin Denied Action
```

应进入 Security Monitoring。

---

# 145. Permission Audit

以下必须重点 Audit：

```text
Role Created
Role Updated
Role Deleted
Permission Added
Permission Removed
Role Assigned
Role Revoked
Admin Promotion
Super Admin Change
```

---

# 146. Audit 必须记录 Before / After

Role Permission Change：

应能够知道：

```text
Before Permissions
After Permissions
Actor
Tenant
Time
```

---

# 147. Permission Change Reason

高风险 Role / Permission 修改：

可以要求：

```text
Reason
```

用于 Audit。

---

# 148. Role Assignment Audit

必须记录：

```text
Who assigned
Which role
To whom
Tenant
Company if applicable
When
```

---

# 149. Self Permission Change

系统必须防止用户直接修改：

```text
自己的 Role Assignment
```

除非拥有合法 Admin 权限且 Policy 允许。

---

# 150. Last Admin Protection

如果 Tenant 只有一个 Tenant Admin：

删除 / 降级最后一个 Admin 前：

应考虑保护。

避免 Tenant 完全没有管理员。

---

# 151. Super Admin Protection

类似地：

Platform 最后关键 Super Admin：

不应轻易被普通操作删除。

具体策略由 Security Policy 定义。

---

# 152. Maker / Checker

Finance、Payment、Procurement 等高风险模块：

权限系统必须支持：

```text
Maker
Checker
Approver
```

职责分离。

---

# 153. Segregation of Duties

例如：

```text
finance.payment.create
```

与：

```text
finance.payment.approve
```

应可以授予不同 Role。

---

# 154. Self Approval

是否允许：

```text
createdBy == approver
```

不能由 Permission 本身决定。

属于：

```text
Business Policy / Approval Policy
```

---

# 155. Amount-Based Authority

例如 Approval Limit：

```text
Manager: 10,000
Director: 100,000
```

应通过：

```text
Policy / Attribute
```

而不是创建：

```text
approve_under_10k
approve_under_100k
```

大量特殊 Permission。

---

# 156. Branch / Outlet Permission

POS / Inventory：

可能需要：

```text
Outlet Scope
Warehouse Scope
```

它们属于 Resource Scope。

不应为每个 Outlet 创建新的 Permission Code。

---

# 157. Warehouse Scope

例如：

```text
inventory.stock.read
+
warehouses = [A, B]
```

比：

```text
inventory.stock.read_warehouse_a
```

更合理。

---

# 158. Project Permission

Project Module 可以同时存在：

```text
Global Project Permission
+
Project Membership
```

例如：

拥有：

```text
project.task.update
```

并且是 Project Member，

才能修改 Task。

---

# 159. CRM Assignment Permission

CRM Lead：

可能使用：

```text
ASSIGNED
```

Scope。

Sales Manager：

可能：

```text
TEAM / COMPANY
```

具体由 Domain Policy 定义。

---

# 160. HRM Permission

HRM 应特别区分：

```text
Employee Profile
Attendance
Leave
Performance
Payroll
Sensitive Personal Data
```

不能只有一个：

```text
hrm.access
```

控制所有内容。

---

# 161. Payroll Permission

Payroll 必须独立高敏感权限。

例如：

```text
hrm.payroll.read
hrm.payroll.process
hrm.payroll.finalize
hrm.payroll.export
```

---

# 162. Finance Permission

Finance 应至少根据业务拆分：

```text
General Ledger
AP
AR
Bank
Expense
Budget
Asset
Tax
Report
```

不能只用：

```text
finance.manage
```

---

# 163. POS Permission

POS 应考虑：

```text
pos.order.create
pos.discount.apply
pos.refund.create
pos.shift.close
pos.cash-drawer.open
```

等实际高风险 Action。

---

# 164. Discount Permission

不同 Discount Level：

可能需要：

```text
ABAC / Policy
```

例如员工最多 10%，Manager 最多 30%。

不应创建几十个 Percent Permission Code。

---

# 165. Inventory Permission

例如：

```text
inventory.stock.read
inventory.stock.adjust
inventory.transfer.create
inventory.transfer.approve
inventory.count.perform
```

必须区分读取和真正影响库存的 Action。

---

# 166. Developer Platform Permission

例如：

```text
developer.api-key.read
developer.api-key.create
developer.api-key.revoke
developer.webhook.manage
```

属于高风险能力。

---

# 167. Integration Permission

例如：

```text
integration.payment.manage
integration.google.connect
integration.microsoft.connect
```

连接第三方账户属于敏感 Action。

---

# 168. Security Module Permission

例如：

```text
security.role.read
security.permission.manage
security.mfa.manage
security.device.read
security.audit.read
```

其中：

```text
permission.manage
```

属于高风险权限。

---

# 169. Audit Log Permission

读取 Audit：

不等于：

```text
delete / update
```

Audit 默认不应提供普通修改 Permission。

---

# 170. AI Permission Model

AIOS AI 必须拥有独立 Permission Boundary。

AI Agent：

不能因为 User 有 Permission：

就自动拥有所有 Tool。

完整判断：

```text
User Permission
+
Agent Permission
+
Tool Permission
+
Resource Scope
```

---

# 171. AI Agent Identity

每个可执行 Action 的 Agent：

应该具有明确：

```text
agentId
```

和权限配置。

---

# 172. AI Agent 默认无业务写权限

新 Agent 默认：

```text
Read-only / No tool permission
```

根据用途明确赋予。

---

# 173. AI Tool Permission

例如：

```text
createSalesOrder
```

对应至少需要：

```text
sales.order.create
```

Tool 不应绕过 Backend Permission。

---

# 174. AI Agent Permission 不能大于 User Delegation

如果 Agent 代表 User：

最终 Effective Permission：

不得超过：

```text
User Permission
```

---

# 175. System AI Agent

真正 System Agent：

必须使用独立 Service Identity。

不能伪装：

```text
User = SUPER_ADMIN
```

---

# 176. AI High-Risk Action

例如：

```text
Refund
Payroll Finalize
Permission Change
Delete
Payment
```

即使 Permission 通过：

仍可能要求：

```text
Human Confirmation
Approval
MFA
```

---

# 177. AI Read Permission

AI RAG：

只能读取：

> User 本来有权读取的数据。

不能给 AI 一个：

```text
knowledge.read_all
```

然后让模型自己判断。

---

# 178. RAG Permission Filter

正确：

```text
User Context
↓
Tenant
↓
Permission Filter
↓
Knowledge Retrieval
↓
LLM
```

禁止：

```text
Retrieve all
↓
LLM filters
```

---

# 179. AI Memory Permission

Memory 必须根据：

```text
Tenant
User
Agent
Session
```

隔离。

不能让 Agent A 随意读取 Agent B / User B Memory。

---

# 180. API Key Permission

Developer API Key：

应拥有：

```text
Scope
Permission
Tenant
```

不能默认继承创建者所有未来权限。

---

# 181. API Key Permission Snapshot

API Key 创建时：

权限策略必须明确：

```text
Fixed Scopes
```

或动态绑定。

不得模糊。

---

# 182. API Key 不拥有 UI Role

API Key 应使用：

```text
API Scope / Permission
```

模型。

不应该假装是 Browser User Role。

---

# 183. Service Account Permission

Service Account：

也必须使用明确：

```text
Service Permission
```

不能共享 Tenant Admin Role。

---

# 184. Permission 不能依赖前端 Route

Route：

```text
/admin/finance
```

不能作为真正 Authorization。

Backend 必须独立判断。

---

# 185. Route Guard

Frontend 可以使用：

```text
Route Guard
```

提升 UX。

但 Route Guard：

不是 Backend Security。

---

# 186. Menu Permission

Sidebar Menu：

可以根据：

```text
Feature
+
Permission
```

显示。

---

# 187. Menu Visibility

推荐：

没有 Module Access：

```text
Hide
```

有 Module Access 但某 Action 不允许：

```text
Action hidden / disabled
```

具体遵守 UI Standard。

---

# 188. Disabled 与 Unauthorized

Disabled：

表示：

> 当前状态不能执行。

Unauthorized：

表示：

> 没有权限。

两者不能混淆。

---

# 189. Permission Loader

Frontend 应统一加载 Current User Effective Permission。

不得每个 Module 自己从不同 API 获取 Role。

---

# 190. Frontend Permission Helper

应统一使用类似逻辑：

```text
can(permission)
can(permission, scope)
```

或项目正式 Helper。

禁止：

```typescript
user.role === "admin"
```

散布全项目。

---

# 191. Frontend Permission 不能自行推算

Backend 应提供足够明确的 Effective Permission / Context。

Frontend 不应自行组合复杂 Role 继承。

---

# 192. Backend 是 Permission Source of Truth

最终 Effective Permission：

必须由 Backend / Permission Engine 决定。

---

# 193. Permission API

Permission API 应明确区分：

```text
Permission Definitions
Roles
Role Assignments
Current User Effective Permissions
```

不得一个巨大 `/permissions` Endpoint 混合所有行为。

---

# 194. Current User Permission

可提供类似：

```text
GET /api/v1/me/permissions
```

或现有 API Standard 对应方式。

返回 Current Context 下必要的 Effective Permission。

---

# 195. Me API

Current User Context 可以提供：

```text
User
Current Tenant
Current Company
Roles
Effective Permissions
Features
```

但避免返回无必要敏感资料。

---

# 196. Tenant Switch 后重新计算权限

Current Tenant 改变：

必须重新获得对应：

```text
Role
Permission
Company Access
```

不能继续使用前一个 Tenant Permission。

---

# 197. Company Switch

如果 Permission Scope 受 Company 影响：

Company Switch 后：

Frontend Context 必须正确刷新。

---

# 198. Permission API Cache

`/me/permissions` 可以合理 Cache。

但 Role / Permission 修改后：

必须能失效。

---

# 199. Permission Change Event

Role / Permission Change：

可产生：

```text
PermissionChanged
RoleAssignmentChanged
```

等系统 Event，

用于：

```text
Cache Invalidation
Session Refresh
Audit
```

具体实现根据架构需要。

---

# 200. Session 与 Permission

不推荐把全部 Permission 永久写死进长寿命 Token。

否则 Permission Revocation 很难即时生效。

Token 中只保存什么信息：

必须由 Authentication Architecture 统一决定。

---

# 201. JWT Permission

如果 JWT 包含 Role / Permission Claim：

必须考虑：

```text
Token Lifetime
Permission Change
Revocation
Stale Claims
```

不能假设 Claim 永远最新。

---

# 202. Permission Failure

Permission Service 发生错误：

必须：

```text
DENY
```

不得：

```text
ALLOW because service failed
```

---

# 203. Scope Resolution Failure

无法确定：

```text
Current Tenant
Company
Owner
```

时：

默认拒绝。

不得：

```text
Use first company
Use default tenant
```

---

# 204. Unknown Permission

代码要求的 Permission：

如果 Permission Definition 不存在：

应：

```text
Fail Secure
```

而不是自动允许。

---

# 205. Unknown Scope

遇到未知 Scope：

必须拒绝。

不得 fallback：

```text
TENANT
```

或：

```text
ALL
```

---

# 206. Security Admin

可以定义专门：

```text
Security Admin
```

负责 Role / Permission / MFA / Security Policy。

但必须仍受 Tenant Boundary。

---

# 207. Permission Admin 不等于所有业务权限

拥有：

```text
core.permission.manage
```

不代表自动拥有：

```text
finance.payment.refund
```

管理权限与执行权限必须分开。

---

# 208. Role Creation Validation

创建 Role 时必须验证：

```text
Tenant
Role Name
Permission Codes
Assignable Permissions
Feature Availability
Scope
```

---

# 209. Duplicate Role Name

Role Name 是否 Tenant 内唯一：

由业务规则统一定义。

如果要求唯一：

必须 Database Constraint 支持。

---

# 210. System Role 修改

System Role 是否允许修改：

必须明确。

不能 Cursor 自行决定。

---

# 211. Role Permission Update

修改 Role：

必须在一个一致的业务操作中处理。

不能：

```text
remove all
↓
temporary zero permission
↓
add new
```

导致并发异常，

应使用 Transaction。

---

# 212. Role Assignment Transaction

Assign / Revoke Role：

必须保持数据一致性。

---

# 213. Permission Audit Transaction

高风险 Permission Change：

Audit 与修改结果必须可靠关联。

---

# 214. Permission 不应该物理删除历史 Audit

旧 Permission 即使废弃：

历史 Audit 仍应该能够理解原 Permission Code。

---

# 215. Permission Deprecation

废弃 Permission 推荐：

```text
ACTIVE
DEPRECATED
DISABLED
```

等正式生命周期。

不要直接静默删除。

---

# 216. Permission Migration

Rename / Split Permission：

必须设计：

```text
Old Role Assignment
↓
Migration
↓
New Permission
```

不能让 Production 所有 Role 丢权限。

---

# 217. Split Permission

例如：

```text
customer.manage
```

拆成：

```text
customer.read
customer.create
customer.update
customer.delete
```

必须明确旧 Role 应获得哪些新权限。

---

# 218. Merge Permission

合并 Permission：

同样必须评估是否造成权限扩大。

---

# 219. Permission Expansion 属于 Security Change

如果一个 Existing Permission 原本只允许 A，

现在新增 B：

这属于：

> Permission Expansion。

必须评估现有所有拥有该 Permission 的 Role。

Tenant Admin / Security Admin：

如果未来支持临时授权：

必须包含：

到期必须自动失效。

# 225. Temporary Permission 不得依赖人工记得删除

必须系统自动 Expire。

# 226. Emergency Access

如未来支持 Emergency Access：

必须：

```text
Reason
```

不能成为日常绕过权限方式。

# 227. Permission 与 Ownership 组合

例如 User 拥有：


Backend 必须确认：

```text

```

再允许。

# 228. Ownership 变更

修改 Resource Owner：

本身可能需要独立 Permission：

```text

```

而不是普通 Update。

---

# 229. Assign Permission

能够 Update Customer：

不代表能够 Assign 给其他 Salesperson。

Assign 应根据业务独立控制。

---

# 230. Cross-Company Assign

User 是否能将 Resource Assign 到其他 Company：

必须受 Company Scope 限制。

---

# 231. Data Scope 与 Query

Scope 必须尽量转换为 DB Query 条件。

例如：

```text
OWN
→ owner_id = current_user

ASSIGNED
→ assigned_to = current_user

COMPANY
→ company_id IN allowed companies

TENANT
→ tenant_id = current_tenant
```

# 232. Scope 与 Pagination

Permission Filter：

必须在 Pagination 之前执行。

禁止：

```text
Query 20 rows
↓
Remove unauthorized
↓
return 6 rows
```

导致 Pagination 错误。

---

# 233. Scope 与 Count

`totalItems`：

必须只统计用户有权访问的数据。

不能泄露 Tenant / Company 其他数据数量。

---

# 234. Scope 与 Analytics

Chart / KPI / Report：

必须应用同一 Permission Scope。

---

# 235. Scope 与 AI

AI Analysis：

只能分析当前 Effective Scope 的数据。

不能：

```text
User can see own sales
AI gives tenant-wide sales insight
```

---

# 236. Permission 与 Notification

用户收到 Notification：

不代表永久拥有对应 Resource Permission。

打开 Notification 时：

必须重新检查 Permission。

---

# 237. Permission 与 Search Result

Search Result 创建时有权限：

之后 Permission 被撤销：

再次打开必须拒绝。

---

# 238. Permission 与 Saved Link

用户保存 Resource URL：

Permission 被撤销后：

链接不能继续访问。

---

# 239. Permission 与 Download URL

File Signed URL：

应短时有效。

Permission 被撤销后的长期 URL：

不能永久继续访问敏感资源。

---

# 240. Permission 与 Export File

生成的 Export File：

必须拥有：

```text

Expiry
Permission
```

不能生成永久公开文件。

# 241. Permission 与 Audit

Audit Log 自身也需要：

```text

```

或对应权限。

读取 Audit 通常属于敏感行为。

---

# 242. Permission 与 Activity Feed

Activity Feed：

也必须过滤：

用户没有权限看到的 Resource。

---

# 243. Permission 与 Notification Count

Count / Badge：

不得泄露无权限数据。

例如：

```text

```

# 244. Permission 与 Related Resource

例如 Sales Order 允许访问：

Nested Response 仍必须遵守 Customer Permission Policy。

# 245. Cross-Domain Permission

模块 A 调用模块 B：

> 用户在 B 也有权限。

必须按照业务 Contract 判断。

不得形成可绕过的公开 Service。

# 273. Permission 最终原则

AIOS Permission 必须坚持：

> Authentication 不等于 Authorization。

> Role 不等于 Permission。

> Permission 不等于 Scope。

> Permission 决定可以做什么。

> Scope 决定可以对哪些数据做。

> Tenant 是不可突破的安全边界。

> Company 是 Tenant 内的进一步访问边界。

> Backend 是 Permission 的最终权威。

> Frontend Permission 只负责用户体验。

> Default Deny，而不是 Default Allow。

> Least Privilege，而不是方便优先。

> Role Name 不能写死成为业务安全逻辑。

> Permission Code 必须稳定、统一、可审计。

> Read、Create、Update、Delete、Approve、Export 等动作必须根据风险分离。

> User 不能授予自己无权管理的 Permission。

> Tenant Admin 永远不是 Platform Super Admin。

> Super Admin 也必须通过明确 Permission，而不是无条件 Bypass。

> Feature Control 与 Permission 是两套不同机制。

> Sensitive Field 必须可以拥有更细权限控制。

> Data Scope 必须在数据库查询阶段生效。

> Pagination、Count、Search、Dashboard、Report、AI 都必须遵守相同 Permission Scope。

> AI Agent 不拥有特殊豁免权。

> Automation 不得默认以 Super Admin 身份运行。

> Permission Change 必须 Audit。

> Permission Revocation 必须及时生效。

> Permission System 必须能够解释为什么允许，以及为什么拒绝。

> Cursor 不得为了功能能运行而扩大权限。

> Cursor 不得因为出现 403 就关闭 Permission。

> AIOS 最终必须做到：用户只能看到自己应该看到的数据，只能执行自己被明确允许执行的动作。
