# AIOS Error Handling Standard

> 文件编号：14
> 文件名称：Error Handling Standard
> 适用范围：AIOS Frontend、Backend、API、Database、AI、Agent、Integration、Workflow、Background Job
> 适用对象：Cursor、AI Agent、Frontend Developer、Backend Developer、AI Developer、Integration Developer
> 前置规则：必须遵守《01 产品原则》至《13 Naming Convention》
> 核心目标：错误可识别、可追踪、可恢复、不泄露敏感信息、不隐藏失败、不制造 Fake Success

---

# 1. 核心原则

AIOS Error Handling 必须遵守：

```text
Fail Clearly
Fail Safely
Fail Predictably
Never Hide Errors
Never Fake Success
Preserve Context
Protect Sensitive Data
Provide Traceability
```

原则：

> Error 是正式系统状态，不是例外情况才临时处理。

---

# 2. 错误必须分类

AIOS 至少区分：

```text
Validation Error
Authentication Error
Authorization Error
Not Found Error
Conflict Error
Business Rule Error
Database Error
External Service Error
Timeout Error
Rate Limit Error
System Error
AI / Agent Error
```

不得所有失败统一：

```text
Something went wrong
500
```

---

# 3. Error Code 必须稳定

系统错误必须拥有机器可读：

```text
error.code
```

统一：

```text
UPPER_SNAKE_CASE
```

例如：

```text
VALIDATION_ERROR
ACCESS_DENIED
CUSTOMER_NOT_FOUND
DUPLICATE_EMAIL
INVALID_ORDER_STATUS
INSUFFICIENT_STOCK
PAYMENT_PROVIDER_UNAVAILABLE
AGENT_TOOL_FAILED
```

---

# 4. Error Message 与 Error Code 分离

`code`：

用于程序判断。

`message`：

用于人阅读。

Frontend 禁止：

```typescript
if (error.message === "Customer not found")
```

必须：

```typescript
if (error.code === "CUSTOMER_NOT_FOUND")
```

---

# 5. 标准 API Error Response

统一使用类似：

```json
{
  "error": {
    "code": "CUSTOMER_NOT_FOUND",
    "message": "Customer was not found.",
    "details": null,
    "fieldErrors": []
  },
  "requestId": "..."
}
```

不得不同 Module 发明不同 Error Format。

---

# 6. Validation Error

Request 格式或字段错误：

必须返回明确 Field Error。

例如：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed.",
    "fieldErrors": [
      {
        "field": "email",
        "code": "INVALID_EMAIL",
        "message": "Enter a valid email address."
      }
    ]
  },
  "requestId": "..."
}
```

---

# 7. Business Error

业务规则失败：

必须使用明确业务 Error Code。

例如：

```text
INSUFFICIENT_STOCK
INVOICE_ALREADY_VOIDED
PAYMENT_ALREADY_REFUNDED
APPROVAL_NOT_ALLOWED
INVALID_STATE_TRANSITION
```

禁止只返回：

```text
BAD_REQUEST
```

掩盖真实原因。

---

# 8. HTTP Status 必须正确

默认：

```text
400 → Invalid Request
401 → Unauthenticated
403 → Unauthorized
404 → Resource Not Found
409 → Conflict
422 → Business Validation
429 → Rate Limited
500 → Unexpected Internal Error
502 → Upstream Invalid Failure
503 → Dependency / Service Unavailable
504 → Upstream Timeout
```

不得所有 Error 都返回：

```text
200
```

或：

```text
500
```

---

# 9. 业务失败不得返回 Fake Success

禁止：

```json
{
  "success": true
}
```

但实际：

```text
Database Write Failed
Payment Failed
Tool Failed
```

任何关键操作只有真正完成后：

才能返回成功。

---

# 10. Exception 不得被吞掉

禁止：

```java
try {
    ...
} catch (Exception e) {
}
```

禁止：

```python
try:
    ...
except Exception:
    pass
```

除非明确属于：

> 可安全忽略的非关键操作

并且有清楚理由。

---

# 11. Catch 必须有目的

Catch Exception 只能为了：

```text
Map Error
Add Context
Retry Safely
Compensate
Log
Convert to Domain Error
```

不得 Catch 后：

继续假装成功。

---

# 12. 不得 Catch Exception 过宽

优先处理具体：

```text
ResourceNotFoundException
DuplicateResourceException
ExternalServiceTimeoutException
```

避免所有层：

```text
catch Exception
```

无差别处理。

---

# 13. Global Exception Handler

Spring Boot 应统一使用：

```text
Global Exception Handler
```

处理：

```text
Validation
Business Exception
Security Exception
System Exception
```

不得每个 Controller：

自己写不同 Error Response。

---

# 14. Controller 不处理底层异常细节

Controller 不应：

```text
catch SQLException
catch HibernateException
```

并自行决定业务含义。

应该由：

```text
Application / Infrastructure Layer
↓
Exception Mapping
↓
Global Error Handler
```

统一转换。

---

# 15. Domain Exception

可预期业务失败：

应使用明确 Domain Exception。

例如：

```text
InsufficientStockException
InvalidInvoiceStatusException
RefundLimitExceededException
```

不要全部：

```text
RuntimeException("error")
```

---

# 16. Infrastructure Error 与 Business Error 分离

例如：

```text
Customer Not Found
```

是 Business / Resource Error。

```text
PostgreSQL Unavailable
```

是 Infrastructure Error。

两者不得映射成同一种错误。

---

# 17. Database Error

数据库内部错误：

不得原样返回用户。

禁止暴露：

```text
SQLSTATE
Table Name
Constraint Internal Name
SQL Statement
Database Host
Stack Trace
```

---

# 18. Database Constraint Error

已知 Constraint：

应转换成业务 Error。

例如：

```text
Unique Violation
↓
DUPLICATE_CUSTOMER_CODE
```

而不是：

```text
duplicate key value violates unique constraint...
```

---

# 19. Unknown Database Error

无法确定的 Database Error：

返回统一：

```text
INTERNAL_SERVER_ERROR
```

并记录内部诊断信息。

不要猜测业务原因。

---

# 20. Authentication Error

未认证：

返回：

```text
401
AUTHENTICATION_REQUIRED
```

Token Invalid / Expired：

可使用明确 Error Code。

不得返回：

```text
500
```

---

# 21. Authorization Error

无 Permission：

返回：

```text
403
ACCESS_DENIED
```

不得因为无权限：

返回成功空数据。

---

# 22. Tenant Error

Cross-Tenant Access：

必须安全失败。

根据 Security Policy：

使用：

```text
404
```

隐藏资源存在，

或：

```text
403
```

明确拒绝。

必须全系统一致。

---

# 23. Unknown Tenant Context

如果 Tenant 无法解析：

必须：

```text
DENY
```

不得：

```text
Use default tenant
Use first tenant
Return all
```

---

# 24. Resource Not Found

找不到 Resource：

使用明确：

```text
CUSTOMER_NOT_FOUND
INVOICE_NOT_FOUND
EMPLOYEE_NOT_FOUND
```

对于普通用户可使用统一用户提示，

但内部 Error Code 必须足够明确。

---

# 25. Conflict Error

例如：

```text
Duplicate Record
Already Processed
Version Conflict
Invalid Current State
```

应使用：

```text
409 Conflict
```

和具体 Error Code。

---

# 26. State Transition Error

非法状态转换：

必须明确：

```text
INVALID_STATE_TRANSITION
```

不得自动修正状态。

例如：

```text
DRAFT
→ COMPLETED
```

不合法时必须拒绝。

---

# 27. Money / Finance Error

金融 Error 必须明确：

```text
INVALID_AMOUNT
CURRENCY_MISMATCH
REFUND_LIMIT_EXCEEDED
EXCHANGE_RATE_MISSING
ACCOUNTING_PERIOD_CLOSED
```

不得静默：

```text
round
convert
change currency
```

解决错误。

---

# 28. Precision Error

如果金额无法安全转换：

必须失败。

禁止：

```text
truncate silently
```

或：

```text
float conversion
```

继续交易。

---

# 29. External Service Error

第三方错误必须转换成 AIOS Error。

例如：

```text
Payment Provider Timeout
↓
PAYMENT_PROVIDER_TIMEOUT
```

而不是直接返回 Provider 原始 Payload。

---

# 30. Third-Party Error 不可信

第三方返回：

```text
200
```

不代表业务一定成功。

必须验证：

```text
Provider Status
Reference
Amount
Currency
Expected Fields
```

---

# 31. Timeout

所有 External Call：

必须拥有合理 Timeout。

发生 Timeout：

必须明确区分：

```text
Connection Timeout
Read Timeout
Operation Timeout
```

如业务需要。

---

# 32. Timeout 不等于操作失败

尤其：

```text
Payment
Refund
External Write
```

出现 Timeout 时：

可能是：

```text
Request succeeded
Response lost
```

因此禁止立即重新执行。

必须先检查状态或使用 Idempotency。

---

# 33. Retry 原则

只有：

```text
Safe
Transient
Idempotent
```

的失败：

才适合 Retry。

---

# 34. 禁止所有 Error 自动 Retry

以下不得无脑 Retry：

```text
400
401
403
Validation Error
Business Rule Error
Invalid State
Permanent Failure
```

---

# 35. Retry 必须有限制

必须定义：

```text
Max Attempts
Delay
Backoff
Timeout
```

禁止：

```text
retry forever
```

---

# 36. Retry 必须避免重复副作用

以下特别注意：

```text
Payment
Refund
Order Creation
Webhook
Email
Agent Tool
```

写操作必须配合：

```text
Idempotency
```

---

# 37. Frontend Error Handling

Frontend 必须区分：

```text
Loading
Success
Validation Error
Business Error
Permission Error
Network Error
System Error
```

不得一个：

```text
catch
→ alert("Error")
```

处理所有情况。

---

# 38. Frontend 不得隐藏 API Error

禁止：

```typescript
catch {
  return [];
}
```

导致：

```text
Server Error
```

被显示成：

```text
No Data
```

---

# 39. Loading 不等于 Error

以下必须分开：

```text
Loading
Empty
Error
Permission Denied
```

不得混用。

---

# 40. Frontend 用户提示

用户提示必须：

```text
Clear
Relevant
Actionable
Non-technical
```

例如：

```text
Unable to save changes. Please try again.
```

而不是：

```text
AxiosError: Request failed with status 500
```

---

# 41. Field Error 应靠近字段

Form Validation：

必须将错误显示在相关 Field 附近。

不要所有 Error 只放一个 Toast。

---

# 42. Critical Error 不应只显示 Toast

重要失败：

例如：

```text
Payment Failed
Import Failed
Save Failed
```

不得只显示 3 秒 Toast 后消失。

必须保留清晰状态或结果。

---

# 43. Error 后不得清除用户输入

普通 Form 保存失败：

原则上保留用户已经输入的资料。

不得：

```text
API Error
↓
Reset entire form
```

---

# 44. Retry UI

适合重试的错误：

可以提供：

```text
Retry
```

但不可恢复 Business Error：

不应一直显示 Retry。

---

# 45. Permission UI

403：

应显示标准：

```text
Access Denied
```

不得：

```text
Loading forever
Blank page
No data
```

---

# 46. 404 UI

Resource 不存在：

显示统一：

```text
Not Found
```

不得白屏。

---

# 47. 500 UI

系统错误：

显示统一：

```text
Something went wrong
Reference ID
Retry if appropriate
```

不得显示 Stack Trace。

---

# 48. requestId

每个重要 Request：

应拥有：

```text
requestId
```

Error Response 应包含 Request ID。

方便：

```text
Frontend
Support
Logs
Backend
```

追踪。

---

# 49. Correlation ID

跨：

```text
Spring Boot
Python AI
Third Party
Worker
```

调用时：

应尽量传播：

```text
Correlation ID / Trace ID
```

---

# 50. Logging Error

Backend Error Log 应至少包含适当：

```text
requestId
tenantId
userId
endpoint
errorCode
exception type
```

根据 Security Policy 记录。

---

# 51. Log 不得包含 Secret

禁止记录：

```text
Password
Access Token
Refresh Token
API Key
Private Key
Database Password
Webhook Secret
```

---

# 52. Log 不得无脑记录 Request Body

尤其：

```text
Login
Payroll
Finance
Bank
Payment
Personal Data
```

不得完整记录。

---

# 53. Error Log Level

推荐概念：

```text
DEBUG
INFO
WARN
ERROR
```

必须根据严重程度使用。

---

# 54. Business Error 不一定是 ERROR Log

例如：

```text
Customer enters invalid input
```

不需要全部：

```text
ERROR
```

否则 Production Log 会充满噪音。

---

# 55. Security Error

以下应进入 Security Monitoring：

```text
Cross-Tenant Attempt
Repeated Access Denied
Privilege Escalation Attempt
Invalid Webhook Signature
Suspicious Login
```

---

# 56. Expected Error 与 Unexpected Error 分离

Expected：

```text
Validation
Not Found
Business Conflict
Permission Denied
```

Unexpected：

```text
NullPointerException
Database Failure
Programming Bug
Unknown Runtime Error
```

必须区分。

---

# 57. Unexpected Error 必须记录 Stack Trace

Backend Internal Log：

对于真正 Unexpected Error：

应记录足够 Stack Trace。

但：

> 不得返回给最终用户。

---

# 58. Error Context 必须保留

重新包装 Exception 时：

不得丢掉原始 Cause。

错误：

```java
throw new RuntimeException("failed");
```

正确原则：

保留：

```text
Original Cause
Business Context
```

供 Debug。

---

# 59. 不得 Log 后再重复无意义 Log

如果同一个 Exception：

每一层都：

```text
ERROR
```

会造成重复日志。

必须选择合适边界记录。

---

# 60. Error Mapping 必须集中

例如：

```text
Database Exception
↓
Application Exception
↓
API Error
```

应该有明确统一 Mapping。

不得每个 Module 随意转换。

---

# 61. Python AI Error

Python AI 必须区分：

```text
Model Error
Provider Error
Tool Error
Schema Error
Permission Error
RAG Error
Agent Runtime Error
```

---

# 62. AI Model Error

例如：

```text
Provider unavailable
Rate limited
Timeout
Invalid model output
```

必须清楚分类。

不得统一：

```text
AI failed
```

---

# 63. Invalid AI Output

Structured Output 验证失败：

应：

```text
Retry within limit
or
Fail safely
```

不得猜测：

```text
Amount
ID
Status
Permission
```

关键值。

---

# 64. Agent Tool Error

Tool 失败：

Agent 最终必须知道：

```text
Tool Failed
```

不得自行生成：

```text
Action completed successfully
```

---

# 65. Agent 不得 Fake Success

任何 Agent Action：

只有收到 Verified Tool Result：

才能告诉用户成功。

---

# 66. Agent Partial Failure

多步骤任务部分成功：

必须返回：

```text
What succeeded
What failed
What remains
```

不得声称全部完成。

---

# 67. Agent Error State

至少应概念区分：

```text
FAILED
PARTIALLY_COMPLETED
WAITING_FOR_USER
WAITING_FOR_APPROVAL
CANCELLED
```

不能所有异常都变：

```text
FAILED
```

如果实际需要等待用户。

---

# 68. Missing Information

Agent 缺少关键：

```text
Resource
Amount
Company
Target
```

时：

不得猜测。

应停止对应高风险执行。

---

# 69. Permission Error 对 Agent 同样适用

如果 Tool 返回：

```text
403
```

Agent 不得：

```text
Try another hidden endpoint
Use system account
Call direct database
```

绕过。

---

# 70. Wrong Tenant Error

Agent 发现 Tenant 不匹配：

必须立即停止。

不得自动：

```text
switch tenant
```

完成操作。

---

# 71. RAG Error

如果 Knowledge Retrieval 没有足够结果：

Agent 应明确：

```text
Insufficient source
```

不得编造业务事实。

---

# 72. AI Provider Fallback

如果使用 Fallback Model：

必须确保：

```text
Tool Capability
Structured Output
Security Requirement
```

仍然满足。

否则应失败。

---

# 73. Background Job Error

Job 必须记录：

```text
status
errorCode
attempt
lastErrorAt
```

等必要执行状态。

---

# 74. Job Retry

只有可恢复错误：

才进入 Retry。

Business Validation Error：

通常不应反复 Retry。

---

# 75. Job Dead Letter

如果未来引入 MQ：

多次失败 Message：

应进入受控：

```text
Dead Letter / Failed State
```

不得无限循环消费。

---

# 76. Scheduler Error

一个 Scheduled Job 失败：

不得无控制导致整个 Application Crash。

但也不得：

```text
catch and ignore
```

必须可观察。

---

# 77. Webhook Error

Webhook 必须区分：

```text
Invalid Signature
Invalid Payload
Duplicate Event
Temporary Processing Failure
Permanent Business Failure
```

---

# 78. Invalid Webhook Signature

必须拒绝。

不得 Retry 业务处理。

---

# 79. Duplicate Webhook

如果 Event 已处理：

应安全返回 Provider 可接受结果，

同时不得重复执行业务动作。

---

# 80. Webhook Processing Failure

如果 Provider 支持重试：

必须配合 Idempotency。

---

# 81. File Error

File 功能必须区分：

```text
FILE_TOO_LARGE
UNSUPPORTED_FILE_TYPE
FILE_NOT_FOUND
FILE_ACCESS_DENIED
FILE_SCAN_FAILED
```

等实际情况。

---

# 82. Upload Partial Failure

Multi-file Upload：

必须明确：

```text
哪些成功
哪些失败
```

不能整批显示模糊 Error。

---

# 83. Import Error

Import 必须能够区分：

```text
File Level Error
Row Level Error
Business Validation Error
Duplicate Error
```

---

# 84. Import Error Report

大型 Import：

应该能够告诉用户：

```text
Row
Field
Error Code
Message
```

方便修复。

---

# 85. Export Error

Export 失败：

必须保留 Job Failure 状态。

不得：

```text
generate empty file
```

伪装成功。

---

# 86. Transaction Error

数据库 Transaction 中任何必要步骤失败：

必须：

```text
Rollback
```

不得留下不符合业务定义的 Partial Data。

---

# 87. External Side Effect

如果：

```text
Database Rollback
```

但：

```text
Email / Third Party
```

已经执行，

必须依据架构处理补偿 / Audit。

不得假装全部 Rollback。

---

# 88. Concurrency Error

Optimistic Lock / Version Conflict：

应返回：

```text
VERSION_CONFLICT
409
```

让用户重新加载。

不得静默覆盖。

---

# 89. Deadlock Error

Database Deadlock：

可以有限 Retry。

但必须：

```text
Limit Retry
Record Error
Investigate if persistent
```

---

# 90. Rate Limit

达到系统限制：

返回：

```text
429
RATE_LIMIT_EXCEEDED
```

如适用提供：

```text
Retry-After
```

---

# 91. Feature Disabled

Feature 未启用：

不得返回：

```text
500
```

应使用明确：

```text
FEATURE_NOT_ENABLED
```

或系统统一 Error。

---

# 92. Subscription Error

例如：

```text
PLAN_LIMIT_REACHED
FEATURE_NOT_INCLUDED
USAGE_LIMIT_EXCEEDED
```

必须与 Permission Error 区分。

---

# 93. Permission 与 Plan Error 不得混淆

```text
403 Access Denied
```

不能代表：

```text
Tenant did not purchase feature
```

两者业务意义不同。

---

# 94. Error Message 不得包含技术细节

用户不需要知道：

```text
Hibernate
Axios
PostgreSQL
NullPointerException
Pydantic
```

内部技术名称。

---

# 95. Error Message 不得误导

禁止：

```text
Network error
```

其实是：

```text
Permission denied
```

必须尽量准确。

---

# 96. Error Message 不应过度承诺

如果不确定是否可恢复：

不要：

```text
Try again and it will work.
```

可以：

```text
Please try again.
```

或提供其他操作。

---

# 97. Error Localization

`error.code`：

固定英文机器码。

用户显示文案：

可以由 Frontend Localization。

不得翻译：

```text
CUSTOMER_NOT_FOUND
```

这个 Canonical Code。

---

# 98. Error Documentation

重要 Domain Error 应可以查到：

```text
Error Code
Meaning
HTTP Status
When It Happens
```

无需写长篇文档。

---

# 99. Error Code 不得随意 Rename

Error Code 属于 Contract。

修改：

```text
CUSTOMER_DUPLICATE
→ DUPLICATE_CUSTOMER
```

可能影响 Frontend / Integration。

必须检查使用方。

---

# 100. Error Code 不得重复不同含义

同一个：

```text
INVALID_STATUS
```

不能：

CRM 是 A 意义，

Finance 是完全不同 B 意义。

必要时使用更明确 Domain Error。

---

# 101. Error Code 不得过度细碎

也不要每一种技术 Exception：

都变成 Public Error Code。

Public Error Code 应表达：

> 调用方真正需要理解的错误。

---

# 102. Internal Error Code

内部 Observability 可以拥有更细技术分类。

但 Public API 不必暴露所有内部细节。

---

# 103. Error Boundary

React 应在合理层级设置：

```text
Error Boundary
```

防止单一 UI Crash：

导致整个 Application 白屏。

---

# 104. Error Boundary 不代替普通错误处理

API Validation / Business Error：

不应靠 React Error Boundary 处理。

Error Boundary 主要处理：

```text
Unexpected Rendering Error
```

---

# 105. Graceful Degradation

非核心服务失败时：

如果业务允许：

系统应尽量：

```text
核心功能继续
↓
局部功能显示 unavailable
```

例如：

AI Insight 失败：

不应导致 Customer Page 整体无法查看。

---

# 106. AI Failure 不应拖垮核心业务

例如：

```text
Python AI Service unavailable
```

如果当前操作并非必须依赖 AI：

Spring Boot 核心 CRUD 应继续可用。

---

# 107. Critical Dependency

如果当前业务必须依赖：

```text
Payment Provider
Database
```

失败：

必须明确失败，

不能继续写入假状态。

---

# 108. Fail Open / Fail Closed

Security / Permission / Tenant：

必须：

```text
Fail Closed
```

普通非安全辅助功能：

可根据业务决定 Graceful Degradation。

---

# 109. Security Error 禁止 Fallback Allow

例如 Permission Service Error：

禁止：

```text
permission service unavailable
→ allow user
```

必须拒绝。

---

# 110. Tenant Resolver Error 禁止 Fallback

禁止：

```text
tenant missing
→ default tenant
```

---

# 111. Audit Failure

高风险业务 Audit 失败：

必须根据架构明确：

```text
Fail Action
```

或：

```text
Reliable recovery mechanism
```

不得永远静默忽略。

---

# 112. Notification Failure

如果 Notification 只是业务 Side Effect：

核心 Transaction 是否回滚：

必须由 Domain Rule 明确。

Cursor 不得自行决定。

---

# 113. Error 与 Transaction Boundary

不能为了捕获 Error：

在错误层次：

```text
commit partial result
```

必须遵守正式 Transaction Boundary。

---

# 114. Error Recovery

恢复机制必须根据错误类型决定：

```text
Validation → User fixes input
Conflict → Reload / Resolve
Timeout → Retry / Status Check
Dependency Failure → Retry later
Permission → Request Access
System Error → Support / Retry
```

---

# 115. Compensation

如果业务需要补偿：

必须使用正式：

```text
Compensating Action
```

不得由 Agent / Cursor 临时猜测逆操作。

---

# 116. Circuit Breaker

未来外部依赖不稳定时：

可以使用：

```text
Circuit Breaker
```

但只有实际需要时引入。

不得所有 API 默认复杂化。

---

# 117. Error Monitoring

Production 应能够监控：

```text
Error Rate
Error Code Distribution
Unhandled Exception
External Failure
Timeout
Agent Failure
```

---

# 118. Error Spike

如果某版本上线后：

```text
500 rate
403 rate
payment failures
agent tool failures
```

明显异常，

应触发调查或 Deployment Rollback 判断。

---

# 119. Alert

不是所有 Error 都需要 Alert。

重点 Alert：

```text
Critical Service Down
Cross-Tenant Error
Payment Failure Spike
Database Failure
Security Failure
Repeated Agent Write Failure
```

# 120. Cursor Debug Error 顺序


# 121. 禁止根据表面错误乱改

不得直接：


必须检查：


# 122. 禁止根据 500 乱加 Try/Catch

不能第一反应：


---

# 123. 禁止返回空值隐藏错误

错误：

```java

    return null;
}
```

或：

```typescript
catch {
  return [];
}
```

如果这会掩盖真实失败。

# 124. 禁止默认值掩盖错误


```text

```

```text
Tenant missing

```

# 132. Error Handling 禁止事项

Cursor 明确禁止：

* 擅自 Catch 后忽略错误

* 擅自把 Error 返回成空列表
* 擅自把 Error 返回成 null
* 擅自所有错误都返回 500
* 擅自所有失败都返回 200
* 擅自把 Database Error 原样暴露
* 擅自暴露 Stack Trace
* 擅自暴露 Secret
* 擅自根据 Error Message 做业务判断
* 擅自用 Generic Error 代替明确 Business Error
* 擅自无限 Retry
* 擅自 Retry 非幂等高风险写操作
* 擅自通过默认值隐藏错误
* 擅自通过关闭 Permission 修 403
* 擅自通过 Catch 修 500
* 擅自把 Loading 当 Error
* 擅自把 Error 当 Empty
* 擅自把 No Permission 当 No Data
* 擅自让 Agent 在 Tool Failure 后报告成功
* 擅自让 Agent 遇到 Permission Error 尝试绕过
* 擅自让 Security Error Fail Open
* 擅自修改稳定 Error Code 不检查调用方

# 140. Error Handling 最终原则

AIOS Error Handling 必须坚持：

> Error 不能被隐藏。

> Failure 不能伪装成 Success。

> Error Code 给系统判断，Message 给用户理解。

> Frontend 不得依赖 Error Message 做业务逻辑。

> Validation、Business、Security、Infrastructure Error 必须区分。

> Database Error 不得直接暴露给用户。

> Stack Trace 不得返回用户。

> Secret 不得进入 Error Response 或 Log。

> Tenant / Permission / Security Failure 必须 Fail Closed。

> Missing Tenant 不能使用默认 Tenant。

> Missing Currency、Rate、Amount 不能自行猜默认值。

> Timeout 不一定代表写操作失败。

> 高风险写操作 Retry 必须先处理 Idempotency。

> Error 不得通过返回 null、[] 或默认值隐藏。

> Loading、Empty、Error、No Permission 是四种不同状态。

> AI Tool 失败后 Agent 不得报告成功。

> Agent 不得因为 Permission Error 尝试其他方式绕过系统。

> External Provider 永远是不可信依赖。

> Error 必须能够通过 requestId / traceId 被追踪。

> Cursor 遇到错误必须先找 Root Cause，不得用 Try/Catch 掩盖问题。

> AIOS 的目标不是“没有错误”，而是任何错误发生时都能安全失败、清楚表达、快速定位并正确恢复。
