# AIOS Performance Standard

> 文件编号：15
> 文件名称：Performance Standard
> 适用范围：AIOS Frontend、Backend、API、PostgreSQL、AI Service、Agent、Background Job、Integration
> 适用对象：Cursor、AI Agent、Frontend Developer、Backend Developer、AI Developer、Database Developer
> 前置规则：必须遵守《01 产品原则》至《14 Error Handling Standard》
> 核心目标：响应稳定、资源合理、可扩展、可观测、避免无依据优化

---

# 1. 核心原则

AIOS Performance 必须遵守：

```text
Correctness First
Measure Before Optimize
Optimize Bottlenecks
Avoid Premature Optimization
Protect Scalability
Control Resource Usage
```

优先级：

```text
Correctness
↓
Security
↓
Tenant Isolation
↓
Data Integrity
↓
Stability
↓
Performance
```

禁止为了性能牺牲正确性。

---

# 2. 性能优化必须有证据

Cursor 不得因为：

> “这个可能比较慢”

就直接：

```text
增加 Cache
增加 Thread
增加 Index
增加 Queue
Denormalize Database
改成 Microservice
```

必须先确认：

```text
Where is slow?
Why is slow?
How slow?
What causes it?
```

---

# 3. 优化流程

标准流程：

```text
Measure
↓
Identify Bottleneck
↓
Find Root Cause
↓
Apply Minimum Optimization
↓
Measure Again
↓
Regression Check
```

禁止：

```text
感觉慢
↓
重构整个系统
```

---

# 4. Performance 不得改变业务结果

优化前后：

```text
Amount
Permission
Tenant Scope
Status
Calculation
Business Result
```

必须保持一致。

---

# 5. 不得通过减少安全检查提升性能

严禁：

```text
Remove Permission Check
Remove Tenant Filter
Skip Validation
Skip Audit
```

来提高速度。

---

# 6. Frontend Performance

React 页面应避免：

```text
Unnecessary Re-render
Large Initial Bundle
Repeated API Call
Huge DOM
Rendering Thousands of Rows
```

---

# 7. React Re-render

Cursor 修改 Component 前：

应先判断是否真的存在 Re-render 问题。

不得所有 Component 无脑加入：

```text
memo
useMemo
useCallback
```

过度优化。

---

# 8. useMemo / useCallback

只有在以下情况使用：

```text
Expensive Calculation
Stable Reference Required
Measured Re-render Problem
```

不得为了“最佳实践”到处添加。

---

# 9. State 必须放在正确层级

不要把所有 State 放到：

```text
Global State
```

如果只属于一个 Component / Page。

Global State 越大：

越容易造成：

```text
Unnecessary Update
Complex Dependency
```

---

# 10. API Request 去重

同一页面不得因为多个 Component：

重复请求完全相同数据。

应合理：

```text
Reuse
Cache
Deduplicate
```

但必须遵循项目现有数据获取方案。

---

# 11. Frontend 不得无限请求 API

禁止：

```text
render
→ request
→ state update
→ render
→ request
```

形成 Request Loop。

---

# 12. Search 防抖

用户输入 Search：

如每个字符都会请求 Backend，

应根据 UX 考虑：

```text
Debounce
```

避免大量无意义 API 请求。

---

# 13. Pagination

大量数据必须分页。

禁止：

```text
Load all customers
Load all invoices
Load all audit logs
```

然后 Frontend 自己分页。

---

# 14. Virtualization

只有真正需要显示大量 Row：

才考虑：

```text
Virtualized List / Table
```

普通几十条数据不需要过度复杂化。

---

# 15. Lazy Loading

大型页面 / Module：

可合理使用：

```text
Lazy Loading
Code Splitting
```

降低 Initial Bundle。

但不得把非常小的 Component 全部拆成异步加载。

---

# 16. Bundle Size

新增大型 Frontend Dependency 前必须检查：

```text
是否真的需要？
现有项目是否已有同类能力？
Bundle Impact 多大？
```

不得为一个小功能引入巨大 Library。

---

# 17. Image Performance

图片必须考虑：

```text
Correct Size
Compression
Lazy Loading
Responsive Size
```

不得把：

```text
5000px image
```

直接用于：

```text
200px thumbnail
```

---

# 18. Backend Performance

Spring Boot 应避免：

```text
N+1 Query
Unbounded Query
Long Transaction
Repeated Database Query
Blocking External Call
```

---

# 19. Controller 不负责重计算

复杂计算：

应由适当 Service / Domain 层处理。

避免 Controller：

```text
Query
Loop
Query
Loop
Query
```

自行处理大量业务逻辑。

---

# 20. N+1 Query

必须重点检查：

```text
List API
Dashboard
Report
Nested Response
```

例如：

```text
1 query orders
+
100 queries customers
```

属于典型问题。

---

# 21. N+1 解决方式

根据 Use Case 使用：

```text
Join
Projection
Batch Fetch
Explicit Fetch
```

不得简单把所有 Relationship：

```text
EAGER
```

---

# 22. List API 必须限制数据量

禁止：

```text
findAll()
```

用于持续增长业务数据。

例如：

```text
Customer
Invoice
Audit
Transaction
Employee
```

---

# 23. API Response 只返回必要字段

List API：

不得返回完整 Detail Entity。

例如 Customer List：

只返回当前页面需要字段。

---

# 24. Payload Size

API 应避免：

```text
Huge JSON
Deep Nested Object
Repeated Data
```

特别是：

```text
Dashboard
List
Mobile / Slow Network
```

---

# 25. Backend Mapping

大量 Entity → DTO Mapping：

如果成为真实瓶颈才优化。

不得因为 Mapping 多几行代码：

直接返回 Entity。

---

# 26. Database Query 是重点性能区域

PostgreSQL Query 优化必须基于：

```text
EXPLAIN
EXPLAIN ANALYZE
Query Timing
Real Data Volume
```

不得凭感觉。

---

# 27. Index 必须服务 Query Pattern

常见评估字段：

```text
tenant_id
company_id
status
created_at
foreign key
business number
```

但不能全部无脑建 Index。

---

# 28. Composite Index

Composite Index 顺序必须根据：

```text
WHERE
JOIN
ORDER BY
Selectivity
```

设计。

不得随机排列字段。

---

# 29. 重复 Index 禁止

新增 Index 前：

必须检查：

```text
Existing Index
Unique Constraint
Composite Index
```

是否已经覆盖。

---

# 30. Index 不是越多越好

Index 会增加：

```text
INSERT Cost
UPDATE Cost
Storage
Maintenance
```

所以必须平衡 Read / Write。

---

# 31. Query 只读取需要字段

避免普通 List：

```sql
SELECT *
```

读取巨大 Row。

尤其存在：

```text
JSONB
Large Text
Sensitive Fields
```

时。

---

# 32. Query Filter 必须进入 Database

禁止：

```text
Load 100,000 rows
↓
Java filter tenant
↓
Java filter status
```

应在 SQL / Repository Query：

完成过滤。

---

# 33. Permission Filter 必须进入 Query

Data Scope：

例如：

```text
OWN
COMPANY
TENANT
```

应尽量转换成数据库条件。

不得加载大量数据后再 Permission Filter。

---

# 34. Pagination 与 Permission 顺序

必须：

```text
Permission Filter
↓
Database Filter
↓
Pagination
```

禁止：

```text
Pagination
↓
Permission Filter
```

导致页面数据量错误。

---

# 35. Sort 必须考虑 Index

高频：

```text
ORDER BY created_at DESC
```

等 Query：

应结合 Filter Pattern 评估 Index。

---

# 36. Offset Pagination

普通后台页面：

可以使用 Offset Pagination。

超大型：

```text
Audit
Event
Activity
```

如出现 Deep Page 性能问题，

再考虑：

```text
Keyset / Cursor Pagination
```

---

# 37. Database Connection

必须使用 Connection Pool。

不得每个 Request：

自行建立 PostgreSQL Connection。

---

# 38. Connection Pool 不得无脑调大

禁止：

```text
10
→
500
```

解决慢的问题。

必须分析：

```text
DB Capacity
Application Instances
Query Duration
Workload
```

---

# 39. Long Transaction

必须避免：

```text
Open Transaction
↓
Call AI
↓
Call External API
↓
Wait 30 seconds
↓
Commit
```

长 Transaction 会占用：

```text
Connection
Lock
MVCC Resources
```

---

# 40. Transaction Scope

Transaction 应只覆盖：

> 必须保持一致性的数据库操作。

不要覆盖整个用户流程。

---

# 41. Lock

Pessimistic Lock：

只能用于确实需要的并发场景。

不得所有 Update：

都加 Lock。

---

# 42. Slow Query

发现 Slow Query：

必须先检查：

```text
Execution Plan
Rows Scanned
Index
Join
Sort
Filter
Lock
```

再决定方案。

---

# 43. Dashboard Performance

Dashboard 不应每次打开：

执行几十个大型 Aggregate Query。

如果真实出现性能问题：

可以逐步考虑：

```text
Pre-Aggregation
Cache
Read Model
Analytics Layer
```

---

# 44. Report Performance

大型 Report：

不应阻塞普通 Transaction API。

可以根据规模：

```text
Async Job
Background Processing
Precomputed Data
```

---

# 45. Export Performance

大量 Export：

应使用：

```text
Async Job
Pagination / Batch
Streaming where appropriate
```

不得一次把全部数据加载进 Memory。

---

# 46. Import Performance

大型 Import：

必须考虑：

```text
Batch
Chunk
Validation
Transaction Size
Memory Usage
```

---

# 47. Memory Usage

Backend / Python：

禁止：

```text
load entire huge file into memory
```

如果可以通过：

```text
Stream
Chunk
Batch
```

处理。

---

# 48. Batch Processing

Batch Size 必须合理。

过小：

```text
Too many DB calls
```

过大：

```text
Memory / Lock / Transaction pressure
```

必须根据实际量调整。

---

# 49. Cache 使用原则

Cache 只能用于：

```text
Repeated Read
Expensive Calculation
Relatively Stable Data
```

不得看到慢：

就加 Cache。

---

# 50. Cache 不得成为 Source of Truth

核心业务事实：

仍以：

```text
PostgreSQL
```

为准。

Cache 只能：

```text
Accelerate Read
```

---

# 51. Cache Key 必须有 Scope

Tenant Data Cache 必须考虑：

```text
tenantId
companyId
userId
resource
```

根据数据范围。

禁止：

```text
customer:list
```

全 Tenant 共用。

---

# 52. Cache Invalidation

使用 Cache 前必须回答：

```text
什么时候失效？
谁负责失效？
数据允许旧多久？
```

如果回答不了：

不要随便加 Cache。

---

# 53. Permission Cache

Permission Cache：

必须在：

```text
Role Change
Permission Revocation
User Disable
```

后及时失效。

性能不能高于安全。

---

# 54. Financial Data Cache

Finance、Balance、Payment 等：

使用 Cache 必须非常谨慎。

不得因为 Cache：

显示错误金额或旧状态。

---

# 55. AI Performance

AI Layer 必须控制：

```text
Latency
Token Usage
Context Size
Model Cost
Tool Calls
Retries
```

---

# 56. AI 不应每次发送全部上下文

禁止：

```text
Entire conversation
Entire tenant knowledge base
Entire customer history
```

每次全部发送给模型。

应只提供当前任务必要 Context。

---

# 57. RAG 优于塞完整文档

大量 Knowledge：

优先：

```text
Retrieve Relevant Content
↓
Send Relevant Context
```

而不是：

```text
Send all documents to LLM
```

---

# 58. RAG Retrieval 数量必须受控

不能：

```text
retrieve 500 chunks
```

然后全部塞进 Prompt。

应根据任务选择合理数量。

---

# 59. Agent Tool Call 数量必须受控

Agent 不应：

```text
Call same search tool 20 times
```

没有必要地循环。

必须有：

```text
maxSteps
retryLimit
```

---

# 60. Agent Retry

Retry 会直接增加：

```text
Latency
Cost
External Load
```

必须只对合理错误 Retry。

---

# 61. Agent Context

长 Agent Run：

可以使用：

```text
Structured State
Summary
Relevant Memory
```

而不是无限累积全部历史。

---

# 62. Agent Memory 查询

Memory Retrieval：

必须：

```text
Scoped
Relevant
Limited
```

不能每次扫描全部 Memory。

---

# 63. Model Selection

Agent 不应所有任务都使用：

> 最昂贵 / 最慢模型。

应根据：

```text
Task Complexity
Risk
Latency
Cost
Capability
```

选择。

具体 Model 由 AI Configuration 管理。

---

# 64. High-Risk Action 不得为了速度省略确认

Payment、Refund、Permission Change 等：

即使 Confirmation 增加一步延迟，

也不得为了更快自动执行。

---

# 65. AI Streaming

Chat / Copilot：

如真实需要改善感知速度，

可以使用：

```text
Streaming
```

但 Streaming：

不等于实际计算更快。

---

# 66. Perceived Performance

Frontend 可以通过：

```text
Skeleton
Progress
Streaming
Optimistic UI
```

改善体验。

但不得伪造业务成功。

---

# 67. Optimistic UI

只有低风险、可恢复 Action：

才考虑 Optimistic Update。

例如部分：

```text
UI preference
Low-risk interaction
```

---

# 68. 高风险业务禁止假 Optimistic Success

Payment、Refund、Approval、Inventory：

不得先显示：

```text
Success
```

再等待 Backend。

必须等待真实结果。

---

# 69. Third-Party API Performance

External Call 必须设置：

```text
Connection Timeout
Read Timeout
```

避免请求无限挂起。

---

# 70. 第三方慢不能拖垮整个系统

非核心 Dependency：

应根据架构使用：

```text
Async
Timeout
Graceful Degradation
```

避免整个页面被阻塞。

---

# 71. AI Service Failure 不应影响非 AI 核心业务

如果：

```text
AI Insights
```

失败，

普通 Customer / Sales CRUD：

应继续可用，

只要它们没有必要依赖 AI。

---

# 72. Async Processing

适合异步：

```text
Large Report
Import
Export
Email
AI Document Processing
Heavy Analytics
```

不适合异步：

```text
用户立即需要知道成功与否的关键 Validation
```

---

# 73. 不能为了性能把所有东西异步化

Async 会增加：

```text
Complexity
Eventual Consistency
Retry
Monitoring
```

只有真实需要才使用。

---

# 74. Background Job

Background Job 必须：

```text
Bounded
Observable
Retry Controlled
```

不得无限占用 Worker。

---

# 75. Worker Concurrency

提高 Worker 数量前：

必须检查：

```text
Database Capacity
External API Limit
Memory
CPU
```

不得无脑提高并发。

---

# 76. Scheduler

Scheduled Job 不得一次处理全部 Tenant 大量数据。

可根据规模：

```text
Batch
Tenant-by-Tenant
Pagination
```

处理。

---

# 77. Multi-Tenant Performance

任何 Tenant 的重负载：

不应轻易拖垮全部 Tenant。

未来需要考虑：

```text
Rate Limit
Quota
Job Isolation
Resource Control
```

但根据实际规模逐步实现。

---

# 78. Noisy Neighbor

高用量 Tenant：

不得无限占用：

```text
AI
Export
Report
API
Worker
```

系统资源。

---

# 79. Rate Limit

Rate Limit 除了 Security：

也属于 Performance Protection。

重点：

```text
AI
Search
Export
Public API
Expensive Report
```

---

# 80. Timeout

必须在合理层级拥有 Timeout：

```text
Frontend Request
Backend External Call
Database Query where needed
AI Call
Background Job
```

不得无限等待。

---

# 81. Timeout 必须基于真实业务

不能所有 Endpoint：

统一：

```text
5 seconds
```

也不能：

```text
5 minutes
```

应按 Use Case。

---

# 82. Performance Monitoring

Production 应逐步监控：

```text
Latency
Throughput
Error Rate
CPU
Memory
Database Query
Connection Pool
External API
AI Latency
```

---

# 83. API Latency

建议至少能够观察：

```text
Average
P95
P99
```

而不是只看平均值。

---

# 84. Slow Endpoint

必须能够识别：

```text
Which Endpoint
Which Tenant
Duration
Dependency
```

方便定位 Bottleneck。

---

# 85. Performance Log 不得泄露敏感数据

不得为了 Debug：

记录完整：

```text
Customer Payload
Password
Token
Financial Data
```

---

# 86. Database Metrics

应逐步能够监控：

```text
Slow Queries
Connections
Locks
Storage
Index Usage
Query Duration
```

---

# 87. AI Metrics

Agent / AI 应逐步监控：

```text
Model Latency
Tool Latency
Token Usage
Retries
Cost
Failure Rate
```

---

# 88. Performance Regression

修改以下 Shared Component 时：

必须注意性能回归：

```text
API Client
Permission Engine
Tenant Resolver
Global Search
Dashboard
Shared Table
Agent Runtime
Database Base Query
```

---

# 89. Performance Test

不是所有 Feature 都需要 Load Test。

重点：

```text
Large Table
Search
Dashboard
Report
Import
Export
AI
Public API
```

在需要时进行。

---

# 90. 测试必须接近真实规模

只有：

```text
10 rows
```

测试通过，

不能证明：

```text
1,000,000 rows
```

场景性能正常。

高数据量模块应使用合理规模测试数据。

---

# 91. Benchmark 必须可重复

性能比较必须保持：

```text
Same Environment
Same Data
Same Query
Same Conditions
```

否则数字没有意义。

---

# 92. 优化必须比较 Before / After

应该能够说明：

```text
Before
↓
Change
↓
After
```

例如：

```text
P95 2.5s
→ query optimized
→ P95 700ms
```

而不是：

> 应该更快了。

---

# 93. Performance Target

项目可以逐步制定：

```text
API P95
Page Load
AI First Token
Report Time
```

等目标。

Cursor 不得自行发明全系统 SLA。

---

# 94. SLA / SLO

正式：

```text
Availability
Latency
Throughput
```

目标属于产品 / Infrastructure 决策。

不是普通代码任务自行决定。

---

# 95. Premature Optimization

禁止项目早期：

```text
Sharding
Database per module
Distributed Cache everywhere
Microservices
Event everything
Kubernetes
```

只因为：

> 未来可能很多用户。

---

# 96. Scalability Awareness

虽然不提前复杂化，

但设计不得明显阻止未来扩展。

例如禁止：

```text
Load all records
Store session only in local memory
Store files only on server local disk
```

作为长期核心设计。

---

# 97. Horizontal Scaling

Spring Boot / Python 服务应尽量：

```text
Stateless
```

便于未来增加 Instance。

---

# 98. Local Memory Cache

Instance Local Cache：

只能用于允许不同 Instance 不完全同步的数据。

不得保存：

```text
Critical Shared Business State
```

作为唯一来源。

---

# 99. Local File

不得把核心上传文件长期依赖：

```text
local server disk
```

否则多实例和 Deployment 会出现问题。

---

# 100. Performance 与 Maintainability

禁止为了减少：

```text
几毫秒
```

引入巨大复杂度。

优化收益必须值得维护成本。

---

# 101. Clever Code

禁止为了性能写：

```text
难以理解
难以测试
难以维护
```

的技巧代码，

除非有明确性能证据与 Documentation。

---

# 102. Duplicate Logic 不属于优化

不要为了避免函数调用：

复制 Business Logic。

可维护性和正确性优先。

---

# 103. Denormalization

只有：

```text
Measured Performance Need
Historical Snapshot
Read Model
```

等明确理由：

才 Denormalize。

不得因为 Join 多：

就复制数据。

---

# 104. Materialized View

只有真实 Reporting / Analytics 瓶颈：

才使用。

必须定义：

```text
Refresh Strategy
Staleness
```

---

# 105. Database Partition

只有真实：

```text
Large Data
Retention
Query Pattern
```

需求才引入。

不得所有 Table 默认 Partition。

---

# 106. Sharding

属于重大 Architecture Decision。

Cursor 明确禁止自行引入。

---

# 107. Read Replica

未来读取压力大时可以考虑。

但必须考虑：

```text
Replication Lag
Strong Consistency Requirement
```

不能对 Payment 刚完成就从旧 Replica 读错误状态。

---

# 108. Data Warehouse

大型 Analytics：

未来可以从 Operational PostgreSQL：

转向：

```text
Data Warehouse
```

但不得因为报表慢就立刻改变整个数据架构。

---

# 109. Error Handling 不得为性能删除

remove timeout

---

# 111. Audit Performance

```text

Storage
Async Strategy where safe
```

而不是移除。

# 144. Performance 最终原则

AIOS Performance 必须坚持：

> Correctness First，Performance Second。

> 没有 Measurement，就不要声称存在 Bottleneck。

> 没有 Before / After，就不要声称优化成功。

> 优化真实 Bottleneck，而不是优化猜测。

> Database Query、Payload、N+1、Pagination 是优先检查对象。

> Cache 是优化工具，不是 Source of Truth。

> Index 必须服务真实 Query Pattern。

> Connection Pool 不是越大越好。

> Worker Concurrency 不是越高越好。

> Async 不代表一定更快。

> Microservices 不代表一定更快。

> AI Context 不是越多越好。

> Agent Tool Call 不是越多越智能。

> RAG Retrieval 不是越多越准确。

> 高风险业务不得为了感知速度伪造成功。

> Permission、Tenant、Validation、Audit 不能为了性能被绕过。

> 当前阶段优先使用简单、可靠、可测量的性能优化。

> Cursor 不得为了未来可能的规模提前复杂化 AIOS。

> AIOS Performance 的目标不是追求理论最快，而是在正确、安全、稳定的前提下保持足够快并能够持续扩展。
