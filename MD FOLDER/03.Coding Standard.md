# AIOS 开发与编码标准

> 文件编号：03
> 文件名称：开发与编码标准
> 适用范围：AIOS 全系统
> 适用对象：Cursor、AI Agent、开发人员、代码生成工具
> 前置规则：必须遵守《01 产品原则》《02 系统架构标准》
> 核心目标：代码统一、可读、可维护、可测试、安全、稳定、低耦合、可持续扩展

---

# 1. 文件目的

本文件定义 AIOS 的开发与编码行为标准。

本文件不仅约束：

* 代码格式
* 命名方式
* 文件结构

同时约束 Cursor 在开发过程中的：

* 阅读代码方式
* 修改代码方式
* 新增代码方式
* 重构方式
* Debug 方式
* Dependency 使用方式
* Error Handling
* Logging
* Validation
* Testing
* Security
* Code Review 思维

Cursor 不得仅以：

> “代码能运行”

作为完成标准。

正确标准应为：

> **代码正确 + 架构正确 + 数据正确 + 权限正确 + 可维护 + 不破坏现有功能。**

---

# 2. 开发总原则

所有代码必须遵守：

```text
Readable
Predictable
Maintainable
Testable
Secure
Consistent
Minimal
Explicit
```

优先级：

```text
正确性
↓
安全性
↓
可维护性
↓
一致性
↓
性能
↓
代码简短
```

不得为了少写几行代码牺牲可读性。

---

# 3. Cursor 执行任务前必须先理解

Cursor 收到开发任务后，不得立即修改代码。

必须先检查：

1. 当前功能属于哪个 Module。
2. 当前代码使用什么 Pattern。
3. 是否已有类似实现。
4. 是否已有可复用 Component / Service / Utility。
5. 是否涉及 Tenant。
6. 是否涉及 Permission。
7. 是否涉及 Database。
8. 是否涉及 Business Rule。
9. 是否涉及 API Contract。
10. 是否影响其他 Module。
11. 是否需要 Migration。
12. 是否需要 Test。

执行顺序：

```text
Read
↓
Understand
↓
Search Existing Implementation
↓
Determine Impact
↓
Modify
↓
Validate
```

---

# 4. 禁止盲目修改

Cursor 禁止：

* 只打开一个文件就判断整个逻辑
* 没有检查调用链就修改函数
* 没有检查使用方就修改 Public API
* 没有检查 Database Schema 就修改 Entity
* 没有检查 Permission 就增加敏感功能
* 没有检查 Tenant Scope 就增加 Query
* 没有检查现有实现就创建重复代码

---

# 5. 最小必要修改原则

任何任务必须遵守：

> Minimum Necessary Change

用户要求修复：

```text
Bug A
```

只能修改完成 Bug A 所必须的范围。

禁止顺便：

* 重写页面
* 重构整个 Module
* 修改无关 API
* 改数据库结构
* 更换 Library
* 改 UI 风格
* 改 Business Rule
* 删除现有功能

除非这些修改是完成任务所必须。

---

# 6. 不允许擅自重构

Cursor 不能因为：

> “这个写法不够漂亮”

就擅自重构正在正常运行的代码。

允许重构的情况：

1. 用户明确要求。
2. 当前代码阻止需求实现。
3. 存在明确 Bug。
4. 存在明显 Security Risk。
5. 存在严重重复代码。
6. 当前结构已经无法维护。

即使需要重构：

也必须限制在必要范围。

---

# 7. 保持现有项目风格

如果项目已经存在：

* Naming Pattern
* Folder Structure
* Error Pattern
* API Pattern
* DTO Pattern
* Service Pattern
* Component Pattern
* State Management Pattern

Cursor 必须优先遵循现有规范。

禁止每次新增功能都创造一种新写法。

---

# 8. 不允许重复实现

创建新代码前必须搜索是否已有：

```text
Component
Hook
Service
Repository
Utility
Mapper
DTO
Type
Enum
Constant
Validator
API Client
Permission
```

存在可复用能力时：

优先复用。

禁止出现：

```text
UserService
UserServiceV2
NewUserService
NewUserService2
```

---

# 9. 代码必须清楚表达意图

代码应该让开发人员能够快速理解：

> 这段代码为什么存在。

禁止使用模糊名称：

```text
data
obj
temp
xxx
test
abc
info
value1
value2
handleThing
doStuff
```

除非作用域非常小且语义明确。

---

# 10. 命名原则

名称必须表达：

```text
What it is
```

或：

```text
What it does
```

例如：

正确：

```text
customerId
salesOrder
calculateTotalAmount
isPaymentCompleted
findActiveEmployees
```

不推荐：

```text
id2
thing
calc
processData
check
```

---

# 11. Boolean 命名

Boolean 推荐使用：

```text
is
has
can
should
was
```

例如：

```text
isActive
hasPermission
canApprove
shouldNotify
```

禁止模糊：

```text
activeFlag
statusCheck
permissionValue
```

---

# 12. Collection 命名

Collection 使用复数。

例如：

```text
customers
orders
employees
permissions
```

禁止：

```text
customerListData
array1
items2
```

除非确有特定含义。

---

# 13. Function 命名

函数名称必须表达动作。

例如：

```text
createCustomer
updateEmployee
calculateInvoiceTotal
validateStockAvailability
sendNotification
```

查询类函数：

```text
get
find
load
search
exists
```

判断类：

```text
is
has
can
should
```

---

# 14. Class 命名

Class 使用 PascalCase。

例如：

```text
SalesOrderService
CustomerController
EmployeeRepository
InvoiceResponse
```

---

# 15. TypeScript 命名

Type / Interface 使用 PascalCase。

例如：

```text
User
Customer
SalesOrder
CreateCustomerRequest
```

禁止：

```text
ICustomer
IUser
```

除非项目现有规范明确如此。

---

# 16. 常量命名

真正全局常量使用：

```text
UPPER_SNAKE_CASE
```

例如：

```text
DEFAULT_PAGE_SIZE
MAX_UPLOAD_SIZE
```

不得把所有变量都写成常量形式。

---

# 17. **文件命名必须统一**

同类文件必须使用统一命名方式。

例如 Frontend：

```text
UserList.tsx
UserForm.tsx
useUsers.ts
userService.ts
user.types.ts
```

或者全部采用项目当前标准。

不得：

```text
UserList.tsx
user_form.tsx
USERservice.ts
usersType.ts
```

混合使用。

---

# 18. 禁止巨大文件

一个文件不应该承载过多职责。

当文件同时负责：

* UI
* API
* Calculation
* Validation
* Permission
* State
* Formatting

说明职责可能过多。

应合理拆分。

但不得为了追求小文件而过度拆分。

---

# 19. 禁止巨大函数

函数必须保持单一目的。

如果一个函数同时：

```text
Validate
Save
Calculate
Send Email
Write Audit
Call Third Party
```

应评估是否拆分职责。

---

# 20. 单一职责原则

Class / Function / Component 应尽量只有一个主要职责。

原则：

> 一个修改原因，对应一个职责。

---

# 21. 避免过度抽象

禁止看到两段类似代码就立即建立：

```text
UniversalManager
GenericProcessor
BaseEverythingService
CommonHelper
```

只有当：

* 行为稳定
* 多处真实复用
* 抽象边界明确

才进行抽象。

---

# 22. 避免 Magic Number

禁止：

```text
if retry > 7
```

却不知道 7 是什么。

应该：

```text
MAX_RETRY_COUNT
```

但简单且明显的数字不需要机械抽取。

---

# 23. 避免 Magic String

核心业务值不得散落字符串。

禁止：

```text
if status == "approved"
```

到处重复。

应使用：

```text
Enum
Constant
Type
```

统一管理。

---

# 24. 注释原则

代码应该优先通过：

* 清晰命名
* 清晰结构

表达意义。

注释用于解释：

> 为什么这样做。

而不是：

> 代码正在做什么。

错误：

```text
// Add 1 to count
count++;
```

有效注释：

```text
// Provider may resend the webhook, therefore processing must remain idempotent.
```

---

# 25. 禁止无意义注释

禁止生成大量：

```text
// initialize variable
// call service
// return response
```

这类无信息价值注释。

---

# 26. TODO 使用规则

允许：

```text
TODO
FIXME
```

但必须说明原因。

例如：

```text
TODO: replace temporary polling after async event infrastructure is introduced
```

禁止：

```text
TODO fix later
```

却没有上下文。

---

# 27. 禁止保留废弃代码

不要通过 Comment 保存旧代码：

```text
// old code
// old implementation
```

版本历史交给 Git。

确认不再使用的代码应删除。

但删除前必须确认没有使用方。

---

# 28. 禁止死代码

Cursor 必须避免留下：

* 未使用 Variable
* 未使用 Import
* 未使用 Function
* 永远不会执行的分支
* 未使用 Component

开发完成后应清理。

---

# 29. TypeScript 必须严格类型化

Frontend 使用 TypeScript 的目的不是：

> JavaScript + any。

禁止无理由大量使用：

```text
any
```

应优先：

```text
type
interface
unknown
generic
```

---

# 30. any 使用规则

只有真正无法提前知道类型时才允许 `any`。

使用 `any` 时必须确认：

* 是否可以用 unknown
* 是否可以建立 Type
* 是否是第三方 Library 限制

禁止为了消除 TypeScript Error 直接改成：

```text
any
```

---

# 31. 禁止关闭 TypeScript 检查逃避问题

禁止为了快速通过编译：

```text
@ts-ignore
@ts-nocheck
```

除非存在明确且合理原因。

优先解决真正的 Type Error。

---

# 32. 不得滥用 Type Assertion

禁止大量：

```text
as SomeType
```

强制让编译器相信数据类型。

外部数据应进行 Validation。

Type Assertion 不能代替数据验证。

---

# 33. React Component 原则

React Component 主要负责：

* Rendering
* Interaction
* Composition

不要承担大量：

* API Logic
* Business Logic
* Complex Calculation
* Permission Engine

---

# 34. Component 不应过大

如果一个 Component：

* 数百行
* 多个 Modal
* 多个 Form
* 多种 Business Flow
* 大量 API

应评估拆分。

拆分必须基于职责。

不是单纯按行数拆。

---

# 35. React Hook 规则

Hook 应封装：

* Reusable State
* Data Fetching
* UI Behavior
* Reusable Side Effect

不得将大量核心业务规则隐藏在 Frontend Hook 中。

---

# 36. useEffect 使用规则

不得将 `useEffect` 当成所有逻辑的默认工具。

Cursor 新增 `useEffect` 前必须判断：

* 是否真的需要 Side Effect
* 是否可以由事件触发
* 是否会重复执行
* Dependency 是否正确
* 是否产生 Loop

---

# 37. React State 原则

State 应放在：

> 最接近使用它的合理层级。

不得所有状态都塞入 Global Store。

也不得多个页面各自维护应该共享的业务状态。

---

# 38. Derived State 原则

能够由已有 State 计算出来的值：

原则上不要再保存为独立 State。

例如：

```text
firstName
lastName
```

可计算：

```text
fullName
```

则无需额外同步 fullName State。

---

# 39. Frontend API Error 必须处理

任何 API Request 必须考虑：

```text
Loading
Success
Empty
Validation Error
Permission Error
Server Error
Network Error
```

不得只写 Success Flow。

---

# 40. Loading State

异步功能必须有明确 Loading State。

禁止用户点击后：

> 没有任何反馈。

---

# 41. Double Submit

涉及 Create / Payment / Save / Approval 等操作：

Frontend 应避免重复点击。

Backend 仍必须提供真正的重复请求保护。

---

# 42. Frontend Validation 不等于 Security

Frontend Validation 仅改善 UX。

Backend 必须再次 Validate。

禁止认为：

```text
Input 已经在 React 检查
```

所以 Backend 不需要验证。

---

# 43. Backend Java 编码原则

Spring Boot 代码必须保持：

* Strong Typing
* Clear Layering
* Explicit Business Logic
* Transaction Safety

不得将 Java 写成动态脚本式代码。

---

# 44. Controller 必须保持轻量

Controller 允许：

* 接收参数
* Request Validation
* 调用 Application Service
* 返回 Response

禁止：

```text
直接写业务计算
直接写 SQL
直接控制 Transaction
```

---

# 45. Service 必须职责明确

禁止出现无限膨胀：

```text
SystemService
CommonService
MainService
```

业务 Service 应明确 Domain。

例如：

```text
SalesOrderService
StockTransferService
LeaveApprovalService
```

---

# 46. Repository 只处理数据访问

Repository 不处理：

* Permission
* Workflow
* Business Decision
* Notification
* Controller Logic

---

# 47. DTO 不得直接复用 Entity

Request / Response 应独立 DTO。

特别是：

```text
User
Employee
Finance
Permission
Security
```

禁止无脑返回完整 Entity。

---

# 48. Sensitive Field 禁止输出

例如：

```text
password
passwordHash
secret
accessToken
refreshToken
privateKey
internalSecurityFlag
```

不得出现在普通 API Response。

---

# 49. Validation 标准

所有外部输入必须 Validate。

包括：

```text
Body
Query Parameter
Path Parameter
Header
Webhook
Imported File
AI Tool Input
```

---

# 50. Validation 应明确层级

Request Validation：

负责格式。

例如：

```text
required
length
format
range
```

Domain Validation：

负责业务规则。

例如：

```text
库存是否足够
订单是否允许取消
员工是否可以申请该假期
```

两者不要混为一谈。

---

# 51. 不信任外部输入

永远视以下内容为不可信：

* Browser Input
* API Input
* CSV
* Excel
* File
* Webhook
* Third-Party API
* AI Output

必须 Validate。

---

# 52. Null Handling

不得依赖 Null 导致运行时异常。

必须明确：

```text
Required
Optional
Nullable
```

三者差异。

---

# 53. Optional 不得滥用

Java Optional 主要用于：

> 表达可能不存在的返回值。

不得将 Optional 随意用于：

* Entity Field
* DTO Field
* Method Parameter

除非项目明确采用。

---

# 54. Exception Handling

禁止：

```text
try {
   ...
} catch (Exception e) {
}
```

吞掉错误。

---

# 55. 禁止 Catch 所有 Exception 后伪装成功

错误：

```text
catch (Exception e) {
    return success();
}
```

这是严重问题。

任何失败必须返回真实状态。

---

# 56. Exception 必须分类

推荐区分：

```text
ValidationException
BusinessException
AuthorizationException
ResourceNotFoundException
ConflictException
ExternalServiceException
```

具体命名跟随项目统一标准。

---

# 57. 不要使用 Exception 控制正常流程

禁止：

```text
try {
   findUser();
} catch (...) {
   // user does not exist
}
```

作为常规业务判断方式。

---

# 58. Logging 标准

必须使用统一 Logger。

禁止：

```text
System.out.println
console.log
print
```

作为 Production Logging 标准。

开发调试临时使用后必须清理。

---

# 59. 日志必须有价值

有效日志应该帮助回答：

```text
什么发生了？
哪个 Tenant？
哪个 Request？
哪个模块？
结果是什么？
```

---

# 60. 禁止记录敏感数据

日志禁止记录：

* Password
* Token
* API Key
* Secret
* Private Key
* Full Card Data
* Sensitive Personal Data

---

# 61. Log Level

正确使用：

```text
DEBUG
INFO
WARN
ERROR
```

不得所有事情都记录 ERROR。

也不得所有事情都记录 INFO。

---

# 62. Python AI 编码原则

Python AI Layer 必须保持：

* Type Hint
* Clear Module Boundary
* Explicit Error Handling
* Input Validation
* Provider Isolation
* Tool Safety

---

# 63. Python Type Hint

重要 Function 必须尽量使用：

```python
def process_document(document_id: str) -> ProcessResult:
```

禁止大型系统长期使用完全无类型的动态代码。

---

# 64. Python 禁止万能 Dictionary

不得所有结构都使用：

```python
dict
```

传递。

复杂数据应使用：

* TypedDict
* dataclass
* Pydantic Model

或项目标准数据模型。

---

# 65. AI Output 必须验证

LLM 输出永远不能直接视为可信结果。

涉及：

```text
Tool Call
Database Query
Business Action
Structured Output
```

必须进行 Schema / Business Validation。

---

# 66. Prompt 不得承载核心业务规则

核心 Business Rule 不应该只存在 Prompt 中。

错误：

```text
Prompt:
Refund only allowed within 7 days.
```

但 Backend 没有验证。

真正业务规则必须存在 Backend。

Prompt 可以帮助 AI 理解规则。

但不能成为唯一安全边界。

---

# 67. AI Tool Input 必须强类型

AI Tool 必须有明确：

```text
Name
Purpose
Input Schema
Output Schema
Permission
Risk Level
```

禁止提供：

```text
executeAnything(command)
```

这类万能工具。

---

# 68. Database Query 编码原则

不得使用：

```text
SELECT *
```

作为所有 Query 默认方式。

只读取实际需要字段。

ORM 使用同样必须关注查询范围。

---

# 69. 查询必须考虑 Tenant Scope

任何 Tenant 数据 Query：

必须确认 Tenant Constraint。

例如逻辑上应类似：

```text
WHERE tenant_id = currentTenant
```

不能先查询全部，再在 Java 中过滤。

---

# 70. 查询必须考虑 Company Scope

Company Scoped 数据同样必须验证：

```text
tenant
+
company
```

之间的合法关系。

---

# 71. 禁止循环查询

避免：

```text
for each order
    query customer
```

形成 N+1。

必须使用合理查询方式解决。

---

# 72. Pagination

可能持续增长的列表不得默认返回全部数据。

例如：

```text
Customers
Orders
Employees
Audit Logs
Invoices
```

必须考虑 Pagination。

---

# 73. Sort 必须可预测

分页数据必须使用稳定排序。

禁止数据库返回顺序不确定造成：

* 重复数据
* 漏数据

---

# 74. Transaction

涉及多步核心写入时：

必须判断是否需要 Transaction。

例如：

```text
Create Invoice
+
Create Invoice Lines
+
Update Status
```

不得发生：

> 一半成功，一半失败。

---

# 75. Transaction 不得无限扩大

不要为了方便将大量：

* External API
* Email
* AI Request

长时间包在 Database Transaction 中。

---

# 76. 外部 API 调用标准

调用第三方 API 必须考虑：

```text
Timeout
Failure
Retry
Rate Limit
Invalid Response
Duplicate Response
```

禁止默认第三方永远成功。

---

# 77. Timeout 必须明确

任何网络调用不得无限等待。

必须设置合理 Timeout。

---

# 78. Retry 不得盲目

Retry 必须考虑：

> 这个操作是否安全重复。

例如读取：

通常可 Retry。

Payment：

不能简单无限 Retry。

---

# 79. Idempotency

以下功能必须特别考虑：

```text
Payment
Refund
Webhook
Order Creation
Invoice Posting
AI Action
```

避免重复请求产生重复业务结果。

---

# 80. Date / Time 标准

禁止到处直接使用服务器本地时间。

必须统一处理：

```text
UTC
Business Timezone
User Timezone
```

具体策略由后续数据库标准统一。

---

# 81. Money 编码标准

Java：

优先：

```text
BigDecimal
```

禁止核心金额使用：

```text
float
double
```

---

# 82. Python Money

Python 核心金额计算：

优先：

```text
Decimal
```

禁止关键金融逻辑依赖 Binary Float。

---

# 83. Frontend Money

Frontend 不应该承担最终金融计算责任。

展示计算可以进行。

最终结果必须由 Backend 确认。

---

# 84. Currency 必须明确

金额必须伴随：

```text
Currency
```

禁止只传：

```json
{
  "amount": 100
}
```

而业务本身可能存在多货币。

---

# 85. Rounding 必须明确

关键金额计算必须定义：

* Scale
* Precision
* Rounding Mode

不得依赖默认行为。

---

# 86. Enum 使用原则

有限且稳定的业务状态应使用 Enum。

例如：

```text
DRAFT
PENDING
APPROVED
REJECTED
```

不得使用：

```text
1
2
3
4
```

没有语义的 Magic Integer。

---

# 87. Boolean 不适合复杂状态

禁止：

```text
isApproved
isCancelled
isCompleted
isRejected
```

共同表达复杂生命周期。

应使用明确 Status。

---

# 88. Environment Variable

环境相关配置不得 Hardcode。

例如：

```text
Database URL
API URL
Secret
Storage Endpoint
AI Key
```

必须从 Environment / Configuration 获取。

---

# 89. 禁止 Secret 进入代码

严禁：

```text
API_KEY = "..."
PASSWORD = "..."
TOKEN = "..."
```

写进源码。

---

# 90. Dependency 管理

新增 Dependency 前必须检查：

1. 项目是否已有同类能力。
2. 标准 Library 是否能解决。
3. 是否真正必要。
4. 是否有维护风险。
5. 是否增加 Bundle / Runtime 成本。
6. 是否引入 Security Risk。

---

# 91. 禁止重复 Library

例如项目已有一个 Date Library：

不要为了一个新页面再引入第二套。

已有 HTTP Client：

不要再随意引入另一个。

---

# 92. Dependency Version 不得擅自升级

Cursor 不得为了实现一个小功能：

> 顺便升级整个 Framework。

尤其：

* React
* Spring Boot
* Java
* Python Core
* PostgreSQL Driver

重大升级必须独立处理。

---

# 93. 禁止复制粘贴大型代码

发现类似功能时：

先判断是否可以复用或提取稳定能力。

禁止大量 Copy-Paste 后分别维护。

---

# 94. DRY 不是绝对规则

不要为了追求 DRY：

将不同业务规则强行抽象在一起。

原则：

> 小量重复优于错误抽象。

---

# 95. Security 编码原则

开发任何 API 时都必须考虑：

```text
Authentication
Authorization
Tenant
Ownership
Validation
Audit
```

不能只考虑：

> API 能否返回数据。

---

# 96. 权限检查必须在 Backend

即使 React：

```text
隐藏了按钮
```

Backend 仍必须判断 Permission。

---

# 97. Resource Ownership

有 Permission 不代表可以访问所有数据。

必须考虑：

```text
Tenant Scope
Company Scope
Department Scope
Own Resource
Assigned Resource
```

---

# 98. 防止越权

任何：

```text
GET /resource/{id}
```

不得只根据 ID 查询后直接返回。

必须验证：

> 当前用户是否有权读取该 Resource。

---

# 99. Mass Assignment

Backend 不应直接接受：

```text
Entity
```

作为 Request。

防止用户提交：

```text
role
permission
tenantId
createdBy
status
```

等本不应该自行修改的字段。

---

# 100. SQL Injection

禁止使用用户输入直接拼接 SQL。

必须使用：

* Parameter Binding
* ORM Safe Query
* Prepared Statement

---

# 101. XSS

Frontend 显示外部内容时必须考虑 XSS。

React 默认 Escaping 不得轻易绕过。

特别谨慎使用：

```text
dangerouslySetInnerHTML
```

---

# 102. File Upload

文件上传必须验证：

```text
Type
Size
Extension
Permission
Ownership
```

不能只相信 Frontend MIME。

---

# 103. API Response 标准

同类 API 应保持一致：

```text
Data
Error
Pagination
Metadata
```

不得每个 Module 各自发明完全不同 Response。

---

# 104. 不返回无意义 Success

禁止：

```text
HTTP 200
```

但实际上业务失败。

HTTP Status 与业务结果必须保持合理一致。

---

# 105. Error Message

用户可见 Error：

必须清楚。

但不能泄露：

* Stack Trace
* SQL
* Internal Path
* Secret
* Infrastructure Detail

---

# 106. Import / Export

批量 Import 必须考虑：

```text
Validation
Duplicate
Partial Failure
Error Report
Tenant
Permission
```

不得读取文件后直接全部写入。

---

# 107. Bulk Operation

Bulk Update / Delete 必须考虑：

* Permission
* Scope
* Transaction
* Performance
* Audit
* Partial Failure

---

# 108. Delete 编码规则

执行删除前必须确认业务类型。

优先考虑：

```text
Archive
Deactivate
Cancel
Void
Soft Delete
```

不得所有数据统一使用：

```text
DELETE FROM
```

---

# 109. Audit

关键写操作必须考虑 Audit。

Audit 不能只是：

```text
"updated record"
```

至少需要足够信息追踪操作。

---

# 110. Code Duplication 检查

完成开发前，应检查当前修改是否：

* 新建重复 Helper
* 新建重复 Service
* 新建重复 Type
* 新建重复 Component

---

# 111. Compile / Build 验证

任务完成前必须尽可能执行对应验证。

Frontend：

```text
Type Check
Build
Lint
Relevant Test
```

Backend：

```text
Compile
Relevant Test
```

Python：

```text
Syntax / Type / Relevant Test
```

具体命令跟随项目实际配置。

---

# 112. 不允许忽略 Build Error

禁止：

> 当前修改完成，但是项目无法 Build。

如果 Error 是当前修改导致：

必须处理。

---

# 113. 不允许删除测试让 Build 通过

禁止通过：

```text
删除 Test
Skip Test
Disable Test
```

来伪造成功。

除非测试本身已失效且有明确依据。

---

# 114. Bug 修复必须修根因

不要只隐藏症状。

例如：

错误：

```text
页面出现 null
→ 用 CSS 隐藏
```

如果真正问题是 Backend Data Error：

应该处理数据根因。

---

# 115. Debug 顺序

出现问题时：

```text
Reproduce
↓
Identify Layer
↓
Trace Data Flow
↓
Find Root Cause
↓
Apply Minimal Fix
↓
Verify Regression
```

---

# 116. 禁止猜测式 Debug

Cursor 不得：

> “应该是这里的问题”

然后连续修改多个文件测试运气。

必须先建立证据。

---

# 117. Bug Fix 不得创建第二套逻辑

如果现有 Service 有 Bug：

应该修复 Service。

不要建立：

```text
NewFixedService
```

让两个逻辑长期并存。

---

# 118. Regression Awareness

修改公共能力时必须检查：

```text
Who Uses This?
```

例如修改：

```text
Button
API Client
Permission Service
Base Entity
Currency Utility
```

必须考虑全局影响。

---

# 119. Backward Compatibility

修改：

```text
Function Signature
DTO
API Response
Enum
Status
Database Field
```

前必须搜索所有使用方。

---

# 120. 禁止静默 Breaking Change

如果必须 Breaking Change：

Cursor 必须明确指出：

* 修改了什么
* 谁会受到影响
* 是否需要 Migration
* 是否需要同步修改调用方

---

# 121. Code Review 自检

完成代码后，Cursor 必须自行检查：

```text
是否符合架构？
是否有重复代码？
是否有安全风险？
是否有 Tenant 泄漏？
是否有 Permission 漏洞？
是否有 Null 问题？
是否有错误吞掉？
是否有 N+1？
是否有重复提交风险？
是否影响旧功能？
```

---

# 122. Cursor 不得伪造完成状态

如果：

* Build 未运行
* Test 未运行
* 某部分无法验证

必须明确说明。

禁止声称：

> “已经完全测试通过”

如果实际没有执行。

---

# 123. 不允许修改用户未要求的业务规则

如果业务逻辑看起来“不合理”：

不能擅自修改。

例如：

```text
Commission = 3%
```

Cursor 觉得 5% 更合理：

绝对不能修改。

业务规则由产品决定。

---

# 124. 计算逻辑不得凭感觉修改

涉及：

```text
Rate
Commission
Fee
Tax
Discount
Exchange Rate
Point
Payroll
```

必须依据明确公式。

如果公式不明确：

不得自行发明。

---

# 125. Precision 优先

涉及金额或比率：

必须保留原始精度直到最终显示或业务规定的舍入点。

禁止每一步都提前 Round。

---

# 126. 状态转换必须受控

禁止直接：

```text
status = APPROVED
```

绕过：

* Permission
* Validation
* Workflow

重要状态变更必须通过业务方法。

---

# 127. 不允许直接修改历史交易

例如：

```text
Posted Invoice
Completed Payment
Finalized Payroll
```

通常应通过：

* Adjustment
* Reversal
* Void

处理。

不能直接覆盖历史。

---

# 128. Concurrency Awareness

涉及：

```text
Stock
Balance
Payment
Sequence
Quota
```

必须判断是否存在并发竞争。

不得默认：

> 同一时间只有一个用户操作。

---

# 129. Sequence Number

业务编号例如：

```text
INV-2026-000001
SO-2026-000001
```

不得简单：

```text
count + 1
```

生成。

必须考虑并发与唯一性。

---

# 130. Cache 使用

不得为了性能直接加入 Cache。

必须先确认：

* 真正存在性能问题
* 数据是否适合缓存
* Cache Invalidation 如何处理

---

# 131. Performance 优化必须基于问题

禁止：

> 预估未来很慢

然后进行大量复杂优化。

先保证：

```text
Correct
Maintainable
```

再根据实际问题优化。

---

# 132. 不允许无分页大查询

任何可能增长的数据：

不得：

```text
findAll()
```

直接返回整个数据集给 UI。

---

# 133. Frontend Rendering Performance

不要无意义添加：

```text
useMemo
useCallback
memo
```

性能优化必须针对实际问题。

---

# 134. API 调用去重

同一页面不得无必要重复请求同一数据。

优先合理使用：

* Shared Query State
* Cache
* Request Deduplication

但不得自行引入大型新框架。

---

# 135. Accessibility

通用 UI 必须尽可能保持基本 Accessibility：

* Label
* Keyboard Access
* Semantic HTML
* Button Type
* Form Relationship

不得全部使用：

```text
<div onClick>
```

替代语义元素。

---

# 136. Responsive

Frontend 新页面必须考虑基本：

```text
Desktop
Tablet
Mobile
```

但 Admin / Enterprise 页面具体支持范围由产品要求决定。

---

# 137. 禁止 Inline Style 泛滥

应跟随项目现有 Styling 方案。

不得一个页面使用完全不同 Styling 技术。

---

# 138. UI 组件应复用 Design System

已有：

```text
Button
Input
Modal
Table
Select
Badge
```

时：

必须复用。

不要重复设计另一套相同组件。

---

# 139. Feature Flag

未完成功能不得通过：

> 页面隐藏

假装不存在。

需要灰度控制时，应使用正式 Feature Control。

---

# 140. Dead Feature

废弃功能必须经过明确决策。

Cursor 不得因为看起来没使用：

就直接删除。

---

# 141. Git 修改范围

Cursor 在一次任务中应保持修改范围聚焦。

避免一次提交混入：

* Bug Fix
* Formatting 全项目
* Dependency Upgrade
* Refactor
* Feature

多个无关变化。

---

# 142. 禁止全项目自动格式化

修复一个文件时：

不得因为 Formatter 导致几十个无关文件变化。

---

# 143. 格式化标准

代码格式交给项目统一工具。

例如：

Frontend：

```text
ESLint
Prettier
```

Backend：

```text
项目 Java Formatter
```

Python：

```text
项目 Python Formatter
```

如果项目尚未配置：

Cursor 不得自行大规模加入工具链。

---

# 144. Import 必须整理

完成代码后：

* 删除未使用 Import
* 避免重复 Import
* 保持项目排序方式

---

# 145. 禁止 Debug Code 留在 Production

开发完成后必须移除：

```text
console.log
System.out.println
print
alert
debugger
```

除非明确属于正式行为。

---

# 146. Mock Data

Mock Data 仅用于：

* Test
* Local Development
* Story / Preview

不得进入 Production Business Logic。

---

# 147. Fake Success 禁止

禁止为了 Demo：

```text
return success
```

但实际没有完成操作。

---

# 148. Feature 必须 End-to-End 一致

一个完整功能可能涉及：

```text
Frontend
API
Backend
Database
Permission
Audit
```

Cursor 必须确认这些层之间 Contract 一致。

---

# 149. 不允许前后端字段名随意不一致

例如 Frontend：

```text
customerName
```

Backend：

```text
client_name_value
```

除非存在明确 Mapping 规范。

API Contract 应保持稳定、清楚。

---

# 150. 不允许重复定义同一 Enum

同一个 API 状态：

Frontend 和 Backend 可以各自拥有类型定义。

但值必须由 API Contract 保证一致。

禁止各自随意新增不同状态。

---

# 151. API Unknown Status

Frontend 对 Backend Enum 应考虑未来新增值的兼容处理。

不要所有未知状态直接 Crash。

---

# 152. Version Compatibility

Python AI Service 与 Spring Boot API 之间：

必须通过稳定 Contract 通信。

不得读取 Backend 内部 Class 或 DB Table 作为集成方式。

---

# 153. AI Service Failure

AI 服务不可用时：

非 AI 核心业务应尽量避免整个系统完全不可用。

例如：

AI Recommendation 失败：

不应该导致 Sales Order 无法打开。

除非该功能本身就是 AI 必需流程。

---

# 154. AI Timeout

LLM 调用必须设置合理 Timeout。

不能无限等待 AI Provider。

---

# 155. AI Retry

AI Retry 必须防止重复 Tool Action。

尤其 Agent 已经成功调用 Backend 后：

不能因为 LLM Response Timeout 又重复执行动作。

---

# 156. AI Tool 与 Reasoning 分离

AI 可以自由进行分析。

但执行系统动作必须通过受控 Tool。

```text
Reason
↓
Propose Action
↓
Validate Tool Call
↓
Permission
↓
Execute
↓
Audit
```

---

# 157. Prompt Injection Awareness

AI Knowledge Base / User Input / External Document：

都必须视为潜在不可信内容。

外部文本不能自动获得：

* System Permission
* Tool Permission
* Higher Priority Instruction

---

# 158. AI Generated Code 也必须遵守全部规则

Cursor 生成代码不代表可以降低标准。

AI 生成的代码同样必须：

* Review
* Compile
* Validate
* Test

---

# 159. 数据迁移必须安全

如果代码变化需要 Migration：

必须考虑：

```text
Existing Data
Default Value
Nullability
Backfill
Rollback / Recovery
Deployment Order
```

---

# 160. 禁止通过删除旧数据解决 Migration

不得因为 Schema 不兼容：

> 清空 Database。

除非明确属于可删除的本地开发环境。

---

# 161. Production 数据必须保护

涉及 Production：

禁止：

* TRUNCATE
* DROP
* Bulk DELETE
* Reset Database

除非用户明确批准且有安全流程。

---

# 162. Seed Data

Seed Data 必须区分：

```text
Required System Data
Development Demo Data
Test Data
```

三者不能混在一起。

---

# 163. 默认数据不得影响所有 Tenant

新增 Tenant 默认配置时：

必须有明确 Initialization Flow。

不得直接用全局默认数据污染现有 Tenant。

---

# 164. 模块边界必须遵守

例如：

Sales 不直接修改：

```text
Inventory Repository
```

HRM 不直接修改：

```text
Finance Repository
```

必须通过正式 Module Contract。

---

# 165. Core 依赖方向

Core 不得依赖具体业务模块。

错误：

```text
core → sales
```

通常应该：

```text
sales → core
```

---

# 166. 禁止 Circular Dependency

如果新代码产生：

```text
A → B → A
```

必须重新设计。

不得通过技术 Hack 掩盖架构问题。

---

# 167. Shared Code 必须保持纯净

Shared / Common 不得依赖具体 Domain。

否则它实际上不是 Shared。

---

# 168. 工具函数必须真正通用

不要创建：

```text
Utils
CommonUtils
Helper
```

然后持续堆放所有逻辑。

优先具体名称：

```text
CurrencyFormatter
DateTimeUtils
PaginationMapper
```

---

# 169. 配置类必须集中管理

不要到处读取：

```text
System.getenv
```

应由 Configuration Layer 统一提供。

Python 同样如此。

---

# 170. Feature Configuration 与 Secret 分离

Feature Setting：

可以来自 Database / Config。

Secret：

必须来自安全 Secret Storage / Environment。

两者不得混用。

---

# 171. 测试标准

新增核心业务逻辑时：

必须考虑 Unit Test。

修改关键流程时：

必须考虑 Integration Test。

---

# 172. 测试重点

优先测试：

```text
Business Rule
Permission
Tenant Isolation
Money Calculation
State Transition
Edge Case
Failure Case
```

而不是只测试简单 Getter / Setter。

---

# 173. 测试必须包含失败情况

不能只测试：

```text
Happy Path
```

还应考虑：

```text
Invalid Input
No Permission
Wrong Tenant
Duplicate Request
Insufficient Stock
Invalid State
```

---

# 174. 测试数据必须隔离

Test 不得依赖：

* Production
* Shared Mutable Environment
* 手动先创建的数据

测试应该尽可能可重复执行。

---

# 175. 不允许为了 Test 改坏 Production 代码

Production Code 不应该因为测试方便而加入：

```text
if test
```

大量特殊逻辑。

---

# 176. Cursor 完成任务前必须自检

至少检查：

* [ ] 是否遵守《01 产品原则》
* [ ] 是否遵守《02 系统架构标准》
* [ ] 是否修改了不必要的文件
* [ ] 是否存在重复实现
* [ ] 是否破坏 Module Boundary
* [ ] 是否存在 Hardcode
* [ ] 是否正确处理 Tenant
* [ ] 是否正确处理 Company Scope
* [ ] 是否正确处理 Permission
* [ ] 是否验证外部输入
* [ ] 是否正确处理 Error
* [ ] 是否可能重复提交
* [ ] 是否存在 Null 风险
* [ ] 是否存在 N+1
* [ ] 是否处理 Transaction
* [ ] 是否有敏感数据泄露
* [ ] 是否需要 Audit
* [ ] 是否需要 Migration
* [ ] 是否完成 Build / Compile
* [ ] 是否完成必要 Test
* [ ] 是否影响旧功能

---

# 177. Cursor 遇到不确定情况

如果 Cursor 无法确认：

```text
Business Rule
Data Ownership
Permission Requirement
Architecture Boundary
Database Meaning
```

不得自行发明规则。

必须优先：

1. 搜索现有代码。
2. 搜索相关 Module。
3. 搜索相似实现。
4. 检查已有文档。
5. 根据已有 Pattern 判断。

如果仍无法确定：

不得进行具有破坏性的架构假设。

---

# 178. 禁止“为了让它能跑”降低标准

以下理由均不能作为违规依据：

```text
这样比较快
这样比较简单
只是暂时
以后再改
先让页面出来
先跳过 Permission
先 Hardcode
先直接操作数据库
```

如果是正式代码：

必须满足正式标准。

---

# 179. 开发速度原则

AIOS 不追求：

> 最少代码。

AIOS 追求：

> 最少的不必要复杂度。

正确开发方式：

```text
需求清楚
↓
边界清楚
↓
最小实现
↓
正确验证
↓
保持一致
```

---

# 180. 最终开发原则

所有 Cursor 开发行为必须遵守：

> 先理解，再修改。

> 先搜索，再创建。

> 先复用，再新增。

> 先保证正确，再优化。

> 核心业务放 Backend，不放 Frontend。

> AI 可以辅助决策，但不能绕过业务规则。

> Tenant、Permission、Audit 不是可选项。

> 不为了完成当前任务破坏整体架构。

> 不为了减少代码牺牲可读性。

> 不为了代码漂亮进行无关重构。

> 不为了性能提前增加复杂度。

> 不为了快速通过编译隐藏真正错误。

> 不允许 Cursor 用猜测代替理解。

> 每一次代码修改都必须保持 AIOS 长期可维护。
