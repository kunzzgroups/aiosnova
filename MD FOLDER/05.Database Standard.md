# AIOS 数据库设计标准

> 文件编号：05
> 文件名称：数据库设计标准
> 适用范围：AIOS 全系统数据库设计、Schema、Migration、Entity、Repository、Query、数据迁移
> 适用对象：Cursor、AI Agent、Backend Developer、Database Developer
> Primary Database：PostgreSQL
> 前置规则：必须遵守《01 产品原则》《02 系统架构标准》《03 开发与编码标准》
> 核心目标：数据正确、Tenant 隔离、结构统一、可审计、可扩展、可维护、高完整性

---

# 1. 文件目的

本文件定义 AIOS PostgreSQL 数据库设计标准。

数据库属于 AIOS 最核心资产之一。

Cursor 在进行以下任何行为时：

```text
CREATE TABLE
ALTER TABLE
DROP TABLE
ADD COLUMN
DROP COLUMN
RENAME COLUMN
CREATE INDEX
CREATE CONSTRAINT
UPDATE DATA
DELETE DATA
DATABASE MIGRATION
```

都必须遵守本文件。

数据库设计不能以：

> “现在可以存进去”

作为完成标准。

必须同时考虑：

```text
Data Integrity
Tenant Isolation
Domain Ownership
Security
Auditability
Performance
Migration Safety
Historical Accuracy
Future Growth
```

PostgreSQL

PostgreSQL 负责：

* Core

* POS
* Commerce

* Procurement

* Finance
* HRM
* Project
* Help Desk
* Marketing
* Manufacturing

等核心 Operational Data。

# 3. PostgreSQL 是核心业务事实来源

核心业务数据的 Source of Truth：

```text
PostgreSQL
```

以下系统未来即使存在：

```text
Redis
Vector Database
Search Engine
Data Warehouse
Data Lake
```

都不能自动取代 PostgreSQL 的核心业务事实来源地位。

例如：

```text
Redis
```

是 Cache。

```text
Vector Database
```

是 AI Retrieval Index。

```text
Data Warehouse
```

是 Analytics。

它们都不是核心 Transaction Source of Truth。

# 4. Cursor 修改数据库前必须检查

Cursor 在新增或修改数据库之前必须先检查：

1. 当前数据属于哪个 Domain。
2. 是否已经存在相关 Table。
3. 是否已经存在类似 Column。
4. 是否已经存在可复用 Entity。
5. Table Owner Module 是谁。
6. 是否属于 Tenant Scoped Data。
7. 是否属于 Company Scoped Data。
8. 是否涉及敏感数据。
9. 是否涉及 Money。
10. 是否涉及历史交易。
11. 是否需要 Audit。
12. 是否需要 Unique Constraint。
13. 是否需要 Foreign Key。
14. 是否需要 Index。
15. 是否影响 Existing Data。
16. 是否需要 Migration。
17. 是否可能产生 Breaking Change。

执行顺序：

```text
Understand Domain
↓
Inspect Existing Schema
↓
Inspect Existing Migration
↓
Inspect Entity / Repository
↓
Determine Ownership
↓
Design
↓
Migration
↓
Validate
```

---

# 5. 禁止 Cursor 擅自修改 Production Schema

禁止直接：

```text
ALTER TABLE production...
DROP TABLE production...
DELETE FROM production...
TRUNCATE...
```

作为普通开发流程。

任何正式 Schema Change：

必须通过版本化：

```text
Database Migration
```

执行。

---

# 6. Migration First

任何 Schema Change 必须存在 Migration。

包括：

* Create Table
* Add Column
* Remove Column
* Add Index
* Remove Index
* Add Constraint
* Change Type
* Rename Field
* Data Backfill

禁止：

> 修改 Entity 后依赖 ORM 自动修改 Production Database。

---

# 7. 禁止 Production 使用自动 Schema Mutation

Production 不得依赖：

```text
auto create
auto update
schema update
```

自动修改正式数据库结构。

ORM 可以进行：

```text
validate
```

或项目指定的安全方式。

正式 Schema Evolution 必须由 Migration 控制。

---

# 8. Migration 工具必须统一

AIOS 必须统一使用一套 Migration System。

项目已经选定：

```text
Flyway
```

则继续使用 Flyway。

项目已经选定：

```text
Liquibase
```

则继续使用 Liquibase。

禁止：

> 一个 Module 使用 Flyway，另一个 Module 使用 Liquibase。

如果项目尚未选择：

Cursor 不得因为当前任务自行同时引入多套 Migration 工具。

---

# 9. Migration 不可随意修改历史版本

已经进入共享环境或 Production 的 Migration：

原则上：

> 不允许直接修改原文件。

应新增下一条 Migration。

禁止为了让当前数据库看起来干净：

> Rewrite Migration History。

---

# 10. Migration 必须向前兼容

修改 Database Schema 时必须考虑：

```text
Old Application
New Application
Existing Data
Deployment Order
```

不能默认：

> Database 与所有 Application Instance 会在同一毫秒完成更新。

---

# 11. 破坏性 Migration 必须分阶段

例如需要删除：

```text
old_column
```

不能直接：

```text
DROP COLUMN old_column
```

标准流程应根据实际情况采用：

```text
Phase 1
新增新结构

Phase 2
应用程序停止使用旧结构

Phase 3
迁移 / Backfill

Phase 4
验证没有使用方

Phase 5
后续 Migration 删除旧结构
```

---

# 12. 禁止通过清空数据库解决 Migration

禁止：

```text
DROP DATABASE
TRUNCATE ALL
DELETE ALL DATA
```

来解决 Schema 不兼容问题。

Local Development 可删除的测试数据库除外。

---

# 13. Database Naming Language

数据库对象名称统一使用：

```text
English
```

禁止：

```text
Chinese Table Name
Chinese Column Name
拼音 Table Name
```

---

# 14. Naming Case

PostgreSQL Table / Column / Constraint / Index：

统一使用：

```text
snake_case
```

例如：

```text
sales_orders
sales_order_items
customer_id
created_at
tenant_id
```

禁止：

```text
SalesOrders
salesOrder
SALES_ORDER
```

混用。

---

# 15. Table 使用复数还是单数必须统一

AIOS 默认使用：

```text
复数 Table Name
```

例如：

```text
users
companies
customers
sales_orders
sales_order_items
employees
```

不得：

```text
user
companies
customer
sales_orders
```

无规律混用。

---

# 16. Table Name 必须表达 Domain

正确：

```text
sales_orders
purchase_orders
inventory_movements
employee_leaves
```

禁止模糊：

```text
records
data
details
information
items
others
misc
```

除非本身存在明确 Domain Context。

---

# 17. 禁止万能 Table

禁止创建：

```text
common_data
general_data
system_data
business_data
misc_data
```

然后把所有不同业务数据塞进去。

每个 Table 必须拥有清晰业务职责。

---

# 18. Column Naming

Column 必须表达业务意义。

正确：

```text
customer_id
invoice_number
total_amount
currency_code
approved_at
```

禁止：

```text
value1
value2
data1
field1
info
flag
```

---

# 19. Foreign Key Column Naming

Foreign Key 默认：

```text
{entity}_id
```

例如：

```text
tenant_id
company_id
customer_id
sales_order_id
created_by
```

如果存在多个不同关系：

名称必须说明关系。

例如：

```text
approved_by
assigned_to
parent_company_id
billing_customer_id
```

---

# 20. Primary Key 标准

AIOS 核心业务 Table 的 Primary Key：

默认使用：

```text
UUID
```

不得不同 Module 随意使用：

```text
Long
Integer
UUID
String
```

作为不同核心 Entity 的 Primary Key。

---

# 21. UUID 策略

如项目具备稳定 UUIDv7 实现：

优先使用：

```text
UUIDv7
```

用于新核心业务 Entity。

原因：

* 全球唯一
* 更适合未来分布式系统
* 大致时间有序
* 相比随机 UUID 更利于索引局部性

如果当前项目或依赖环境无法稳定使用 UUIDv7：

可以统一使用：

```text
UUIDv4
```

但必须保持整个项目策略一致。

Cursor 不得自行混合生成策略。

---

# 22. ID 与 Business Number 必须分开

数据库 Primary Key：

```text
id
```

与业务编号：

```text
invoice_number
sales_order_number
employee_number
purchase_order_number
```

必须分开。

错误：

```text
Primary Key = INV-2026-00001
```

正确：

```text
id = UUID
invoice_number = INV-2026-00001
```

---

# 23. Business Number 可以改变展示规则

业务编号可能随着：

* Tenant
* Company
* Fiscal Year
* Business Configuration

改变格式。

所以不能让 Business Number 成为数据库关系的核心 Foreign Key。

---

# 24. 禁止 count + 1 生成业务编号

禁止：

```text
SELECT COUNT(*) + 1
```

生成：

```text
INV-00001
SO-00001
```

因为会产生：

* Concurrency Problem
* Duplicate Number
* Deleted Record Problem

必须使用：

* Sequence
* Controlled Number Generator
* Atomic Counter
* Database Lock

等安全机制。

---

# 25. Tenant 是一级数据边界

AIOS 是 Multi-Tenant Platform。

所有属于 Tenant 的业务数据必须明确：

```text
tenant_id
```

除非该数据明确属于：

```text
Global Platform Data
```

---

# 26. Tenant Scoped Table

典型 Tenant Scoped 数据：

```text
companies
customers
employees
products
sales_orders
invoices
payments
projects
inventory
purchase_orders
```

通常必须包含：

```text
tenant_id
```

---

# 27. Tenant ID 默认 NOT NULL

真正属于 Tenant 的数据：

```text
tenant_id
```

原则上必须：

```text
NOT NULL
```

禁止大量：

```text
tenant_id NULL
```

然后使用 NULL 表示 Global。

Global Data 应有清晰独立模型。

---

# 28. Company Scoped Data

属于 Company 范围的数据：

通常必须同时拥有：

```text
tenant_id
company_id
```

不得因为有：

```text
company_id
```

就完全省略 Tenant Scope。

---

# 29. Company 必须属于同一个 Tenant

涉及：

```text
tenant_id
company_id
```

时必须保证：

> company_id 所属 Tenant 与当前 row 的 tenant_id 一致。

不得允许：

```text
tenant_id = Tenant A
company_id = Tenant B Company
```

的数据组合。

---

# 30. 禁止只依赖 Frontend Tenant ID

数据库设计不能建立在：

> Frontend 一定会传正确 tenant_id

的假设上。

Tenant Context 必须由 Backend Authentication Context 验证。

---

# 31. Query 必须在数据库层面限制 Tenant

禁止：

```text
SELECT all rows
↓
Java filter tenant
```

正确：

```text
Database Query
↓
WHERE tenant_id = current_tenant
```

---

# 32. Tenant Unique Constraint

如果业务唯一性只在 Tenant 内成立：

Unique Constraint 必须包含：

```text
tenant_id
```

例如：

```text
UNIQUE (tenant_id, customer_code)
```

而不是：

```text
UNIQUE (customer_code)
```

---

# 33. Company Unique Constraint

如果业务编号只在 Company 内唯一：

使用：

```text
UNIQUE (tenant_id, company_id, business_number)
```

根据实际业务设计。

---

# 34. Multi-Tenant 默认策略

AIOS 当前默认采用：

> Shared PostgreSQL Database + Shared Schema + Tenant Scoped Rows

即：

```text
Database
└── Schema
    ├── Tenant A Data
    ├── Tenant B Data
    └── Tenant C Data
```

通过：

```text
tenant_id
```

进行数据边界管理。

---

# 35. 不得自行切换 Database-per-Tenant

Cursor 不得擅自将某个模块改为：

```text
Database per Tenant
```

或：

```text
Schema per Tenant
```

这属于重大架构决策。

必须经过明确批准。

---

# 36. PostgreSQL Row Level Security

PostgreSQL RLS 可以作为未来 Tenant Isolation 的 Defense-in-Depth。

但 Cursor 不得在单个功能开发时擅自：

```text
全面启用 RLS
```

改变现有访问架构。

如采用 RLS：

必须全局设计：

* Tenant Context
* Connection Pool
* Background Job
* Super Admin
* Migration
* Reporting

不能局部随意开启。

---

# 37. Foreign Key 原则

具有真实关系的数据：

原则上应使用：

```text
Foreign Key
```

保证 Referential Integrity。

例如：

```text
sales_orders.customer_id
→ customers.id
```

---

# 38. 不得因为 ORM 就放弃 Foreign Key

禁止认为：

> Spring Boot Entity 已经定义关系，所以 Database 不需要 FK。

应用代码不能代替数据库完整性。

---

# 39. Foreign Key 删除策略必须明确

必须明确：

```text
ON DELETE RESTRICT
ON DELETE CASCADE
ON DELETE SET NULL
```

使用原因。

Cursor 不得随意全部使用：

```text
CASCADE
```

---

# 40. 默认优先 RESTRICT

核心业务数据默认应优先考虑：

```text
RESTRICT
```

防止删除 Parent 时：

> 自动删除大量重要业务记录。

---

# 41. CASCADE 只用于真正生命周期绑定的数据

例如：

```text
draft temporary child
technical join row
```

等明确依附 Parent 存在的数据。

对于：

```text
Invoice
Payment
Stock Movement
Audit
Payroll
```

不得随意 Cascade Delete。

---

# 42. NOT NULL 原则

业务真正必填字段：

必须数据库级：

```text
NOT NULL
```

不能只靠 Frontend 或 Java Validation。

---

# 43. Nullable 必须有意义

允许 NULL 前必须回答：

> NULL 在这个字段中具体代表什么？

如果无法清楚解释：

不应该默认 Nullable。

---

# 44. NULL 不等于 Empty String

以下必须区分：

```text
NULL
''
```

不得无规则混用。

例如：

不存在的 description：

可以是 NULL。

但必须系统统一。

---

# 45. Default Value 原则

Default 必须具有稳定业务意义。

适合：

```text
created_at
boolean default
initial technical status
```

不适合：

> 为了 Migration 容易，随便给业务数据一个假的 Default。

---

# 46. 禁止 Fake Default

例如新增：

```text
currency_code
```

不能为了 NOT NULL：

直接：

```text
DEFAULT 'MYR'
```

如果已有数据可能不是 MYR。

必须先明确历史数据如何 Backfill。

---

# 47. Boolean 标准

Boolean 使用 PostgreSQL：

```text
boolean
```

禁止：

```text
0 / 1
Y / N
YES / NO
```

无理由表示 Boolean。

---

# 48. Boolean 只表示真正二元状态

适合：

```text
is_active
is_default
is_system
```

不适合：

```text
is_approved
is_rejected
is_cancelled
is_completed
```

共同表达复杂生命周期。

复杂生命周期必须使用：

```text
status
```

---

# 49. Status 字段

有限业务状态应使用明确：

```text
status
```

例如：

```text
DRAFT
PENDING
APPROVED
REJECTED
CANCELLED
```

禁止用：

```text
1
2
3
4
```

没有语义的状态值。

---

# 50. PostgreSQL ENUM 使用原则

PostgreSQL Native ENUM 不得默认用于所有业务状态。

因为业务状态未来可能改变。

默认优先考虑：

```text
varchar + application enum + validation
```

或项目统一策略。

只有非常稳定、极少变化的数据类型才考虑 PostgreSQL ENUM。

---

# 51. String 长度必须合理

禁止所有文本字段统一：

```text
varchar(255)
```

也禁止所有字段统一：

```text
text
```

必须根据业务含义选择。

例如：

```text
currency_code
country_code
email
name
description
notes
```

需求不同。

---

# 52. Code 字段长度必须明确

例如：

```text
currency_code
country_code
language_code
```

应根据标准长度设计。

不得使用巨大 `text`。

---

# 53. 大文本

以下可以考虑：

```text
text
```

例如：

```text
description
notes
content
reason
```

但不得把大型 Binary File 存入普通 text 字段。

---

# 54. 文件不得默认存 PostgreSQL Binary

AIOS File Center：

默认数据库保存：

```text
File Metadata
Storage Key
URL / Object Key
Ownership
Tenant
Permission
Checksum
```

文件本体应由 Object Storage 等文件存储负责。

禁止默认：

```text
把所有 PDF / Image / Video 存入 PostgreSQL BYTEA
```

除非有明确业务需求。

---

# 55. JSONB 使用原则

PostgreSQL `jsonb` 可以用于：

* Dynamic Metadata
* Provider Response Snapshot
* Flexible Configuration
* Non-Core Extension Data

但不能成为逃避数据库设计的工具。

---

# 56. 禁止 JSONB 万能化

错误：

```text
customers
├── id
└── data jsonb
```

把：

```text
name
email
phone
status
currency
address
```

全部塞进去。

核心可查询业务字段必须正规建模。

---

# 57. JSONB 中的重要字段应升级为正式 Column

如果一个 JSONB Key：

* 经常 Filter
* 经常 Sort
* 经常 Join
* 经常 Report
* 属于核心业务规则

应考虑成为正式 Column。

---

# 58. JSONB 必须有 Schema 意识

即使数据库允许动态 JSON：

Application 层也必须拥有明确 Model / Validation。

不得将：

```text
Map<String, Object>
```

无限扩散。

---

# 59. Money 数据类型

所有金额字段必须使用：

```text
numeric / decimal
```

禁止：

```text
real
double precision
float
```

处理核心金额。

---

# 60. Money 必须定义 Precision 与 Scale

金额 Column 必须明确：

```text
precision
scale
```

例如实际值需要根据业务确定：

```text
numeric(p, s)
```

Cursor 不得随意统一选择一个精度给所有金融数据。

---

# 61. 金额必须伴随 Currency

多货币环境中的金额：

必须能够明确知道：

```text
amount
currency_code
```

禁止：

```text
amount = 100
```

却不知道是什么货币。

---

# 62. 金额字段必须表达含义

不要只使用：

```text
amount
```

当一个 Table 有多个金额。

应该：

```text
subtotal_amount
discount_amount
tax_amount
total_amount
paid_amount
balance_amount
```

---

# 63. Rate 与 Money 不同

以下：

```text
exchange_rate
commission_rate
tax_rate
discount_rate
```

必须根据业务精度独立设计。

不能直接沿用 Money Scale。

---

# 64. Rate 禁止使用 Float

Rate 同样优先：

```text
numeric
```

避免 Binary Floating Point Error。

---

# 65. Percentage 必须定义存储含义

例如：

```text
8%
```

数据库究竟保存：

```text
8
```

还是：

```text
0.08
```

必须统一定义。

禁止不同 Module 使用不同含义。

---

# 66. 时间存储标准

服务器时间与用户显示时间必须分离。

核心 DateTime 默认优先使用：

```text
timestamp with time zone
```

即 PostgreSQL：

```text
timestamptz
```

---

# 67. 时间统一按绝对时间存储

系统核心事件时间：

```text
created_at
updated_at
approved_at
paid_at
posted_at
```

必须能够表达准确时间点。

不得依赖服务器 Local Time。

---

# 68. Date 与 DateTime 必须区分

只有日期含义：

```text
birth_date
invoice_date
leave_date
```

可使用：

```text
date
```

准确事件发生时间：

```text
created_at
paid_at
approved_at
```

使用：

```text
timestamptz
```

不得混淆。

---

# 69. Timezone 属于业务 Context

例如：

```text
Tenant Timezone
Company Timezone
User Timezone
Outlet Timezone
```

应作为明确配置存在。

不得依赖 PostgreSQL Server Timezone 表达所有业务时区。

---

# 70. created_at

核心业务 Table 默认应考虑：

```text
created_at
```

且：

```text
NOT NULL
```

---

# 71. updated_at

可修改业务记录通常应拥有：

```text
updated_at
```

用于追踪最后修改时间。

---

# 72. created_by / updated_by

对于需要业务追踪的 Table：

应考虑：

```text
created_by
updated_by
```

但不能取代正式 Audit Log。

---

# 73. Audit Field 不等于 Audit Log

```text
created_at
updated_at
created_by
updated_by
```

只能回答：

> 谁最后改了。

真正 Audit Log 必须能够追踪：

```text
Before
After
Action
Actor
Time
```

---

# 74. Soft Delete 不得无脑加入所有 Table

不是所有 Table 都必须：

```text
deleted_at
```

必须根据 Domain 决定。

适合：

```text
Master Data
Configurable Data
Recoverable Data
```

交易类数据通常更适合：

```text
Cancel
Void
Reverse
Archive
```

而不是普通 Soft Delete。

---

# 75. Soft Delete 标准

如果 Domain 使用 Soft Delete：

应统一使用明确字段。

例如：

```text
deleted_at
deleted_by
```

不得部分 Table 使用：

```text
is_deleted
```

部分使用：

```text
delete_flag
```

部分使用：

```text
status = DELETE
```

无规律混合。

---

# 76. Soft Deleted Data 默认不得返回

Repository / Query 必须清楚处理 Soft Delete Scope。

禁止忘记过滤导致已删除数据重新出现在业务页面。

---

# 77. 历史交易不得 Soft Delete 当作取消

例如：

```text
Invoice
Payment
Payroll
Stock Movement
Journal Entry
```

通常不应：

```text
deleted_at = now
```

来代表业务取消。

应使用正式：

```text
VOID
REVERSED
CANCELLED
```

等业务状态。

---

# 78. Financial Record 不允许静默修改

已 Posting / Finalized 的金融记录：

原则上不得直接：

```text
UPDATE amount
```

覆盖历史。

应根据业务使用：

```text
Adjustment
Reversal
Correction Entry
Void
```

---

# 79. Inventory Movement 必须可追踪

库存不能只保存：

```text
current_stock = 100
```

而无法知道为什么变成 100。

库存系统必须能够通过：

```text
Stock Movement
Stock Transaction
Ledger
```

追踪变化。

---

# 80. Balance 与 Ledger 分离

涉及：

```text
Stock Balance
Account Balance
Wallet Balance
```

时必须明确：

```text
Balance
```

是当前快照，

```text
Ledger / Movement
```

是历史事实。

不能只存 Balance 而没有历史依据。

---

# 81. Historical Snapshot 原则

历史交易必须保存完成交易当时需要的 Snapshot。

例如 Invoice：

即使 Customer 后来修改：

```text
Name
Address
Tax Number
```

旧 Invoice 仍然应该保留原交易信息。

---

# 82. Snapshot 不等于重复所有数据

只保存业务必须保留的历史事实。

不要无脑复制完整 Entity JSON。

---

# 83. Master Data 与 Transaction Data 必须区分

Master Data：

```text
Customer
Supplier
Product
Employee
Account
```

Transaction Data：

```text
Sales Order
Invoice
Payment
Purchase Order
Stock Movement
Payroll
```

两者生命周期不同。

Cursor 不得使用相同删除及修改策略。

---

# 84. Header / Line Pattern

具有多明细的交易：

例如：

```text
Sales Order
Invoice
Purchase Order
```

应合理使用：

```text
Header
+
Line Items
```

例如：

```text
sales_orders
sales_order_items
```

---

# 85. Line Item 必须保留交易事实

例如 Order Item：

应保存当时交易需要的：

```text
product_id
product_name snapshot if required
sku
quantity
unit_price
discount
tax
line_total
```

具体字段根据 Domain 定义。

不能只依赖 Product 当前资料。

---

# 86. Table Ownership

每个 Table 必须属于明确 Domain Module。

例如：

```text
customers
→ CRM

sales_orders
→ Sales

stock_movements
→ Inventory

purchase_orders
→ Procurement

employees
→ HRM
```

---

# 87. 禁止跨模块随意修改 Table

例如：

Sales Module 不允许直接：

```sql
UPDATE stock_balances
```

应该调用 Inventory Domain。

数据库 Table Ownership 必须与代码 Module Boundary 一致。

---

# 88. 不同 Domain 不应共享一个万能 Table

错误：

```text
transactions
```

同时存：

* Sales
* Payment
* Inventory
* Payroll
* Procurement

除非它本身拥有真正统一且经过设计的业务 Domain。

---

# 89. Association Table

Many-to-Many Relationship 应使用清晰 Join Table。

例如：

```text
user_roles
role_permissions
employee_skills
```

不得：

```text
role_ids = "1,2,3,4"
```

以字符串保存 Foreign Key List。

---

# 90. 禁止 CSV Foreign Key

严禁：

```text
company_ids = "id1,id2,id3"
```

应正规化为 Relationship Table。

---

# 91. Array 使用原则

PostgreSQL Array 只用于真正适合 Array 的数据。

如果 Array Element：

* 需要独立查询
* 需要 Foreign Key
* 有自己的属性
* 有生命周期

应该建独立 Table。

---

# 92. Normalization 原则

核心业务数据默认优先：

```text
Normalized Relational Design
```

减少：

* Data Duplication
* Update Anomaly
* Inconsistent Data

---

# 93. 不得盲目追求最高 Normal Form

历史 Snapshot、Analytics、Read Model：

可以根据实际需求适当 Denormalize。

但必须明确原因。

---

# 94. Denormalization 必须有依据

允许 Denormalization 的常见原因：

* Performance
* Historical Snapshot
* Reporting
* Read Model
* Immutable Transaction Fact

不得因为：

> Join 写起来麻烦

就随意复制字段。

---

# 95. Unique Constraint 是业务规则的一部分

如果业务要求：

> 同 Tenant Email 唯一。

数据库必须考虑：

```text
UNIQUE
```

不能只在 Java：

```text
if (!exists)
    insert
```

因为存在并发竞争。

---

# 96. Application Validation 不能代替 Unique Constraint

正确：

```text
Application Pre-check
+
Database Unique Constraint
```

Application 提供良好 Error。

Database 保证最终一致性。

---

# 97. Case-Insensitive Unique

例如：

```text
Email
Username
Code
```

如果业务要求大小写不敏感唯一：

必须明确 Normalization Strategy。

禁止：

```text
ABC@email.com
abc@email.com
```

意外成为两个账户。

---

# 98. Email Normalization

Email 是否：

* Trim
* Lowercase
* Case Handling

必须由统一 Identity Standard 定义。

Cursor 不得不同模块自行处理。

---

# 99. Index 原则

Index 必须服务于实际 Query Pattern。

常见需要考虑 Index：

```text
Foreign Key
tenant_id
company_id
status
created_at
business_number
searchable identifier
```

但不得看到 Column 就全部建立 Index。

---

# 100. Foreign Key Index

PostgreSQL 不会因为 Foreign Key 自动为 Referencing Column 创建 Index。

对于常用：

```text
JOIN
FILTER
DELETE CHECK
```

的 Foreign Key：

必须评估是否需要 Index。

---

# 101. Tenant Composite Index

Multi-Tenant Query 常见：

```text
WHERE tenant_id = ?
AND status = ?
ORDER BY created_at DESC
```

应根据真实 Query Pattern 考虑：

```text
Composite Index
```

---

# 102. Composite Index 顺序必须基于 Query

禁止随机：

```text
INDEX (status, tenant_id, created_at)
```

必须根据：

* Filter
* Selectivity
* Sort
* Query Pattern

设计。

---

# 103. Index 不是越多越好

过多 Index 会增加：

* INSERT Cost
* UPDATE Cost
* Storage
* Maintenance

Cursor 不得为了“性能”给每个字段建立 Index。

---

# 104. 禁止重复 Index

创建新 Index 前必须检查：

* Existing Index
* Composite Index
* Unique Constraint

是否已经覆盖。

---

# 105. Partial Index

PostgreSQL Partial Index 可以用于明确 Query Pattern。

例如：

```text
active records
pending jobs
unprocessed events
```

但必须有真实性能需求。

不得过度设计。

---

# 106. Expression Index

Expression Index 只有在实际 Query 使用相同表达式时才建立。

不得为了“以后可能会搜索”提前创建。

---

# 107. Full Table Scan 不一定是错误

小 Table 或低选择性 Query：

Full Scan 可能是合理行为。

不得机械看到：

```text
Seq Scan
```

就强行加 Index。

---

# 108. 性能优化必须有证据

优化复杂 Query 前应使用：

```text
EXPLAIN
EXPLAIN ANALYZE
```

等实际数据库证据。

禁止凭感觉增加大量 Index。

---

# 109. Query 必须只读取需要的数据

禁止默认：

```sql
SELECT *
```

用于所有生产查询。

特别是：

* 大型 Table
* Sensitive Table
* API List

应读取需要字段。

---

# 110. Pagination

持续增长的大 Table 必须考虑 Pagination。

禁止：

```text
findAll()
```

读取：

```text
All Customers
All Invoices
All Audit Logs
```

---

# 111. Stable Sort

Pagination 必须拥有稳定排序。

例如：

```text
ORDER BY created_at DESC, id DESC
```

避免同一时间值导致分页：

* Duplicate
* Missing

---

# 112. Offset Pagination

普通后台页面可以使用：

```text
Offset Pagination
```

但超大型数据或高频 Feed：

应评估：

```text
Keyset / Cursor Pagination
```

Cursor 不得一开始全部复杂化。

---

# 113. N+1 Query

Spring Boot / ORM 设计必须防止：

```text
1 Query Parent
+
N Query Children
```

尤其：

* List API
* Dashboard
* Reporting

---

# 114. Fetch Strategy 必须明确

JPA Relationship 不得所有关系无脑：

```text
EAGER
```

也不能无脑：

```text
LAZY
```

必须根据 Use Case 设计。

---

# 115. 禁止通过 EAGER 解决所有 Lazy 问题

将所有 Relationship 改成：

```text
EAGER
```

通常会制造更大性能问题。

应通过：

* Projection
* Explicit Fetch
* Query
* DTO

解决。

---

# 116. Entity Relationship 不得无限双向

禁止：

```text
A → B
B → A
A → B → A
```

导致：

* Serialization Loop
* Complex Persistence
* Hidden Query

Relationship 必须有明确 Ownership。

---

# 117. Database Entity 不得直接作为 API Contract

数据库字段：

```text
Internal Model
```

API DTO：

```text
External Contract
```

必须保持边界。

不得因为 Table 新增一个敏感 Column：

就自动出现在 API Response。

---

# 118. Sensitive Data Classification

数据库字段应根据业务识别：

```text
Public
Internal
Confidential
Highly Sensitive
Secret
```

特别注意：

* Password
* Salary
* Bank
* Identity Document
* API Credential
* Token
* Personal Data

---

# 119. Password 永远不能明文保存

密码必须保存经过安全 Password Hash Algorithm 处理后的结果。

数据库不得存在：

```text
plain_password
password_text
```

---

# 120. Password Hash 与 Encryption 不同

Password 使用：

```text
One-Way Hash
```

不能使用：

```text
Encrypt then decrypt password
```

作为正常认证方案。

---

# 121. Secret 不得明文入普通 Table

例如：

```text
API Key
OAuth Secret
Private Key
Bank Credential
```

应使用：

* Secret Manager
* Encryption
* Restricted Storage

等明确安全方案。

Cursor 不得默认普通 VARCHAR 明文存储。

---

# 122. Token Storage

Access / Refresh Token 是否保存、如何保存：

必须遵循 Authentication Security Design。

Cursor 不得自行将完整长期 Token 明文保存。

---

# 123. Personal Data 最小化原则

数据库只保存业务真正需要的数据。

不要因为：

> “以后可能会有用”

收集大量个人敏感数据。

---

# 124. 加密字段必须明确搜索需求

如果字段需要：

```text
Encryption at Application Layer
```

必须提前考虑：

* Search
* Sort
* Unique
* Index

不能先加密后才发现业务需要直接查询。

---

# 125. Audit Log 必须 Append-Oriented

Audit Log 原则：

> 已发生的 Audit Record 不应随意 UPDATE。

应以 Append 为主。

---

# 126. Audit Log 不得被普通 Tenant User 修改

普通业务 API：

不得提供：

```text
Edit Audit Log
Delete Audit Log
```

能力。

Audit Retention 应由平台政策控制。

---

# 127. Audit Log 必须包含 Tenant Context

Multi-Tenant Audit：

应能够识别：

```text
tenant_id
company_id if applicable
actor
action
resource
timestamp
result
```

---

# 128. Audit Before / After

对于重要修改：

应根据安全与数据体量保存足够：

```text
Before
After
Changed Fields
```

不得把 Password、Token 等敏感值写入 Audit。

---

# 129. Transaction 原则

多个数据库操作构成同一个业务原子动作时：

必须使用 Transaction。

原则：

```text
All Success
or
All Rollback
```

---

# 130. Transaction Boundary 属于 Business Use Case

不要简单按照：

```text
Controller Request
```

就全部包成巨大 Transaction。

Transaction 必须围绕业务一致性边界。

---

# 131. 外部 API 不应长期占用 DB Transaction

禁止：

```text
BEGIN TRANSACTION
↓
Call AI for 30 seconds
↓
Call Payment API
↓
Send Email
↓
COMMIT
```

这样长期持有数据库资源。

---

# 132. External Side Effect 与 Transaction

数据库提交和外部 Event / Message 需要一致性时：

未来应考虑：

```text
Transactional Outbox
```

等可靠模式。

但 Cursor 不得无需求提前加入复杂架构。

---

# 133. Concurrency 必须考虑

以下业务必须考虑并发：

```text
Stock
Payment
Balance
Quota
Sequence
Subscription Usage
Booking
Approval
```

---

# 134. Check-Then-Update 风险

错误：

```text
Check stock = 10
↓
if stock >= 5
↓
stock = 5
```

多个 Request 同时执行可能 Oversell。

必须使用：

* Atomic Update
* Lock
* Version
* Constraint

等正确并发控制。

---

# 135. Optimistic Lock

对于适合低冲突更新的业务：

可以考虑：

```text
version
```

进行 Optimistic Lock。

例如：

```text
@Version
```

但不得所有 Table 无脑添加。

---

# 136. Pessimistic Lock

只有确实存在强一致性并发场景时才使用。

例如部分：

```text
Stock Allocation
Sequence
Critical Balance
```

Cursor 不得因为害怕并发把所有 Query 加 Lock。

---

# 137. Constraint 优先保证最终正确性

以下规则适合数据库 Constraint：

```text
NOT NULL
UNIQUE
FOREIGN KEY
CHECK
```

Application Validation 提供 UX。

Database Constraint 负责最后防线。

---

# 138. CHECK Constraint

稳定且明确的数据规则：

可以考虑：

```text
CHECK
```

例如：

```text
quantity >= 0
```

但复杂业务规则不要全部塞进 CHECK Constraint。

---

# 139. Database 不承担全部 Business Logic

PostgreSQL 负责：

* Data Integrity
* Constraint
* Persistence

Spring Boot 负责：

* Business Workflow
* Authorization
* Domain Rule
* Approval
* Complex Calculation

禁止把整个 AIOS Business Logic 写成 Database Trigger。

---

# 140. Trigger 使用原则

PostgreSQL Trigger 不是默认业务实现方式。

允许用于：

* 技术一致性
* 特定审计
* 必须数据库级保证的机制

复杂业务流程禁止大量隐藏在 Trigger 内。

---

# 141. Trigger 必须可发现

如果确实使用 Trigger：

必须：

* 有明确命名
* 有 Migration
* 有 Documentation
* 有测试

禁止存在团队完全不知道的 Hidden Business Logic。

---

# 142. Stored Procedure 使用原则

默认核心业务逻辑仍由 Spring Boot Domain 层负责。

Stored Procedure 只在：

* 明确性能需求
* 数据密集操作
* 特定数据库事务能力

时考虑。

不得为了少写 Java 将整个 Domain 搬到 PostgreSQL。

---

# 143. Reporting Query 与 Transaction Query 分离意识

Operational API Query：

优先服务业务操作。

大型 Report：

应避免直接使用超复杂 Query 长时间压住 Production DB。

未来数据量上升后应逐渐使用：

```text
Analytics Layer
Read Model
Data Warehouse
```

---

# 144. Dashboard 不得无限查询主库

一个 Dashboard 不应：

```text
每次刷新执行几十个巨大 Aggregate Query
```

未来应根据性能：

* Pre-Aggregate
* Cache
* Analytics Store

但必须基于实际性能问题引入。

---

# 145. Aggregate 数据必须有定义

例如：

```text
Daily Sales
Monthly Revenue
Active Customers
Inventory Value
```

必须明确：

* Data Source
* Timezone
* Currency
* Status Included
* Refund Handling
* Cancellation Handling

不能仅凭 SQL SUM 就视为正确。

---

# 146. Finance Reporting 必须由业务规则定义

Profit & Loss、Balance Sheet 等：

不是：

> 查几个 Table SUM 一下。

必须依据：

* Accounting Rule
* Posting
* Account Structure
* Fiscal Period

建立。

Cursor 不得自行发明财务逻辑。

---

# 147. Currency Conversion 不得覆盖原始金额

多货币交易必须根据业务保留：

```text
Original Amount
Original Currency
Exchange Rate
Converted Amount
Base Currency
```

中需要的历史数据。

不能转换后只保留最终数字。

---

# 148. Exchange Rate 必须保存交易时值

历史交易需要使用：

> 当时生效的 Exchange Rate。

不能每次显示旧 Invoice 时重新读取今天 Rate。

---

# 149. Rounding Result 必须按业务保存

如果业务明确某个步骤：

```text
Round to 2 decimal
```

必须由 Backend Calculation Rule 确定。

数据库不得自行隐式改变金额。

---

# 150. Precision Loss 禁止

Migration / Type Conversion 时：

必须检查是否会：

```text
truncate
round
overflow
```

已有数据。

不得静默损失精度。

---

# 151. Sequence / Identity

数据库内部 Sequence 可用于：

* Technical Sequence
* Business Number Counter

但必须明确 Scope。

例如：

```text
Global
Tenant
Company
Year
```

不得一开始默认所有企业共用一个业务号码。

---

# 152. Business Number Unique

如果 Invoice Number 应在 Company 内唯一：

必须数据库约束：

```text
tenant_id
company_id
invoice_number
```

的合理 Unique Scope。

---

# 153. Identifier 不允许重复使用

Void / Cancel 的业务编号：

原则上不得回收后分配给新 Transaction。

历史追踪必须保持唯一。

---

# 154. Reference Number 与 Internal ID 分离

第三方 Payment ID、Bank Reference、Provider Transaction ID：

应独立保存。

不要替代内部：

```text
id
```

---

# 155. External ID 必须考虑 Provider Scope

如果不同 Provider 可能产生相同 Reference：

Unique Constraint 应考虑：

```text
provider
external_id
```

而不是只约束 external_id。

---

# 156. Webhook Event 必须去重

第三方 Webhook：

应保存或能够识别：

```text
provider_event_id
```

并建立必要 Unique Constraint。

防止重复处理。

---

# 157. Idempotency Key

高风险 Create / Payment API：

如采用：

```text
idempotency_key
```

数据库必须设计唯一作用范围。

例如：

```text
tenant_id
operation_type
idempotency_key
```

具体根据 Use Case 定义。

---

# 158. Settings 数据模型

Settings 必须区分 Scope：

```text
System
Tenant
Company
User
Module
```

不得建立一个：

```text
settings(key, value)
```

然后所有设置无边界混入。

---

# 159. Settings Value 类型必须可控

如果使用 JSONB 存部分 Settings：

必须有：

* Schema
* Validation
* Default
* Version

不能任意 Key / Value 无规则增长。

---

# 160. Feature Control

Feature Flag / Plan Feature：

必须明确：

```text
Feature Definition
Plan Assignment
Tenant Override
Effective State
```

不得只在：

```text
tenants.feature_a = true
feature_b = true
feature_c = true
```

不断追加 Boolean Column。

---

# 161. Permission 数据模型

Permission 应使用统一 Permission Domain。

禁止每个业务 Table 添加：

```text
can_edit
can_delete
can_approve
```

作为用户权限系统。

---

# 162. Role 与 Permission Many-to-Many

通常通过：

```text
roles
permissions
role_permissions
```

等正规关系建模。

不得把 Permission List 存成：

```text
"read,write,delete"
```

字符串。

---

# 163. Organization Hierarchy

组织结构必须允许：

```text
Parent
Child
```

并防止：

```text
Circular Hierarchy
```

例如：

```text
A parent B
B parent C
C parent A
```

不得成立。

---

# 164. Tree Model 必须根据 Query 选择

Organization、Category 等 Tree：

可以根据实际需要使用：

* Adjacency List
* Closure Table
* Materialized Path

Cursor 不得为了“高级”自行选择复杂 Tree Model。

默认从最简单满足需求的结构开始。

---

# 165. Address 建模

Address 不得默认写死只有：

```text
Malaysia
```

应允许未来 Country / Region Variation。

但当前阶段也不得过度拆成几十个 Table。

---

# 166. Country / Currency Code

国家、货币等标准 Code：

应使用统一标准 Code。

例如 Currency 应以 ISO 4217 类标准 Code 为基础。

不得：

```text
Malaysia Dollar
RinggitMalaysia
RM
```

随机作为数据库 Canonical Value。

---

# 167. Display Name 与 Canonical Code 分离

例如：

```text
currency_code = MYR
display = RM
```

不要让 Display Symbol 成为核心数据库 Identifier。

---

# 168. Language / Locale

未来 Localization 相关数据必须明确：

```text
language_code
locale
timezone
```

不要混成一个字符串字段。

---

# 169. Address / Name 长度不能根据当前样本决定

不能因为当前测试：

```text
Customer Name 都很短
```

就把字段设计成极小长度。

必须依据真实业务范围。

---

# 170. Import Data 必须经过 Staging / Validation 思维

大型 CSV / Excel Import：

不得：

```text
read row
↓
direct insert production tables
```

而没有 Validation。

应考虑：

```text
Parse
Validate
Detect Duplicate
Report Error
Commit
```

---

# 171. Bulk Insert 必须考虑 Transaction Size

大型 Import：

不能无脑：

> 一个百万 Row 的巨大 Transaction。

应根据数据量进行：

* Batch
* Chunk
* Staging

设计。

---

# 172. Bulk Update 必须考虑 Lock

大规模 Update：

可能导致：

* Long Lock
* Table Bloat
* Performance Degradation

Production Migration 必须谨慎。

---

# 173. PostgreSQL Vacuum / Bloat Awareness

Cursor 不得通过大量频繁：

```text
UPDATE same huge table
DELETE huge dataset
```

却完全忽略 PostgreSQL MVCC 特性。

大规模数据维护属于专门运维任务。

---

# 174. Partition 使用原则

Table Partition 只在真实数据规模、Retention 或 Query Pattern 需要时使用。

可能适合未来：

```text
audit_logs
events
large transaction history
```

但不得项目初期给所有 Table 建 Partition。

---

# 175. Archive 原则

大量长期历史数据未来可能需要：

```text
Archive Strategy
```

但 Archive 不等于 Delete。

Finance、Audit、Compliance 数据必须遵循对应 Retention Policy。

---

# 176. Retention Policy

以下数据应未来拥有明确 Retention：

```text
Audit
Log
AI Conversation
Notification
Webhook
Temporary File
Session
```

Cursor 不得自行设置随意删除周期。

---

# 177. AI Data 与业务数据边界

以下 AI 数据：

```text
Prompt
Embedding
Chunk
Conversation
AI Memory
Agent Run
Model Output
```

必须明确：

* Tenant
* User
* Permission
* Source
* Retention

---

# 178. AI Embedding 不是 Source of Truth

Embedding / Vector：

可以重新生成。

Original Source：

必须保留正确 Source Reference。

禁止只有 Vector：

却无法找到原始 Document。

---

# 179. RAG Chunk 必须带 Source Metadata

至少应能够关联：

```text
tenant
source_document
chunk
version
permission
```

防止 AI 搜索错误 Tenant 或过期内容。

---

# 180. AI Memory 必须隔离

AI Memory 必须有明确 Scope：

```text
tenant_id
user_id
agent_id
session_id
```

根据 Memory 类型设计。

禁止所有 AI Memory 存进一个没有 Scope 的 Table。

---

# 181. Prompt Version

如果 Prompt Center 支持正式业务 Prompt：

应考虑：

```text
Prompt Version
Status
Published Version
Created By
Updated At
```

重要 Prompt 不应每次直接覆盖导致无法追踪历史。

---

# 182. Workflow Version

正式 Workflow 被业务 Transaction 使用后：

如果流程改变：

必须考虑 Version。

不能让过去审批记录因为今天 Workflow 改变：

> 无法解释过去发生了什么。

---

# 183. Configuration Historical Consistency

如果 Transaction 依赖：

```text
Tax Rate
Commission Rule
Exchange Rate
Price
```

必须保存交易时真正使用的值。

不能只保存 Config ID 后永远读取最新配置。

---

# 184. Database View

View 可以用于：

* Stable Read Model
* Reporting
* Security Abstraction

但不得为了避免写清楚 Query 而大量创建隐藏复杂业务 View。

---

# 185. Materialized View

只在真实 Analytics / Performance 需求下使用。

必须明确：

```text
Refresh Strategy
Staleness
Ownership
```

不得默认实时。

---

# 186. Database Function

Database Function 应用于明确数据库层职责。

不能成为隐藏 Spring Boot Business Logic 的地方。

---

# 187. Schema 使用原则

PostgreSQL Schema 是否按：

```text
core
crm
sales
finance
```

区分，属于项目级架构决策。

如果项目已有 Schema Strategy：

必须遵守。

如果当前统一使用：

```text
public
```

Cursor 不得因单一模块擅自搬迁。

---

# 188. 不得混乱使用 Schema

禁止：

```text
CRM 放 public
Sales 放 sales schema
Finance 放 finance schema
HRM 又放 public
```

没有全局策略。

---

# 189. Table Comment

重要业务 Table / 特殊 Column：

如果名称无法完整表达规则，

可以使用 Database Comment 说明。

但 Comment 不能代替正式文档和清晰命名。

---

# 190. Constraint Naming

Constraint 应使用可识别统一规则。

例如：

```text
pk_
fk_
uk_
ck_
```

具体 Naming Pattern 跟随项目统一标准。

不得让所有 Constraint 都保留无法识别的随机生成名。

---

# 191. Index Naming

Index 应使用清晰统一命名。

例如逻辑：

```text
idx_{table}_{columns}
```

或项目标准。

重点：

> 看名称能够理解用途。

---

# 192. Migration Naming

Migration Name 必须描述：

> 发生什么变化。

正确：

```text
create_sales_orders
add_currency_to_invoices
add_customer_email_unique_constraint
```

禁止：

```text
update_db
fix_table
changes
new_migration
final_fix
```

---

# 193. Migration 不得包含无关修改

一个 Feature Migration 应尽量聚焦。

禁止修一个 Customer Feature：

顺便：

* 改 Finance
* 改 HRM
* 删除 Index
* Rename 其他 Table

除非存在明确依赖。

---

# 194. Data Backfill

新增必填字段时必须设计：

```text
Existing Row 如何得到正确值？
```

不能：

```text
ADD COLUMN x NOT NULL
```

直接让 Existing Data 失败。

---

# 195. Backfill 必须可验证

Migration 后必须能够检查：

* 是否有 NULL
* 是否有 Invalid Data
* 是否有 Duplicate
* 是否符合 Constraint

---

# 196. 大规模 Backfill 要分批

Production 大 Table：

不得无脑一次：

```text
UPDATE millions of rows
```

必须根据规模设计安全 Migration。

---

# 197. Column Rename 必须检查所有使用方

Rename：

```text
customer_name
→ legal_name
```

前必须检查：

* Entity
* Repository
* Query
* API
* Report
* Integration
* Export
* AI
* BI

---

# 198. Column Type Change

Type Change 前必须检查：

```text
是否可转换？
是否损失数据？
是否锁表？
是否破坏 Index？
是否影响 Application？
```

---

# 199. Drop Column 属于高风险操作

Cursor 不得因为：

> 看起来没使用

就 Drop Column。

必须搜索：

* Code
* SQL
* Report
* Integration
* Migration
* Job

确认无使用方。

---

# 200. Drop Table 属于极高风险操作

必须有明确用户要求或经过正式确认。

Cursor 不得自行：

```text
这个 Table 好像重复，所以删掉。
```

---

# 201. Rename Table 也属于 Breaking Change

必须检查：

* Foreign Key
* Query
* ORM Mapping
* Reporting
* Integration
* Manual Operations

不能视为单纯整理名称。

---

# 202. Production 数据修复

如果需要修复 Production Data：

必须区分：

```text
Schema Migration
Data Migration
Operational Data Fix
```

不能在 Application 启动时偷偷批量修改历史数据。

---

# 203. Application Startup 不应执行危险 Migration

禁止 Spring Boot 启动时：

```text
scan all rows
update data
delete old rows
repair finance
```

作为长期启动逻辑。

应使用正式 Migration / Job。

---

# 204. Seed Data

Seed Data 必须分为：

```text
System Required Data
Development Demo Data
Test Data
```

---

# 205. Production Seed 不得包含 Demo Data

禁止 Production 自动创建：

```text
Demo Customer
Test Admin
Fake Order
Sample Payment
```

---

# 206. Default Super Admin

不得通过公开固定密码创建：

```text
admin / admin123
```

正式 Super Admin 初始化必须有安全流程。

---

# 207. Test Database 必须隔离

Automated Test：

不得连接：

```text
Production Database
Shared Production-like Writable Database
```

测试环境必须独立。

---

# 208. Test Data 必须可重复

Test 不应依赖：

> 数据库里面刚好已经有 Customer A。

Test 应自行建立所需 Fixture / Dataset。

---

# 209. Database Connection

Application 应通过 Connection Pool 管理数据库连接。

Cursor 不得：

> 每个 Request 手动建立一个新 PostgreSQL Connection。

Spring Boot 应遵循项目标准 DataSource。

---

# 210. Connection Pool 不是越大越好

不得因为性能问题：

直接将 Pool：

```text
10
→
500
```

而没有数据库容量分析。

连接数必须根据：

* Application Instance
* PostgreSQL Capacity
* Workload

设计。

---

# 211. Long Transaction 必须避免

Transaction 长时间保持：

会导致：

* Lock
* MVCC Bloat
* Resource Usage

业务流程必须缩小 Transaction Scope。

---

# 212. Query Timeout

高风险或外部触发 Query：

应根据系统策略考虑合理 Timeout。

不得让错误 Query 无限运行。

---

# 213. Lock Timeout

涉及高并发敏感业务时：

可根据系统策略设置 Lock Timeout。

不得无限等待造成整个请求链堆积。

---

# 214. Database Error 不得直接暴露给用户

禁止 API 返回：

```text
duplicate key value violates unique constraint...
SQLSTATE...
relation does not exist...
```

给普通用户。

Backend 应映射为：

```text
Business / Validation / Conflict Error
```

---

# 215. Database Error 不得全部吞掉

同时禁止：

```text
catch SQLException
return success
```

数据库失败必须正确向上处理。

---

# 216. Unique Violation 必须处理并发情况

即使 Application 已经：

```text
existsByEmail()
```

仍然必须正确处理 Database Unique Violation。

因为并发请求可能同时通过 Pre-check。

---

# 217. Deadlock Awareness

复杂并发 Transaction 必须保持一致：

```text
Lock Order
Update Order
```

降低 Deadlock 风险。

如果发生 Deadlock：

应查 Root Cause。

不能简单无限 Retry。

---

# 218. Delete 与 Referential Integrity

删除 Parent 前：

必须明确 Child Data 如何处理。

不得通过：

```text
disable FK
delete
enable FK
```

绕过数据完整性。

---

# 219. 禁止关闭 Constraint 解决问题

如果 Migration 因 Constraint 失败：

说明数据或 Migration 有问题。

不能默认：

```text
disable constraint
```

解决。

---

# 220. 禁止 Production 使用超级权限应用账户

Application Database User：

应遵循：

```text
Least Privilege
```

正常 Runtime 不应拥有：

```text
DROP DATABASE
CREATE SUPERUSER
```

等权限。

---

# 221. Migration User 与 Runtime User 可以分离

如果基础设施允许：

Migration Account 可以拥有 Schema Change 权限。

Runtime Application Account 仅拥有必要：

```text
SELECT
INSERT
UPDATE
DELETE
```

等权限。

这是推荐安全方向。

---

# 222. Database Credential

Database：

```text
Host
Username
Password
Connection String
```

不得写进：

* Git
* Source Code
* Frontend
* README Example with real credential

必须使用安全 Configuration。

---

# 223. Frontend 永远不得知道 PostgreSQL Credential

React：

绝对禁止直接连接 PostgreSQL。

数据库 Credential 不得进入：

```text
VITE_*
```

公开 Frontend Environment Variable。

---

# 224. Python AI 默认不得直接写核心 DB

Python AI Service：

原则上通过：

```text
Spring Boot API
```

执行核心业务动作。

禁止 AI Agent：

```text
Generated SQL
↓
Direct Execute Production PostgreSQL
```

---

# 225. AI Read Access 也必须受控

即使只读：

AI 也不能获得：

> 全 Tenant 数据库任意 SELECT 权限。

AI Retrieval 必须经过：

* Tenant
* Permission
* Scope
* Data Classification

控制。

---

# 226. SQL Generated by LLM

LLM 生成 SQL：

不得直接在 Production Operational DB 执行。

如未来提供 AI Analytics：

必须通过受控：

* Read Model
* Semantic Layer
* Query Validation
* Read-Only Credential
* Scope Control

设计。

---

# 227. Backup Awareness

任何重大 Database Change：

必须考虑：

```text
Backup
Recovery
Rollback / Roll Forward
```

但 Backup 本身由 Infrastructure Standard 管理。

---

# 228. Migration Rollback

不是所有 PostgreSQL Migration 都适合简单 Down Migration。

特别是：

```text
Delete Data
Drop Column
Type Conversion
```

可能无法真正恢复。

所以 Migration 设计必须优先：

> Forward Recovery。

---

# 229. 不得伪造 Rollback

禁止写：

```text
rollback supported
```

但实际上已经永久丢失数据。

必须诚实说明 Recoverability。

---

# 230. Disaster Recovery

数据库架构不得建立：

> 只有一份数据，没有 Backup

的长期 Production 设计。

具体 RPO / RTO 由 Cloud / Infrastructure Standard 定义。

---

# 231. Monitoring

Production PostgreSQL 应未来能够监控：

```text
Connections
CPU
Memory
Disk
Locks
Slow Queries
Replication
Storage Growth
Transaction
Error
```

---

# 232. Slow Query

发现 Slow Query 时应先检查：

```text
Query Plan
Rows
Index
Join
Filter
Sort
Data Volume
```

禁止第一反应：

> 升级更大的服务器。

---

# 233. Database Size Growth

大型 Table 应关注：

```text
Growth Rate
Retention
Index Size
Archive
Partition Need
```

不能等磁盘满了才处理。

---

# 234. Audit / Event 大表

Audit、Event、Notification 等高增长 Table：

从设计开始必须：

* Pagination
* Created At Index
* Tenant Scope

并保留未来：

```text
Partition / Archive
```

能力。

但当前无需过度实现。

---

# 235. 数据库不要提前为未来几十亿数据复杂化

原则：

> Architecture must not block scale.

但：

> Implementation must match current need.

禁止一开始就：

* 所有表 Partition
* 所有数据 Sharding
* 多 Region Write
* Distributed SQL

除非明确需求。

---

# 236. Sharding 属于重大架构决策

Cursor 不得自行加入：

```text
Database Sharding
```

必须经过架构批准。

---

# 237. Read Replica

未来可以用于：

* Reporting
* Heavy Read
* Analytics

但应用必须考虑：

```text
Replication Lag
```

不能要求强一致读取时错误使用 Replica。

---

# 238. Data Warehouse 与 PostgreSQL Operational DB

大型 BI / Forecast：

未来应逐渐通过：

```text
ETL / ELT
↓
Data Warehouse
```

处理。

不得长期将所有复杂 Analytics 压在 Operational DB。

---

# 239. Master Data

跨模块共享的 Master Data：

必须拥有明确 Owner。

例如：

```text
Company
Currency
Country
Product
Customer
Supplier
```

不能每个模块维护自己的版本。

---

# 240. Customer 与 User 不得混为一谈

```text
User
```

表示系统 Identity。

```text
Customer
```

表示 CRM Business Entity。

两者可以有关联。

但不能默认是同一个 Table。

---

# 241. Employee 与 User 不得混为一谈

```text
Employee
```

属于 HRM。

```text
User
```

属于 Authentication / Core。

员工可以没有系统账号。

系统 User 也不一定是 Employee。

必须允许建立关联而不是强行合并。

---

# 242. Supplier / Customer / Company Relationship

这些业务 Entity 即使字段类似：

也不得因为：

> 都有 Name / Phone / Address

就强行放入一个万能 `entities` Table。

除非未来明确建立 Party Domain。

---

# 243. 多态关系谨慎使用

类似：

```text
resource_type
resource_id
```

的 Generic Polymorphic Relationship：

使用前必须谨慎。

因为可能失去：

```text
Foreign Key Integrity
```

---

# 244. Polymorphic Reference 只用于真正通用平台能力

例如：

```text
Attachments
Comments
Audit
```

可能需要通用 Resource Reference。

但必须设计：

* Resource Type
* Permission
* Integrity
* Cleanup

不能随便使用。

---

# 245. File Association

File Center 与业务 Resource 的关系：

优先通过正式 Association：

```text
file_id
resource_type
resource_id
```

或明确业务 Join Table。

具体方式必须统一。

---

# 246. Comments / Activity

通用 Activity / Comment 系统：

必须拥有明确 Resource Scope。

不得每个 Module 创建完全不同 Comments Table。

如果 Core 已有统一能力：

必须复用。

---

# 247. Notification 数据

Notification 必须区分：

```text
Notification Definition / Event
Delivery
Recipient
Read State
```

不能所有内容塞一个巨大 Row 且没有扩展能力。

具体结构根据需求逐步实施。

---

# 248. Workflow / Approval 数据

Workflow Template 与 Runtime Instance：

必须区分。

例如：

```text
Workflow Definition
Workflow Version
Workflow Instance
Approval Step
Approval Decision
```

不能修改 Definition 后破坏历史 Instance。

---

# 249. Subscription / Billing

Platform Subscription 数据：

必须与 Tenant Business Finance 数据保持 Domain Boundary。

```text
AIOS Platform Billing
```

不等于：

```text
Tenant Finance Module
```

禁止混入同一个无边界 Invoice Table。

---

# 250. Super Admin 数据访问

普通 Tenant Query 默认：

```text
Tenant Scoped
```

Super Admin 跨 Tenant Query：

必须使用专门 Platform / Admin Access Pattern。

禁止为了 Super Admin：

取消所有 Repository Tenant Filter。

---

# 251. Global Data

Global Data 必须明确标记为：

> Platform Owned。

例如部分：

```text
Countries
Currencies
System Features
Plans
```

不得因为没有 tenant_id：

就自动认为任何 Table 都是 Global。

---

# 252. Global 与 Tenant Override

如果未来支持：

```text
Global Default
+
Tenant Override
```

必须建立清晰继承规则。

不能用 NULL / Magic Value 隐含复杂行为。

---

# 253. Schema Documentation

新增重要 Table 时，Cursor 必须能够说明：

```text
Purpose
Owner Module
Tenant Scope
Important Columns
Unique Rule
Foreign Key
Lifecycle
```

如果无法说明：

说明设计可能还不清楚。

---

# 254. Cursor 创建 Table 前自检

创建 Table 前必须检查：

* [ ] 是否已经存在类似 Table
* [ ] Owner Module 是否明确
* [ ] 是否需要 tenant_id
* [ ] 是否需要 company_id
* [ ] Primary Key 是否符合统一策略
* [ ] Business Number 是否与 ID 分离
* [ ] Foreign Key 是否完整
* [ ] NOT NULL 是否合理
* [ ] Unique Constraint 是否合理
* [ ] Money 类型是否正确
* [ ] Currency 是否存在
* [ ] DateTime 类型是否正确
* [ ] created_at 是否需要
* [ ] updated_at 是否需要
* [ ] Audit 是否需要
* [ ] Soft Delete 是否真的需要
* [ ] Status 是否建模正确
* [ ] Index 是否根据 Query Pattern 设计
* [ ] 是否存在 JSONB 滥用
* [ ] 是否存在历史 Snapshot 需求
* [ ] 是否需要 Migration

---

# 255. Cursor 修改 Table 前自检

修改已有 Table 前必须检查：

* [ ] Existing Data 是否受影响

# 260. AIOS 核心数据库原则

AIOS 数据库必须坚持：

> PostgreSQL 是核心 Operational Source of Truth。

> 数据库 Schema 必须通过 Migration 管理。

> Tenant Isolation 从第一张业务 Table 开始，而不是后期补。

> Tenant 与 Company 是两个不同 Scope。

> Primary Key 与 Business Number 必须分离。

> Foreign Key 与 Constraint 是数据完整性的最后防线。

> Money 不允许使用 Float。

> Rate 不允许使用 Float。

> 时间必须具有明确 Date / DateTime / Timezone 语义。

> 历史交易必须保留历史事实。

> 当前 Balance 不能取代 Ledger / Movement。

> 已完成金融记录不能静默覆盖。

> JSONB 是补充能力，不是逃避数据建模的工具。

> Index 必须基于 Query Pattern，而不是越多越好。

> Migration 必须保护 Existing Data。

> Cursor 不得为了快速完成任务破坏数据库长期一致性。

> Spring Boot 掌控核心业务规则，PostgreSQL保证数据完整性。

> React 永远不能直接访问 PostgreSQL。

> Python AI 默认不得绕过 Spring Boot 修改核心业务数据。

> 每一条正式业务数据都必须知道：属于谁、为什么存在、如何变化、如何追踪。
