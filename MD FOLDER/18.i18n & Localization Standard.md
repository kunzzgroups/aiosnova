# AIOS i18n & Localization Standard

> 文件编号：18
> 文件名称：i18n & Localization Standard
> 适用范围：AIOS 全部 Web 前端
> 适用对象：Cursor、AI Agent、Frontend Developer、UI/UX Designer
> 前置规则：必须遵守《01 产品原则》至《17 Sidebar & Navigation Standard》
> 前端技术：React + Vite + TypeScript + i18next / react-i18next
> 核心目标：一套机制、扁平 key、缺译必回退、数据永不翻译

---

# 1. 文件目的

定义 AIOS 前端的国际化实现规范。

**全站只允许一套 i18n 机制。** 历史上 auth 模块曾自带一份 `authCopy.ts` 私有字典，与全局方案并存，导致「同一个词两处翻译、改一处漏一处」，最终被合并删除。新增文案一律走本文件。

## 1.1 代码位置

| 关注点 | 文件 |
|--------|------|
| i18next 实例与初始化 | `src/i18n/index.ts` |
| 英文词典（源语言） | `src/i18n/locales/en/*.ts` |
| 中文词典 | `src/i18n/locales/zh-CN/*.ts` |
| 词典聚合 | `src/i18n/locales/{en,zh-CN}/index.ts` |
| 导航文案解析 | `src/i18n/useNavLabel.ts` |
| 语言偏好存储 | `src/stores/localeStore.ts` |
| 语言切换 UI | `src/components/navigation/LanguageSwitcher.tsx` |

词典按区域分文件：`common`（外壳与通用）、`nav`（导航，仅中文）、`home`、`auth`、`users`、`org`。新增区域时同时新增 `en/<area>.ts`、`zh-CN/<area>.ts`，并在两个 `index.ts` 里注册。

# 2. Key 规范

## 2.1 扁平 key

i18next 初始化时 **`keySeparator: false`**，因此 key 是**字面量**，点号**不代表层级**：

```ts
'shell.workspace': '工作区'
'nav.customer-revenue.crm.leads': '线索'
'users.lastActiveToday': '今天 {{time}}'
```

命名约定：`<area>.<subject>`，全小写驼峰，层级用点号表达语义（用 `nav.<导航 id>` 复用导航 id）。

## 2.2 插值

使用 i18next 双花括号：

```ts
t('home.welcome', { name: user.name })   // '欢迎，{{name}}'
```

## 2.3 组件里怎么用

```tsx
import { useTranslation } from 'react-i18next'

export function SomePage() {
  const { t } = useTranslation()
  return <h1>{t('users.title')}</h1>
}
```

禁止在组件内写 `locale === 'zh-CN' ? '中文' : 'English'` 这类就地三元。

# 3. 导航文案：唯一例外

**导航文案不进字典。** `sidebarNav.ts` 的 `label` 同时派生 `id` 与 `path`，是唯一真源；翻译通过 id 解析：

```ts
const navLabel = useNavLabel()          // src/i18n/useNavLabel.ts
navLabel(section)                       // t('nav.' + id, { defaultValue: label })
```

英文词典里**没有** `nav`，缺译时由 `defaultValue`（来自 `sidebarNav.ts` 的英文 label）兜底，所以**永远不会露出原始 key**。

新增导航项时：只在 `zh-CN/nav.ts` 补 `'nav.<id>': '中文'`，`en` 不需要动。

# 4. 必须遵守

1. **缺译必须回退英文，不允许显示 key。** 所有动态拼 key 的调用都要带 `defaultValue`。
2. **数据永不翻译。** 公司名（`KUNZZ HOLDINGS SDN BHD`）、人名、邮箱、编码（`RETAIL`、`J1`）、编号、接口返回的 message 一律保持原样。只翻译围绕它们的 UI chrome。
3. **同一 key 集合必须同时存在于 `en` 与 `zh-CN`**（`nav` 除外）。合并到 `zh-CN/index.ts` 时 `nav` 放最后，便于发现意外冲突。
4. **状态值翻译「展示名」，不翻译数据值。** 例如 `status` 数据仍是 `'active'`，展示时用 `t('users.statusActive')`。
5. **纯函数要翻译就传入 `t`。** 例如 `formatStatusLabel(status, t)`、`formatLastActive(value, t)`。函数保持纯函数，调用点显式可见，禁止在工具模块里 import 全局 i18n 实例去偷偷翻译。
6. **模块级常量里不要放展示文案。** 需要翻译时只放 value/key（如 `STATUS_FILTERS = ['all','active']`、`ORG_TYPE_KEYS`），标签在组件内用 `t()` 生成。
7. **日期/时间格式**目前仍跟随浏览器 locale（`toLocaleTimeString` / `toLocaleDateString`），已知局限：切换应用语言不会改变这些系统格式的呈现细节。
8. **服务端/ mock 返回的 message 不本地化。** `ApiError.message` 原样展示；不要为了翻译它去改 mock handler。
9. **语言偏好持久化在 `localStorage['aios.locale']`**，切换后由 `localeStore` 订阅同步给 i18next，不要在组件里直接调 `i18n.changeLanguage`。
10. **不要新增第二套字典机制**（私有 copy 文件、`Record<string, string>` 内联映射等）。

---

# 5. 新增文案 Checklist

1. 归到某个 `area`；不存在就新建 `en/<area>.ts` + `zh-CN/<area>.ts` 并在两个 `index.ts` 注册。
2. 在两个文件里用**完全相同的 key**写入英文与中文。
3. 组件内 `const { t } = useTranslation()`，用 `t('area.subject')`。
4. 动态 key（列表/枚举驱动）必须带 `defaultValue`。
5. 属于导航的文案：只补 `zh-CN/nav.ts`，key 用 `nav.<导航 id>`。
