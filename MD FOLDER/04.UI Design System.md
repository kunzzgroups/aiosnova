# AIOS UI 设计系统

> 文件编号：04
> 文件名称：UI 设计系统
> 适用范围：AIOS 全部 Web 前端、Admin、Super Admin、Dashboard、业务模块、AI 功能界面
> 适用对象：Cursor、AI Agent、Frontend Developer、UI/UX Designer
> 前置规则：必须遵守《01 产品原则》《02 系统架构标准》《03 开发与编码标准》
> 前端技术：React + Vite + TypeScript
> 核心目标：统一、专业、清晰、高效、可扩展、可复用、企业级

---

# 1. 文件目的

本文件定义 AIOS 的统一 UI Design System。

AIOS 包含：

* Core
* AI
* Dashboard
* CRM
* Sales
* POS
* Inventory
* Procurement
* Finance
* HRM
* Project
* Marketing
* Manufacturing
* Admin
* Super Admin

等大量模块。

因此绝对禁止每个模块拥有完全不同的 UI 风格。

所有页面必须遵守统一：

```text
Design Token
Layout
Spacing
Typography
Color
Component
Table
Form
Modal
Status
Feedback
Interaction
Responsive
Accessibility
```

原则：

> AIOS 是一个产品，不是 27 个拼接起来的网站。

---

# 2. Cursor UI 开发最高原则

Cursor 在创建或修改任何 UI 前必须先检查：

1. 是否已有相同 Component。
2. 是否已有类似 Page Pattern。
3. 是否已有对应 Design Token。
4. 是否已有 Layout。
5. 是否已有 Table Pattern。
6. 是否已有 Form Pattern。
7. 是否已有 Modal / Drawer Pattern。
8. 是否已有 Status Component。
9. 是否已有 Loading / Empty / Error State。
10. 当前页面是否属于现有 Design System。

执行顺序：

```text
Search Existing UI
↓
Understand Existing Pattern
↓
Reuse Existing Component
↓
Extend Existing Component
↓
Only Then Create New Component
```

禁止直接重新设计。

---

# 3. UI 总体设计原则

AIOS UI 必须遵守：

```text
Clear
Consistent
Efficient
Predictable
Accessible
Professional
Scalable
Data-Oriented
Enterprise Ready
```

设计优先级：

```text
可用性
↓
信息清晰
↓
操作效率
↓
一致性
↓
可访问性
↓
视觉美观
↓
装饰效果
```

禁止：

> 为了“看起来高级”牺牲使用效率。

---

# 4. Enterprise UI 原则

AIOS 是企业管理系统。

UI 应优先满足：

* 大量数据
* 高频操作
* 多步骤流程
* 权限管理
* Dashboard
* Table
* Form
* Approval
* Status
* Filtering
* Search
* Bulk Action

设计不能按照：

```text
Landing Page
Marketing Website
Portfolio Website
```

的思路开发企业后台。

---

# 5. UI 必须统一

以下内容必须全系统统一：

* Button
* Input
* Select
* Checkbox
* Radio
* Switch
* Table
* Modal
* Drawer
* Dropdown
* Tooltip
* Badge
* Status
* Card
* Tabs
* Pagination
* Date Picker
* Empty State
* Loading
* Error State
* Toast
* Confirmation
* Page Header
* Breadcrumb
* Sidebar
* Navigation

禁止不同 Module 自行建立第二套。

---

# 6. Design Token First

任何视觉规则必须优先通过 Design Token 管理。

例如：

```text
Color
Spacing
Font Size
Font Weight
Border Radius
Shadow
Border
Z-Index
Breakpoint
```

禁止 Component 中大量出现随意设计值：

```css
color: #2389ff;
margin: 13px;
padding: 17px;
border-radius: 11px;
```

如果该值属于设计系统，应使用 Token。

---

# 7. 禁止 Random Design

Cursor 禁止自行随机决定：

```text
Color
Radius
Shadow
Spacing
Font Size
Button Height
Input Height
```

新页面必须从现有 Design System 获取。

如果系统尚未定义该 Token：

必须使用最接近的现有标准。

不得为了一个页面制造新体系。

---

# 8. Design Token 建议结构

设计 Token 可以按以下逻辑组织：

```text
tokens/
├── colors
├── typography
├── spacing
├── radius
├── shadows
├── borders
├── sizes
├── breakpoints
└── zIndex
```

实际文件结构跟随项目当前实现。

重点是：

> Token 必须集中管理。

---

# 9. Spacing System

AIOS 默认使用统一 Spacing Scale。

建议基础单位：

```text
4px
```

常用：

```text
4
8
12
16
20
24
32
40
48
64
```

优先组合：

```text
8 / 12 / 16 / 24 / 32
```

禁止随意出现：

```text
13px
17px
19px
27px
```

除非存在明确设计理由。

---

# 10. 页面整体间距

页面内容不能：

* 太拥挤
* 太松散
* 每个页面 Padding 不同

页面应该使用统一：

```text
Page Padding
Section Gap
Card Gap
Form Gap
Table Gap
```

同级页面必须保持一致。

---

# 11. Grid 原则

复杂页面优先使用清晰 Grid / Flex Layout。

不要通过：

```text
margin-left: 137px
position: absolute
```

强行定位正常业务布局。

---

# 12. 禁止 Absolute Layout 滥用

`position: absolute` 只用于：

* Overlay
* Badge
* Floating Element
* Decorative Element
* 明确需要脱离文档流的元素

禁止用 Absolute 完成普通：

```text
Form
Table
Card
Page Layout
```

否则 Responsive 容易失效。

---

# 13. Typography System

全系统必须使用统一 Typography Scale。

至少定义：

```text
Page Title
Section Title
Card Title
Body
Secondary Text
Caption
Label
Table Text
```

禁止每个页面自行决定字号。

---

# 14. Typography 层级

必须通过：

```text
Font Size
Font Weight
Color
Spacing
```

建立清晰信息层级。

原则：

```text
Page Title
↓
Section Title
↓
Component Title
↓
Body
↓
Secondary Information
```

不能全部文字：

> 一样大小、一样粗细。

---

# 15. 字体数量

AIOS 不允许随意使用大量 Font Family。

原则：

> 一个主要 UI Font Family。

如涉及：

* Code
* Technical ID
* Log

可使用 Monospace。

不得不同 Module 使用不同字体。

---

# 16. Font Weight

避免所有标题：

```text
font-weight: 700 / 800
```

造成视觉过重。

必须根据层级合理使用：

```text
Regular
Medium
Semibold
Bold
```

---

# 17. Text Color

文字颜色必须区分：

```text
Primary Text
Secondary Text
Muted Text
Disabled Text
Inverse Text
Danger Text
```

禁止所有文字统一使用纯黑。

也禁止使用过浅灰色导致难以阅读。

---

# 18. Color System

颜色必须使用 Semantic Token。

例如：

```text
Primary
Secondary
Success
Warning
Danger
Info
Neutral
Background
Surface
Border
Text
```

业务 Component 不应直接依赖某个 HEX Color 的业务含义。

---

# 19. Semantic Color

正确：

```text
color-success
color-warning
color-danger
```

而不是：

```text
green-500 = success
yellow-300 = warning
red-600 = danger
```

在业务代码内 Hardcode。

Color Mapping 应由 Design System 管理。

---

# 20. Primary Color

Primary Color 用于：

* Main CTA
* Active State
* Selected State
* Important Interaction
* Focus

不得一个页面出现大量 Primary Color。

Primary Color 应用于强调，而不是填满界面。

---

# 21. Status Color

状态颜色必须统一。

例如：

```text
Success
Warning
Danger
Info
Neutral
```

相同业务意义必须使用相同 Semantic Color。

禁止：

Sales 的 Approved 是绿色，

Finance 的 Approved 却变成蓝色。

---

# 22. 颜色不能作为唯一信息

禁止仅通过颜色表达：

```text
Approved
Rejected
Warning
Error
```

必须同时提供：

* Text
* Icon
* Label

中的至少一种。

---

# 23. Background 层级

界面应该清楚区分：

```text
Application Background
Surface
Card
Elevated Surface
Overlay
```

禁止所有区域全部使用大量不同背景色。

---

# 24. Border System

Border 必须统一：

```text
Default Border
Strong Border
Focus Border
Error Border
```

不要每个 Component 自行选择 Border Color。

---

# 25. Radius System

Border Radius 必须来自统一 Token。

例如：

```text
Small
Medium
Large
Full
```

禁止：

```text
Button = 6px
Input = 7px
Card = 11px
Modal = 13px
```

无规律出现。

---

# 26. Shadow System

Shadow 只用于表达：

```text
Elevation
Overlay
Floating Layer
```

不要为了“高级感”到处添加强烈 Shadow。

Enterprise UI 应保持干净。

---

# 27. Layout 架构

AIOS 默认页面结构：

```text
Application Shell
├── Sidebar / Navigation
├── Top Bar
└── Main Content
    ├── Page Header
    ├── Page Actions
    └── Page Content
```

特殊模块可以变化。

但必须基于统一 Shell。

---

# 28. Sidebar

Sidebar 必须：

* 结构稳定
* Active State 明确
* 支持 Module Group
* 支持 Permission
* 支持 Collapse

禁止不同页面切换完全不同 Sidebar 风格。

---

# 29. Navigation

Navigation 必须反映系统信息架构。

不能单纯按照：

> 开发文件顺序

建立 Menu。

Navigation 必须与业务 Module 对齐。

---

# 30. Permission 与 Navigation

用户没有权限的 Module / Menu：

应根据产品规则：

* Hide
* Disabled

统一处理。

不得每个页面自行判断。

Backend Permission 仍然必须独立验证。

---

# 31. Page Header

标准业务页面应拥有统一 Page Header。

Page Header 可以包含：

```text
Breadcrumb
Title
Description
Primary Action
Secondary Action
```

禁止每个页面使用不同 Header 结构。

---

# 32. Page Title

Page Title 应：

* 简洁
* 清楚
* 表达当前业务对象

禁止：

```text
Welcome to Customer Management System Page
```

这种冗长标题。

优先：

```text
Customers
Sales Orders
Employees
Inventory
```

---

# 33. Breadcrumb

超过明显一级层级的页面应考虑 Breadcrumb。

例如：

```text
Sales
/
Sales Orders
/
SO-2026-00125
```

不要对简单一级页面强制添加无意义 Breadcrumb。

---

# 34. Page Action

页面主要操作应保持清晰。

例如：

```text
Create Customer
Create Sales Order
Add Employee
```

一个页面原则上只应有一个明显 Primary Action。

---

# 35. Button Hierarchy

Button 至少区分：

```text
Primary
Secondary
Tertiary / Ghost
Danger
Icon
```

不得所有按钮都是 Primary。

---

# 36. Primary Button

Primary Button 仅用于当前区域最重要操作。

例如：

```text
Save
Create
Submit
Approve
```

一个操作区域避免同时出现多个竞争性的 Primary Button。

---

# 37. Danger Button

危险操作例如：

```text
Delete
Void
Revoke
Disable
Terminate
```

必须使用明确 Danger Style。

不得与普通操作视觉一致。

---

# 38. Button 文案

Button 必须使用 Action Verb。

正确：

```text
Create Customer
Save Changes
Approve
Export
```

避免：

```text
Yes
OK
Go
Click Here
```

如果上下文不够明确。

---

# 39. Icon Button

只有图标的按钮必须：

* 图标含义足够常见
* 提供 Tooltip 或 Accessible Label

例如：

```text
Edit
Delete
More
Close
```

复杂业务行为不得只放一个难懂 Icon。

---

# 40. Button Loading

提交操作期间：

必须提供：

```text
Loading
Disabled
Progress Feedback
```

防止重复点击。

---

# 41. Button Disabled

Disabled 状态必须明显。

但不能只通过降低到几乎看不见的颜色表达。

---

# 42. Form 总原则

Enterprise Form 必须：

```text
Clear
Predictable
Efficient
Validated
Accessible
```

字段顺序应该符合业务逻辑。

不能按照 Database Column 顺序机械生成表单。

---

# 43. Form Label

所有需要理解含义的 Input 必须有明确 Label。

Placeholder 不能代替 Label。

错误：

```text
[ Enter customer name ]
```

没有 Label。

正确：

```text
Customer Name
[ Enter customer name ]
```

---

# 44. Required Field

Required Field 必须统一表达。

例如：

```text
*
```

或统一 Design System 标识。

不得不同页面使用：

```text
*
Required
红色边框
```

三种不同规则。

---

# 45. Placeholder

Placeholder 用于：

* Example
* Hint
* Expected Format

不能重复 Label。

不推荐：

```text
Label: Name
Placeholder: Name
```

更好：

```text
Label: Company Name
Placeholder: Example Sdn. Bhd.
```

---

# 46. Form Helper Text

复杂字段应提供 Helper Text。

例如：

```text
Password Requirement
File Requirement
Tax Rule
Currency Rule
```

不要让用户提交后才发现规则。

---

# 47. Form Error

Validation Error 必须：

* 靠近 Field
* 清楚解释问题
* 告诉用户如何修正

禁止只显示：

```text
Invalid
Error
Failed
```

---

# 48. Form Error 不应清空输入

Validation 失败后：

原则上保留用户已经输入的数据。

禁止因为一个字段错误：

> 整张 Form 重置。

---

# 49. Form Layout

简单 Form：

可以单列。

复杂 Enterprise Form：

可以合理使用双列。

但必须考虑：

* 阅读顺序
* Responsive
* 字段关联

不要为了节省空间无脑三列、四列。

---

# 50. 长 Form

大型 Form 应根据业务逻辑分组：

```text
Basic Information
Contact
Billing
Permission
Settings
```

必要时使用：

```text
Section
Tabs
Step Form
```

不要建立一张无限向下的巨大表单。

---

# 51. Step Form

只有存在真实流程步骤时才使用 Stepper。

禁止把普通 Form 为了视觉效果强行拆成 5 Steps。

---

# 52. Save 行为

Form 必须明确：

```text
Save
Cancel
Save & Continue
Submit
```

之间的意义。

禁止同一系统：

某页面 Save 会关闭，

另一页面 Save 不关闭，

却没有明确设计规则。

---

# 53. Unsaved Changes

重要或复杂 Form 应考虑：

> Unsaved Changes Warning。

避免用户误操作离开导致资料丢失。

---

# 54. Input Height

Button、Input、Select 等常见 Control 应保持统一高度体系。

不得同一 Form 出现：

```text
Input 32px
Select 38px
Date Picker 42px
Button 36px
```

视觉不一致。

---

# 55. Select

Select 用于有限选项。

大量选项必须考虑：

```text
Search
Async Search
Virtualization
```

不要让用户在数百个选项中手动滚动。

---

# 56. Checkbox

Checkbox 用于：

> 多选或独立 Boolean Option。

不要用 Checkbox 模拟 Single Select。

---

# 57. Radio

Radio 用于：

> 少量且互斥、应该同时可见的选择。

选项过多时应改用 Select 等更合适组件。

---

# 58. Switch

Switch 适用于：

> 立即表达 On / Off 状态。

不要用于复杂状态：

```text
Approved / Rejected
Paid / Refunded
```

---

# 59. Date Input

全系统 Date / DateTime 必须使用统一 Component。

格式必须根据：

```text
Locale
Timezone
Business Requirement
```

统一处理。

禁止页面 A：

```text
DD/MM/YYYY
```

页面 B：

```text
MM-DD-YY
```

无规则混用。

---

# 60. Currency Input

金额输入必须明确：

```text
Amount
Currency
```

如果 Currency 已由 Context 决定：

UI 仍应让用户能够清楚知道当前 Currency。

---

# 61. Number Input

Number Input 必须根据业务限制：

```text
Min
Max
Decimal Scale
Negative Allowed
```

禁止所有数字都当普通 Text Input。

---

# 62. Search

Search 必须明确搜索范围。

Placeholder 可以使用：

```text
Search customers...
Search by name or email...
```

避免只有：

```text
Search...
```

但不知道搜索什么。

---

# 63. Table 是核心组件

AIOS 是 Enterprise System。

Table 必须作为 Design System 的核心组件。

所有业务 Table 应尽可能建立在统一 Table System 上。

---

# 64. Table 必须支持的基础能力

根据实际业务，Table 应能够支持：

```text
Column
Sorting
Filtering
Pagination
Row Selection
Row Action
Loading
Empty
Error
```

不是所有 Table 都必须开启全部功能。

---

# 65. Table Header

Column Header 必须：

* 简洁
* 清楚
* 对齐业务含义

避免：

```text
Customer Related Information
```

可以使用：

```text
Customer
```

---

# 66. Table Alignment

默认：

```text
Text → Left
Number → Right
Money → Right
Date → Consistent
Status → Consistent
Action → Right
```

整个系统保持统一。

---

# 67. Table Density

AIOS 属于高信息密度系统。

Table 不应为了视觉留白而每行异常巨大。

应提供舒适但高效的信息密度。

---

# 68. Table Action

Row Action 数量少时：

可以直接显示。

操作较多时：

应使用：

```text
More Menu
```

避免每一行出现 6-10 个按钮。

---

# 69. Table Primary Identifier

业务 Table 应清楚突出主要 Identifier。

例如：

```text
Customer Name
Invoice Number
Order Number
Employee Name
```

用户必须能够快速扫描。

---

# 70. Table Status

状态应使用统一：

```text
Status Badge / Tag
```

不要单纯显示彩色文字。

---

# 71. Table Empty State

无数据时：

不得只显示空白 Table。

应该说明：

```text
No customers found
No invoices yet
No results match your filters
```

必要时提供下一步 Action。

---

# 72. Table Loading

加载期间：

不得直接显示：

```text
No Data
```

然后数据出现。

必须区分：

```text
Loading
Empty
```

---

# 73. Table Pagination

大数据必须分页。

Pagination 的：

```text
Current Page
Page Size
Total
```

应使用统一 Pattern。

---

# 74. Filters

Filter 应与 Table 数据逻辑一致。

常见：

```text
Status
Date Range
Company
Owner
Category
```

不要将所有 Filter 一开始全部铺满页面。

复杂 Filter 可以放：

```text
Filter Panel
Drawer
Popover
```

---

# 75. Active Filter

用户必须能够看到：

> 当前有哪些 Filter 生效。

并能够快速：

```text
Clear
Reset
Remove Individual Filter
```

---

# 76. Reset Filter

Reset 必须只重置 Filter Scope 内的内容。

不得因为 Reset Filter：

> 清除用户其他不相关页面设置。

---

# 77. Bulk Action

支持 Multi Select 时：

Bulk Action 必须只有选中 Row 后才出现或激活。

高风险 Bulk Action 必须有 Confirmation。

---

# 78. Card 使用原则

Card 用于：

* 信息分组
* Summary
* KPI
* 独立功能区域

不要所有内容都套 Card。

否则界面会形成：

> Card inside Card inside Card。

---

# 79. KPI Card

Dashboard KPI 必须优先显示：

```text
Metric Name
Value
Context
Trend / Comparison
```

装饰其次。

---

# 80. KPI 数字

数字必须易于扫描。

例如：

```text
RM 1.25M
12,480
18.2%
```

并保持统一 Number Formatting。

---

# 81. Dashboard 原则

Dashboard 不是：

> 把所有数据都塞进首页。

Dashboard 应帮助用户回答：

```text
发生了什么？
现在情况如何？
哪里需要注意？
下一步做什么？
```

---

# 82. Chart

Chart 必须根据数据选择正确类型。

禁止 Cursor 为了“好看”随意使用：

```text
3D Chart
Gauge
Pie Chart
```

---

# 83. Pie Chart

Pie / Donut 只适合：

> 少量类别占比。

类别很多时不得使用 Pie Chart。

---

# 84. Line Chart

Line Chart 用于：

> 时间趋势。

必须明确：

```text
Time Range
Unit
Legend
Axis
```

---

# 85. Bar Chart

Bar Chart 适合：

```text
Category Comparison
Ranking
```

必须保证 Label 可读。

---

# 86. Chart Color

图表颜色必须来自 Design System Palette。

禁止每一个 Chart 随机生成不同颜色。

---

# 87. Chart Tooltip

复杂数据必须通过 Tooltip 清楚显示：

```text
Date
Value
Unit
Series
```

---

# 88. Modal 使用原则

Modal 用于：

* 简短确认
* 简单 Form
* 中断式重要操作

不要把复杂完整页面塞入 Modal。

---

# 89. Modal Size

Modal Size 必须基于内容：

```text
Small
Medium
Large
```

使用统一 Size Token。

禁止任意 Width。

---

# 90. Modal Action

标准 Modal Footer：

```text
Cancel
Primary Action
```

Danger Modal：

```text
Cancel
Danger Action
```

顺序必须全系统统一。

---

# 91. Modal 关闭

用户关闭存在未保存数据的复杂 Modal：

应考虑确认。

不得无提示丢失输入。

---

# 92. Confirmation

普通无风险操作不需要 Confirmation。

危险操作必须确认。

禁止：

> 所有按钮都弹 Confirmation。

这样会降低效率。

---

# 93. Destructive Confirmation

以下操作必须考虑明确 Confirmation：

```text
Delete
Void
Terminate
Revoke
Reset
Remove Permission
Bulk Delete
```

Confirmation 必须说明后果。

---

# 94. 高风险确认文案

不要只写：

```text
Are you sure?
```

应说明：

```text
Delete customer "ABC"?
This action cannot be undone.
```

具体行为根据业务性质确定。

---

# 95. Drawer

Drawer 适合：

* Detail Preview
* Filter
* Secondary Form
* Contextual Edit

复杂主流程不要全部塞进 Drawer。

---

# 96. Tabs

Tabs 只能表示：

> 同一个 Context 下的平行内容。

例如：

```text
Customer
├── Overview
├── Orders
├── Payments
└── Activity
```

不要用 Tabs 表达真正的流程步骤。

---

# 97. Tabs 数量

Tabs 过多会降低可用性。

大量模块应考虑：

```text
Sub Navigation
Sidebar Navigation
Group
```

不要 15 个 Tabs 横排。

---

# 98. Badge

Badge 用于：

```text
Status
Count
Category
Label
```

不得用大量 Badge 装饰普通文本。

---

# 99. Tooltip

Tooltip 用于补充信息。

不能依赖 Tooltip 才能让核心操作被理解。

---

# 100. Toast / Notification

Toast 用于：

```text
Success
Info
Warning
Non-blocking Error
```

不得将关键错误只在几秒 Toast 中显示后消失。

---

# 101. Success Feedback

用户完成重要操作后必须得到反馈。

例如：

```text
Customer created
Changes saved
Invoice submitted
```

不要点击后没有任何反应。

---

# 102. Error Feedback

错误必须告诉用户：

```text
What happened
What can be done
```

如果属于不可恢复 System Error：

应提供：

* Retry
* Contact Support
* Reference ID

等合理方式。

---

# 103. Loading System

全系统统一 Loading Pattern：

```text
Button Loading
Section Loading
Page Loading
Table Loading
Background Processing
```

不能所有场景都使用全屏 Spinner。

---

# 104. Skeleton

Skeleton 适用于：

> 页面结构已知、数据正在加载。

避免过度使用复杂 Skeleton。

---

# 105. Progress

长时间任务：

例如：

```text
Import
Export
AI Processing
Document Parsing
Report Generation
```

应尽量显示：

```text
Processing
Progress
Status
```

而不是无限 Spinner。

---

# 106. Empty State

Empty State 应区分：

```text
No Data Yet
No Search Result
No Permission
Feature Disabled
Error
```

这些状态不能全部显示：

```text
No Data
```

---

# 107. First Use Empty State

第一次没有数据：

可以提供：

```text
说明
Primary Action
```

例如：

```text
No customers yet.
Create your first customer.
```

---

# 108. Search Empty State

搜索没有结果时：

应告诉用户：

> 当前 Filter / Search 没有匹配结果。

不要鼓励创建重复数据。

---

# 109. Permission UI

没有 Permission：

必须使用统一处理方式。

根据业务可以：

```text
Hide
Disable
Show Access Denied
```

但必须来自统一 Permission UI Pattern。

---

# 110. Disabled 与 No Permission 不等价

Disabled：

通常表示当前条件不能使用。

No Permission：

表示用户没有权限。

两者不能视觉和业务逻辑全部混在一起。

---

# 111. 403 页面

明确无权访问页面时：

应显示统一 Access Denied Page。

不要：

* 白屏
* 404
* 无限 Loading

---

# 112. 404 页面

Resource 不存在时：

应显示标准 Not Found。

不要暴露内部异常。

---

# 113. 500 / System Error

系统错误页面应：

* 简洁
* 不显示 Stack Trace
* 支持 Retry
* 必要时提供 Reference ID

---

# 114. Responsive 原则

AIOS 必须考虑：

```text
Desktop
Tablet
Mobile
```

但企业复杂功能可以优先 Desktop Experience。

不得为了 Mobile：

破坏 Desktop 数据效率。

---

# 115. Breakpoint

Breakpoint 必须统一集中定义。

禁止每个 Component：

```css
@media (max-width: 731px)
@media (max-width: 777px)
@media (max-width: 812px)
```

自行发明 Breakpoint。

---

# 116. Responsive Table

Mobile / Narrow Screen 下大型 Table：

应根据情况采用：

```text
Horizontal Scroll
Priority Columns
Card View
Detail Drawer
```

不得简单压缩到所有内容无法阅读。

---

# 117. Responsive Form

多列 Form 在小屏幕下：

应自然降为：

```text
Single Column
```

---

# 118. Fixed Width

禁止大量使用固定页面宽度导致：

```text
Small Screen Overflow
Large Screen Excessive Empty Space
```

应该使用合理：

```text
Min Width
Max Width
Responsive Width
```

---

# 119. Accessibility 原则

所有核心 Component 应尽可能满足基础 Accessibility。

必须关注：

* Semantic HTML
* Keyboard Navigation
* Focus
* Label
* ARIA
* Contrast
* Screen Reader

---

# 120. Keyboard Navigation

企业用户大量高频操作。

Form、Menu、Modal、Table Action 应尽可能支持合理 Keyboard Interaction。

---

# 121. Focus State

Interactive Element 必须拥有清楚 Focus State。

禁止：

```css
outline: none;
```

然后没有替代 Focus Style。

---

# 122. Semantic HTML

优先：

```text
button
input
label
nav
main
table
```

而不是全部：

```html
<div>
```

模拟。

---

# 123. Clickable Element

禁止：

```tsx
<div onClick={...}>
```

作为所有 Button 的替代。

应优先使用正确 Semantic Element。

---

# 124. Contrast

文字与背景必须保持足够对比度。

禁止为了高级感：

> 大量浅灰文字放在白色背景。

---

# 125. Icon System

全系统必须尽量使用统一 Icon Library / Icon System。

Cursor 不得：

```text
页面 A → Library A
页面 B → Library B
页面 C → SVG 网站复制
```

混用。

---

# 126. 新增 Icon Library

如果项目已经有 Icon Library：

不得为了一个图标引入第二套 Icon Library。

---

# 127. Icon Size

Icon Size 必须与 Component Size 对应。

例如：

```text
Small Control → Small Icon
Normal Control → Normal Icon
Large Empty State → Larger Icon
```

不得随机。

---

# 128. Icon 含义

相同行为使用相同 Icon。

例如：

```text
Edit
Delete
Search
Filter
Settings
More
```

必须全系统保持一致。

---

# 129. Animation

Animation 用于：

* Feedback
* State Transition
* Context Change

禁止大量 Decorative Animation。

Enterprise System 应：

```text
Fast
Subtle
Purposeful
```

---

# 130. Transition

普通 UI Transition 应保持快速。

避免：

```text
1s
2s
```

的慢动画影响操作效率。

---

# 131. 禁止动画阻碍操作

用户不应该为了等待 Animation：

才能继续工作。

---

# 132. Z-Index

必须定义统一 Layer System。

例如：

```text
Base
Sticky
Dropdown
Overlay
Modal
Toast
Tooltip
```

禁止：

```css
z-index: 999999999;
```

解决问题。

---

# 133. Sticky Element

Sticky：

例如：

```text
Table Header
Action Bar
Sidebar
```

必须确保不会覆盖重要内容。

---

# 134. AI UI 原则

AIOS 的 AI 功能不能只是：

> 一个 Chat Box。

AI UI 应根据业务场景提供：

```text
Suggestion
Insight
Action
Source
Confidence
Approval
History
```

等适当信息。

---

# 135. AI 与普通系统功能必须区分

用户必须能够知道：

> 这是 AI 生成的结果。

不要让 AI 生成内容伪装成确定的系统事实。

---

# 136. AI Suggestion

AI Suggestion 应视觉上与：

```text
Confirmed Data
Approved Result
System Record
```

区分。

---

# 137. AI Action

AI 准备执行业务动作时：

必须清楚显示：

```text
What AI will do
Target
Impact
Need Confirmation?
```

高风险动作不得一键静默执行。

---

# 138. AI Loading

AI Response 通常比普通 API 慢。

必须提供适当状态：

```text
Thinking
Analyzing
Generating
Processing
```

但不得伪造具体 AI 思维过程。

---

# 139. AI Failure

AI 失败时：

不得造成整个页面 Crash。

应该允许：

```text
Retry
Continue Manually
```

如果业务允许。

---

# 140. AI Source

RAG / Knowledge Base 回答如果需要来源：

UI 应能够展示 Source / Reference。

不得让引用信息与 AI 自己生成内容难以区分。

---

# 141. AI Confidence

只有系统真正拥有可靠 Confidence 指标时：

才显示 Confidence。

禁止 Cursor 自行生成：

```text
98% confidence
```

等虚假数字。

---

# 142. AI Confirmation

高风险 AI Action 必须根据产品规则提供 Confirmation / Approval。

例如：

```text
Refund
Payment
Permission Change
Delete
Payroll
```

---

# 143. Audit UI

重要业务详情页可以根据权限提供：

```text
Activity
History
Audit Trail
```

帮助理解谁做了什么。

---

# 144. Activity Timeline

Timeline 应统一：

```text
Actor
Action
Time
Context
```

格式。

---

# 145. Date / Time Display

全系统 Date / Time Display 必须统一。

不能：

```text
16/08/2026
Aug 16
2026-08-16
16-8-26
```

在同一 Context 无规则混合。

---

# 146. Relative Time

例如：

```text
5 minutes ago
```

适用于：

* Notification
* Activity

正式业务记录应能够查看精确 DateTime。

---

# 147. Number Formatting

所有数字必须统一 Locale Formatting。

例如：

```text
1,000
10,250.50
18.5%
```

禁止：

```text
10000.500000
```

直接显示。

---

# 148. Money Display

Money 必须显示：

```text
Currency + Amount
```

例如：

```text
MYR 1,250.00
SGD 490.00
```

具体 Currency Symbol / Code 规则由统一 Formatter 负责。

---

# 149. Large Number

Dashboard 可以合理简化：

```text
1.2K
1.5M
```

但 Detail / Finance 数据必须能够查看完整精确值。

---

# 150. Status System

Status 必须集中管理。

每个 Domain 可以有自己的业务 Status。

但视觉状态必须映射到统一 Semantic System。

例如：

```text
DRAFT      → Neutral
PENDING    → Warning / Info
APPROVED   → Success
REJECTED   → Danger
CANCELLED  → Neutral
```

具体 Mapping 根据业务定义。

---

# 151. Status 不能自行猜测颜色

Cursor 新增业务 Status 时：

不得单凭英文意思随意决定颜色。

必须检查：

* 现有 Mapping
* Domain Meaning
* Design Token

---

# 152. 状态文案必须统一

同一个 Status：

不能页面 A：

```text
In Progress
```

页面 B：

```text
Processing
```

页面 C：

```text
Ongoing
```

如果实际指同一个状态。

---

# 153. Localization Ready

UI 不得假设系统永远只有一种语言。

避免：

* 文案与 Layout 强耦合
* 固定宽度只能装英文
* 通过字符串长度定位

当前阶段不代表必须立即完成完整 i18n。

但架构不能堵死未来。

---

# 154. UI 文案原则

UI 文案必须：

```text
Short
Clear
Actionable
Consistent
```

避免技术术语直接暴露给普通用户。

---

# 155. 技术错误不得直接显示

禁止：

```text
NullPointerException
SQLState
AxiosError
HTTP 500 Java...
```

直接展示给最终用户。

---

# 156. System ID

技术 ID / UUID：

只有业务确实需要时显示。

普通用户优先看到：

```text
Business Number
Name
Reference
```

而不是 UUID。

---

# 157. Confirmation 文案

Confirmation 必须清楚表达：

```text
Action
Target
Result
Consequence
```

尤其危险操作。

---

# 158. Tooltip 文案

Tooltip 应短。

复杂解释使用：

```text
Helper Text
Popover
Documentation
```

不要在 Tooltip 放一整篇说明。

---

# 159. Component API 必须稳定

Shared UI Component 的 Props 必须：

```text
Clear
Typed
Predictable
Consistent
```

禁止建立：

```tsx
<Button type2="blue" abc={true} specialMode="x" />
```

这种无法维护的 API。

---

# 160. Component Variant

通用 Component 应通过有限 Variant 控制。

例如：

```text
size
variant
state
disabled
loading
```

不要为每个页面增加一个专用 Boolean Prop。

---

# 161. 禁止 Boolean Prop Explosion

例如：

```text
isBlue
isRound
isBig
isSpecial
isAdmin
isFinance
```

不断增加。

应该建立清晰 Variant / Composition。

---

# 162. Component Ownership

Shared Component：

负责视觉与通用交互。

Domain Component：

负责业务组合。

例如：

```text
Badge
```

属于 Shared。

```text
InvoiceStatusBadge
```

可以属于 Finance Domain。

---

# 163. 不允许 Business Logic 进入基础 UI Component

例如：

```text
Button
Table
Modal
```

不得知道：

```text
Finance
Sales
HRM
```

业务规则。

---

# 164. Table Component 不应拥有 Domain Knowledge

基础 Table 不应该内置：

```text
Invoice Permission
Employee Rule
Customer Business Logic
```

这些应由 Domain Layer 提供。

---

# 165. Design System Folder

根据项目实际架构，可以使用类似：

```text
src/
├── components/
│   ├── ui/
│   ├── feedback/
│   ├── navigation/
│   ├── data-display/
│   └── forms/
│
├── design-system/
│   ├── tokens/
│   ├── theme/
│   └── styles/
```

但不得为了遵守本文件强制重构已有合理目录。

原则：

> 保持清晰，而不是死守目录名称。

---

# 166. CSS / Styling 原则

AIOS 必须使用统一 Styling Approach。

如果项目已经选择：

```text
CSS Modules
Tailwind
CSS-in-JS
Component Library Theme
```

其中一种：

Cursor 必须遵守现有方式。

禁止不同 Module 随意混用大量 Styling 技术。

---

# 167. 不得擅自引入 UI Framework

在用户没有明确批准前：

Cursor 不得自行引入：

```text
Material UI
Ant Design
Chakra UI
Mantine
Bootstrap
shadcn/ui
```

或其他大型 UI Framework。

如果已有 Framework：

必须优先复用。

---

# 168. 不得擅自引入 Tailwind

如果项目当前没有 Tailwind：

不得因为 Cursor 熟悉 Tailwind 就擅自安装。

反之亦然。

---

# 169. Inline Style

禁止大量：

```tsx
style={{ ... }}
```

作为主要 Styling System。

简单动态值可以使用。

设计 Token 与复杂样式应进入正式 Styling Layer。

---

# 170. Hardcoded Color

禁止业务页面大量：

```css
#FFFFFF
#000000
#FF0000
```

直接 Hardcode。

应优先使用 Design Token。

---

# 171. Hardcoded Spacing

禁止业务页面充斥：

```css
margin: 17px;
padding: 23px;
```

优先使用 Spacing Token。

---

# 172. !important

禁止使用：

```css
!important
```

作为默认解决 CSS 问题方式。

如果出现大量 `!important`：

应检查：

* Specificity
* Component Structure
* Style Architecture

---

# 173. Global CSS

Global CSS 应保持有限。

不得使用非常宽泛 Selector：

```css
div {}
button {}
table {}
```

无差别影响整个系统。

---

# 174. Responsive CSS

Responsive Rule 应跟随统一 Breakpoint。

不要每个页面单独建立随机 Media Query。

---

# 175. Browser Behavior

不得随意覆盖标准 Browser Behavior：

例如：

* Scroll
* Focus
* Text Selection
* Keyboard

除非有明确产品理由。

---

# 176. Cursor 不得自行“美化”

如果用户要求：

```text
修复 Customer Table 搜索问题
```

Cursor 禁止顺便：

* 换颜色
* 改 Layout
* 改 Button
* 改 Border Radius
* 改 Font
* 增加 Animation

遵守：

> UI Minimum Necessary Change。

---

# 177. Cursor 不得根据个人偏好改设计

Cursor 禁止使用：

```text
I think this looks better
Modern design
More beautiful
Cleaner
```

作为擅自修改 UI 的理由。

必须遵循：

```text
Design System
Existing Pattern
User Requirement
```

---

# 178. Cursor 创建新页面前必须搜索参考页面

必须寻找系统中：

> 最接近当前功能的已存在页面。

例如：

创建 Supplier List：

可以参考：

```text
Customer List
Employee List
Product List
```

的统一 Pattern。

禁止从零随意设计。

---

# 179. Cursor 修改 Shared Component 必须评估全局影响

修改：

```text
Button
Input
Modal
Table
Badge
Select
```

前必须搜索使用范围。

不得为了一个页面破坏全系统。

---

# 180. Shared Component 不得加入 Domain Hack

例如：

```tsx
<Button financeMode />
```

只为了 Finance 页面特殊处理。

应该在 Domain 层 Composition。

---

# 181. 不得复制 Shared Component

如果 Button 不满足需求：

不要：

```text
Button2
NewButton
ModernButton
FinanceButton
```

首先判断：

* 是否应该扩展现有 Button
* 是否属于 Domain Component
* 是否真的需要新基础 Component

---

# 182. Design Token 修改属于全局修改

修改：

```text
Primary Color
Spacing
Font
Radius
Button Height
```

意味着可能影响整个 AIOS。

Cursor 不得因单页需求直接改 Global Token。

---

# 183. UI Regression

任何 Shared UI 修改必须考虑：

```text
Desktop
Tablet
Mobile
Light / Dark if supported
Different Modules
Long Text
Empty Data
Large Data
```

---

# 184. Long Content

UI 必须考虑：

```text
Long Customer Name
Long Company Name
Long Email
Long File Name
Long Translation
```

不得假设所有文本都很短。

---

# 185. Text Overflow

根据场景使用：

```text
Wrap
Ellipsis
Tooltip
Expandable Content
```

禁止简单：

```css
overflow: hidden;
```

导致关键信息永久消失。

---

# 186. Empty Value

空值必须统一显示。

例如：

```text
—
```

或 Design System 定义方式。

不要混合：

```text
null
undefined
N/A
-
空白
```

---

# 187. Zero 不等于 Empty

业务数据：

```text
0
```

不得因为 Falsy 判断显示成：

```text
—
```

这是严重的数据展示错误。

---

# 188. Loading 不等于 Empty

加载中不得显示 Empty。

Error 不得显示 Empty。

No Permission 不得显示 Empty。

四者必须明确区分。

---

# 189. Sensitive Data UI

涉及：

```text
Password
Bank
Salary
Personal Data
API Key
Token
```

应根据权限及业务规则考虑：

```text
Mask
Reveal
Copy Permission
Audit
```

---

# 190. Password

Password 默认不得明文显示。

如支持 Reveal：

必须是用户明确操作。

---

# 191. Secret / API Key

Secret 类数据：

创建后是否允许再次查看，

必须由 Security Policy 决定。

Cursor 不得自行决定永久展示。

---

# 192. Finance UI

Finance、Payment、Payroll 等页面：

必须优先：

```text
Accuracy
Clarity
Auditability
```

而不是装饰。

金额、Currency、Status、Date 必须清楚。

---

# 193. Dangerous Financial Action

例如：

```text
Void Invoice
Refund Payment
Post Journal
Finalize Payroll
```

必须比普通 Edit 操作具有更明确视觉警告。

---

# 194. Permission UI

Role / Permission 页面属于高复杂度功能。

禁止使用无结构的数百 Checkbox。

应考虑：

```text
Module
Resource
Action
Scope
```

形成清晰 Matrix / Group。

---

# 195. Organization UI

组织架构数据应根据场景使用：

```text
Tree
Hierarchy
List
Org Chart
```

而不是强制所有数据放 Table。

---

# 196. Workflow UI

Workflow 应清楚表达：

```text
Trigger
Step
Condition
Action
Approver
Result
```

流程图必须帮助理解业务。

不能只为了视觉做复杂 Node Graph。

---

# 197. Audit UI

Audit Log 属于高密度信息界面。

应优先：

```text
Search
Filter
Actor
Action
Resource
Time
Result
```

而不是 Card Grid。

---

# 198. Notification UI

Notification 必须区分：

```text
Unread
Read
Important
Actionable
```

不要所有 Notification 视觉权重一样。

---

# 199. AIOS UI 完成标准

一个页面不能因为：

> 已经 Render 出来了

就视为完成。

必须检查：

```text
正常状态
Loading
Empty
Error
Permission
Long Text
Large Data
Responsive
Validation
Disabled
Submitting
```

# 202. UI 决策优先级

出现 UI 决策冲突时，按照以下优先级判断：

```text
1. Business Correctness
2. Usability
3. Accessibility
4. Existing Design System
5. Consistency
6. Information Clarity
7. Operation Efficiency
8. Responsive Behavior
9. Visual Quality
10. Decoration
```

---

# 203. Cursor 默认 UI 决策流程

如果用户没有明确指定设计方式：

Cursor 必须：

```text
寻找现有页面
↓
寻找现有 Design Pattern
↓
复用现有 Component
↓
复用 Design Token
↓
保持现有布局
↓
做最小必要实现
```

不得：

```text
自由发挥
↓
重新设计
```

---

# 204. UI 最终原则

AIOS UI 必须坚持：

> 一个产品，一套设计语言。

> Design Token 优先于 Hardcode。

> Shared Component 优先于重复创建。

> 可用性优先于装饰。

> 信息清晰优先于视觉炫技。

> 企业操作效率优先于 Landing Page 式设计。

> Table、Form、Filter、Status 是 AIOS 的核心 UI 能力。

> Loading、Empty、Error、Permission 都是正式 UI 状态。

> 危险操作必须明确。

> AI 生成内容必须与系统事实区分。

> UI Permission 不能代替 Backend Permission。

> Responsive 不能破坏 Desktop 企业操作效率。

> Accessibility 是基础质量要求，不是额外功能。

> Cursor 不得因为个人审美擅自改变已有 Design System。

> 修复功能时，不得顺便重新设计 UI。

> 新页面必须优先参考现有页面，而不是重新发明。

> 修改 Shared Component 前必须评估全系统影响。

> AIOS 必须随着模块增加仍然保持统一、专业、可预测。
