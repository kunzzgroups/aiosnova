# AIOS Documentation Standard

> 文件编号：11
> 文件名称：Documentation Standard
> 适用范围：AIOS 全项目
> 适用对象：Cursor、AI Agent、开发人员
> 核心目标：让 AI Agent 能快速理解系统、减少猜测、避免错误修改

---

# 1. 核心原则

Documentation 的目的不是写很多文字。

目的是让：

```text
Human
Cursor
AI Agent
```

都能够快速知道：

```text
这是什么？
为什么存在？
谁负责？
怎么使用？
依赖什么？
不能怎么改？
```

原则：

> Documentation 必须短、准、可执行。

禁止为了“有文档”而写大量无实际价值内容。

---

# 2. 文档优先级

AI Agent 阅读项目时，应按以下顺序理解规则：

```text
01 产品原则
↓
02 系统架构标准
↓
03 开发与编码标准
↓
对应 Domain / Module 文档
↓
对应代码
```

低层文档不得违反高层规则。

---

# 3. 文档必须与代码一致

Documentation 不允许长期出现：

```text
文档说 A
代码已经变成 B
```

如果：

```text
Architecture
API
Database
Permission
Business Rule
Agent Tool
```

发生重要变化，

对应 Documentation 必须同步更新。

---

# 4. AI Agent 不得盲目信任过期文档

如果 Documentation 与实际代码冲突：

AI Agent 必须：

```text
检查代码
↓
检查最新 Migration / API / Config
↓
确认当前真实实现
```

不得因为旧文档存在：

就直接修改代码去“配合文档”。

---

# 5. 每个 Module 必须有基础说明

重要 Module 至少应该说明：

```text
Module Name
Purpose
Responsibilities
Owned Data
Main Dependencies
Main APIs
Permissions
Important Business Rules
```

例如：

```text
Module: Sales

Purpose:
负责 Quotation、Sales Order 等销售业务。

Owns:
Sales Order
Sales Order Item

Depends On:
CRM
Inventory
Finance

Must Not:
直接修改 Inventory Table。
直接修改 Finance Ledger。
```

---

# 6. Module 必须说明边界

每个 Module 必须让 AI Agent 明白：

```text
这个 Module 负责什么
```

以及：

```text
这个 Module 不负责什么
```

避免 AI Agent 创建重复功能。

---

# 7. Data Ownership 必须记录

关键数据必须明确 Owner。

例如：

```text
Customer → CRM
Sales Order → Sales
Stock → Inventory
Employee → HRM
Tenant → Core
```

如果 AI Agent 不知道 Data Owner：

不得直接跨 Module 修改。

---

# 8. Business Rule 必须记录重点规则

关键业务规则必须 Documentation 化。

尤其：

```text
Finance
Payment
Inventory
Payroll
Permission
Workflow
Approval
Rate / Fee / Calculation
```

例如：

```text
Invoice Finalized 后不得直接修改 Amount。
必须通过 Void / Adjustment。
```

不能只把重要规则藏在代码里。

---

# 9. 计算规则必须写清楚

涉及：

```text
Amount
Rate
Fee
Commission
Tax
Discount
Exchange Rate
Payroll
```

必须明确：

```text
Formula
Input
Output
Precision
Rounding
Example
```

AI Agent 不得自行猜公式。

---

# 10. API Documentation

重要 API 至少说明：

```text
Purpose
Method
Path
Permission
Request
Response
Main Error
```

不需要重复复制全部代码。

---

# 11. API 文档必须说明权限

例如：

```text
POST /api/v1/invoices/{id}/void

Permission:
finance.invoice.void
```

禁止只记录 Endpoint：

却不记录 Permission。

---

# 12. Database Documentation

重要 Table 至少应能知道：

```text
Purpose
Owner Module
Tenant Scope
Important Relationship
Important Constraint
```

不需要逐字段写长篇说明。

---

# 13. 特殊字段必须说明

如果字段含义无法从名称判断：

必须 Documentation。

例如：

```text
base_amount
settlement_amount
rate_multiplier
```

必须明确真实业务含义。

---

# 14. Status 必须记录生命周期

重要 Resource 应记录允许状态。

例如：

```text
DRAFT
↓
SUBMITTED
↓
APPROVED
↓
COMPLETED
```

以及非法 Transition。

AI Agent 不得自行发明状态转换。

---

# 15. Permission Documentation

新增 Permission 时必须说明：

```text
Permission Code
Purpose
Risk Level
Scope
```

例如：

```text
finance.payment.refund

Purpose:
允许执行 Refund。

Risk:
HIGH

Scope:
Company / Tenant according to role configuration.
```

---

# 16. Agent Documentation

每个正式 Agent 至少记录：

```text
Agent Name
Goal
Domain
Autonomy Level
Allowed Tools
Required Permissions
Risk Level
```

---

# 17. Tool Documentation

每个 Agent Tool 必须说明：

```text
Purpose
Input
Output
Required Permission
Risk
Side Effect
```

例如：

```text
Tool:
refund_payment

Purpose:
执行正式 Payment Refund。

Permission:
finance.payment.refund

Side Effect:
会产生真实财务交易。

Risk:
HIGH
```

---

# 18. 文档必须说明危险操作

以下变化必须明确记录风险：

```text
Database Migration
Permission Change
Security Change
API Breaking Change
Financial Rule Change
Agent Tool Change
Tenant Model Change
```

---

# 19. Architecture Decision

重大架构决定应留下简短记录。

例如：

```text
Decision:
AIOS 当前使用 Modular Monolith。

Reason:
降低系统初期复杂度。

Do Not:
未经批准拆分成 Microservices。
```

---

# 20. 不记录无价值内容

禁止 Documentation 出现大量：

```text
This class is a class.
This method gets customer.
This function returns data.
```

这类代码本身已经表达的信息。

---

# 21. 注释不是 Documentation 替代品

Comment 用于解释局部代码。

Documentation 用于解释：

```text
Architecture
Domain
Business Rule
Contract
Decision
```

两者职责不同。

---

# 22. README 只写入口信息

Project README 建议只包含：

```text
Project Purpose
Tech Stack
How to Run
Project Structure
Important Documentation Links
```

不要把所有系统规则塞进一个巨大 README。

---

# 23. 文档文件命名必须清楚

正确：

```text
01-product-principles.md
02-system-architecture.md
sales-module.md
permission-model.md
```

禁止：

```text
notes.md
new.md
final.md
final2.md
important.md
```

---

# 24. 禁止重复文档

同一个规则：

应该有一个主要 Source of Truth。

禁止：

```text
Permission rule
```

分别复制到十个文件，

最后内容不一致。

其他文档可以引用主规则。

---

# 25. 文档修改原则

修改 Documentation 时：

不得为了让文档“看起来正确”：

擅自修改业务含义。

如果发现文档与代码冲突：

必须先确定真实业务规则。

---

# 26. AI Agent 阅读规则

AI Agent 执行复杂任务前：

必须优先搜索：

```text
Project Rules
Module Documentation
API Documentation
Database Documentation
Permission Documentation
```

再修改代码。

---

# 27. AI Agent 不得因为没找到文档就自行发明

如果以下信息不明确：

```text
Business Formula
Permission
Status Transition
Data Ownership
Tenant Scope
High-Risk Behavior
```

AI Agent 必须先检查现有代码和系统规则。

不得凭经验自行决定。

---

# 28. 文档更新触发条件

以下变化应更新 Documentation：

```text
新增 Module
新增重要 API
新增重要 Table
新增 Permission
新增 Agent
新增 Agent Tool
修改 Business Rule
修改 Calculation
修改 Workflow
重大 Architecture Change
```

---

# 29. 小修改不需要过度更新文档

以下通常无需新增大量 Documentation：

```text
CSS Fix
Text Fix
Minor Refactor
Internal Variable Rename
```

除非改变正式行为。

---

# 30. Example 必须真实

文档 Example：

必须符合当前系统规则。

禁止：

```text
为了容易理解
```

写一个实际上无法运行的错误 Example。

---

# 31. 文档中的 Secret

Documentation 禁止包含：

```text
Password
API Key
Token
Private Key
Production Credential
```

示例必须使用：

```text
<API_KEY>
<SECRET>
example-value
```

等 Placeholder。

---

# 32. TODO Documentation

未完成设计：

必须明确：

```text
TODO
Not Yet Decided
Planned
```

不得写成已经确定。

---

# 33. Future Design

未来计划必须与当前实现区分。

例如：

```text
Current:
PostgreSQL

Future Option:
Data Warehouse
```

禁止 AI Agent 把 Future Option 当成当前已经存在。

---

# 34. Deprecated

废弃规则 / API / Module：

必须明确标记：

```text
DEPRECATED
```

并说明：

```text
Replacement
```

如存在。

---

# 35. 文档必须使用确定性语言

优先：

```text
MUST
MUST NOT
SHOULD
MAY
```

避免：

```text
maybe
probably
normally
try to
```

造成 AI Agent 无法判断优先级。

---

# 36. MUST

`MUST`：

代表强制规则。

例如：

```text
Tenant Query MUST include Tenant Scope.
```

---

# 37. MUST NOT

`MUST NOT`：

代表明确禁止。

例如：

```text
Agent MUST NOT directly update core PostgreSQL business data.
```

---

# 38. SHOULD

`SHOULD`：

表示默认推荐。

除非存在明确理由：

否则应遵守。

---

# 39. MAY

`MAY`：

表示允许，

但不是强制要求。

---

# 40. Documentation 冲突优先级

如果文档之间冲突：

默认：

```text
Product Principle
↓
Architecture
↓
Security / Permission
↓
Domain Rule
↓
API / Database
↓
Implementation Documentation
```

如果仍无法确认：

不得进行破坏性修改。

---

# 41. Cursor Documentation 禁止事项

Cursor 明确禁止：

* 擅自删除重要 Documentation
* 擅自重写 Architecture Decision
* 擅自改变 Business Rule 文档
* 擅自改变 Permission 含义
* 擅自将未来计划写成当前实现
* 擅自将假设写成事实
* 擅自写入 Secret
* 擅自创建重复规则文件
* 擅自写大量无价值注释
* 擅自让文档与实际代码长期不一致
* 擅自在不了解系统时重写整个 README

---

# 42. AI Agent 最低阅读要求

执行重大任务前：

至少必须知道：

```text
What Module?
What Data Owner?
What Permission?
What Tenant Scope?
What Business Rule?
What API / Tool?
What Risk?
```

任何一个关键答案未知：

不得直接执行破坏性修改。

---

# 43. 标准 Module Documentation 模板

```text
# Module Name

Purpose:
这个 Module 解决什么问题。

Owns:
这个 Module 拥有什么数据。

Depends On:
依赖哪些 Module。

Main APIs:
主要 API。

Permissions:
主要 Permission。

Business Rules:
重要业务规则。

Must Not:
明确禁止事项。
```

---

# 44. 标准 Agent Documentation 模板

```text
# Agent Name

Goal:
Agent 的目标。

Domain:
属于哪个业务 Domain。

Autonomy:
L0 / L1 / L2 / L3 / L4 / L5

Allowed Tools:
允许调用什么。

Permissions:
需要什么权限。

Risk:
LOW / MEDIUM / HIGH / CRITICAL

Must Not:
Agent 明确禁止做什么。
```

---

# 45. 标准 Decision Documentation 模板

```text
Decision:
决定了什么。

Reason:
为什么这样决定。

Impact:
影响什么。

Must Not:
之后不能擅自怎么修改。
```

---

# 46. Documentation 最终原则

AIOS Documentation 必须坚持：

> 文档是给人和 AI Agent 快速理解系统的，不是为了数量。

> 一个规则只保留一个主要 Source of Truth。

> 文档必须短、准、明确。

> Business Rule、Permission、Data Ownership、Agent Tool 必须可找到。

> 文档必须区分 Current、Future、Deprecated。

> 文档不得包含 Secret。

> Documentation 与代码必须保持一致。

> AI Agent 必须先读规则，再改代码。

> AI Agent 不知道业务规则时，不得自行发明。

> AI Agent 不知道 Data Owner 时，不得跨 Module 直接修改。

> AI Agent 不知道 Permission 时，不得默认 Allow。

> AI Agent 不知道风险时，应选择更安全的实现。

> 最好的 Documentation，是让下一个开发者或 AI Agent 不需要猜。
