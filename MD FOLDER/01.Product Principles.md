# AIOS 产品原则

> 文件级别：最高优先级产品规则
> 适用范围：AIOS 全系统
> 适用对象：Cursor、AI Agent、开发人员、代码生成工具
> 技术栈：React + Vite + TypeScript / Spring Boot / Python / PostgreSQL

---

# 1. 文件目的

本文件定义 AIOS 的最高层产品原则。

任何功能开发、代码修改、数据库设计、API 设计、AI Agent 行为、系统架构调整，都必须遵守本文件。

Cursor 在执行任何开发任务时：

1. 必须优先遵守本文件。
2. 不得为了快速完成当前任务而违反产品原则。
3. 不得擅自降低系统安全性、稳定性或可扩展性。
4. 不得为了减少代码量而破坏系统架构。
5. 不得为了当前页面或当前模块正常运行，而破坏其他模块。

如果用户指令、现有代码、临时实现方案与本文件发生冲突：

> 必须优先保护系统架构、数据安全、租户隔离和业务正确性。

---

# 2. AIOS 产品定位

AIOS 是一个：

> AI-Native Enterprise Operating System

AIOS 不是单一 CRM、ERP、POS、HRM 或 AI Chatbot。

AIOS 是一个统一企业操作系统，将以下能力整合在同一个平台中：

* 企业管理
* 用户管理
* 组织架构
* 权限管理
* CRM
* Sales
* POS
* Commerce
* Inventory
* Procurement
* Supply Chain
* Finance
* HRM
* Project
* Help Desk
* Marketing
* Manufacturing
* Asset Management
* Document Management
* Communication
* Automation
* Developer Platform
* Integration Hub
* Marketplace
* Security
* Data Platform
* Cloud Platform
* AI Platform

所有模块必须建立在统一的：

* User
* Tenant
* Company
* Organization
* Role
* Permission
* Workflow
* Approval
* Audit
* Notification
* File
* Settings

基础能力之上。

禁止不同业务模块重复开发自己的基础能力。

---

# 3. 核心产品原则

AIOS 必须长期遵守以下核心原则：

```text
统一
安全
模块化
可扩展
可审计
多租户
数据一致
AI Native
API First
Automation First
Enterprise Ready
```

任何功能设计都必须考虑这些原则。

---

# 4. Core First 原则

AIOS Core 是整个系统的基础。

以下能力属于平台级基础能力：

* User
* Company
* Organization
* Role
* Permission
* Multi-Tenant
* Authentication
* SSO
* Audit Log
* Notification
* File Center
* Workflow
* Approval
* Settings

其他业务模块必须尽可能复用 Core。

例如：

禁止 CRM 自己重新建立 User 系统。

禁止 HRM 自己建立独立 Permission 系统。

禁止 Finance 自己建立独立 Approval Engine。

禁止 Procurement 自己建立独立 Notification 系统。

禁止 Project 自己建立独立 File Storage 机制。

统一使用 AIOS Core 提供的能力。

---

# 5. 单一事实来源原则

Single Source of Truth，简称 SSOT。

同一种核心业务数据只能存在一个权威来源。

例如：

```text
User
→ AIOS Core

Company
→ AIOS Core

Permission
→ AIOS Core

Customer
→ CRM

Product
→ Inventory / Product Domain

Employee
→ HRM

Sales Order
→ Sales

Invoice
→ Finance / Sales Integration

Payment
→ Payment Domain

Tenant
→ AIOS Core
```

禁止多个模块各自维护同一份核心数据。

如果其他模块需要使用这些数据：

必须通过：

* API
* Domain Service
* Event
* Shared Contract

进行访问。

禁止复制一份数据然后独立维护。

---

# 6. Backend 是核心业务规则中心

AIOS 的核心业务规则必须以 Spring Boot Backend 为主要执行中心。

Frontend：

```text
React + Vite + TypeScript
```

负责：

* UI
* UX
* 用户交互
* 数据展示
* 表单
* 前端状态
* 客户端验证
* 调用 Backend API

Frontend 不得成为核心业务规则的唯一执行位置。

---

Spring Boot Backend 负责：

* Business Logic
* Validation
* Authorization
* Permission
* Transaction
* Workflow
* Approval
* Data Integrity
* Domain Rules
* Audit
* Database Operations

任何关键业务规则必须由 Backend 再次验证。

不能因为 Frontend 已经验证，就跳过 Backend 验证。

---

# 7. Frontend 不可信原则

永远不能假设来自 Frontend 的数据是安全或正确的。

Backend 必须验证：

* User Identity
* Tenant
* Company
* Permission
* Input
* Business Rule
* Resource Ownership
* Data Scope

即使 Frontend：

* 隐藏了按钮
* 禁用了按钮
* 限制了输入
* 做了 Permission 判断

Backend 仍然必须重新验证。

Frontend Permission：

> 主要用于 UI / UX。

Backend Permission：

> 才是真正的安全边界。

---

# 8. 多租户优先原则

AIOS 是 Multi-Tenant 系统。

任何业务功能在设计时都必须先考虑：

```text
Tenant A
Tenant B
Tenant C
```

之间的数据隔离。

任何 Tenant 都不能：

* 读取其他 Tenant 数据
* 修改其他 Tenant 数据
* 删除其他 Tenant 数据
* 查询其他 Tenant 数据
* 导出其他 Tenant 数据
* 通过 API 获取其他 Tenant 数据

Cursor 在新增任何业务表、Entity、Repository、Service、API 或 Query 时，都必须考虑 Tenant Scope。

不得默认：

> 系统只有一个 Company 或一个 Tenant。

---

# 9. Company 与 Tenant 不得混为一谈

Tenant 和 Company 必须视为两个不同概念。

基本关系应支持：

```text
Tenant
 ├── Company A
 ├── Company B
 └── Company C
```

未来必须允许一个 Tenant 管理多个 Company。

禁止在代码中默认：

```text
Tenant = Company
```

除非对应 Domain 明确定义如此。

---

# 10. 安全优先原则

Security 不是后期功能。

Security 必须存在于所有模块中。

任何功能设计都必须考虑：

* Authentication
* Authorization
* RBAC
* ABAC
* Tenant Isolation
* Encryption
* Audit
* Input Validation
* API Security
* Secret Management
* Sensitive Data Protection

禁止为了方便开发：

* 临时关闭 Permission
* 绕过 Authentication
* Hardcode Admin
* Hardcode API Key
* 暴露 Password
* 暴露 Token
* 将 Secret 写入 Git
* 使用不安全默认配置

---

# 11. 最小权限原则

所有用户、角色、服务、AI Agent 默认必须使用：

> Least Privilege

即：

只给予完成任务所必须的最低权限。

不得因为开发方便直接给予：

```text
SUPER_ADMIN
ADMIN
ALL
*
```

权限。

尤其 AI Agent 不得默认拥有全系统权限。

---

# 12. AI 不拥有无限权限

AIOS 是 AI-Native 系统，但 AI 不能绕过系统规则。

AI Assistant、AI Copilot、AI Agent、Multi-Agent 都必须遵守：

* Authentication
* Authorization
* Tenant Scope
* Company Scope
* RBAC
* ABAC
* Workflow
* Approval
* Audit

AI 不得因为是内部 AI 就自动拥有额外权限。

---

# 13. AI 不得直接绕过业务层修改核心数据

Python AI Layer 原则上不得直接修改核心业务 PostgreSQL 数据。

标准流程：

```text
User
↓
AI Assistant / AI Agent
↓
Python AI Service
↓
Spring Boot API
↓
Authentication
↓
Permission
↓
Business Validation
↓
Transaction
↓
PostgreSQL
```

禁止：

```text
AI Agent
↓
Python
↓
直接 UPDATE / DELETE / INSERT 核心业务数据库
```

除非后续存在经过专门设计及授权的内部数据服务。

---

# 14. AI 建议与 AI 执行必须区分

AIOS 必须区分：

```text
AI Suggestion
```

与：

```text
AI Action
```

AI 可以：

* 分析
* 推荐
* 预测
* 总结
* 提醒
* 生成草稿

但涉及重要业务动作，例如：

* Payment
* Refund
* Payroll
* Purchase Order
* Contract
* Invoice
* Financial Posting
* Permission Change
* Employee Termination
* Data Delete

不得默认自动执行。

必须根据风险等级决定是否：

* 用户确认
* Workflow
* Approval
* Permission Check

---

# 15. 模块化原则

所有 AIOS 功能必须按照 Domain / Module 进行设计。

禁止建立一个巨大、无边界的系统。

模块之间必须保持清晰责任。

例如：

```text
CRM
Sales
Inventory
Finance
HRM
Project
Marketing
```

每个模块必须明确：

* 自己负责什么
* 自己拥有什么数据
* 可以调用什么
* 可以被什么调用

禁止跨模块随意访问内部实现。

---

# 16. 禁止重复造轮子

在创建新功能之前，Cursor 必须先检查现有系统是否已经存在：

* Component
* Hook
* Utility
* Service
* API
* Entity
* DTO
* Enum
* Permission
* Workflow
* Notification
* File Service
* Audit Service
* Validation
* Shared Type

如果已有能力能够复用：

> 必须优先复用。

禁止创建：

```text
UserService2
NewUserService
UserServiceNew
CommonServiceV2
HelperNew
TempHelper
```

这类重复实现。

---

# 17. 不得为未来假设过度开发

Cursor 不得因为：

> “以后可能会用到”

就擅自建立大量：

* Table
* Service
* Interface
* Abstraction
* Microservice
* API
* Feature
* Configuration

只开发当前需求真正需要的能力。

设计可以支持扩展。

但禁止无需求的过度工程化。

原则：

> 设计可扩展，实施不过度。

---

# 18. 不得用临时方案污染正式架构

禁止为了让当前功能暂时运行而加入：

```text
temporary
temp
hack
quick fix
mock production logic
hardcoded production data
```

正式业务代码。

如果确实必须进行临时处理：

必须：

1. 明确标记原因。
2. 限制影响范围。
3. 不破坏正式架构。
4. 不作为长期设计。

---

# 19. 禁止 Hardcode 核心业务规则

以下内容原则上不得散落 Hardcode：

* Role
* Permission
* Tenant
* Company
* Currency
* Tax
* Country
* Status
* Workflow
* Approval Level
* Subscription Plan
* Feature
* Business Rate
* Secret
* API Key

应该根据实际性质使用：

* Enum
* Configuration
* Database
* Feature Flag
* Permission System
* Settings

进行管理。

---

# 20. 数据完整性优先原则

任何功能都不得以牺牲数据正确性为代价。

必须考虑：

* Transaction
* Constraint
* Foreign Key
* Unique Constraint
* Validation
* Concurrency
* Duplicate Request
* Idempotency
* Data Ownership

尤其以下模块：

* Finance
* Payment
* Inventory
* Payroll
* Sales
* Procurement

必须优先保证数据一致性。

---

# 21. 金融数据高精度原则

涉及：

* Money
* Price
* Rate
* Exchange Rate
* Tax
* Discount
* Commission
* Cost
* Profit
* Payroll

时：

禁止使用普通浮点逻辑处理关键金额。

必须使用适合精确 Decimal 计算的数据类型。

所有金额计算必须明确：

* Precision
* Scale
* Currency
* Rounding Mode

不得依赖默认四舍五入行为。

---

# 22. 所有重要操作必须可审计

关键业务操作必须考虑 Audit Log。

至少应该能够追踪：

```text
Who
When
Tenant
Company
Action
Resource
Before
After
Result
```

尤其：

* Permission 修改
* Role 修改
* Payment
* Refund
* Invoice
* Finance Posting
* Inventory Adjustment
* Payroll
* Approval
* Contract
* User Disable
* Security Setting

必须具备可追踪能力。

---

# 23. 删除操作必须谨慎

Cursor 不得轻易实现物理删除。

涉及核心业务数据时，应优先判断是否应该使用：

* Soft Delete
* Archive
* Disable
* Cancel
* Void
* Status Transition

特别是：

* Finance
* Invoice
* Payment
* Payroll
* Audit
* Contract

原则上不得随意物理删除记录。

---

# 24. 历史记录不可被静默改写

已经发生的业务事实不能因为当前数据变化而失去历史真实性。

例如：

客户今天修改地址，不代表三个月前 Invoice 的地址应该自动改变。

历史交易必须保存必要 Snapshot。

适用于：

* Invoice
* Sales Order
* Purchase Order
* Payment
* Payroll
* Contract
* Shipment

---

# 25. API First 原则

前后端、AI、Integration 之间应通过明确接口协作。

API 必须：

* 可预测
* 一致
* 有版本意识
* 有权限
* 有 Validation
* 有明确 Error
* 有稳定 Contract

禁止让 Frontend 或 Python 依赖 Backend 内部实现细节。

---

# 26. Automation First 原则

任何重复性企业流程，在设计时必须考虑是否能够通过：

* Trigger
* Rule
* Workflow
* Scheduler
* Webhook
* AI Workflow

进行自动化。

但 Automation 不得绕过：

* Permission
* Approval
* Audit
* Business Rule

---

# 27. Workflow 优先于 Hardcoded Flow

如果业务流程未来可能由不同企业配置：

不得把完整流程永久 Hardcode 在代码中。

例如：

```text
Leave Approval
Purchase Approval
Expense Approval
Contract Approval
Refund Approval
```

应该优先考虑 Workflow / Approval Engine。

业务代码负责规则。

Workflow Engine 负责流程。

---

# 28. 配置优先于代码修改

凡是不同 Tenant、Company 或行业可能存在不同设置的内容，应优先设计为配置能力。

例如：

* Approval Level
* Currency
* Timezone
* Language
* Number Format
* Tax
* Notification
* Working Day
* Feature Availability

不得每次变化都要求修改源代码。

---

# 29. Enterprise Ready 原则

AIOS 的设计不能只考虑：

```text
10 Users
1 Company
1 Tenant
```

必须考虑未来可能出现：

```text
Thousands of Tenants
Thousands of Companies
Millions of Users
Large Transaction Volume
Large Data Volume
```

但当前开发不得因此进行无必要的过度优化。

原则：

> 架构不能堵死未来，开发仍然保持当前阶段合理复杂度。

---

# 30. 性能原则

Cursor 不得为了代码简单而制造明显性能问题。

必须避免：

* N+1 Query
* 无限制查询
* 无 Pagination
* 重复 API 请求
* 重复数据库查询
* 巨大 Payload
* 无必要全表扫描
* 无必要同步阻塞

大数据列表必须考虑：

* Pagination
* Filter
* Search
* Sort
* Index

---

# 31. UX 一致性原则

AIOS 是一个统一产品。

不同模块不能表现得像不同公司开发的软件。

必须统一：

* Layout
* Navigation
* Form
* Table
* Modal
* Button
* Status
* Loading
* Empty State
* Error State
* Confirmation
* Notification
* Permission Behavior

已有 Design System 时：

必须优先使用 Design System。

不得随意创建新的视觉体系。

---

# 32. 不得擅自改变产品行为

当用户要求：

```text
修复 Bug A
```

Cursor 不得顺便：

* 重做 UI
* 改 API
* 改数据库
* 重构其他模块
* 修改业务流程
* 更换 Library
* 删除旧功能
* 修改权限逻辑

除非这些修改是完成任务所必须的。

遵守：

> Minimum Necessary Change

最小必要修改原则。

---

# 33. 向后兼容原则

修改已有功能前必须考虑：

* Existing Data
* Existing API
* Existing UI
* Existing Integration
* Existing Permission
* Existing Workflow

不得为了新功能直接破坏已有功能。

如果必须进行 Breaking Change：

必须明确识别影响范围。

不得静默产生 Breaking Change。

---

# 34. 不允许隐藏错误

禁止：

```text
catch error → 什么都不做
```

禁止为了 UI 看起来正常而吞掉错误。

错误必须：

* 正确处理
* 正确记录
* 返回适当错误
* 必要时写入 Logging / Monitoring

不得伪造成功结果。

---

# 35. 系统必须可观测

重要模块应逐步支持：

* Logging
* Metrics
* Tracing
* Monitoring
* Alerting

系统出现问题时必须能够回答：

```text
发生了什么？
什么时候发生？
谁执行的？
哪个 Tenant？
哪个服务？
哪个 API？
为什么失败？
影响了什么？
```

---

# 36. 不得信任 AI 自己的猜测

Cursor 遇到不确定的系统行为时：

禁止直接猜测。

必须优先：

1. 阅读相关代码。
2. 检查调用关系。
3. 检查数据结构。
4. 检查相关 API。
5. 检查现有 Pattern。
6. 再决定修改方式。

禁止：

> 没有检查现有实现，就创建另一套新实现。

---

# 37. 修改前必须理解上下文

Cursor 在修改代码前必须理解：

```text
Current Flow
↓
Related Module
↓
Dependency
↓
Data Model
↓
Permission
↓
Business Rule
↓
Impact
```

不得只看当前文件就立即修改。

涉及跨模块功能时，必须先理解相关依赖。

---

# 38. 不得擅自改变技术栈

当前 AIOS 核心技术栈：

## Frontend

```text
React
Vite
TypeScript
```

## Backend

```text
Spring Boot
```

## AI Layer

```text
Python
```

## Primary Database

```text
PostgreSQL
```

Cursor 不得擅自：

* 更换 Framework
* 引入另一个 Backend Framework
* 更换 Database
* 同时创建另一套 Frontend Framework
* 为相同能力建立重复技术栈

如果需要引入新的技术：

必须存在明确需求。

---

# 39. 禁止无理由增加 Dependency

新增 Library / Package / Dependency 前必须判断：

1. 现有项目是否已有类似能力。
2. 标准能力是否可以完成。
3. 是否值得引入额外依赖。
4. 是否增加维护成本。
5. 是否影响安全。

禁止为了一个简单功能引入大型 Dependency。

---

# 40. 开发完成不等于任务完成

Cursor 不得只以：

> Code 已经写完

作为任务完成标准。

任务完成至少应该确认：

```text
代码能够编译
核心逻辑正确
类型正确
权限正确
Tenant Scope 正确
错误处理正确
不会明显破坏现有功能
```

具体测试要求由后续 Testing Rules 定义。

---

# 41. 模块之间必须低耦合

模块之间禁止：

* 直接依赖对方内部 Repository
* 随意访问对方 Database Table
* 调用内部 Private Logic
* 复制对方 Domain Logic

应优先通过：

* Public Service
* API
* Event
* Domain Contract

进行协作。

---

# 42. 共享能力必须真正通用

不要因为两个模块暂时有类似代码，就立即抽成 Shared。

只有真正具备跨模块稳定意义的能力才应该进入：

```text
shared
common
core
platform
```

否则应保留在所属 Domain。

防止：

> Common Module 最后变成所有垃圾代码的集中地。

---

# 43. 状态必须明确

重要业务对象应该拥有明确生命周期。

例如：

```text
DRAFT
PENDING
APPROVED
REJECTED
ACTIVE
COMPLETED
CANCELLED
VOID
```

不得依赖多个 Boolean 表示复杂状态，例如：

```text
isApproved
isCancelled
isCompleted
isActive
```

造成非法组合。

应该优先使用明确 State / Status Model。

---

# 44. 所有业务规则必须考虑并发

涉及：

* Stock
* Payment
* Balance
* Invoice
* Sequence Number
* Quota
* Subscription Usage

等功能时，必须考虑多个请求同时发生。

不得默认所有请求都会按顺序执行。

---

# 45. 重复请求不得产生重复业务结果

重要写入 API 必须考虑 Idempotency。

例如：

用户重复点击 Payment：

不得生成两笔 Payment。

Webhook 重试：

不得重复建立订单。

AI Agent 重试：

不得重复执行同一个高风险 Action。

---

# 46. 用户体验不能牺牲业务正确性

可以优化：

* Loading
* Optimistic UI
* Cache
* Prefetch

但不能让 UI 表面看起来更快，却产生错误业务数据。

原则：

> Business Correctness > Perceived Speed

---

# 47. 产品能力必须支持未来国际化

设计时不要默认：

```text
只有 Malaysia
只有 MYR
只有 English
只有一个 Timezone
```

应该避免将：

* Currency
* Country
* Timezone
* Locale
* Date Format
* Number Format

写死。

但当前阶段无需一次性开发全部国家能力。

---

# 48. 系统必须支持 Feature Control

AIOS 是 SaaS Platform。

未来不同：

* Plan
* Tenant
* Subscription

可能拥有不同功能。

产品设计不得将所有功能永久写死为所有用户可用。

必须预留：

```text
Feature Control
Feature Flag
Plan Feature
Tenant Feature
```

的产品能力。

---

# 49. Super Admin 与 Tenant Admin 必须严格区分

Super Admin：

> AIOS 平台运营管理者。

Tenant Admin：

> 某一个 Tenant 的管理员。

两者不得视为相同角色。

Tenant Admin 不得拥有平台级能力。

Super Admin 的敏感操作必须具备更高安全要求与 Audit。

---

# 50. 产品优先级判断原则

当多个目标冲突时，按照以下优先级判断：

```text
1. Data Security
2. Tenant Isolation
3. Data Integrity
4. Authentication / Authorization
5. Business Correctness
6. Auditability
7. System Stability
8. Backward Compatibility
9. Maintainability
10. Performance
11. User Experience
12. Development Convenience
```

开发方便永远不能优先于安全和业务正确性。

---

# 51. Cursor 的默认决策原则

当本文件没有明确覆盖某种情况时，Cursor 必须采用以下默认原则：

```text
安全优先
↓
数据正确优先
↓
兼容现有系统
↓
复用现有架构
↓
最小必要修改
↓
保持模块边界
↓
避免过度工程
↓
保持代码简单清晰
```

---

# 52. Cursor 禁止事项

Cursor 禁止：

* 擅自删除功能
* 擅自删除数据库字段
* 擅自删除 Table
* 擅自修改核心业务逻辑
* 擅自修改权限模型
* 擅自修改 Tenant 模型
* 擅自改变技术栈
* 擅自升级重大 Dependency
* 擅自创建重复系统
* 擅自创建第二套 Authentication
* 擅自创建第二套 Permission
* 擅自创建第二套 Workflow
* 擅自创建第二套 Notification
* 擅自绕过 Backend
* 擅自让 AI 直接修改核心数据库
* 擅自 Hardcode Secret
* 擅自关闭 Security
* 擅自吞掉 Error
* 擅自伪造数据
* 擅自伪造 API Response
* 擅自创建与需求无关的功能
* 擅自大规模重构与当前任务无关的代码

---

# 53. 最终原则

AIOS 所有开发必须遵守：

> 一个系统，而不是 27 个独立系统。

> 一个 Core，而不是每个模块重复建立基础设施。

> 一个统一权限体系，而不是每个模块自己判断权限。

> 一个统一 Tenant 架构，而不是后期才补多租户。

> 一个可信 Backend，而不是依赖 Frontend 安全。

> AI 必须被系统规则约束，而不是凌驾于系统规则之上。

> 数据正确性优先于开发速度。

> 安全优先于方便。

> 可维护性优先于短期捷径。

> 最小必要修改优先于无关重构。

> 设计允许未来扩展，但当前实现不得过度工程化。
