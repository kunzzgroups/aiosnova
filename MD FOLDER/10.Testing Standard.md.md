# AIOS Testing Standard

> 文件编号：10
> 文件名称：Testing Standard
> 适用范围：AIOS Frontend、Backend、Database、API、AI Agent、Integration、Workflow、Security、Permission、Automation
> 适用对象：Cursor、AI Agent、Frontend Developer、Backend Developer、AI Developer、QA、Database Developer、Integration Developer
> 前置规则：必须遵守《01 产品原则》至《09 Agent Standard》
> Frontend：React + Vite + TypeScript
> Backend：Spring Boot
> AI Layer：Python
> Database：PostgreSQL
> 核心目标：Correctness、Regression Prevention、Tenant Isolation、Security、Reliability、Repeatability

---

# 1. 文件目的

本文件定义 AIOS 全系统 Testing Standard。

任何功能：

```text
开发完成
```

不代表：

```text
任务完成
```

任务完成必须至少经过合理：

```text
Validation
Testing
Regression Check
```

Cursor 不得仅因为：

```text
Code compiles
Page renders
API returns 200
```

就宣布功能完成。

---

# 2. Testing 最高原则

AIOS Testing 必须遵守：

```text
Test Business Behavior
Test Security Boundary
Test Tenant Isolation
Test Permission
Test Failure
Test Edge Case
Test Regression
Test Integration
Test Data Integrity
Test AI Action Safety
```

---

# 3. 测试优先级

发生时间或测试范围冲突时：

优先测试：

```text
1. Data Integrity
2. Tenant Isolation
3. Security
4. Permission
5. Money / Finance Logic
6. Business Rule
7. Critical Workflow
8. API Contract
9. Integration
10. User Experience
11. Cosmetic Detail
```

---

# 4. 测试不能只覆盖 Happy Path

禁止只测试：

```text
Valid Input
+
Authorized User
+
Correct Tenant
+
Everything Successful
```

至少还必须考虑：

```text
Invalid Input
No Permission
Wrong Tenant
Wrong Company
Wrong Status
Duplicate Request
Missing Data
Dependency Failure
Concurrency
```

---

# 5. Testing Pyramid

AIOS 默认采用：

```text
        E2E
       /   \
 Integration
    /       \
   Unit Tests
```

原则：

```text
大量 Unit Test
适量 Integration Test
少量关键 E2E Test
```

不得所有业务都只靠：

```text
E2E
```

测试。

---

# 6. Test 类型

AIOS 至少区分：

```text
Unit Test
Component Test
Integration Test
API Test
Database Test
Security Test
Permission Test
Tenant Isolation Test
E2E Test
Agent Test
Contract Test
Regression Test
Performance Test
```

根据功能风险选择。

---

# 7. Cursor 开发前必须判断测试需求

Cursor 开始修改前必须判断：

```text
是否修改 Business Rule？
是否修改 Permission？
是否修改 Tenant Scope？
是否修改 Database？
是否修改 API Contract？
是否修改 Money Calculation？
是否修改 Workflow？
是否修改 Agent？
是否修改 Shared Component？
```

并决定需要哪些测试。

---

# 8. Cursor 不得等到最后才考虑测试

正确流程：

```text
Understand Requirement
↓
Identify Risk
↓
Identify Test Cases
↓
Implement
↓
Run Tests
↓
Regression Check
```

不是：

```text
Implement Everything
↓
看看能不能跑
```

---

# 9. Existing Test 优先

修改现有功能前：

必须先检查：

```text
Existing Unit Test
Existing Integration Test
Existing E2E Test
Existing Fixtures
```

不得无视现有 Test Pattern：

重新建立另一套测试体系。

---

# 10. Bug 修复必须加入 Regression Test

如果 Bug 可以通过自动测试稳定重现：

应优先：

```text
先建立失败 Test
↓
修复 Bug
↓
确认 Test 通过
```

防止未来再次出现。

---

# 11. Bug Test 必须验证根因

例如 Bug：

```text
0 被显示成空值
```

Regression Test 应测试：

```text
value = 0
→ 应显示 0
```

而不是只测试 CSS 是否存在。

---

# 12. Unit Test

Unit Test 用于验证：

```text
Function
Domain Rule
Calculation
Policy
Validator
Mapper
Utility
```

不依赖完整外部系统。

---

# 13. Unit Test 优先测试 Business Logic

高价值 Unit Test：

```text
Tax Calculation
Commission Calculation
Invoice Total
Stock Validation
State Transition
Approval Rule
Permission Scope
```

低价值：

```text
Getter
Setter
Simple Constructor
```

无需机械测试。

---

# 14. Unit Test 必须可重复

同一个 Unit Test：

运行：

```text
1次
100次
CI
Local
```

结果必须一致。

---

# 15. 测试不得依赖真实当前时间

禁止测试依赖：

```text
LocalDateTime.now()
```

然后期待固定结果。

时间敏感业务必须使用：

```text
Injectable Clock
Fixed Test Time
```

或项目统一时间抽象。

---

# 16. 测试不得依赖随机结果

如果使用 Random：

必须：

```text
固定 Seed
```

或确保断言不依赖不稳定随机值。

---

# 17. 测试不得依赖执行顺序

错误：

```text
Test A creates customer
Test B assumes customer exists
```

每个 Test 应尽量独立。

---

# 18. Test Isolation

每个 Test：

必须能够单独运行。

不能依赖：

```text
Previous Test
Developer Machine State
Manual Database Setup
```

---

# 19. Test Naming

测试名称必须表达：

```text
Scenario
Expected Result
```

例如：

```text
shouldRejectRefundWhenAmountExceedsRefundableBalance
```

优于：

```text
testRefund1
```

---

# 20. AAA Pattern

Unit Test 推荐：

```text
Arrange
Act
Assert
```

保持结构清楚。

---

# 21. 一个 Test 应有明确目的

不要一个 Test 同时验证：

```text
Customer
Invoice
Stock
Payroll
Email
```

完全无关内容。

---

# 22. Test Assertion 必须有意义

禁止：

```text
assertNotNull(result)
```

就代表完整业务正确。

应检查关键：

```text
Status
Amount
Currency
Owner
Tenant
State
```

---

# 23. 不要过度 Mock

Mock 用于隔离：

```text
External Dependency
Repository
Provider
```

但不能把：

```text
所有 Business Logic
```

全部 Mock 掉。

否则 Test 没有价值。

---

# 24. 不得 Mock 被测试对象

例如测试：

```text
InvoiceService
```

不能把：

```text
InvoiceService
```

自己 Mock。

---

# 25. Mock 必须符合真实 Contract

Mock Response：

不能为了 Test 方便：

返回 Production 永远不会返回的结构。

---

# 26. Integration Test

Integration Test 用于验证多个真实 Component：

```text
Controller
Service
Repository
Database
Security
```

之间正确协作。

---

# 27. Backend Integration Test

重要 Use Case 应重点验证：

```text
Request
↓
Security
↓
Application
↓
Domain
↓
Repository
↓
PostgreSQL
```

整体正确。

---

# 28. Database Integration Test

涉及：

```text
Constraint
Unique
Foreign Key
Transaction
Query
Migration
```

时：

不能只靠 Mock Repository。

必须使用真实 PostgreSQL 行为进行测试。

---

# 29. PostgreSQL 行为不能用不同数据库代替

禁止长期使用：

```text
H2 / SQLite
```

完全代替 PostgreSQL Integration Test，

如果生产依赖：

```text
JSONB
PostgreSQL Constraint
PostgreSQL SQL
UUID
Locking
```

等 PostgreSQL 行为。

测试环境应尽量匹配 PostgreSQL。

---

# 30. Test Database

Test Database 必须：

```text
独立
可重置
不可连接 Production
```

---

# 31. Production Database 禁止测试

自动测试：

绝对禁止连接：

```text
Production PostgreSQL
```

---

# 32. Test Database Credential

Test Config：

必须与 Production Credential 分离。

---

# 33. Migration Test

所有 Database Migration：

必须确认：

```text
Fresh Database 可以成功执行
Existing Schema 可以升级
Application 可以启动
```

---

# 34. Migration 不仅测试空数据库

重要 Migration：

必须考虑：

```text
已有数据
NULL
Duplicate
Legacy Value
Large Data
```

情况。

---

# 35. Constraint Test

例如：

```text
UNIQUE(tenant_id, customer_code)
```

必须验证：

```text
Same tenant duplicate → reject
Different tenant same code → allowed
```

---

# 36. Foreign Key Test

必须验证：

```text
Invalid Parent
```

不能写入 Child。

---

# 37. Tenant Database Constraint Test

如果 Database 设计提供 Tenant Composite Constraint：

必须验证 Cross-Tenant Relationship 无法成立。

---

# 38. Transaction Test

涉及多步骤业务：

必须验证：

```text
Step 1 success
Step 2 fail
→ All expected transactional changes rollback
```

---

# 39. Partial Side Effect Test

如果：

```text
DB rollback
```

但：

```text
Email already sent
```

必须判断系统是否符合设计。

重要流程需要测试 Side Effect Boundary。

---

# 40. API Test

所有重要 API：

必须验证：

```text
Method
Path
Request
Response
Status Code
Error Code
Permission
Tenant
```

---

# 41. API Success Test

Create API：

例如必须验证：

```text
201 Created
Response Contract
Database Record
Tenant
Audit if required
```

---

# 42. API Validation Test

至少根据字段测试：

```text
Missing Required
Invalid Format
Too Long
Out of Range
Invalid Enum
```

---

# 43. API Error Contract Test

错误必须验证统一：

```text
error.code
error.message
fieldErrors
requestId
```

如 API Standard 定义。

---

# 44. 不允许测试只检查 HTTP 200

API Test 必须检查：

```text
业务结果
```

而不是仅：

```text
status == 200
```

---

# 45. 401 Test

受保护 Endpoint：

必须测试未认证：

```text
→ 401
```

---

# 46. 403 Test

已认证但无 Permission：

必须测试：

```text
→ 403
```

或系统定义的安全行为。

---

# 47. 404 Test

不存在或安全隐藏 Resource：

必须验证正确：

```text
404
```

行为。

---

# 48. 409 Test

必须根据业务测试：

```text
Duplicate
Concurrency Conflict
Invalid State Conflict
```

---

# 49. 422 / Business Validation Test

业务规则失败：

必须验证对应：

```text
HTTP Status
Error Code
```

符合 API Standard。

---

# 50. API Contract Stability

修改 Response：

必须测试 Existing Client 依赖字段。

---

# 51. Contract Test

Spring Boot ↔ React：

Spring Boot ↔ Python：

Public API ↔ External Client：

应根据重要性建立 Contract Test。

---

# 52. Contract Test 目标

防止：

```text
Backend rename field
Frontend still expects old field
```

或：

```text
Python expects string
Backend changed to object
```

---

# 53. Frontend Testing

Frontend 测试应根据风险覆盖：

```text
Component
Interaction
Form
Permission UI
Loading
Error
Empty State
```

---

# 54. Frontend Test 不测试实现细节

优先测试：

```text
用户看到什么
用户可以做什么
```

而不是：

```text
内部 state variable 是多少
```

---

# 55. Component Test

共享：

```text
Button
Input
Modal
Table
Select
```

等 Design System Component：

应重点测试基础行为。

---

# 56. Shared Component Regression

修改：

```text
Button
Modal
Table
API Client
Permission Helper
```

属于高影响修改。

必须运行相关全局测试。

---

# 57. Form Test

重要 Form 至少测试：

```text
Required Field
Validation
Submit
API Error
Loading
Double Submit
```

---

# 58. Form Error Preservation

Validation Error 后：

应测试用户输入是否按照产品规则保留。

---

# 59. Loading State Test

必须确认：

```text
Loading
```

不会错误显示：

```text
No Data
```

---

# 60. Empty State Test

必须区分：

```text
No Data
No Search Result
No Permission
Error
```

---

# 61. Error State Test

API Failure：

必须验证 UI 不会：

```text
Crash
White Screen
Fake Success
```

---

# 62. Permission UI Test

无权限时：

必须测试：

```text
Button hidden / disabled
Route blocked
Sensitive field hidden
```

但同时必须有 Backend Permission Test。

---

# 63. Frontend Permission Test 不代替 Security Test

隐藏按钮通过：

不能证明 API 安全。

---

# 64. Table Test

业务 Table 应根据功能测试：

```text
Pagination
Sort
Filter
Search
Empty
Loading
Error
Row Action
```

---

# 65. Zero Value Test

必须特别测试：

```text
0
0.00
false
```

不能被当作 Empty。

---

# 66. Long Text Test

重要 UI 应测试：

```text
Long Company Name
Long Customer Name
Long Email
Long Translation
```

避免 Layout 破坏。

---

# 67. Responsive Test

关键页面至少验证：

```text
Desktop
Tablet / Narrow Width
```

如果产品要求 Mobile：

也必须测试 Mobile。

---

# 68. Accessibility Test

共享 UI 应至少检查：

```text
Label
Keyboard
Focus
Semantic Element
```

---

# 69. Browser Error Test

Frontend 不得存在：

```text
Unhandled Promise Rejection
React Error
Console Error
```

由当前修改导致。

---

# 70. TypeScript Test Gate

Frontend 完成前至少执行：

```text
Type Check
```

不得通过：

```text
any
@ts-ignore
```

隐藏错误。

---

# 71. Frontend Build

Frontend 修改完成后：

必须尽可能执行：

```text
Build
```

确保正式 Bundle 可以生成。

---

# 72. Backend Build

Spring Boot 修改：

必须执行项目对应：

```text
Compile / Build
```

---

# 73. Python Validation

Python 修改：

必须根据项目执行：

```text
Syntax
Type Check
Lint
Relevant Test
```

已有工具时必须使用现有工具。

---

# 74. Build 通过不等于测试通过

Build 只能证明：

> 基础代码结构可编译。

不能证明：

```text
业务逻辑正确
权限正确
Tenant 正确
```

---

# 75. Security Test

安全相关功能必须测试：

```text
Unauthenticated
Unauthorized
Wrong Tenant
Wrong Company
IDOR
Mass Assignment
Injection
Sensitive Data Exposure
```

---

# 76. IDOR Test

例如：

```text
GET /customers/{id}
```

必须测试：

```text
User A changes ID to inaccessible resource
→ DENY
```

---

# 77. Mass Assignment Test

普通 Update Request 加入：

```text
tenantId
role
isAdmin
permission
createdBy
approved
```

必须不能修改受保护字段。

---

# 78. SQL Injection Test

Search / Sort / Filter：

必须验证用户输入无法改变 SQL Structure。

---

# 79. XSS Test

允许用户输入文本 / HTML 的功能：

应测试恶意 Script 不会在 UI 执行。

---

# 80. File Security Test

文件上传至少根据业务测试：

```text
Unsupported Type
Oversized File
Invalid MIME
Unauthorized File
Path Traversal
```

---

# 81. Sensitive Response Test

普通 User API：

必须确认不会返回：

```text
passwordHash
token
secret
salary
bank information
```

超出权限的数据。

---

# 82. Tenant Isolation Test 是强制测试

任何 Tenant Scoped Feature：

必须拥有 Tenant Isolation Test。

至少：

```text
Tenant A cannot read Tenant B
Tenant A cannot update Tenant B
Tenant A cannot delete Tenant B
```

---

# 83. Tenant List Test

List API：

必须测试 Tenant A：

只返回 Tenant A Data。

---

# 84. Tenant Search Test

Search：

必须测试不会搜索到 Tenant B。

---

# 85. Tenant Count Test

```text
totalItems
KPI
Dashboard Count
```

必须只统计 Authorized Tenant Data。

---

# 86. Tenant Export Test

Export：

必须确认不会包含其他 Tenant 数据。

---

# 87. Tenant AI Test

AI Agent / RAG：

必须确认 Tenant A：

无法检索 Tenant B Knowledge / Memory / Business Data。

---

# 88. Company Isolation Test

同 Tenant 多 Company 时：

必须测试：

```text
User only Company A
→ Cannot access Company B
```

如果权限模型要求隔离。

---

# 89. Permission Test

每个高风险 Action：

必须至少测试：

```text
Has Permission → allowed
No Permission → denied
```

---

# 90. Permission Scope Test

例如：

```text
OWN
COMPANY
TENANT
```

必须分别验证。

---

# 91. OWN Scope Test

必须测试：

```text
Own resource → allow
Other user's resource → deny
```

---

# 92. Company Scope Test

必须测试：

```text
Allowed company → allow
Other company → deny
```

---

# 93. Permission Revocation Test

Role Permission 被撤销后：

必须验证：

```text
Old access no longer works
```

包括 Cache 场景。

---

# 94. Multiple Role Test

如果支持多个 Role：

必须验证 Effective Permission 合并规则。

---

# 95. Privilege Escalation Test

必须测试普通 User：

不能通过：

```text
roleId
permissionId
tenantId
companyId
API payload
```

提升权限。

---

# 96. Tenant Admin Test

必须测试 Tenant Admin：

无法访问 Platform Super Admin API。

---

# 97. Last Admin Test

如果系统保护最后一个 Admin：

必须测试对应逻辑。

---

# 98. Finance Test

Finance 属于最高风险测试领域。

必须重点测试：

```text
Precision
Currency
Posting
Reversal
Void
Idempotency
Permission
Audit
```

---

# 99. Money Precision Test

禁止只测试整数。

必须测试：

```text
0
0.01
0.005
Large Amount
Decimal Rate
```

根据业务 Precision。

---

# 100. Rounding Test

必须明确测试：

```text
Rounding Mode
Scale
Rounding Point
```

例如边界：

```text
1.004
1.005
1.006
```

具体按业务规则。

---

# 101. Currency Test

必须测试：

```text
MYR
SGD
USD
AUD
```

等多 Currency 行为，

如果对应模块支持多货币。

---

# 102. Currency Mismatch Test

例如：

```text
Refund Currency != Payment Currency
```

必须根据业务拒绝或正确处理。

---

# 103. Exchange Rate Test

必须测试：

```text
Decimal precision
Historical rate
Zero
Negative if invalid
Missing rate
```

---

# 104. Financial History Test

已 Posted / Finalized Record：

必须测试不能通过普通 Update：

静默修改金额。

---

# 105. Reversal Test

如果支持 Reversal：

必须验证：

```text
Original remains
Reversal created
Net effect correct
Audit correct
```

---

# 106. Payment Idempotency Test

同一个：

```text
Idempotency-Key
```

重复调用：

不得生成多笔 Payment。

---

# 107. Refund Test

必须至少测试：

```text
Valid Refund
Refund > Remaining Amount
Duplicate Refund
Wrong Currency
No Permission
Already Fully Refunded
```

---

# 108. Inventory Test

Inventory 应重点测试：

```text
Stock Movement
Balance
Concurrency
Transfer
Adjustment
```

---

# 109. Stock 不允许直接覆盖测试

必须确认：

库存变化通过：

```text
Movement
```

正确记录。

---

# 110. Stock Concurrency Test

例如库存：

```text
10
```

两个请求同时扣：

```text
8 + 8
```

必须防止：

```text
-6
```

或 Oversell，

除非业务允许负库存。

---

# 111. Stock Transfer Test

必须验证：

```text
Source decrease
Destination increase
Movement history
Transaction consistency
```

---

# 112. Workflow Test

Workflow 必须测试：

```text
Valid Transition
Invalid Transition
Correct Approver
Wrong Approver
Reject
Cancel
```

---

# 113. Status Transition Test

必须验证：

```text
DRAFT → APPROVED
```

如果不允许直接跳过：

必须拒绝。

---

# 114. Approval Test

至少测试：

```text
Correct Approver
Wrong Approver
Duplicate Approval
Already Rejected
Already Approved
```

---

# 115. Self Approval Test

如果 Policy 禁止：

```text
Creator == Approver
```

必须测试。

---

# 116. Approval Amount Limit Test

如存在金额授权：

必须测试边界：

```text
below limit
equal limit
above limit
```

---

# 117. Audit Test

关键业务动作：

必须验证 Audit 是否产生。

---

# 118. Audit 内容 Test

至少确认：

```text
Actor
Tenant
Action
Resource
Time
Result
```

准确。

---

# 119. Audit Sensitive Data Test

必须确认 Audit：

不会保存：

```text
Password
Token
Secret
```

# 276. Testing 最终原则

AIOS Testing 必须坚持：

> 能运行，不代表正确。

> Build 通过，不代表业务正确。

> API 返回 200，不代表业务成功。

> Frontend 隐藏按钮，不代表权限安全。

> Unit Test 通过，不代表 Integration 正确。

> Happy Path 通过，不代表系统可靠。

> 每个 Tenant Scoped 功能都必须考虑 Cross-Tenant Test。

> 每个高风险功能都必须测试 Permission。

> Finance、Payment、Payroll、Inventory 必须测试 Precision、Transaction 与 Concurrency。

> 每个关键 Bug 都应该尽可能留下 Regression Test。

> PostgreSQL 的关键行为必须使用真实 PostgreSQL 语义验证。

> Test 不得依赖 Production 数据。

> Test 不得使用 Production Secret。

> Test 必须可重复、可独立、可预测。

> Flaky Test 是需要修复的问题，不是正常现象。

> Cursor 不能通过删除 Test 让项目变绿。

> Cursor 不能通过降低业务标准让 Test 通过。

> Cursor 不能伪造没有执行过的测试结果。

> AI Agent 测试不能只测试回答文字，还必须测试 Tool、Permission、Tenant、Retry 与 High-Risk Action。

> Multi-Agent 必须测试不能通过 Agent Delegation 进行权限升级。

> Testing 的目标不是证明代码没有 Bug。

> Testing 的目标是持续降低系统发生错误、数据损坏、越权和回归的风险。

> AIOS 的正式完成标准必须是：功能正确、安全边界正确、数据正确、测试证据明确。
