> 文件编号：16

> Layer：1 — Identity & Organization（身份与组织层）  
> 适用范围：AIOS Core  
> 适用对象：Cursor、AI Agent、Frontend、Backend、Database  
> 优先级：服从《01 产品原则》《02 架构标准》《05 Database》《07 Security》《08 Permission》

# 1. 文件目的

定义 Layer 1 四个 Core Domain 的边界、关系与实现约束：

| # | Core Domain | 中文 | 核心作用 |
|---|-------------|------|----------|
| 03 | Identity / User | 用户身份 | 管理自然人、账号、Profile |
| 04 | Organization | 组织架构 | 部门、事业部、团队、组织树 |
| 05 | Position | 职位岗位 | CEO、Manager、Accountant 等岗位 |
| 06 | Membership | 成员关系 | User 与 Tenant / Company / Organization 的关系 |

本层属于 **AIOS Core**。  
CRM / HRM / Finance 等业务模块 **不得** 自建第二套 User / Org / Position / Membership。

---

# 2. 分层定位

```text
Layer 0  Tenant / Company（多租户与法人主体）
↓
Layer 1  Identity & Organization   ← 本文件
↓
Layer 2  Role / Permission / Security Policy
↓
Business Modules
```

原则：

> 先有 Identity 与组织归属，再谈 Role / Permission。

Membership 是授权与业务数据范围的前置关系，不是 Permission 本身。

# 3. Domain Ownership

| Domain | Owner Module | SSOT |
|--------|--------------|------|
| User / Identity | Core Identity | `users` + profile |
| Organization | Core Identity | `organizations` 树 |
| Position | Core Identity | `positions` |
| Membership | Core Identity | `memberships` |

禁止：

* HRM 另建 `employees` 作为系统登录身份（Employee 可关联 User，但不能替代 User）

* 各模块私自存 `department_name` 字符串代替 Organization 引用

# 4. Identity / User（03）

## 4.1 定义

User 表示可认证的平台身份（自然人账号），不是 Tenant，也不是 Company。

至少包含：

```text
id
email
status                    # active | disabled | invited
display_name / profile
email_verified_at
mfa_enabled
created_at
updated_at
```

密码、OAuth identity、MFA secret 属于 Security / Auth 子域，不得明文出现在普通业务 API。

## 4.2 规则

1. Email 在平台级应唯一（具体 uniqueness 策略由 Identity Standard 与 Tenant 策略共同约束）。
2. Disabled User 不得继续有效 Session（见 Security Standard）。
3. User 本身 **不直接等于** 某 Company 员工；归属通过 Membership 表达。
4. Profile 字段最小化；敏感字段按 Database / Security 分级。

## 4.3 禁止

```text
user.companyId 作为唯一归属
user.role = "ADMIN" 写死在 User 表代替 RBAC
业务表冗余完整 user profile 副本长期不同步
```

# 5. Organization（04）

## 5.1 定义

Organization 是 Tenant 内的组织树节点，例如：

```text
集团 / 事业部 / 部门 / 团队 / 门店编制单元
```

至少包含：

```text
id
tenant_id
parent_id                 # nullable = root
code
name
type                      # division | department | team | other
status                    # active | inactive
sort_order
```

## 5.2 规则

1. Organization **必须** 带 `tenant_id`。
2. 树不可成环；移动节点必须校验祖先关系。
3. 删除默认应软停用或限制：存在子节点 / 有效 Membership 时禁止硬删。
4. Company（法人主体）与 Organization（编制树）分离：Company 不是 Org 的别名。

## 5.3 禁止

```text
用扁平 department 字符串替代组织树
跨 Tenant 复用 organization_id
前端自行拼树作为权限边界依据
```

# 6. Position（05）

## 6.1 定义

Position 是岗位定义（职缺模板），不是具体人。

```text
id
tenant_id
code
name                      # CEO / Manager / Accountant
description
status
```

可选：`organization_id`（岗位默认挂靠某组织节点）——若使用，不得替代 Membership 上的实际组织归属。

## 6.2 规则

1. Position 是可复用主数据；多人可通过 Membership 占用同一 Position。
2. Position ≠ Role。Role 属于 Permission 层；Position 属于组织层。
3. 职称变更不影响历史单据上的审计快照策略（由 Audit / Domain 标准另定）。

## 6.3 禁止

```text
position = role 混用
把 Position 名称硬编码进业务 if 判断作为授权
```

---

# 7. Membership（06）

## 7.1 定义

Membership 描述 User 在租户上下文中的组织归属关系：

```text
id
tenant_id
user_id
company_id                # optional / required by policy
organization_id           # optional
position_id               # optional
is_primary                # 主隶属
status                    # active | ended
valid_from / valid_to
```

## 7.2 规则

1. 同一 User 可在同一 Tenant 下有多条 Membership（多公司 / 多部门兼职）。
2. 业务请求的 Company / Org scope 必须能回溯到有效 Membership（或更高权限的平台角色，由 Permission 层定义）。
3. `is_primary` 在同一 Tenant（或同一 Company，按产品策略）至多一条 active primary。
4. 结束 Membership 不删除历史；用 `status` / `valid_to`。
5. Membership **不存储** Permission 列表。

## 7.3 禁止

```text
仅凭 user.email 域后缀推断公司归属
前端传 organizationId 却不校验 Membership
删除 User 时级联物理删除全部 Membership 审计线索（应遵循 Retention）
```

# 8. 关系总览

```text
Tenant
  ├── Company
  ├── Organization (tree)
  ├── Position
  └── Membership
         ├── User
         ├── Company?
         ├── Organization?
         └── Position?
```

认证后的请求上下文最小集合：

```text
Authenticated User
+ Active Tenant
+ Authorized Company / Organization Scope（源自 Membership + Permission）
```

# 9. API 边界（Application API）

统一前缀建议：

```text
/api/identity/users
/api/identity/organizations
/api/identity/positions
/api/identity/memberships
```

要求：

1. 所有写操作校验 Tenant Context。
2. Organization 提供树形读取与节点移动专用 API，避免客户端任意改 parent 造成环。
3. Membership 创建/变更必须验证 User、Org、Position、Company 同属当前 Tenant。
4. 列表接口支持分页与状态过滤；禁止默认全表导出无审计。

错误语义遵循 API / Error Handling Standard（401 / 403 / 404 / 409）。

# 10. Frontend 模块标准

Frontend 位置：

```text
src/modules/core/identity/
```

页面（与 Sidebar System → Core 对齐）：

```text
Users
Organization
Position
Membership
```

规则：

1. React 只负责展示与交互；归属校验在 Backend（当前阶段由 Mock 模拟）。
2. Organization 使用树 / 层级列表，不得做成无父子关系的假树。
3. Membership 表单必须显式选择 User，并按策略选择 Company / Org / Position。
4. 不得在业务模块复制这些页面逻辑。

---

# 11. Database 要点

1. 业务表如需记录操作者：存 `user_id`，不要存整份 profile。
2. 业务表如需组织范围：存 `organization_id` / `company_id`，并与 Tenant 一致。
3. Membership、Organization、Position 均需 `tenant_id`。
4. 唯一约束示例：

```text
positions: UNIQUE (tenant_id, code)
organizations: UNIQUE (tenant_id, code)
memberships: 按产品定义防重（如 active 同一 user+company+org+position）
```

---

# 12. Permission 衔接

```text
User
↓
Membership（归属）
↓
Role Assignment（授权，Permission 层）
↓
Permission Check
```

没有 Membership 时，默认不应访问 Tenant 业务数据（平台级 Super Admin 除外，由 Security / Permission 定义）。

---

# 13. Cursor / Agent 禁令

1. 不得在 CRM/HRM/Finance 新建平行 User/Org 表作为 SSOT。
2. 不得用前端隐藏菜单代替 Membership / Permission 校验。
3. 不得把 Position 当成 Role。
4. 不得把 Company 与 Organization 混名混表。
5. 不得为了演示去掉 `tenant_id`。
