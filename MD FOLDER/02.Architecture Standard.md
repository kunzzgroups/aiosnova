# AIOS 系统架构标准

> 文件编号：02
> 文件名称：系统架构标准
> 适用范围：AIOS 全系统
> 适用对象：Cursor、AI Agent、开发人员、架构设计人员
> 优先级：仅次于《01 产品原则》
> 架构目标：统一、模块化、可扩展、安全、可维护、可审计、支持多租户与 AI Native

---

# 1. 文件目的

本文件定义 AIOS 的系统架构标准。

所有：

* Frontend
* Backend
* AI Service
* Database
* API
* Module
* Integration
* Automation
* Infrastructure

都必须遵守本文件。

Cursor 在开发任何功能前，必须先判断：

1. 功能属于哪个架构层。
2. 功能属于哪个业务模块。
3. 谁拥有该数据。
4. 谁拥有该业务规则。
5. 模块之间应该如何通信。
6. 是否会破坏现有架构边界。
7. 是否产生重复能力。
8. 是否影响 Tenant Isolation。
9. 是否影响 Security。
10. 是否产生不必要耦合。

禁止直接以：

> “哪里方便就写哪里”

作为代码设计方式。

---

# 2. AIOS 总体架构

AIOS 采用：

> **模块化企业平台架构 + API First + AI Native**

整体逻辑架构：

```text
┌─────────────────────────────────────────────┐
│                 Client Layer                │
│                                             │
│   Web / Admin / Super Admin / Future App    │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│               Frontend Layer                │
│                                             │
│       React + Vite + TypeScript             │
└──────────────────────┬──────────────────────┘
                       │
                       │ REST API
                       ▼
┌─────────────────────────────────────────────┐
│                Backend Layer                │
│                                             │
│               Spring Boot                   │
│                                             │
│ Authentication / Permission / Business      │
│ Transaction / Workflow / Audit / Domain     │
└──────────────┬──────────────────┬───────────┘
               │                  │
               │                  │ API / Event
               ▼                  ▼
┌──────────────────────┐  ┌──────────────────────┐
│   PostgreSQL         │  │     AI Layer         │
│                      │  │                      │
│ Primary Business DB  │  │       Python         │
└──────────────────────┘  │                      │
                          │ RAG / Agent / LLM     │
                          │ Memory / AI Workflow  │
                          └──────────────────────┘
```

未来可以增加：

```text
Cache
Message Queue
Object Storage
Search Engine
Vector Database
Data Warehouse
Data Lake
Observability
```

但 Cursor 不得在没有需求时擅自加入。

---

# 3. 核心架构原则

AIOS 架构必须遵守：

```text
Separation of Concerns
Single Responsibility
Domain Ownership
Low Coupling
High Cohesion
API First
Security by Design
Tenant by Design
Audit by Design
AI by Design
Observability by Design
```

---

# 4. 系统分层标准

AIOS 应至少区分：

```text
01 Presentation Layer
02 Application Layer
03 Domain Layer
04 Infrastructure Layer
05 Data Layer
06 AI Layer
07 Integration Layer
```

各层职责不得混乱。

---

# 5. Presentation Layer

Presentation Layer 主要为：

```text
React + Vite + TypeScript
```

负责：

* 页面展示
* 用户交互
* Routing
* Form
* Table
* Modal
* Dashboard
* Client State
* UI Permission
* Loading State
* Error State

不得负责：

* 核心业务计算
* 最终权限判断
* 数据库逻辑
* Transaction
* 核心 Finance Calculation
* 核心 Inventory Calculation
* 核心 Approval Rule

---

# 6. Application Layer

Application Layer 负责协调一个完整 Use Case。

例如：

```text
Create Sales Order
Approve Purchase Order
Process Refund
Create Employee
Transfer Stock
Generate Invoice
```

Application Layer 负责：

* 接收请求
* 调用 Domain Logic
* 调用 Permission
* 调用 Workflow
* 调用 Repository
* 调用 Integration
* 管理 Use Case

但不应该包含大量底层技术实现。

---

# 7. Domain Layer

Domain Layer 是业务规则核心。

例如：

```text
Sales
Inventory
Finance
HR
CRM
Procurement
```

Domain Layer 负责：

* Business Rule
* Domain Validation
* State Transition
* Domain Model
* Calculation
* Business Policy

例如：

```text
订单什么时候可以取消
库存什么时候可以扣减
Invoice 什么时候可以 Void
Refund 是否允许
Leave 是否符合申请规则
```

这些规则不得放在 Controller 或 Frontend。

---

# 8. Infrastructure Layer

Infrastructure Layer 负责技术能力。

例如：

* Database Access
* Redis
* File Storage
* Email
* SMS
* WhatsApp
* Message Queue
* Third-Party API
* Payment Gateway
* Cloud Storage

Domain 不应直接依赖具体第三方实现。

---

# 9. Data Layer

AIOS Primary Database：

```text
PostgreSQL
```

PostgreSQL 是核心业务数据来源。

核心业务数据必须以 PostgreSQL 作为主要持久化数据库。

禁止 Cursor 擅自引入：

* MySQL
* MongoDB
* Firebase
* Supabase Database
* SQLite

作为第二套核心业务数据库。

如未来确实需要其他数据库：

必须有明确架构用途。

---

# 10. Frontend 技术标准

Frontend 固定使用：

```text
React
Vite
TypeScript
```

禁止擅自更换为：

```text
Next.js
Vue
Angular
Svelte
```

除非用户明确批准。

---

# 11. Frontend 推荐分层

Frontend 应尽量按照：

```text
src/
├── app/
├── modules/
├── components/
├── layouts/
├── routes/
├── services/
├── hooks/
├── stores/
├── types/
├── utils/
├── constants/
└── assets/
```

进行组织。

具体目录可根据项目实际情况调整。

但必须保持：

> Domain Module 优先。

---

# 12. Frontend Module 标准

大型业务模块应独立组织。

例如：

```text
modules/
├── core/
├── crm/
├── sales/
├── pos/
├── inventory/
├── procurement/
├── finance/
├── hrm/
├── project/
└── marketing/
```

禁止所有页面堆积在：

```text
pages/
```

形成巨大无边界目录。

---

# 13. Frontend Component 分级

组件至少区分：

```text
Shared UI Component
Domain Component
Page Component
```

例如：

```text
Button
Input
Modal
Table
```

属于 Shared UI。

而：

```text
SalesOrderTable
InvoiceStatusBadge
EmployeeLeaveForm
```

属于 Domain Component。

不得为了“复用”将所有业务组件放进：

```text
common
shared
```

---

# 14. Frontend 不允许直接访问 Database

任何 React 代码禁止：

```text
直接访问 PostgreSQL
直接操作数据库
直接保存核心业务数据
```

所有业务数据必须：

```text
Frontend
↓
Spring Boot API
↓
Business Logic
↓
PostgreSQL
```

---

# 15. Frontend API Access 标准

Frontend 不应在组件内部到处直接：

```text
fetch(...)
axios(...)
```

应通过统一 API Client / Service Layer。

推荐：

```text
Component
↓
Hook / Service
↓
API Client
↓
Backend
```

这样方便统一处理：

* Authentication
* Token
* Error
* Retry
* Base URL
* Logging
* Response Format

---

# 16. Backend 技术标准

Backend 固定使用：

```text
Spring Boot
```

Backend 是 AIOS：

> 核心业务系统。

负责：

* Authentication
* Authorization
* Tenant Isolation
* Business Logic
* Workflow
* Approval
* Transaction
* Audit
* Domain Rules
* Database Access
* API
* Integration

---

# 17. Backend 模块化原则

Spring Boot 禁止发展成：

> 一个所有代码互相调用的巨大 Monolith。

当前阶段可以使用：

> **Modular Monolith**

作为主要架构。

也就是说：

```text
一个主要 Spring Boot Platform
+
清晰独立业务 Module
```

而不是一开始就拆成几十个 Microservices。

---

# 18. 默认不使用 Microservice

Cursor 不得因为 AIOS 很大就自动拆成：

```text
User Service
Role Service
CRM Service
Sales Service
Inventory Service
Finance Service
HR Service
```

几十个微服务。

默认优先：

```text
Modular Monolith
```

原因：

* 降低运维复杂度
* 降低网络通信成本
* 降低分布式事务复杂度
* 更容易快速发展 Core
* 更容易保证业务一致性

未来业务规模达到要求后，再根据实际需要拆分。

---

# 19. Backend 推荐模块结构

可以按照：

```text
com.aios
├── core
├── ai
├── dashboard
├── crm
├── sales
├── pos
├── commerce
├── inventory
├── procurement
├── supplychain
├── finance
├── hrm
├── project
├── helpdesk
├── marketing
├── manufacturing
├── asset
├── document
├── communication
├── automation
├── developer
├── integration
├── marketplace
├── security
├── data
└── admin
```

建立 Domain Boundary。

实际命名可根据项目标准调整。

---

# 20. Module 内部分层

每个 Backend Module 应尽量保持统一结构。

例如：

```text
sales/
├── controller/
├── application/
├── domain/
├── repository/
├── dto/
├── mapper/
├── event/
└── integration/
```

或按照项目现有规范执行。

重点不是目录名称。

重点是：

> Responsibility 必须清楚。

---

# 21. Controller 标准

Controller 只负责：

* 接收 HTTP Request
* Request Validation
* 调用 Application Service
* 返回 Response

禁止 Controller 包含：

* 大量 Business Logic
* SQL
* Complex Calculation
* Transaction Logic
* Permission Hardcode

---

# 22. Service 标准

Service 不得成为：

> 所有代码都丢进去的巨大类。

必须区分：

```text
Application Service
Domain Service
Infrastructure Service
```

一个 Service 应拥有明确职责。

---

# 23. Repository 标准

Repository 只负责：

> Data Access。

Repository 不应承担：

* Business Decision
* Permission
* Workflow
* UI Logic

---

# 24. DTO 与 Entity 必须分离

禁止长期直接：

```text
Entity
→ API Response
```

尤其是复杂系统。

API 应使用：

```text
Request DTO
Response DTO
```

这样避免：

* 暴露内部字段
* Lazy Loading 问题
* API 与 Database 强耦合
* Sensitive Data 泄露

---

# 25. Entity 不等于 Domain

Database Entity：

> 数据持久化模型。

API DTO：

> 数据传输模型。

Domain Model：

> 业务概念模型。

Cursor 不得默认三者永远完全相同。

---

# 26. AI Layer 技术标准

AI Layer 固定使用：

```text
Python
```

负责：

* AI Assistant
* AI Copilot
* AI Agent
* Multi-Agent
* RAG
* Knowledge Retrieval
* Prompt Processing
* AI Memory
* AI Decision
* AI Automation
* LLM Integration

---

# 27. AI Layer 与 Backend 边界

Python AI Layer：

不负责核心：

* Finance Transaction
* Inventory Transaction
* User Permission
* Tenant Security
* Payroll Transaction
* Order Transaction

核心业务执行仍由：

```text
Spring Boot
```

负责。

---

# 28. AI Action 标准架构

正确：

```text
User
↓
React
↓
Python AI Service
↓
Spring Boot API
↓
Permission
↓
Business Rule
↓
Database
```

或者：

```text
User
↓
React
↓
Spring Boot
↓
Python AI Service
↓
AI Result
↓
Spring Boot
↓
Business Action
```

具体流程根据 Use Case 决定。

---

# 29. AI 禁止绕过 Backend

禁止：

```text
Python
↓
直接 UPDATE customer
```

禁止：

```text
AI Agent
↓
直接 DELETE invoice
```

禁止：

```text
AI Agent
↓
直接修改 employee salary
```

所有核心业务动作必须经过 Backend。

---

# 30. Database Ownership 原则

每类核心数据必须明确 Owner Module。

例如：

| 数据             | Owner                      |
| -------------- | -------------------------- |
| User           | Core                       |
| Tenant         | Core                       |
| Company        | Core                       |
| Role           | Core                       |
| Permission     | Core                       |
| Customer       | CRM                        |
| Sales Order    | Sales                      |
| Product        | Inventory / Product Domain |
| Stock          | Inventory                  |
| Purchase Order | Procurement                |
| Invoice        | Finance / Sales Contract   |
| Employee       | HRM                        |
| Project        | Project                    |

其他模块不能随意修改非自己拥有的数据。

---

# 31. Cross-Module Communication 标准

模块之间优先使用：

```text
Application Service
Domain Contract
Event
```

禁止：

```text
FinanceRepository
```

直接被：

```text
SalesModule
```

跨模块调用。

---

# 32. 禁止跨模块直接操作 Table

例如：

Sales 不应该直接：

```sql
UPDATE inventory_stock
```

正确方式应是：

```text
Sales
↓
Inventory Service
↓
Inventory Domain
↓
Stock Repository
```

这样 Inventory 才能够保证自己的业务规则。

---

# 33. 同步调用与 Event

需要立即得到结果时：

使用同步调用。

例如：

```text
检查库存
验证客户
计算权限
```

不需要阻塞当前流程时，可以使用 Event。

例如：

```text
发送 Notification
写 Analytics
触发 Email
更新 Search Index
```

---

# 34. Event 不得滥用

Cursor 不得为了“架构高级”而将所有逻辑改成 Event Driven。

如果：

```text
A 操作必须知道 B 成功以后才能继续
```

那么通常应优先使用同步调用或明确 Transaction Flow。

---

# 35. Transaction Boundary

一个业务操作必须明确 Transaction Boundary。

例如：

```text
Create Sales Order
```

可能包含：

```text
Create Order
Create Order Items
Reserve Stock
Write Audit
```

但必须明确：

哪些必须共同成功。

哪些可以异步处理。

不得随意拆开造成部分成功。

---

# 36. Distributed Transaction 原则

当前 Modular Monolith 阶段：

优先使用本地 Database Transaction。

未来拆 Microservice 后：

不得直接依赖传统跨服务数据库 Transaction。

应考虑：

* Saga
* Outbox
* Eventual Consistency
* Idempotency

但 Cursor 当前不得提前实现复杂分布式架构。

---

# 37. API 架构标准

Frontend、AI、Third Party 必须通过正式 API 与 Backend 交互。

API 必须：

* 有明确 Resource
* 有 Permission
* 有 Tenant Scope
* 有 Validation
* 有统一错误结构
* 有 Pagination
* 有版本策略
* 有清晰 Request / Response

---

# 38. REST API 默认原则

默认优先采用：

```text
REST API
```

例如：

```text
GET    /api/customers
POST   /api/customers
GET    /api/customers/{id}
PUT    /api/customers/{id}
DELETE /api/customers/{id}
```

但具体命名必须跟随后续 API Standard。

---

# 39. GraphQL 使用原则

Developer Platform 中未来可以支持 GraphQL。

但 Cursor 不得因为系统列表中存在 GraphQL，就现在同时为所有功能建立 REST + GraphQL。

除非明确要求。

---

# 40. Authentication 架构

Authentication 属于 Core / Security。

所有业务模块不得自行建立独立 Login 系统。

统一：

```text
Authentication
↓
Identity
↓
Authorization
↓
Tenant Scope
↓
Business Access
```

---

# 41. Permission 架构

Permission 必须统一。

禁止：

CRM：

```text
if role == ADMIN
```

Sales：

```text
if isManager
```

Finance：

```text
if user.type == 1
```

形成多套权限逻辑。

统一经过：

```text
RBAC
ABAC
Permission Service
```

---

# 42. Multi-Tenant 架构

所有核心业务请求必须带有明确 Tenant Context。

基本请求上下文：

```text
Authenticated User
↓
Tenant
↓
Company
↓
Role / Permission
↓
Resource Scope
```

Cursor 不得写出：

```text
findAll()
```

然后返回所有 Tenant 数据。

---

# 43. Tenant Context 不得由用户自由指定

禁止只相信：

```text
tenantId
```

来自 Frontend。

Backend 必须根据：

* Authentication
* Membership
* Permission

验证当前用户是否有权访问对应 Tenant。

---

# 44. Company Context

一个 Tenant 可以拥有多个 Company。

所以所有 Company Scoped 数据必须明确：

```text
tenant_id
company_id
```

之间的关系。

不得默认：

```text
一个 Tenant 永远只有一个 Company。
```

---

# 45. Super Admin 架构

Super Admin 属于 Platform Control Plane。

普通 Tenant Business API 不得默认支持跨 Tenant。

跨 Tenant 能力必须：

* 明确接口
* 明确权限
* 明确审计
* 明确 Security Boundary

---

# 46. Configuration 架构

配置必须根据作用范围分类。

例如：

```text
System Setting
Tenant Setting
Company Setting
User Setting
Module Setting
```

禁止所有设置塞入一个巨大：

```text
settings
```

对象而没有 Scope。

---

# 47. Shared Kernel 原则

真正跨模块公共能力可进入 Core / Shared Kernel。

例如：

* Base ID
* Tenant Context
* Audit Metadata
* Common Error
* Permission Contract
* Date Utilities
* Pagination

但 Shared Kernel 必须保持小。

---

# 48. Core 不得成为垃圾场

AIOS Core 非常重要。

但不能因为一个功能不知道放哪里，就放：

```text
core/
```

Core 只接受：

> 真正所有模块需要的基础平台能力。

---

# 49. Workflow 架构

Workflow 是 Platform Capability。

业务模块负责告诉 Workflow：

```text
什么事情需要审批
需要什么业务 Context
```

Workflow 负责：

```text
Flow
Step
Approver
Decision
Transition
```

业务模块不得各自重复实现完整审批引擎。

---

# 50. Notification 架构

Notification 应统一经过 Notification Platform。

例如：

```text
Sales
↓
Notification Service
↓
Email / SMS / WhatsApp / Push / In-App
```

业务模块不应该自行直接管理所有发送渠道。

---

# 51. File 架构

所有业务文件原则上通过：

```text
File Center
```

统一管理。

包含：

* File Metadata
* Permission
* Ownership
* Tenant
* Version
* Storage Provider

业务模块仅保存：

```text
fileId
```

或关联关系。

不要不同模块自己建立不同文件系统。

---

# 52. Audit 架构

Audit 属于平台能力。

关键业务模块调用统一 Audit 能力。

不要每个模块建立：

```text
crm_audit
sales_audit
finance_audit
```

完全不同的审计机制。

---

# 53. Integration Hub 架构

第三方系统整合应尽量通过：

```text
Integration Hub
```

例如：

* Payment
* Google
* Microsoft
* Delivery
* Ecommerce
* Banking
* Social Media

业务模块不要直接深度绑定具体 Provider。

---

# 54. Provider Abstraction

例如 Payment：

正确：

```text
Payment Domain
↓
Payment Provider Interface
├── Provider A
├── Provider B
└── Provider C
```

不要：

```text
SalesService
↓
Stripe-specific code
```

直接写死。

---

# 55. External API Failure

所有外部系统必须被视为：

> 不可靠。

必须考虑：

* Timeout
* Retry
* Rate Limit
* Duplicate
* Partial Failure
* Provider Downtime
* Invalid Response

不能假设第三方 API 永远成功。

---

# 56. Cache 架构原则

如未来使用 Redis：

Cache 只用于：

* Performance
* Temporary State
* Session
* Rate Limit
* Frequently Read Data

核心业务事实仍由 PostgreSQL 负责。

禁止：

> Cache 成为唯一数据来源。

---

# 57. Message Queue 原则

只有实际出现：

* Async Processing
* Event Distribution
* High Load
* Decoupling Need

时才引入 Message Queue。

Cursor 不得现在为了未来可能使用，提前建立复杂 MQ 架构。

---

# 58. Search Engine 原则

如果 PostgreSQL Search 已足够：

优先使用 PostgreSQL。

只有存在明确：

* Full Text Search
* Large Search
* Complex Ranking

需求后，再考虑专门 Search Engine。

---

# 59. Vector Database 原则

AI RAG 可以未来使用 Vector Storage。

但 Vector Database：

> 不等于业务数据库。

核心业务数据仍然以 PostgreSQL 为 Source of Truth。

Vector Data 只是 AI Retrieval Index。

---

# 60. AI Knowledge Base 数据边界

Knowledge Base 应区分：

```text
Source Document
Parsed Content
Chunk
Embedding
Metadata
Permission
Tenant
```

AI Retrieval 必须遵守 Tenant 与 Permission Scope。

禁止：

> Tenant A 的 Embedding 被 Tenant B 搜索到。

---

# 61. AI Memory 架构

AI Memory 必须明确 Scope：

```text
User Memory
Session Memory
Agent Memory
Tenant Memory
Business Memory
```

不得将不同用户、Tenant 的 Memory 混在一起。

---

# 62. AI Tool Calling 架构

AI Agent 不直接执行任意系统代码。

必须通过：

```text
Approved Tool
↓
Permission
↓
Validation
↓
Backend Action
↓
Audit
```

AI Tool 必须有明确输入输出 Contract。

---

# 63. AI High-Risk Action

以下操作属于高风险：

* Payment
* Refund
* Payroll
* Permission
* Role Change
* User Disable
* Delete
* Financial Posting
* Bank Action
* Contract
* Invoice Void

AI 执行时必须考虑：

```text
Confirmation
Approval
Audit
Risk Control
```

---

# 64. Database 与 AI 分离

禁止 AI Prompt 直接生成 SQL 后执行核心业务修改。

禁止：

```text
LLM
↓
Generated SQL
↓
Production DB
```

直接运行。

任何核心数据修改必须走受控业务 API。

---

# 65. Data Platform 与 Operational System 分离

未来：

```text
Operational Database
Data Warehouse
Data Lake
```

必须明确职责。

PostgreSQL Operational DB：

负责日常交易。

Warehouse：

负责分析。

Data Lake：

负责大规模原始数据。

不得为了 BI 报表直接无限压榨生产数据库。

---

# 66. Dashboard 架构

简单 Dashboard：

可以读取业务 API。

复杂 BI：

未来应逐渐通过：

```text
Analytics Layer
Data Warehouse
```

提供。

禁止前端一次调用几十个 API 然后自行拼接大型企业报表。

---

# 67. Reporting 架构

报表计算应明确：

* Data Source
* Calculation Rule
* Time Range
* Currency
* Tenant
* Company

关键财务报表不得由 Frontend 自行计算。

---

# 68. Security Boundary

系统至少存在：

```text
Public Boundary
Authenticated Boundary
Tenant Boundary
Company Boundary
Permission Boundary
Admin Boundary
Super Admin Boundary
AI Tool Boundary
Integration Boundary
```

任何跨 Boundary 操作都必须明确验证。

---

# 69. Secret Management

以下禁止进入代码库：

```text
DB Password
API Secret
OAuth Secret
Private Key
Access Token
Production Credential
```

必须通过：

* Environment Variable
* Secret Manager

进行管理。

---

# 70. Environment 架构

至少区分：

```text
local
development
staging
production
```

禁止：

* Production Credential 用于 Local
* Dev DB 与 Prod DB 混用
* 测试数据写入 Production

---

# 71. Configuration 不应写死环境

代码禁止：

```text
if production then URL A
if dev then URL B
```

到处 Hardcode。

应使用标准 Environment Configuration。

---

# 72. Logging 架构

所有服务必须使用统一 Logging 机制。

日志至少可关联：

```text
Request ID
User ID
Tenant ID
Module
Action
Timestamp
Result
```

敏感数据不得进入 Log。

---

# 73. Trace ID

一个跨多个层的 Request 应尽量具备统一：

```text
Trace ID
Request ID
Correlation ID
```

方便追踪：

```text
Frontend
↓
Backend
↓
AI
↓
External API
```

---

# 74. Error Architecture

系统必须统一错误类型。

至少区分：

```text
Validation Error
Authentication Error
Authorization Error
Business Error
Not Found
Conflict
System Error
External Service Error
```

禁止所有错误都返回：

```text
500 Internal Server Error
```

---

# 75. Error 不得泄露内部细节

API 不应返回：

```text
SQL
Stack Trace
Database Password
Internal Server Path
Secret
```

给 Frontend 或外部用户。

---

# 76. Idempotency Architecture

高风险写操作应支持 Idempotency。

尤其：

```text
Payment
Refund
Order
Webhook
Invoice Posting
AI Action
```

防止重复执行。

---

# 77. Background Job

耗时工作不得长期阻塞 HTTP Request。

例如：

* Large Report
* AI Document Parsing
* Export
* Bulk Notification
* Large Import

未来应使用：

```text
Job
Queue
Worker
Scheduler
```

但实际引入方式必须跟随需求。

---

# 78. Scheduler 架构

所有 Scheduled Job 必须：

* 可追踪
* 可失败重试
* 避免重复执行
* 考虑多实例部署
* 有明确 Owner

禁止同一个 Job 因多服务器重复运行产生重复业务数据。

---

# 79. Webhook 架构

Webhook 必须：

* Signature Verification
* Idempotency
* Retry Handling
* Audit
* Security
* Provider Identification

不能收到 Webhook 就直接修改业务数据。

---

# 80. 文件上传架构

文件上传必须考虑：

* File Type
* Size
* Permission
* Tenant
* Malware Risk
* Storage
* Metadata

禁止将任意文件直接保存进应用程序运行目录。

---

# 81. API Versioning

正式公开 API 需要版本意识。

例如：

```text
/api/v1/
```

Internal API 是否使用版本，根据实际架构决定。

不得频繁 Breaking API。

---

# 82. Backward Compatibility

修改 API 时必须评估：

* Frontend
* Mobile
* Integration
* AI Service
* Third Party

是否依赖旧 Contract。

禁止随意：

```text
Rename Field
Delete Field
Change Type
Change Status Meaning
```

而不考虑影响。

---

# 83. Database Schema Change

Database Schema 必须通过：

> Migration。

禁止：

```text
手动修改 Production DB
```

然后不记录 Migration。

---

# 84. Database Schema Ownership

每个 Table 应属于明确 Module。

禁止创建：

```text
common_data
general_data
other_data
misc
```

等没有清楚 Domain Meaning 的大型通用表。

---

# 85. Global ID

所有核心 Entity 必须使用统一 ID 策略。

具体：

```text
UUID / UUIDv7 / Long
```

由后续 Database Standard 统一决定。

Cursor 不得不同模块随意选择不同策略。

---

# 86. Time Architecture

系统必须区分：

```text
Stored Time
Business Timezone
User Timezone
```

禁止假设服务器 Local Time 就是所有用户时间。

---

# 87. Currency Architecture

Money 数据必须同时明确：

```text
Amount
Currency
```

不得只保存：

```text
100
```

但不知道：

```text
MYR
USD
SGD
```

---

# 88. Module Dependency Direction

依赖方向必须清晰。

例如：

```text
Business Module
↓
Core Platform
```

允许。

但：

```text
Core
↓
Sales
```

应谨慎。

Core 不应该依赖具体业务模块。

---

# 89. 禁止 Circular Dependency

禁止：

```text
Sales → Inventory
Inventory → Sales
```

互相直接依赖形成循环。

如确实存在双向业务关系：

应通过：

* Contract
* Event
* Application Orchestration

解除耦合。

---

# 90. Dependency Rule

Cursor 新增 Dependency 前必须回答：

```text
为什么需要？
现有系统是否已有？
是否属于正确层？
是否会造成循环依赖？
```

---

# 91. Architecture Decision

重大架构修改包括：

* 引入 Microservice
* 引入 MQ
* 引入 Redis
* 更换 DB
* 引入 Elasticsearch
* 引入 GraphQL
* 引入新 Auth System
* 改 Multi-Tenant Model

Cursor 不得自行决定。

必须由用户明确批准。

---

# 92. Minimum Architecture Change

修复一个小功能时：

禁止顺便：

```text
重构整个 Backend
重写 API
改 Database
更换 State Management
拆 Microservice
```

遵守：

> Minimum Necessary Architecture Change。

---

# 93. 先读再改

Cursor 修改架构相关代码前必须：

1. 查看当前 Module。
2. 查看现有 Pattern。
3. 查看依赖关系。
4. 查看现有 Service。
5. 查看现有 Entity。
6. 查看 Permission。
7. 查看 Tenant Scope。
8. 查看 API Contract。

再开始修改。

---

# 94. 不得假设不存在

当 Cursor 找不到某能力时：

不得立即创建。

必须搜索：

```text
Service
Component
Hook
Repository
Utility
Module
API
Entity
```

是否已有类似实现。

---

# 95. Architecture Consistency

如果项目已有明确实现模式：

例如：

```text
Controller
Service
Repository
Mapper
DTO
```

新功能必须保持一致。

不得一个模块使用 A Pattern，另一个模块随意使用完全不同 Pattern。

---

# 96. 可测试架构

业务逻辑必须设计成可测试。

禁止将所有逻辑：

```text
写死在 Controller
写死在 React Component
写死在第三方 SDK Callback
```

使其无法独立测试。

---

# 97. 可替换架构

第三方 Provider 应保持可替换。

例如：

```text
Email Provider
Payment Provider
Storage Provider
LLM Provider
SMS Provider
```

不得让整个业务系统深度锁死某一个 Vendor。

---

# 98. AI Provider Independence

AI Layer 不应默认只支持一个 LLM Provider。

业务 AI 能力应尽量与具体 Provider 解耦。

例如：

```text
AI Application
↓
Model Provider Interface
↓
Provider
```

但当前阶段不得为了“支持所有模型”过度抽象。

---

# 99. Architecture Priority

发生架构冲突时，按以下顺序判断：

```text
1. Security
2. Tenant Isolation
3. Data Integrity
4. Business Correctness
5. Domain Ownership
6. Transaction Correctness
7. Backward Compatibility
8. Maintainability
9. Scalability
10. Performance
11. Development Convenience
```

# 102. AIOS 架构最终原则

AIOS 必须坚持：

> **一个平台，多业务模块。**

> **一个 Core，多 Domain。**

> **一个统一 Security Boundary。**

> **一个统一 Tenant Context。**

> **Spring Boot 掌控核心业务。**

> **React 负责交互，不负责最终业务判断。**

> **Python 负责 AI，不绕过业务系统。**

> **PostgreSQL 是核心业务事实来源。**

> **模块拥有自己的业务边界。**

> **模块之间通过明确 Contract 协作。**

> **当前优先 Modular Monolith，而不是过早 Microservice。**

> **架构允许未来扩展，但当前禁止过度工程化。**

> **Cursor 必须遵守架构，而不是为了完成当前任务破坏架构。**
